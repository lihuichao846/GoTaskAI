## 2. 测试方法

1. **并发承载**：以递增并发量级（1→1500）分别运行饱和压测，记录各量级的成功率、QPS 与延迟分位数。采用「预热→清零→测量」三段式，排除冷启动干扰。
2. **吞吐量**：同一批并发断点下的总请求数 / 有效测量时长 = 吞吐率（RPS），绘制随并发变化的吞吐曲线。
3. **QPS**：在稳定低并发区间（并发 1~35）精扫，寻找 QPS 峰值与瓶颈阈值。
4. **任务调度成功率**：通过 `POST /api/tasks/batch-submit` 提交 30 个任务（+ 预检的 1 个），轮询至终态统计，并用 Worker Prometheus 指标 `task_runs_total` 交叉验证。
5. **交叉验证**：以 9101/9102 的 `gotaskai_*` 指标核对在途任务、完成数、重试数、LLM 计量。

## 5. 问题清单（按严重等级）

| 等级 | 问题 | 影响 | 等级判定 |
|---|---|---|---|
| P1 | 并发 ≥600 出现传输层错误（连接被拒/超时），成功率回落至 54~84% | 过载时用户体验受损，HTTP 无 5xx/4xx 暴露、错误被客户端吞为 transport_err | 建议优化（高并发承载上限 500，已远超业务基线 200） |

无 P0 级缺陷；任务调度链路（提交→排队→处理→终态→计量）全程一致，无丢包/重试失效。

## 7. 整改建议（可选项）

1. **（建议）** 在并发过载区（≥600）增加服务端拒绝策略的显式错误返回（如 503 + Retry-After），避免客户端只能感知连接超时/被拒。
2. **（建议）** 对 Worker 消费带设置队列积压告警，防止任务提交速率长期高于消费速率导致队列膨胀。
3. **（建议）** 若需支撑 >500 并发，引入水平扩容（多 API 实例 + 负载均衡）与连接池参数调优（`MaxIdleConnsPerHost`、GOMAXPROCS）。
