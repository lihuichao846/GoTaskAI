## 0. 一句话总览

**M6 = 让模型能"做事"的那一层：把外部能力统一包装成 `Tool`，然后在一次任务里跑起「模型要求调工具 → 我们执行 → 把结果喂回模型 → 模型继续」的循环，直到模型不再要求调工具为止。**

```
模型 ──(我要调 internet_search)──▶ 框架执行工具 ──(搜索结果)──▶ 模型 ──(最终回答)──▶ 用户
        ▲                                                      │
        └──────────────── 循环直到没有 tool_calls ───────────────┘
```

这个循环是**整个项目里唯一一处"非确定性控制流"**：循环次数不由代码决定，而由模型决定。所以 M6 的绝大部分设计都是围绕"**怎么把它关进笼子**"——调用次数上限、参数校验、事件可观测、超时中断。

## 1. 这个模块解决什么问题

### 1.1 没有工具层会怎样

| 缺什么 | 后果 |
|---|---|
| 统一的工具抽象 | 每接一个新能力（搜索/数据库/内部 API）都要改 LLM 调用代码 |
| 标准协议 | 每接一个第三方能力都要手写适配层、自己处理进程/连接生命周期 |
| 调用循环 | 模型不能"先查再答"，只能凭训练数据回答（本项目 prompt 里反复强调的"必须搜索"就无处落地） |
| 循环上限 | 模型一旦陷入"反复调工具"就无限烧钱、任务永不结束 |

### 1.2 本模块的三个层次

```
① 抽象层  Tool 接口          —— 一切可调用能力的统一形状（Name/Description/Schema/Execute）
② 注册层  Registry + 白名单   —— 进程内已就绪的工具集合；按 Agent 绑定做子集裁剪（M3）
③ 协议层  MCP Wrapper/Pool   —— 把外部进程/stdin-stdout 或远程 SSE 封装成 Tool
                │
                ▼
④ 编排层  工具调用循环         —— 模型驱动的多轮工具往返（本篇核心）
```

## 2. `Tool` 抽象：四个方法

```go
// internal/pkg/toolregistry/tool.go:11-16
type Tool interface {
    Name() string
    Description() string
    ToOpenAITool() openai.Tool
    Execute(ctx context.Context, args map[string]any) (string, error)
}
```

四个方法各自承担一件事：

| 方法 | 给谁看 | 作用 |
|---|---|---|
| `Name()` | 框架 + 模型 | **唯一标识**。模型返回的 `tool_calls[].name` 靠它做匹配（§5.4 的问题也出在这里） |
| `Description()` | 模型 | **决定模型会不会用它**。写不好这段描述，工具就等于不存在（`internet_search` 的描述写了"这是首选且最强大的全局搜索引擎工具…都必须优先调用"，明显是刻意强化） |
| `ToOpenAITool()` | 模型 | 转成 OpenAI 的 function-calling 声明（含 JSON Schema 参数） |
| `Execute()` | 框架 | 真正干活，返回**字符串** |

**注意 `Execute` 的返回类型是 `string`，不是结构体**。这是个有意的简化：不管工具返回的是 JSON、HTML、还是纯文本，**统一压成字符串塞回模型**。好处是任何工具都能接；代价是**结构化信息被扁平化**——模型拿到的是文本，不是可编程的对象（这也是 MCP 协议本身的设计取向：以 LLM 可读为目标，而非机器可解析）。

### 2.1 Registry：进程内的工具全集

```go
type Registry struct {
    mu    sync.RWMutex
    tools map[string]Tool
    order []string          // 保持注册顺序
}
```

三个细节：

1. **`map` + `order` 双结构**：`map` 用于 O(1) 按名查找（`Get`），`order` 用于稳定遍历（`List`/`ToOpenAITools`）。**为什么要保序**：工具声明的顺序会影响模型的选择倾向，也影响 `resolveTools` 产出的白名单顺序，进而影响可复现性（评测时尤其重要）。
2. **`Get` 用 `RLock`、`Register` 用 `Lock`**：注册只在启动时发生、读取在每个任务里发生，所以读多写少，读写锁是对的。
3. **`Register` 同名覆盖，但 `order` 不重复追加**：

```go
if _, exists := r.tools[t.Name()]; !exists {
    r.order = append(r.order, t.Name())
}
r.tools[t.Name()] = t          // 覆盖
```

这个处理是对的（否则 `order` 会出现重复项，`List` 就会返回同一工具两次）。

### 2.2 内置工具：只有一个

```go
// internal/pkg/toolregistry/builtin.go
type CurrentTimeTool struct{}
func (CurrentTimeTool) Name() string        { return "get_current_time" }
func (CurrentTimeTool) Description() string { return "获取当前的日期和时间" }
func (CurrentTimeTool) ToOpenAITool() openai.Tool { ... }
func (CurrentTimeTool) Execute(_ context.Context, _ map[string]any) (string, error) {
    return time.Now().Format("2006-01-02 15:04:05"), nil
}

func RegisterBuiltins(r *Registry) {
    r.Register(CurrentTimeTool{})
}
```

**只有 `get_current_time` 一个**。它的意义不在于功能，而在于：

- **零参数工具的最小样例**（`Properties: map[string]jsonschema.Definition{}`）——说明"可以在进程内直接实现、不需要 MCP"；
- **一个"永远不会失败"的工具**——排障时可以用它验证"工具调用链路本身是否通"（如果连它都调不起来，问题在框架/协议层，而不是某个外部 MCP 服务）。

**注意它和 DB 里那行种子数据是两套东西**（M3 §2.3 已详述）：`seedBuiltinTools` 往 `tools` 表插一行 `builtin_current_time` 是**为了让 UI 能显示、Agent 能绑定**；真正执行时用的是 Registry 里的这个 Go 结构体。**两边靠 `Name` 对齐**（都叫 `get_current_time`）——这是一处**隐式契约**，改名就会断。

## 3. MCP：把外部能力接进来的协议层

### 3.1 两种连接方式

```go
// internal/model/tool.go:23-33
type ToolConfig struct {
    Command string            `json:"command"`   // 本地子进程（stdio）
    Args    []string          `json:"args"`
    URL     string            `json:"url"`       // 远程 HTTP/SSE
    Env     map[string]string `json:"env"`       // 传给子进程的额外环境变量
}
func (c ToolConfig) Valid() bool { return c.Command != "" || c.URL != "" }
```

| 方式 | 实现 | 适用 |
|---|---|---|
| **stdio 子进程** | `NewWrapperWithEnv` → `client.NewStdioMCPClient(command, env, args...)` | 本地/自建工具（如自带的 `search_mcp.exe`） |
| **SSE 远程** | `NewHTTPWrapper` → `client.NewSSEMCPClient(url)` | 第三方托管服务 |

**选择顺序**（`mcpclient/pool.go:31-35` 与 `api/tool.go:242-246`）：

```go
if url != "" {
    w, err = NewHTTPWrapper(ctx, url)          // URL 优先
} else {
    w, err = NewWrapperWithEnv(ctx, command, env, args...)   // 否则回退 stdio
}
```

### 3.2 握手：MCP 不是"启动就能用"

```go
// internal/pkg/mcpclient/client.go:47-65
func initWrapper(ctx context.Context, c *client.Client) (*Wrapper, error) {
    initRequest := mcp.InitializeRequest{}
    initRequest.Params.ProtocolVersion = mcp.LATEST_PROTOCOL_VERSION
    initRequest.Params.ClientInfo = mcp.Implementation{
        Name:    "GoTaskAI-Client",
        Version: "1.0.0",
    }
    initResult, err := c.Initialize(ctx, initRequest)
    if err != nil {
        return nil, fmt.Errorf("failed to initialize mcp connection: %w", err)
    }
    log.Printf("Connected to MCP Server: %s (v%s)", initResult.ServerInfo.Name, initResult.ServerInfo.Version)
    return &Wrapper{Client: c}, nil
}
```

**这一步必须做**：MCP 是一个**有握手的状态协议**（类似 LSP）。不完成 `initialize`，后续 `ListTools` / `CallTool` 都会失败。所以项目里"能不能用"的判据是"**握手是否成功**"，而不是"进程是否起来了"——这解释了 M3 §5.4 那个现象：`bin/search_mcp.exe` 不存在时，`NewWrapper` 在握手阶段就返回错误，`mcpClient` 被置 nil。

**`ProtocolVersion` 用的是 `mcp.LATEST_PROTOCOL_VERSION`**（不固定版本号）：好处是自动跟随库升级，代价是**与旧版 MCP 服务的兼容性取决于服务端是否接受协商**。真实部署里固定一个经验证的版本更稳。

### 3.3 适配：MCP Tool → 项目的 Tool

```go
// internal/pkg/toolregistry/mcp.go
type MCPServerTool struct {
    wrapper *mcpclient.Wrapper
    tool    mcp.Tool
}

func (t *MCPServerTool) Name() string        { return t.tool.Name }
func (t *MCPServerTool) Description() string { return t.tool.Description }

func (t *MCPServerTool) ToOpenAITool() openai.Tool {
    var params jsonschema.Definition
    if b, err := json.Marshal(t.tool.InputSchema); err == nil {
        _ = json.Unmarshal(b, &params)          // MCP Schema → OpenAI Schema（靠 JSON 序列化中转）
    }
    return openai.Tool{Type: openai.ToolTypeFunction, Function: &openai.FunctionDefinition{
        Name: t.tool.Name, Description: t.tool.Description, Parameters: params,
    }}
}

func (t *MCPServerTool) Execute(ctx context.Context, args map[string]any) (string, error) {
    result, err := t.wrapper.CallTool(ctx, t.tool.Name, args)
    if err != nil { return "", err }
    var content string
    for _, c := range result.Content {
        if text, ok := c.(mcp.TextContent); ok {
            content += text.Text + "\n"          // 文本内容直连
            continue
        }
        if b, err := json.Marshal(c); err == nil {
            content += string(b) + "\n"          // 非文本内容 JSON 化
        }
    }
    return content, nil
}
```

**关键设计：Schema 用"JSON 序列化 ↔ 反序列化"做跨类型转换**（`mcp.Tool.InputSchema` 是 `any`，`jsonschema.Definition` 是强类型）。这个技巧很实用（绕开两套类型体系的直接映射），但有两个后果：

1. **`json.Marshal` 的错误被忽略**（`if err == nil` 无 else 分支）——失败时 `params` 保持零值 `jsonschema.Definition{}`；
2. **零值 Schema 会被当成"无 Schema"**，而 `validateToolArguments` 对空 Schema 的处理是**放行**（见 §5.3）——所以**转换失败 = 参数校验静默关闭**。这个降级方向是"宽松"，值得注意。

**`Execute` 的多内容拼接**：MCP 的 `CallToolResult.Content` 是**数组**（可能同时含文本、图片、资源引用）。这里把文本逐段拼接、其它类型 JSON 化。所以**图片类内容会变成一大坨 base64 JSON 塞进模型上下文**——这是个真实的成本风险（§9.6）。

### 3.4 连接池：按工具 ID 缓存

```go
// internal/pkg/mcpclient/pool.go
type Pool struct {
    mu      sync.Mutex
    clients map[string]*Wrapper
}

func (p *Pool) Get(ctx, id, command, url string, args []string, env map[string]string) (*Wrapper, error) {
    p.mu.Lock()
    defer p.mu.Unlock()
    if w, ok := p.clients[id]; ok { return w, nil }     // ★ 命中即返回，忽略新配置
    ...创建并缓存...
}
```

**动机是对的**（注释："按 ID 懒加载并复用，避免每个任务都拉起子进程"）——stdio MCP 服务的启动成本不低（拉进程 + 握手 + `ListTools`），每个任务都重建是不可接受的。

**但缓存键只有 `id`（tool ID），不含配置指纹**。配置改了、ID 没变 → 命中旧连接 → **新配置被静默忽略，必须重启 worker 才生效**。这在 M3 §4.4 已从"配置管理"角度记录，此处从协议层补充一点：**这也是 MCP 会话状态无法热更新的直接原因**——`Wrapper` 内部的 `client.Client` 承载着已建立的会话（含已协商的协议版本、服务端能力），换配置本质上是"换一个会话"，而池按 ID 复用会话。

**另外：连接池没有"空闲回收"**。`Close()` 只在 worker 停止时调用一次（`Pool.Stop()` → `p.mcpPool.Close()`，`pool.go:187`）。所以：

- MCP 子进程**会一直活着**（随 worker 生命周期），这是刻意的（避免反复启停）；
- 但**用户删除工具后，对应子进程不会被回收**（无引用释放逻辑）→ 子进程成为孤儿，直到 worker 重启。

## 4. 工具的两条来源与装配

这部分在 M3 §4.2 已详述，此处只做一张对照表，避免重复：

| | 静态注册区 | 动态 MCP |
|---|---|---|
| 何时进入 | **worker 启动时**（`pool.go:103-113`） | **每个任务解析白名单时**（`resolveTools`） |
| 内容 | `RegisterBuiltins()` + `mcpClient.GetTools()` 的全部工具 | 绑定行 `Type=="mcp" && Config!=""` 的工具 |
| 查找顺序 | **优先**（`p.toolRegistry.Get(bt.Name)` 命中即用） | 静态未命中才走 |
| 例 | `get_current_time`、`internet_search` | 用户私有 MCP（`npx -y xxx-mcp`） |

**一句话记忆**：**内置与自带的 `search_mcp` 走"静态注册"（启动时一次性就绪），用户私有的走"动态拉起"（每任务按配置连，池里复用）。**

## 5. 工具调用循环（本篇核心）

### 5.1 整体结构

```go
// internal/pkg/llm/client.go:167-317（节选骨架）
func (c *Client) generateWithClient(ctx, client, model, systemPrompt string,
        history []openai.ChatCompletionMessage, userPrompt string,
        tools []toolregistry.Tool, observer ToolCallObserver,
        budget *Budget, sampling *Sampling) (string, error) {

    // ① 组装初始消息：system + history + user
    messages := []openai.ChatCompletionMessage{ {Role: system, Content: systemPrompt} }
    messages = append(messages, history...)
    messages = append(messages, {Role: user, Content: userPrompt})

    // ② 把 Tool 转成 OpenAI 声明
    var openaiTools []openai.Tool
    for _, t := range tools { openaiTools = append(openaiTools, t.ToOpenAITool()) }

    for {                                        // ★ 循环：次数由模型决定
        if err := budget.BeforeCall(); err != nil { return "", err }   // ③ 预算闸门

        req := openai.ChatCompletionRequest{Model: model, Messages: messages}
        if sampling != nil { req.Temperature = sampling.Temperature; req.TopP = sampling.TopP }
        if len(openaiTools) > 0 { req.Tools = openaiTools }

        resp, err := client.CreateChatCompletion(ctx, req)             // ④ 调模型
        if err != nil { return "", fmt.Errorf("AI API call failed: %w", err) }
        if len(resp.Choices) == 0 { return "", fmt.Errorf("AI returned empty response") }

        budget.Record(resp.Usage.PromptTokens, resp.Usage.CompletionTokens)   // ⑤ 计量

        msg := resp.Choices[0].Message
        ...（⑥ 文本式工具调用兜底，见 §5.5）...
        messages = append(messages, msg)

        if len(msg.ToolCalls) == 0 { return msg.Content, nil }         // ⑦ 唯一的"正常出口"

        for _, toolCall := range msg.ToolCalls {                       // ⑧ 逐个执行（串行）
            ...（参数解析 → schema 校验 → 执行 → 回填 tool 消息）...
        }
    }
}
```

### 5.2 出口只有一个（外加两个异常出口）

这个 `for {}` 是**无条件的无限循环**，退出路径只有三条：

| 出口 | 条件 | 位置 |
|---|---|---|
| ✅ **正常完成** | 模型这一轮**没有**返回 `tool_calls` | ② L245-247 |
| ⛔ **预算耗尽** | `budget.BeforeCall()` 返回 `ErrBudgetExceeded` | L189-191 |
| ⛔ **API 错误** | `CreateChatCompletion` 失败，或 `Choices` 为空 | L206-211 |

**第一条是唯一"正常"的退出**——它的语义是"**模型决定不再需要工具了**"。也就是说：**循环次数完全由模型控制**，代码不预设轮数。

这正是需要 `budget` 的原因。而 `budget` 的检查是**每轮开头**做的（`BeforeCall`），所以：

```
MaxCalls = 15  →  最多 15 次模型调用
                →  最多 14 轮工具调用（最后一次调用只能产出最终答案）
```

### 5.3 ⚠️ 循环上限依赖 `budget` 非 nil

`GenerateWithToolsAndObserver` 的文档注释里明确写了：

```go
// budget 可为 nil，表示不启用调用次数上限与 token 计量。
```

而 `Budget` 的每个方法都是 **nil-safe**：

```go
func (b *Budget) BeforeCall() error {
    if b == nil { return nil }        // ★ nil → 直接放行
    ...
}
```

**所以当 `budget == nil` 时，这个 `for {}` 就没有任何次数上限了**。此时唯一的兜底是**外层 ctx 的超时**：

```go
// worker/pool.go:872-878
timeout := 2 * time.Minute
if s := config.AppConfig.LLM.TimeoutSeconds; s > 0 { timeout = time.Duration(s) * time.Second }
apiCtx, cancel := context.WithTimeout(ctx, timeout)     // 默认 120 秒
defer cancel()
p.registerInFlight(t.ID, cancel)
```

所以实际链路是：**`budget` 非 nil → 15 次调用上限；`budget` 为 nil → 靠 120 秒超时**。

在当前代码里 `handleTaskProcess` **总是构造 budget**（`pool.go:767-775`）并传入（`pool.go:913` 附近的 `GenerateWithToolsAndObserver`），所以生产路径是有上限的。但这是**隐式依赖**：任何人写一个新的调用点、顺手传 `nil`（因为注释说"可为 nil"），就会得到一个"只能靠超时兜底"的循环。**建议把"上限"从可选的 budget 里拆出来，作为不可省的参数。**

### 5.4 `executeTool` 按名字线性查找

```go
func executeTool(ctx context.Context, tools []toolregistry.Tool, name string, args map[string]interface{}) (string, error) {
    for _, t := range tools {
        if t.Name() == name { return t.Execute(ctx, args) }
    }
    return "", fmt.Errorf("tool %s not registered", name)
}
```

**两个后果**：

1. **首个同名工具胜出**。如果某 Agent 同时绑定了两个 MCP 服务、且它们都暴露了名为 `search` 的工具，那么：
   - `openaiTools` 里会出现**两个同名 function 声明**（多数供应商会拒绝或静默去重）；
   - `executeTool` 永远只会调用**列表里靠前的那一个**，后者无法被触达。
   **当前没有任何重名检测或告警**。
2. **错误信息是"未注册"而不是"不在白名单"**：如果模型幻觉出一个工具名，返回的是 `tool xxx not registered`，但**这个错误被包装成 tool 消息回给模型**（L301），模型看到后通常会自动改用其它工具或直接作答——行为是正确的，只是措辞容易让排障者误以为"注册步骤出错"。

### 5.5 文本式工具调用的兜底（很值得讲）

```go
// L217-241
// 针对某些开源模型（如 Qwen 2.5）未正确使用 tool_calls，而是把 JSON 写进 Content 的兜底处理。
if len(msg.ToolCalls) == 0 && msg.Content != "" {
    re := regexp.MustCompile(`(?s)\{\s*"name"\s*:\s*"[^"]+"\s*,\s*"arguments"\s*:\s*\{.*?\}\s*\}`)
    match := re.FindString(msg.Content)
    if match != "" {
        var callData struct {
            Name      string                 `json:"name"`
            Arguments map[string]interface{} `json:"arguments"`
        }
        if err := json.Unmarshal([]byte(match), &callData); err == nil && callData.Name != "" {
            argsBytes, _ := json.Marshal(callData.Arguments)
            msg.ToolCalls = []openai.ToolCall{{
                ID:   "call_" + callData.Name,        // ★ 由名字合成 ID
                Type: openai.ToolTypeFunction,
                Function: openai.FunctionCall{Name: callData.Name, Arguments: string(argsBytes)},
            }}
            msg.Content = ""                          // ★ 丢弃 JSON 之外的文字
        }
    }
}
```

**它是和系统提示词配套的一半**（M3 §5.4 的呼应）：worker 在注入"强制联网"指令时，明确要求模型**放弃标准协议、直接输出 JSON**：

```
2. 【调用格式】：如果你决定调用工具，请在回复中**仅输出工具调用的 JSON 格式**
   （可放在代码块内或直接输出），不要包含任何其他分析或废话。格式必须为：
   {"name": "internet_search", "arguments": {"query": "你要搜索的具体关键词"}}
```

于是形成一条**完整的替代通路**：

```
系统提示词要求"输出 JSON"  ──▶ 模型把 JSON 写进 content
                                     │
                                     ▼
                        ★ 这个正则把它"翻译"成标准 tool_calls
                                     │
                                     ▼
                        后续走标准执行流程（executeTool）
```

**这个设计的价值**：兼容不支持 function-calling 的模型（成本/私有部署场景常见）。

**但三个代价必须知道**：

| 问题 | 说明 |
|---|---|
| **正则在嵌套参数上会截断** | `"arguments"\s*:\s*\{.*?\}` 用的是**非贪婪** `.*?`，遇到 `{"arguments":{"a":{"b":1}}}` 会**在第一个 `}` 就收尾**，产出非法 JSON → `json.Unmarshal` 失败 → 调用被跳过。对 `internet_search`（参数是扁平的 `{query}`）没问题，对参数带嵌套对象的工具就会失效 |
| **合成的 `ToolCall.ID` 不唯一** | `"call_" + callData.Name`：同一轮里模型若输出两次**同名**调用，两条 `tool` 消息会带**相同的 `ToolCallID`** → 严格校验的供应商会返回 400 |
| **丢弃了模型 JSON 之外的文字** | `msg.Content = ""` 把模型的解释性文字一并清空。若模型写"我先查一下：{...}"，前半句消失（对最终答案无影响，但会丢失模型的推理痕迹） |

**另外还有一个设计张力**（值得作为复盘点）：**对已经能正确使用 `tool_calls` 的模型（如 DeepSeek），那段"仅输出 JSON"的系统提示词是多余甚至反向的**——它在引导一个规范实现的模型去用**文本约定**。两种机制同时开启时，模型可能选择任一条路径，导致行为不一致（有时走标准 tool_calls、有时走文本兜底）。

### 5.6 参数校验：两道闸门，都"失败即回传模型自修"

```go
// 闸门一：JSON 解析
var args map[string]interface{}
if err := json.Unmarshal([]byte(toolCall.Function.Arguments), &args); err != nil {
    // 工具入参解析失败时，不再静默跳过（否则 messages 中会出现带 tool_calls
    // 的 assistant 消息却无配对 tool 响应，严格提供方下一次请求将 400）。
    // 这里以 tool 角色错误消息回传 LLM，让其自行修正参数。
    messages = append(messages, {Role: tool, Content: "Error executing tool ...: invalid arguments: ...",
                                Name: toolName, ToolCallID: toolCall.ID})
    continue
}

// 闸门二：schema 校验
if schema := toolArgumentsSchema(tools, toolName); schema != nil {
    if err := validateToolArguments(*schema, args); err != nil {
        ...同样回传 tool 错误消息...
        continue
    }
}
```

**这段注释是整个循环里最有价值的一条工程经验**，值得展开：

> 工具入参解析失败时，不再静默跳过（否则 messages 中会出现带 `tool_calls` 的 assistant 消息**却无配对 tool 响应**，严格提供方下一次请求将 **400**）。

它说的是 OpenAI 协议的一条**硬约束**：**`assistant(tool_calls)` 消息里的每一个 `tool_call_id`，都必须在后续有一条对应的 `role=tool` 消息**。少一条，请求就非法。所以"参数坏了就跳过"这种看似合理的写法，会让整个对话在下一轮直接 400 失败。

**正确做法就是这里的分支：无论成功失败，都必须给每条 `tool_call` 补一条 `tool` 消息。** 失败时把错误写进内容、交给模型自修正——既有协议合规，又给了模型纠错机会（模型看到 `invalid arguments` 通常会重发一个格式正确的调用）。

**关于 `validateToolArguments` 的宽松性**：

```go
func validateToolArguments(schema jsonschema.Definition, args map[string]any) error {
    if schema.Type == "" && len(schema.Required) == 0 && len(schema.Properties) == 0 {
        return nil                              // ★ 空 schema → 放行
    }
    if !jsonschema.Validate(schema, args) { return fmt.Errorf("arguments do not match tool schema") }
    return nil
}
```

两个宽松点：
1. **空 schema 视为通过**——这是必要妥协（有些工具确实无参数或有参数但没声明 schema），但结合 §3.3 的"Schema 转换失败会退化成空 schema"，意味着**转换失败 = 校验关闭**；
2. **`jsonschema.Validate` 只支持 JSON Schema 的子集**（类型/必填/枚举等），对 `oneOf` / `$ref` / `anyOf` 之类的复杂约束往往不生效 → **复杂 MCP 工具的校验偏松**。

所以这条闸门是"**挡住明显错误**"，不是"保证参数正确"。最终的兜底仍然是**工具自己**（`internet_search` 的 Handler 里手工校验 `query` 是不是 string）。

### 5.7 事件回传：`observer` 让"工具在干什么"可见

```go
type ToolCallObservation struct {
    ToolName  string
    Arguments string
    Status    string        // started / success / failed
    Result    string
    Error     string
}
type ToolCallObserver func(ToolCallObservation)
```

一次工具调用**可能触发三次回调**：

| 时机 | Status | 携带 |
|---|---|---|
| 即将执行（校验通过后） | `started` | 名字 + 原始 arguments |
| 解析/校验失败 | `failed` | 名字 + arguments + error |
| 执行成功 | `success` | 名字 + **完整 result** |
| 执行失败 | `failed` | 名字 + error（注意：**不带 arguments**） |

worker 侧把它转成 `ToolCallEvent` → ①打指标 ②推 NATS → SSE → 前端展示"工具调用轨迹"（M2/X2 已详述）：

```go
// worker/pool.go:881-898
observer := func(obs llm.ToolCallObservation) {
    ev := &model.ToolCallEvent{ TaskID: t.ID, TraceID: t.TraceID, UserID: t.UserID,
        AgentID: t.AgentID, ToolName: obs.ToolName, Arguments: obs.Arguments,
        Status: obs.Status, Result: obs.Result, Error: obs.Error, Timestamp: time.Now() }
    metrics.ToolCalls.WithLabelValues(obs.Status).Inc()
    p.manager.PublishToolEvent(ev)
    if err := p.manager.SaveToolCallLog(&model.ToolCallLog{ ... }); err != nil { ... }
}
```

**一个对称性瑕疵**：`started` 事件带 `arguments`，但 `success` 事件**不带** `arguments`（只有 result），而 `failed`（执行失败那个分支）既不带 arguments 也不带 result。后果是**前端无法把 `started` 和 `success` 配对后展示"某次调用的入参 + 出参"**——同一工具被调用多次时，前端只能按顺序猜。修法是让三条事件都带 `arguments`（或用 `toolCall.ID` 做配对键）。

## 6. 自带 MCP 服务：`search_mcp`

### 6.1 它是什么

```
tools/search_mcp/
  main.go                  —— 15 行：建 MCP Server、注册一个工具、ServeStdio
  pkg/serpapi/serpapi.go   —— 101 行：internet_search 的定义与实现（转调 SerpApi）
```

```go
// tools/search_mcp/main.go
func main() {
    s := server.NewMCPServer("Multi-Tool-Search", "1.0.0")
    s.AddTool(serpapi.GetTool(), serpapi.Handler)
    if err := server.ServeStdio(s); err != nil { panic(err) }
}
```

**它是"极简 MCP 服务端"的范例**：一个 stdio MCP 服务可以只有 15 行——建 server、注册工具、`ServeStdio`。这也解释了为什么 MCP 生态能快速铺开。

**它在项目里的定位**：worker 启动时通过 `bin/search_mcp.exe` 把它作为**子进程**拉起，握手后 `ListTools` 拿到 `internet_search`，注册进 Registry（`cmd/worker/main.go:199-208`）。

### 6.2 工具实现里的三个细节

**① 描述是"强指令式"的**

```go
mcp.WithDescription("这是首选且最强大的全局搜索引擎工具（谷歌搜索）。当用户询问任何你不确定的知识、历史、代码问题、最新资讯或百科时，都必须优先调用此工具获取答案。")
```

**工具描述是给模型看的 prompt**，不是给人看的文档。这里用了"首选""最强大""必须优先"这类强引导词，明显是为了对抗"模型倾向凭已有知识直接回答"的惯性。

**② 结果里又嵌了一段指令（grounding 手法）**

```go
sb.WriteString(fmt.Sprintf("以下是来自谷歌搜索关于 '%s' 的严格事实搜索结果：\n", query))
sb.WriteString("【重要指令】：请严格基于以下内容回答用户的问题。如果以下内容不足以回答问题，请直接告知用户“搜索到的资料不足”。不要自行编造未出现在以下内容中的事实！\n\n")
```

它把"不许编造"的约束**塞在工具返回结果里**，而不是塞在 system prompt 里。为什么这样做有效：**约束紧贴数据**，模型在处理这段数据前立刻看到它，比放在遥远 system 区的约束更"贴身"。

> ⚠️ 但这也是**"把指令和数据混在同一条消息里"**的模式——而 prompt injection 正是利用同一模式（让不可信内容冒充指令）。这里的顺序是"先工具写的指令、后网络来的数据"，方向是安全的；但如果工具把**网络内容**放在指令**前面**，就会给注入留下空间。这是个需要在扩展工具时保持的纪律。

**③ 返回值有明确的条数上限**

```go
limit := 5 // 限制返回前5条结果
if len(searchResp.OrganicResults) < limit { limit = len(searchResp.OrganicResults) }
for i := 0; i < limit; i++ { ... Title / Summary / Link ... }
```

**这是必要的自律**，因为框架层对工具返回**没有长度闸门**（§9.6）。每条 result 含 title+snippet+link，5 条约几百字符——可控。

### 6.3 ⚠️⚠️ 高：SerpApi 密钥硬编码在源码里

```go
// tools/search_mcp/pkg/serpapi/serpapi.go:48
apiKey := "5c8e77bae8cdb7c83bd42416595dbfdd7ca16f430f2613829dac2d045a97f24"
searchURL := fmt.Sprintf("https://serpapi.com/search.json?engine=google&q=%s&api_key=%s&hl=zh-cn&gl=cn",
    url.QueryEscape(query), apiKey)
```

**这是一枚真实的付费 API 密钥，明文写在源码里**。而且情况比"源码泄露"更糟，因为 `bin/` 下还有**已编译的二进制**：

```
bin/api.exe
bin/worker.exe
bin/search_mcp.exe
bin/search_mcp.exe~        ← 编辑器备份文件
```

- `search_mcp.exe` 是**编译产物**，里面同样嵌着这把密钥（字符串常量会被编进 PE 文件）→ **密钥在仓库里出现了两次**（源码 + 二进制）；
- 该密钥还被**拼进 URL 的 query**（`?api_key=...`）→ 除源码外，它还会出现在：**代理/网关的访问日志**、**HTTP 抓包**、**任何记录出网 URL 的中间件**。
- `bin/*.exe` 与 `*.exe~` **被提交进了仓库**——本身就是构建产物卫生问题（`.gitignore` 显然没覆盖 `bin/`，而且 `~` 备份文件更是意外产物）。

**修法**（未实施）：
1. **立即吊销这把密钥**（应视为已泄露）；
2. 改为从环境变量读取（`os.Getenv("SERPAPI_API_KEY")`），并把 `Env` 通过 `ToolConfig.Env` 注入（项目已具备该能力，`mcpclient` 的 `NewWrapperWithEnv` 就是为此设计的）；
3. 用 `Authorization` 头代替 query 参数；
4. 把 `bin/` 与 `*~` 加入 `.gitignore`，并从版本历史中清理（若历史里已提交，需按泄露事件处理——**改代码不会让历史里的密钥消失**）。

## 7. 工具注册与发现

### 7.1 注册：`POST /api/tools`

```go
// internal/api/tool.go:43-88（要点）
if req.Type != "mcp" { 400 "仅支持注册 mcp 类型工具" }        // 只能注册 MCP，内置由代码管理
if !json.Valid([]byte(req.Config)) { 400 "config 必须是合法 JSON" }
var cfg model.ToolConfig
if err := json.Unmarshal([]byte(req.Config), &cfg); err != nil || !cfg.Valid() {

```

**校验只到"是合法 JSON 且含 command 或 url"为止**——对 `command` 的内容**没有任何白名单**。这是 §9.5 那个 RCE 风险的入口。

### 7.2 测试连接：`POST /api/tools/test`

```go
// internal/api/tool.go:211-264
ctx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
tools, err := testMCPConfig(ctx, cfg)
if err != nil { c.JSON(200, gin.H{"ok": false, "error": err.Error()}); return }
c.JSON(200, gin.H{"ok": true, "tools": tools})

func testMCPConfig(ctx context.Context, cfg model.ToolConfig) ([]string, error) {
    var wrapper *mcpclient.Wrapper
    if cfg.URL != "" { wrapper, err = mcpclient.NewHTTPWrapper(ctx, cfg.URL) }
    else             { wrapper, err = mcpclient.NewWrapperWithEnv(ctx, cfg.Command, cfg.Env, cfg.Args...) }
    if err != nil { return nil, err }
    defer wrapper.Close()
    tools, err := wrapper.GetTools(ctx)
    ...返回工具名列表...
}
```

**设计意图很好**：注册前先"试连"、把服务端暴露的工具名列出来，让用户在 UI 上确认这个 MCP 服务真能用、真提供他想用的工具。返回 `200` 而非 4xx/5xx 也是对的（这是"探测结果"而非"请求错误"，前端按 `ok` 字段分支）。

**但它是一个"任意命令执行"原语**——见 §9.5。

### 7.3 发现：自然语言 → LLM 翻译 → GitHub/npm

```go
// internal/api/tool.go:292-323
intent, err := h.parseMCPSearchIntent(ctx, req.Query)     // ① LLM 解析成 {keywords, npm_search, description}
items := append(h.searchNPM(ctx, intent.NpmSearch), h.searchGitHub(ctx, intent.Keywords)...)  // ② 确定性搜索
sort.SliceStable(items, func(i, j int) bool { return items[i].Stars > items[j].Stars })       // ③ 按 star 排序
c.JSON(200, gin.H{"parsed": intent, "items": items})
```

这段在 M3 §4.7 已详述，从 M6 视角补三点：

1. **LLM 只做"查询词翻译"**（把中文需求 → 英文关键词），**不参与结果生成**——幻觉最坏是搜不到，不会凭空造工具；
2. **两侧都强制 `mcp` 过滤**（关键词补 mcp + 结果名/描述须含 mcp），避免返回一堆无关高星仓库；
3. **返回的 `Config` 是"猜"的**（`{"command":"npx","args":["-y",<pkg>]}`），`InstallCommand` 也注明"具体启动方式以仓库 README 为准"。所以**一键注册后会在 worker 上跑 `npx -y <任意 npm 包>`**——这条链路把"发现"直接接成了"执行"（§9.5）。

## 10. 已知缺陷与未验证项

### 10.1 高：SerpApi 密钥明文硬编码，且随二进制二次泄露

见 §6.3。要点：源码一份、`bin/search_mcp.exe` 里一份；密钥拼在 URL query 里（还会进代理日志与抓包）；`bin/` 与 `*.exe~` 被提交进版本库。

### 10.2 高：任意已登录用户可在**服务器上执行任意命令**

三条入口，全部能触达"按用户提供的 `command`/`args`/`env` 启动子进程"：

| 入口 | 执行位置 | 鉴权 |
|---|---|---|
| `POST /api/tools/test` | **API 进程所在主机** | 需登录 |
| `POST /api/tools` 注册后由任务触发 | **Worker 进程所在主机** | 需登录 |
| `POST /api/tools/search` → 一键注册 `npx -y <pkg>` | Worker 主机（执行任意 npm 包） | 需登录 |

`testMCPConfig` 直接调 `mcpclient.NewWrapperWithEnv(cfg.Command, cfg.Env, cfg.Args...)`，而 `NewStdioMCPClient` 会**立即 `exec` 这个命令**。即使后续 MCP 握手失败（非 MCP 程序会在 `Initialize` 阶段失败）、即使进程马上被 `defer wrapper.Close()` 杀掉，**命令本身已经执行过了**——副作用（外连、写文件、拉起其它进程）已经发生。

**所以这是一个"盲 RCE"原语**：攻击者看不到命令输出（stdout 被 MCP 协议占用），但足以用来外连反弹、写计划任务、横向探测。

**修法方向**（未实施，按优先级）：
1. **命令白名单**：只允许 `npx` / `uvx` / `node` 等已知 MCP 运行器，禁止 shell 与系统命令；
2. **禁止 `cmd.exe` / `sh` / `powershell`**，并对 `args` 做模式校验；
3. 把 `POST /api/tools/test` 与"执行用户私有 MCP"放到**受限沙箱**（独立容器/低权限用户/seccomp）；
4. 至少加**审计日志 + 频率限制**（当前 `/api/tools/*` 无限流）。

### 10.3 中：工具返回内容**没有长度闸门**

对照鲜明：知识库上下文有 `max_context_chars = 6000` 的总量闸门（M4），**而工具返回没有任何闸门**：

```go
contentStr, err := executeTool(ctx, tools, toolName, args)      // 返回任意长度的字符串
...
messages = append(messages, openai.ChatCompletionMessage{ Role: tool, Content: contentStr, ... })
```

后果：一个返回 10 万字的 MCP 工具（或返回一大段 base64 图片的 `Execute`，见 §3.3）会**直接挤爆上下文窗口**，触发供应商报错或让模型忽略前面的系统提示。**当前完全依赖每个工具自律**（`search_mcp` 自己限了 5 条）。

**修法方向**：在 `executeTool` 之后统一加 `truncate`（像 M4 的 `truncateChunk` 那样按 rune 截断 + 标记省略），并复用配置里的字符上限。

### 10.4 中：循环上限隐式依赖 `budget != nil`

见 §5.3。注释明说"budget 可为 nil"，而 nil 时 `BeforeCall` 全部放行 → **无调用次数上限**，只剩 120 秒 ctx 超时兜底。建议把上限提为必传参数。

### 10.5 中：工具重名无检测

见 §5.4。`executeTool` 首个同名命中胜出，且 `openaiTools` 会出现重复 function 声明。绑定两个都提供 `search` 的 MCP 服务时，行为不可预期且无告警。

### 10.6 中：文本式兜底正则脆弱

见 §5.5。三点：非贪婪 `.*?` 遇嵌套参数会截断；`ToolCall.ID = "call_" + Name` 不唯一；`msg.Content = ""` 丢弃模型其余文字。

### 10.7 中：生产路径无采样参数与输出上限

`openai.ChatCompletionRequest` 只设了 `Model` 与 `Messages`（`sampling != nil` 时才设 `Temperature`/`TopP`），**没有 `MaxTokens`**。而 `sampling` 只由评测 harness 传入（`GenerateWithToolsAndObserverSampling`）。

后果：**生产环境的回答随机性不可控、单次输出长度不可控**——而这两者直接影响成本与延迟的可预测性（结合 X2 的成本指标，会出现"同样的问题花钱差好几倍"却无法从配置层面收敛）。建议把 `temperature` / `max_tokens` 提为配置项（甚至按 Agent 配置）。

### 10.8 低：`observer` 事件字段不对称

见 §5.7。`success` 事件不带 `arguments`、执行失败的 `failed` 事件既不带 arguments 也不带 result → 前端无法可靠配对"入参 ↔ 出参"。

### 10.9 低：MCP 响应读取无长度上限（对比 `tool.go` 有）

`pkg/serpapi/serpapi.go:66` 是 `io.ReadAll(resp.Body)` **裸读**；而 `api/tool.go:396/467` 的外呼都用了 `io.LimitReader(resp.Body, 1<<20)`。同样的"读外部响应"场景，两处策略不一致。

### 10.10 低：`http.DefaultClient` 无超时、无重试

`serpapi.go:56` 用 `http.DefaultClient`（`Timeout` 为 0，无重试）。功能上靠外层 ctx（120s）兜底，但**没有针对搜索接口自己的短超时**——搜索慢会直接吃掉整个任务的超时预算。另外 `http.DefaultClient` 是全进程共享的，改动它的 Transport 会影响所有使用者（当前没人改，属潜在耦合）。

### 10.11 低：MCP 子进程无空闲回收 / 删工具不回收

见 §3.4。连接池只在 worker 停止时统一 `Close()`；工具被删除后其子进程仍存活至 worker 重启。

### 10.12 低：`Schema` 转换失败会静默关闭参数校验

见 §3.3 + §5.6：`json.Marshal`/`Unmarshal` 出错时 `params` 为零值 → `validateToolArguments` 对空 schema **放行**。降级方向是"更宽松"，建议至少打一条 warning。

### 10.13 低：路径硬编码 `.exe`，无构建脚本，跨平台不可用

```go
// cmd/worker/main.go:201 与 cmd/eval/main.go:37
mcpServerPath := config.ResolveProjectPath("bin", "search_mcp.exe")
```

- 文件名**写死 `.exe`** → Linux/macOS 上永远找不到（即便编译出 `bin/search_mcp`）；
- 全仓 grep `*.bat` / `*.ps1` / `*.sh` / `*.yml` 中**没有任何脚本会构建它**（构建方式只在 `test/test_mcp/main.go:25` 的注释里提到 `go build -o bin/search_mcp.exe ./tools/search_mcp/main.go`）；
- 所以**新克隆仓库 + 非 Windows 环境 = 联网搜索静默不可用**（与 M3 §5.4 的"静默失效"叠加）。

### 10.14 未验证项

| 项 | 说明 |
|---|---|
| 标准 tool_calls 与文本兜底的实际占比 | 两种机制同时开启时模型如何选择，未实测；建议对 DeepSeek 观察是否出现"输出 JSON 文本" |
| 文本兜底正则在嵌套参数上的失败率 | 已从正则结构推导；未用真实嵌套参数工具验证 |
| 工具重名时的供应商行为 | `openaiTools` 含重复 function 名时供应商是拒绝还是去重，未实测 |
| 工具返回超长内容的表现 | 未实测上下文溢出时的具体错误形态 |
| MCP 子进程的资源占用 | 无指标（X2 已记：没有任何 Gauge），无法观测子进程数/内存 |
| 密钥是否已实际泄露 | `bin/*.exe` 已提交，取决于仓库的可见范围；**应默认已泄露并按泄露处置** |

## 12. 一页速记（面试/复盘用）

- **一句话定位**：M6 用 `Tool` 接口统一一切可调用能力，用 MCP 协议接入外部进程/服务，再在 `generateWithClient` 里跑一个**由模型驱动、由 `Budget` 关进笼子**的多轮工具往返循环。
- **四个最容易被追问的设计点**：
  1. **工具调用的出口为什么只有一个？**——`for {}` 唯一的正常出口是"模型这一轮没有 `tool_calls`"，即**循环次数由模型决定**。所以必须靠 `budget.BeforeCall()`（默认 15 次）和 120 秒 ctx 超时把非确定性关起来。
  2. **参数坏了为什么不能跳过？**——OpenAI 协议硬约束：`assistant(tool_calls)` 里每个 `tool_call_id` 都必须有一条配对的 `role=tool` 消息，少一条下一轮直接 **400**。所以必须**无论成败都给每条调用补一条工具消息**，把错误内容交给模型自修正。这是本项目里最值得抄的一条工程经验。
  3. **为什么要兼容"把 JSON 写进 content"的模型？**——为不支持 function-calling 的模型（如 Qwen 2.5）留后路；配套的是系统提示词里"仅输出 JSON 格式"的指令 + `client.go:219` 的正则兜底，两者是一套组合拳。
  4. **`Execute` 为什么返回 `string`？**——把任意工具的返回值（JSON/HTML/文本/图片）统一压成 LLM 可读的一段文字，任何工具都能接；代价是结构化信息被扁平化。
- **五个必须说清的事实修正**：
  1. **SerpApi 密钥明文硬编码**（`serpapi.go:48`），且**同一把密钥又被编进已提交的 `bin/search_mcp.exe`** → 仓库里出现两次；密钥还拼在 URL query 里（会进代理日志/抓包）。`bin/` 与 `*.exe~` 被提交进版本库本身也是卫生问题。
  2. **任意已登录用户可在服务器上执行任意命令**：`POST /api/tools/test` 会**用请求方给的 `command`/`args`/`env` 在 API 主机上 `exec`**；`POST /api/tools` + 任务触发会在 Worker 主机上执行；`/api/tools/search` 一键注册等于跑 `npx -y <任意 npm 包>`。**MCP 握手失败不代表命令没执行**（盲 RCE）。
  3. **工具返回内容没有任何长度闸门**：对比知识库上下文有 6000 字总量闸门，工具结果（以及 MCP 的图片内容会 JSON 化成一大坨 base64）**原样进 messages**，完全依赖每个工具自律。
  4. **循环上限隐式依赖 `budget != nil`**：注释明说"budget 可为 nil"，而 nil 时 `BeforeCall` 全部放行 → **无次数上限**，只剩 120 秒超时。
  5. **生产路径无采样参数与输出上限**：`ChatCompletionRequest` 不设 `Temperature`/`TopP`/`MaxTokens`（只有评测 harness 通过 `Sampling` 控制）→ 回答随机性与单次输出长度都不可控，直接影响成本可预测性。
- **三条可量化的证据**：
  - §11.1：SSE 收到 `tool_call{status=started}` → `tool_call{status=success}` → `task_update{completed}`，且 `tool_call_logs` 有对应两行 → 证明循环 + 事件 + 落库三条路全通；
  - §11.2：把 `max_calls_per_task` 压到 2，任务以 `budget exceeded` 失败、`run_logs.calls == 2` → 证明循环确实被预算关住；
  - §11.9：`/api/tools/test` 传一个非 MCP 命令，返回"握手失败"**但文件被创建** → 证明盲 RCE。
