## 0. 一句话总览

**任务调度中心 = 把"一次大模型调用"从同步请求改造成"可排队、可重试、可取消、可观测的异步任务"，并把状态变更实时送回浏览器。**

它不产生业务价值，但**所有产生业务价值的模块都跑在它上面**：对话问答、文档入库、图谱抽取、定时扫描、删除清理——全部是它的任务类型。

---

## 1. 这个模块解决什么问题

### 1.1 三个绕不开的痛点

**痛点一：大模型太慢，HTTP 撑不住**

一次带检索、带工具调用的模型请求，耗时从几秒到 120 秒不等（本项目把超时默认设成 2 分钟，`internal/worker/pool.go:872`）。如果用户点一下"发送"就占着一个 HTTP 连接等 2 分钟：

- 浏览器、Nginx、网关任一层都会超时断连；
- 单机并发连接数被长连接吃光（见 `test/perf/PERFORMANCE_REPORT.md` 的承载拐点）；
- 用户刷新页面 = 任务丢失。

**痛点二：调用会失败，而失败必须能重来**

上游模型接口限流、网络抖动、超时，都是常态。失败后：

- 不能让用户手动重新提问（他会丢掉已生成到一半的上下文）；
- 不能无脑重试（重试要花钱，且要防止无限重试）；
- 重试上限必须跨"队列层"和"业务层"两套机制同时成立。

**痛点三：用户不知道在等什么**

异步化之后，前端立刻拿不到答案了。必须有一条**反向通道**把进度推回去，否则用户只能傻等或不停刷新。

### 1.2 本模块的解法（一张图）

```
提交：  HTTP 请求 ─▶ 落库(MySQL) ─▶ 写缓存(Redis) ─▶ 投递队列(Asynq/Redis) ─▶ 立即返回 202
执行：  独立 Worker 进程 ─▶ 从队列取任务 ─▶ 改状态为 processing ─▶ 执行 ─▶ 写回结果
回传：  Worker ─▶ 消息总线(NATS) ─▶ API 进程订阅 ─▶ 进程内 channel ─▶ SSE ─▶ 浏览器
```

关键设计取舍：**提交与执行物理隔离在两个进程**（`cmd/api` / `cmd/worker`），两者之间只通过 4 样东西耦合——MySQL（状态真相）、Redis（队列 + 缓存）、NATS（事件）、Asynq 的任务名契约。这样 API 进程可以随时重启而不丢任务，Worker 可以水平扩容。

## 3. 端到端流程

### 3.1 流程一：提交任务

```
浏览器             API 进程                    MySQL      Redis(缓存)   Redis(队列)
  │                  │                          │            │            │
  │ POST /api/tasks/submit                        │            │            │
  ├─────────────────▶│ 1 参数绑定校验 ShouldBindJSON │            │            │
  │                  │ 2 补默认值(优先级/类型)      │            │            │
  │                  │ 3 取 userID(中间件注入)      │            │            │
  │                  │ 4 查/建会话 resolveConversationID          │            │
  │                  │ 5 构造 Task 实体(状态=pending, MaxRetry=3) │            │
  │                  │                          │            │            │
  │                  │ 6 AddTask ── Create ────▶│            │            │
  │                  │            ── cacheTask(24h) ────────▶│            │
  │                  │            ── Enqueue(task:process) ──────────────▶│
  │  HTTP 202 {id}   │                          │            │            │
  │◀─────────────────┤                          │            │            │
```

对应代码：
1. 参数校验与默认值：`internal/api/handler.go:140-152`
2. 会话解析：`handler.go:158-159` → `resolveConversationID`（未在本次精读范围内的辅助函数，位于同文件）
3. 构造实体：`handler.go:162-177`（注意 `MaxRetry: 3` 是**业务级**上限，与队列级 `asynq.MaxRetry(3)` 不是同一个东西）
4. 落库 + 缓存 + 入队：`manager.go:190-201`

**为什么提交能立刻返回**：整个 AddTask 只做一次 MySQL INSERT、一次 Redis SET、一次 Redis LPUSH，都是毫秒级；真正耗时的模型调用被甩给了另一个进程。

**批量提交的处理哲学**（`handler.go:36-95`）：逐条处理，**任一条失败不中断整批**，失败项单独记 `status: "failed_to_submit"` 返回。这是"部分成功可接受"的取舍——批量提交 100 条时，不该因为第 3 条失败就丢掉后面 97 条。

### 3.2 流程二：执行任务（`handleTaskProcess`，16 步）

这是整个模块最核心的函数（`internal/worker/pool.go:724-968`）。逐步拆解：

| 步 | 做什么 | 行号 | 关键点 |
|---|---|---|---|
| 1 | 反序列化 payload | 726 | 失败直接返回 error → 交给队列重试 |
| 2 | **回读数据库最新状态** | 730-742 | 若已取消 → 直接跳过；用 DB 的 `Retries/MaxRetry` **覆盖** payload 里的旧值 |
| 3 | 置为 `processing` | 744-748 | 用条件更新；失败说明被并发取消/完成 → 丢弃本次 |
| 4 | 解析本次可用工具 | 753 | 按 Agent 绑定白名单 |
| 5 | 构造成本预算 Budget | 757-775 | 单次上限 15、跨重试上限 30、单价、历史累计基线 |
| 6 | 解析 Agent 级模型凭证 | 779-786 | Agent 可覆盖全局密钥/地址/模型 |
| 7 | **意图路由** | 789-790 | 决定要不要检索，独立 5 秒超时 |
| 8 | 组装系统提示词 | 792-808 | 默认提示词 + 联网强制指令（仅非寒暄且绑了搜索工具） |
| 9 | 注入知识库上下文 | 810-824 | 受 `max_context_chars` 约束 |
| 10 | 注入图谱上下文 | 826-858 | 先做关联度过滤，再与 RAG **共享**剩余额度 |
| 11 | 加载会话历史（含自动压缩） | 860-868 | 超阈值时把旧轮次压成摘要 |
| 12 | 派生可取消 ctx 并登记在途 | 870-879 | 超时默认 2 分钟；登记取消函数 |
| 13 | 挂工具观测回调 | 881-911 | 每个工具事件 → 指标 + NATS 推送 + 落库 |
| 14 | **调模型（ReAct 工具循环）** | 913 | 内部循环，受 Budget 约束 |
| 15 | 生成后再次检查取消 | 915-920 | 取消则只写运行日志，丢弃结果 |
| 16 | 结果分支处理 | 922-967 | 预算超限→永久失败；可重试→回 pending；成功→completed + 落日志 |

**第 2 步为什么必须回读数据库**（`pool.go:736-741` 的注释说得很直白）：

> asynq 重试时复用原始 payload，其中的 `Retries` 不会随每次重试递增，若不覆盖，业务级 `MaxRetry` 将失效。

也就是说，队列层看见的重试次数和业务层需要的重试次数**不是同一个数**。业务层的判断在 `pool.go:934`（`if t.Retries < t.MaxRetry`），如果不用数据库的值覆盖，这个判断永远为真，任务会无限重试。

**第 16 步的三个分支**（`pool.go:922-954`）：

```
err != nil
├── 是 ErrBudgetExceeded（预算耗尽）
│      → 直接 failed，且 return nil（不返回错误 → 队列不再重试）
│      理由：重试只会继续被累计上限拦住，白烧钱
├── 业务重试次数 < 上限
│      → Retries++，状态回 pending，落一条 RunLog(pending)，return err
│      理由：返回错误让 Asynq 也记一次重试，形成"队列重试 + 业务重试"双轨
└── 业务重试次数已耗尽
       → failed，落 RunLog(failed)，return nil（不再交给队列重试）
```

这是**双轨重试**的设计：Asynq 的 `MaxRetry(3)` 是传输级兜底（进程崩溃、序列化失败等），业务层的 `t.Retries < t.MaxRetry` 才是真上限。两条轨道靠"业务成功就 `return nil`"来切断，避免队列层无意义地反复重跑昂贵的模型调用。

### 3.3 流程三：取消任务（跨进程中断）

这是本模块最精彩的一段，因为它要解决一个异步系统里最难的问题：**如何打断一个已经在另一个进程里跑起来的、长达 2 分钟的模型调用？**

```
浏览器          API 进程                       NATS             所有 Worker 进程
  │               │                             │                    │
  │ POST /tasks/:id/cancel                      │                    │
  ├──────────────▶│ CancelTaskIfActive           │                    │
  │               │  条件 UPDATE:                │                    │
  │               │  status IN (pending,processing)                   │
  │               │  SET status=cancelled ─────▶ │ (MySQL)            │
  │               │  若 0 行受影响 → 返回 409    │                    │
  │               │                              │                    │
  │               │ PublishTaskCancel ──────────▶│ 广播 global_task_cancel
  │               │                              ├───────────────────▶│
  │               │                              │      命中在途任务？ │
  │               │                              │      inFlight[id]() │
  │               │                              │      → cancel()     │
  │               │                              │      → 模型调用中断  │
  │  HTTP 200     │                              │                    │
  │◀──────────────┤                              │                    │
```

**三个设计要点**：

1. **条件更新而不是无条件更新**（`manager.go:432-451`）：只有任务还在 `pending` / `processing` 时才允许改成 `cancelled`。如果任务已经 `completed`，取消请求会被拒绝并返回 **409 Conflict**（`handler.go:345-348`）。这消除了一类经典竞态：用户点取消的同时 Worker 恰好写回成功，谁后写谁赢，导致"已完成的答案被改成已取消"。

2. **数据库改状态 ≠ 中断执行**：改 DB 只能让"还没开始的任务"跳过（第 2 步的短路），但对**正在跑模型调用**的任务无效——那个 goroutine 不会自己停下来。

3. **所以要靠"在途取消表"**（`pool.go:192-214`）：
   - 任务开始执行前，把自己的 `context.CancelFunc` 登记进 `inFlight` map（`pool.go:878`）；
   - 收到取消广播时，按 taskID 取出 cancel 函数并调用（`pool.go:206-214`）；
   - context 取消会顺着 `apiCtx` 传播到 HTTP 客户端调用，**真正掐断正在进行的模型请求**；
   - 执行结束时 `defer` 注销（`pool.go:879`）。

   > 细节：意图路由阶段也用同一套机制登记（`pool.go:289`），所以"路由阶段卡住"也能被取消。

**降级设计**（`manager.go:453-454` 注释）：如果消息总线不可达，取消指令发不出去，但**数据库状态已经改了**，任务执行完会发现自己是 cancelled 而被丢弃（`pool.go:915-920`）。即：取消功能"必定生效"，只是"立即中断"这个增强项依赖消息总线。

**一个浪费点**（诚实记录）：取消一个还在队列里排队的任务，并不会把它从 Redis 队列里删掉。Asynq 里它仍然会被调度一次，只是 Worker 取出来发现是 cancelled 就跳过（`pool.go:732-735`）。也就是说取消**浪费一次调度**，但不会产生错误结果。

### 3.4 流程四：手动重试

`handler.go:281-321`：

```
1 取任务 → 2 鉴权 → 3 校验状态必须是 failed（否则 400）
     → 4 把 status 重置为 pending、Retries 归零、清空 Error
     → 5 UpdateTask（写库+缓存+广播）
     → 6 Enqueue（重新投递队列）
```

注意第 4 步把 `Retries` **归零**：这意味着手动重试给了任务一条新命，可以再走满 3 次自动重试。而 `TotalCalls/TotalTokensIn/TotalTokensOut`（跨重试累计计量）**没有被归零**——这是有意的：手动重试不能绕过任务级成本上限，否则可以无限烧钱。

### 3.5 流程五：实时回传（四级传递链路）

```
① Worker 侧写状态
   manager.UpdateTaskIfActive()
     ├─ 条件 UPDATE MySQL                    （真相落库）
     ├─ 回读后 cacheTask → Redis SET 24h      （刷新缓存）
     ├─ eventBus.PublishJSON(global_task_updates)   （跨进程广播）★
     └─ broadcast() → 本进程订阅者 channel     （进程内广播）

② NATS 把消息投给所有订阅者（API 进程的 TaskManager 在订阅）

③ API 侧 TaskManager.listenForGlobalUpdates（manager.go:55-79）
     收到 JSON → 反序列化 → broadcast(t)
     broadcast（manager.go:115-127）：
       按 t.UserID 找到该用户的所有 SSE channel，逐个塞进去

④ Gin 的 SSE handler（handler.go:357-408）
     for { select { <-ctx.Done() 断开 / <-ch 推 task_update / <-toolCh 推 tool_call } }
     c.SSEvent(...) + c.Writer.Flush()
```

**四个关键细节**：

1. **按用户分桶**（`manager.go:31-32`）：`clients map[uint]map[chan *model.Task]bool` 是"用户 ID → 一组通道"。广播时只发给任务归属的那个用户，天然做了数据隔离。

2. **通道满了就丢弃**（`manager.go:121-124`）：
   ```go
   select {
   case ch <- t:
   default:  // 通道满了就丢弃，防止阻塞整个系统
   }
   ```
   通道容量 10（`manager.go:95`）。如果一个浏览器标签页卡住不消费，绝不能让它拖垮整个 API 进程。代价是前端可能漏掉某次状态更新——所以前端还有 `refreshTasks()` 轮询兜底（`web/src/App.vue`）。

3. **SSE 鉴权走 URL 参数**（`handler.go:358-371`）：浏览器的 `EventSource` 不支持自定义请求头，所以没法带 `Authorization: Bearer`。只能 `GET /api/tasks/stream?token=xxx`，然后在 handler 里手动解析 JWT。这也是为什么这个路由**没有挂鉴权中间件**（它挂在 `/api` 组而不是 `/api/tasks` 组，`cmd/api/main.go:211`）——鉴权逻辑被内联进了 handler。

4. **用请求上下文判断断开**（`handler.go:388-390` 注释）：不用已废弃的 `CloseNotify()`，改用 `c.Request.Context()`，否则客户端断开后 handler 不退出，会造成 goroutine 与订阅泄漏。

## 4. 核心机制逐个讲透

### 4.1 三档优先级队列：是"权重"不是"抢占"

**代码**（`internal/worker/pool.go:60-70`）：

```go
srv := asynq.NewServer(redisOpt, asynq.Config{
    Concurrency: workers,                       // 单进程并发协程数
    Queues: map[string]int{
        "high":    6,
        "default": 3,
        "low":     1,
    },
})
```

**入队侧按优先级选队列**（`manager.go:204-223`）：

```go
switch t.Priority {
case model.PriorityHigh: queueName = "high"     // 3
case model.PriorityLow:  queueName = "low"      // 1
default:                 queueName = "default"  // 2
}
```

**任务到队列的完整映射**：

| 任务类型 | 队列 | 队列级最大重试 | 业务级 MaxRetry | 代码 |
|---|---|---|---|---|
| `task:process`（用户对话） | 按 Priority → high/default/low | 3 | 3（提交时写死） | `manager.go:204-223` |
| `kb:build`（文档建库） | low | 3 | — | `manager.go:1045-1055` |
| `kb:delete`（知识库清理） | low | 5 | — | `manager.go:685-693` |
| `doc:delete`（文档清理） | low | 5 | — | `manager.go:984-992` |
| `kb:scan`（定时增量扫描） | low | — | — | `cmd/worker/main.go:141` |

**必须纠正一个说法**：README 写的是"多优先级队列：确保高优任务的绝对抢占权"——**这不准确**。Asynq 的 `Queues map[string]int` 里，数字是**权重**：调度器按 6:3:1 的比例从三个队列取任务，高优队列只是"被取到的频率更高"，**不是"来了就抢占"**。要真正严格抢占需要开启 Asynq 的 `StrictPriority` 选项，而本项目的 `asynq.Config{}` 里**没有设置它**。

实际影响：一条 `low` 队列的长任务（比如图谱抽取，可能跑几分钟）在跑的时候，`high` 队列的新任务**不能打断它**，只能在它释放出的并发槽位里优先被取到。由于 `Concurrency = workers`（默认 5）是共享的，极端情况下如果 5 个槽位都被 `kb:build` 占住，用户对话任务会被饿到等它们跑完。

> ⚠️ 这是本模块**最重要的一个认知修正点**，也是"配置项存在 ≠ 语义成立"的典型例子。

### 4.2 状态机与"条件写回"：消灭 TOCTOU

这是并发系统的经典问题。**TOCTOU = Time-Of-Check-To-Time-Of-Use**：先检查再操作，两步之间状态可能已被别人改掉。

**反面写法**（本项目没有这么写）：

```go
// ❌ 先查后写：查的时候是 processing，写的时候可能已经 completed 了
task, _ := db.GetTask(id)
if task.Status == processing {
    task.Status = cancelled
    db.Save(task)   // 覆写了别人的 completed
}
```

**本项目写法**（`manager.go:375-400`）：

```go
func (m *TaskManager) UpdateTaskIfActive(t *model.Task) bool {
    res := m.db.Model(&model.Task{}).
        Where("id = ? AND status NOT IN ?", t.ID,
              []string{string(model.StatusCancelled), string(model.StatusCompleted)}).
        Updates(map[string]any{
            "status": string(t.Status), "result": t.Result,
            "error": t.Error, "retries": t.Retries, "updated_at": t.UpdatedAt,
        })
    if res.Error != nil || res.RowsAffected == 0 {
        return false   // ★ 0 行受影响 = 状态已被别人改成终态 = 调用方必须丢弃本次结果
    }
    // 回读 + 刷新缓存 + 广播
    ...
    return true
}
```

**精髓在于把"检查"和"更新"压进一条 SQL 的 WHERE 子句**，由数据库的行锁保证原子性：

- `status NOT IN (cancelled, completed)` 这条 WHERE 就是"检查"；
- `Updates` 就是"更新"；
- `RowsAffected == 0` 就是"检查失败"，意味着任务已被并发改到终态。

**调用方必须尊重返回值**，这是设计契约。代码里 4 处都做了正确处置：

| 位置 | 场景 | `false` 时怎么做 |
|---|---|---|
| `pool.go:745-748` | 开始执行前置 processing | 记日志，直接跳过本次执行 |
| `pool.go:939-943` | 失败后置回 pending（准备重试） | 丢弃重试，记一条 RunLog(cancelled) |
| `pool.go:959-963` | 成功后置 completed | **丢弃结果**，记一条 RunLog(cancelled) |
| `pool.go:927` | 预算超限置 failed | （未检查返回值，见 §8.4） |

第 3 行最值得体会：**"用户取消了" 优先于 "我算出来了"**。哪怕模型已经生成完答案，只要用户在写回前一刻取消，答案就被丢弃。

同时提供两个方向的条件更新：

| 方法 | 条件 | 用于 |
|---|---|---|
| `UpdateTaskIfActive` | 状态 **不是** 终态 | Worker 写中间态/终态 |
| `CancelTaskIfActive` | 状态 **是** pending/processing | API 侧处理用户取消 |

### 4.3 双写与 Cache-Aside：真相在 MySQL，快在 Redis

**写路径**（`manager.go:351-370` `UpdateTask`）：

```
MySQL Save  →  Redis SET (TTL 24h)  →  NATS 广播  →  进程内广播
```

**读路径**（`manager.go:226-245` `GetTask`）：

```
Redis GET ──命中──▶ 直接返回
     │
     └─未命中─▶ MySQL 查询 ──▶ 回写 Redis ──▶ 返回
```

这是标准的 **Cache-Aside（旁路缓存）**：读时"缓存优先、未命中回源并回填"；写时"先写库、再更新缓存"。

**为什么缓存是必要的**：Worker 在一个任务里会调用 `GetTask` 多次（第 2 步回读状态、第 5 步读累计计量、第 15 步检查取消），每次都打 MySQL 是浪费。缓存 TTL 24 小时，足够覆盖任务的整个生命周期。

**缓存有一处刻意失效**（`manager.go:426-427`）：

```go
// 失效 Redis 缓存：否则下次 GetTask 读到过期的累计计量，跨重试熔断会失效。
m.rdb.Del(m.ctx, "task:"+taskID)
```

`AccumulateTaskUsage` 用 `gorm.Expr("total_calls + ?", calls)` 在数据库里做**原子累加**，但**不刷新缓存**——因为累加的只是 3 个计量字段，重写整个缓存反而可能把别的新状态覆盖掉。所以选择**删缓存**而不是**改缓存**，让下一次读自然回源，拿到最准的值。

这个"删除而不是更新"的选择是缓存设计的经典权衡：更新缓存在并发下容易写出旧值，删除缓存更安全（代价是下一次读会 miss 一次）。

### 4.4 成本预算：防止"工具乒乓"烧钱

**问题**：ReAct 风格的工具调用循环里，模型可能反复调工具、反复拿不到想要的答案，形成无限循环，每轮都扣钱。

**方案**（`internal/pkg/llm/budget.go` + `pool.go:757-775`）：双层预算

| 字段 | 默认值 | 语义 | 超限后果 |
|---|---|---|---|
| `MaxCalls` | 15 | **单次运行**内模型调用次数上限 | 返回 `ErrBudgetExceeded` |
| `MaxTotalCalls` | 30（= `MaxCalls × 2`） | **跨重试累计**上限 | 同上 |
| `MaxCallsPerTask` 配置 | 15 | 来自 `llm.max_calls_per_task` | — |
| `MaxTotalCallsPerTask` 配置 | 30 | 来自 `llm.max_total_calls_per_task` | — |

**跨重试累计怎么做到**（`pool.go:773-775`）：

```go
if usageTask, ok := p.manager.GetTask(t.ID); ok {
    budget.SetBase(usageTask.TotalCalls, usageTask.TotalTokensIn, usageTask.TotalTokensOut)
}
```

每次任务开始时，把数据库里**历史累计**的用量塞进 Budget 作为基线。于是"这次运行"的上限是 15，但"任务一生"的上限是 30——**重试 3 次不会变成 45 次调用**。

**预算耗尽为什么不重试**（`pool.go:923-931`，注释原文）："重试只会继续被累计上限拦截，直接置 failed"。这是很务实的判断：预算耗尽不是偶发故障，是确定性状态，重试无意义。

**成本怎么算**（`budget.go:93-99`）：

```go
CostUSD = TokensIn × PriceIn / 1e6 + TokensOut × PriceOut / 1e6
```

单价来自配置（`llm.cost_per_1m_in: 0.27` / `out: 1.10`）。单价为 0 时成本返回 0，即"不配单价就不算钱"，不会报错。

**落库的观测记录**（`pool.go:971-1008` `saveRunLog`）：每次运行（含失败、取消、重试）都写一条 `RunLog`，字段包括模型名、状态、调用次数、输入输出 token、成本、耗时毫秒、错误信息。模型名还有一个细节：**优先取 Agent 覆盖的模型名**（`pool.go:984-989`），这样日志里的模型和实际调用的一致。

### 4.5 消息总线：为什么从 Redis Pub/Sub 换成 NATS

`internal/events/events.go:1-6` 的包注释就是答案：

> 设计动机：实时事件原先与 Asynq 队列、任务/缓存共用同一个 Redis。为了让任务队列与实时事件通道解耦（避免相互影响、单一 Redis 故障波及全链路），这里改用 NATS。

**三个 Subject（频道）**（`events.go:25-29`）：

| 常量 | 值 | 用途 | 发布者 | 订阅者 |
|---|---|---|---|---|
| `SubjectTaskUpdates` | `global_task_updates` | 任务状态变更 | Worker | API |
| `SubjectToolEvents` | `global_tool_events` | 工具调用过程 | Worker | API |
| `SubjectTaskCancel` | `global_task_cancel` | 取消指令广播 | API | 所有 Worker |

**内嵌 nats-server**（`events.go:82-109`）：NATS 服务端不是独立容器，而是**在 API 进程内嵌启动**的（`cmd/api/main.go:57`，受 `eventbus.embedded` 控制）。Worker 子进程只作客户端连过来（`cmd/worker/main.go:169`）。好处是零额外部署；代价是**Worker 强依赖 API 先启动**——API 没起来，Worker 连不上就会降级（只打警告，`cmd/worker/main.go:171`），此时跨进程事件全丢。

**连接参数**（`events.go:38-44`）：`RetryOnFailedConnect(false)` + `MaxReconnects(-1)`。首次连不上就放弃（返回错误，由调用方降级）；连上之后无限重连。

**故障降级**（诚实记录）：`eventBus == nil` 时所有发布/订阅静默跳过（`manager.go:56-58, 174-176, 366`）。此时：
- 任务状态**照常落库**，数据不会错；
- 但 API 进程收不到 Worker 的状态更新 → **前端 SSE 收不到实时推送**；
- 用户需要手动刷新（走 REST 查询）才能看到结果。

也就是说：**消息总线故障不影响正确性，只影响实时性**。这是一个合理的取舍。

### 4.6 删除链路的状态兜底与补偿

删除不是"删一行"这么简单，涉及三个存储（Milvus 向量、Neo4j 图谱、MySQL 行）。设计上是**先改状态、再异步清理、失败可重试、卡住能补偿**：

```
① API: RequestDocumentDelete / RequestKnowledgeBaseDelete
        先把状态改成 deleting（保证中断可恢复），再入队
        （manager.go:970-981 / 671-682）
              │
② 队列: doc:delete / kb:delete，low 队列，队列级最大重试 5
        （manager.go:984-992 / 685-693）
              │
③ Worker: 三段式清理
        （pool.go:1165-1205 知识库 / 1209-1248 文档）
              │
④ 补偿: kb:scan 定时任务每次先跑 compensateStaleDeleting
        把 updated_at 早于 10 分钟前、且仍是 deleting 的记录重新入队
        （pool.go:1393-1413；阈值常量 staleDeletingGrace=10min，
         单批上限 staleDeletingBatch=200，pool.go:1386-1389）
```

**为什么要"先改状态"**：如果直接入队，队列投递失败（Redis 抖动）就会出现"用户以为删了、其实一点没删"的静默不一致。先改状态后入队，最坏情况是"标记了删除但没删干净"——这种**可被扫描发现并补偿**。

**为什么需要补偿**：删除任务重试 5 次仍失败后，会永久停在 `deleting`。如果没有补偿，这条记录就永远卡住（知识库列表里显示"删除中"永不结束）。补偿逻辑把它重新投递，实现**最终一致**。

**知识库删除的额外一步**：`ListDocumentIDsByKB`（`manager.go:696-703`）先取出该库下所有文档 ID，用于删 Neo4j 里按 `source_doc` 归属的边——因为图谱里的边不直接带 kb_id，只能靠文档 ID 反查。

### 5.2 状态机

```
                    ┌──────────┐
      提交 ────────▶│ pending  │
                    └────┬─────┘
                         │ Worker 取出（条件更新）
                         ▼
                  ┌─────────────┐
                  │ processing  │
                  └──┬───┬───┬──┘
       成功 │        │   │   └──────────┐
            ▼        │   │              │ 失败且重试未耗尽
     ┌───────────┐   │   │              ▼
     │ completed │   │   │      （Retries++ → 回到 pending）
     └───────────┘   │   │
                     │   └────────────┐
        用户取消 │    │                │ 失败且重试耗尽 / 预算超限
                ▼    ▼                ▼
         ┌───────────┐          ┌────────┐
         │ cancelled │          │ failed │
         └───────────┘          └────────┘
```

**终态**：`completed` / `failed` / `cancelled`。进入终态后，`UpdateTaskIfActive` 和 `CancelTaskIfActive` 都会拒绝写入——这是整个并发安全的基石。

**手动重试**是唯一的"复活"路径，且只能从 `failed` 复活（`handler.go:301-303`）。

### 6.3 进程与并发模型

```
Worker 进程（supervisor，cmd/worker/main.go:49-102）
 ├─ 注册 kb:scan 定时器（仅此处注册，避免重复投递）★
 ├─ 子进程 0（GOTASKAI_WORKER_CHILD_INDEX=0）
 │    ├─ Asynq Server（Concurrency = queue.workers = 5）
 │    ├─ /metrics on 9100+0+1 = 9101
 │    └─ 5 个 handler
 ├─ 子进程 1（...=1）
 │    ├─ Asynq Server（Concurrency = 5）
 │    └─ /metrics on 9102
 └─ ...
总消费并发 ≈ queue.workers × queue.processes = 5 × 2 = 10
```

**为什么定时器只在 supervisor 注册**（`cmd/worker/main.go:57-58` 注释）：如果每个子进程都注册一份 cron，同一时刻会有 N 份 `kb:scan` 被投递，扫描任务被重复执行 N 次。这是一个真实的坑——Asynq Scheduler 没有 leader 选举，只能靠"谁注册谁负责"的约定来保证单实例。

**为什么每个子进程的指标端口要错开**（`cmd/worker/main.go:229-235`）：`port = metrics.port + childIndex + 1`，否则多个子进程抢同一个端口，只有第一个能起来。

**为什么用 `exec.Command(os.Args[0])` 自举**（`cmd/worker/main.go:70`）：supervisor 直接重新执行自己这个二进制，通过环境变量区分身份（`main.go:41-47`）。好处是二进制单文件、无额外入口；代价是子进程崩溃后 supervisor 只记日志不重启（`main.go:78-85`）。

## 8. 已知缺陷与未验证项

> 全部基于代码事实，并给出行号。「运行时行为」类标注需实测。

### 8.1 高：`queue.capacity` 配置项完全未生效

- 事实：`queue.capacity: 1000` 定义在 `config/config.yaml:39`，结构体字段在 `internal/config/config.go:75`，但**全仓库无任何读取点**（已全量检索 `Capacity`，只命中结构体定义）。
- 后果：`AddTask` 失败时 handler 返回 **503 "队列已满"**（`handler.go:180-183`），但 Asynq 本身没有"队列容量"概念，`AddTask` 只在 **MySQL INSERT 失败或 Redis 不可用**时才返回错误。因此这条 503 分支实际上几乎永远不会因为"队列满"而触发。
- 影响：限流靠的是上游 3 次/分的接口限流（`cmd/api/main.go:150`），而不是队列容量。压测时不要按"容量 1000"估算保护阈值。

### 8.2 高：`DeleteSession` 可能"复活"已删除的任务

- 代码路径（`manager.go:248-278`）：
  1. 先查出会话下所有任务；
  2. **`Delete` 批量物理删除这些行**（`manager.go:261`）；
  3. 再遍历这批任务，对 `pending` / `processing` 的调用 `m.UpdateTask(&t)`（`manager.go:266-275`）。
- 问题：`UpdateTask` 内部是 `m.db.Save(t)`（`manager.go:355`）。GORM 的 `Save` 对"带主键但数据库中不存在"的记录会**回退为 INSERT**。于是第 3 步会把第 2 步刚删掉的行**重新插回来**（状态为 `cancelled`）。
- 也就是说：删除一个含有"排队中/执行中"任务的会话，**可能会留下若干条 cancelled 空壳任务**。
- 该项目在《技术情报知识平台-改造计划》的独立审查中已记录过"GORM Save 影响 0 行时回退 Create → 删除后行复活"这一类风险；此处是它在任务域的一个**实际落点**。
- **需实测确认**：属于对 GORM `Save` 语义的推断，建议按 §9.4 的方式造数据复现。

### 8.3 中：优先级是加权而非抢占（见 §4.1）

- 事实：未设置 Asynq 的 `StrictPriority`；`Concurrency` 是所有队列共享的。
- 后果：`low` 队列的长任务（图谱抽取、批量建库）可能占满并发槽位，导致用户对话任务被延迟。
- 与文档不符：README 声称"高优任务的绝对抢占权"。
- 建议方向（仅记录，未实施）：开启 `StrictPriority`，或给 `low` 队列单独分配进程/并发。

### 8.4 中：预算超限分支未检查条件写回的返回值

- 事实：`pool.go:925-930` 把状态置为 `failed` 后调用 `UpdateTaskIfActive(&t)`，**没有判断返回值**。
- 对比：同文件另外三处（`pool.go:745, 939, 959`）都做了判断并妥善处置。
- 后果：如果任务在预算耗尽的瞬间被用户取消，条件写回会返回 `false`（因为已是终态），代码继续执行 `saveRunLog(failed)`，于是**运行日志记为 failed，而任务实际是 cancelled** —— 日志与任务状态不一致。
- 影响面：仅影响观测数据的准确性，不影响任务结果。

### 8.5 中：事件通知是"发了不管"，无补偿

- 事实：所有 `PublishJSON` 的返回值都被丢弃（`manager.go:367, 396, 446, 459, 177` 均写作 `_ = ...`）。
- 后果：消息总线抖动时，前端会**永久漏掉**那一次状态更新，只能靠刷新或轮询补齐。
- 缓解：前端有 `refreshTasks()` 兜底；且数据库状态是对的。

### 8.6 中：SSE 通道满即丢弃，无背压

- 事实：`broadcast` 用 `select/default` 丢弃（`manager.go:121-124`），通道容量 10。
- 后果：客户端处理慢时静默丢事件。
- 取舍说明：这是**刻意的**设计——绝不能为了一个慢客户端阻塞整个广播路径。但缺少丢弃计数指标，问题发生时不可观测。

### 8.7 低：`Task.Result` 列为 `text`（上限 64KB）

- 事实：`internal/model/task.go:44` 为 `gorm:"type:text"`。
- 与同项目已修的问题同源：`Document.Content` 已从 `text` 改为 `mediumtext`（因 10MB 上传闸门，见项目记忆 2026-09-13 补丁）。而 `Task.Result` 存的是模型输出，正常远小于 64KB，因此风险低。
- 但**同一条链路上的 `Task.Payload`、`SystemPrompt` 也是 `text`**：`Payload` 是用户输入（前端可粘贴长文），理论上可超限；MySQL 8 默认 `STRICT_TRANS_TABLES` 下会抛 Error 1406，**不会静默截断**。
- 建议：给 `tasks.payload` 也加长度闸门，或与 `documents.content` 一样升级为 `mediumtext`（**未实施**）。

### 8.8 低：`ListTasks` 条数硬编码 100

- 事实：`manager.go:346` 的 `Limit(100)` 无配置入口。
- 后果：任务多了以后，前端"任务中心"看不到更早的记录。属于产品取舍，非缺陷。

## 9. 怎么验证

> 以下命令均假设已按 README 启动基础设施（`docker compose up -d`）与 API/Worker（`run_microservices.bat`，或需要前端时用 `run_fullstack_dev.bat`）。

### 9.1 验证"提交即刻返回 + 异步执行"

```bash
# 1) 登录拿 token
curl -s -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"你的账号","password":"你的密码"}'

# 2) 提交任务，观察是否立刻返回 202（而不是等模型答完）
curl -s -w "\nHTTP %{http_code}  耗时 %{time_total}s\n" \
  -X POST http://localhost:8080/api/tasks/submit \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"payload":"你好","priority":2}'
```

**期望**：HTTP 202，耗时在毫秒级；响应体含 `id` 与 `status: "pending"`。

### 9.2 验证状态机与实时推送

```bash
# 另开一个终端，建立 SSE 长连接（注意 token 走 query）
curl -N "http://localhost:8080/api/tasks/stream?token=<token>"
```

**期望**：提交任务后，该连接上依次出现 `event: task_update`，状态从 `pending` → `processing` → `completed`（或 `failed`）。

### 9.3 验证重试与预算

```bash
# 把 llm 的 base_url 改成不可达地址，重启 worker，然后提交任务
# 观察：任务状态在 pending/processing 间反复，retries 递增到 3 后变 failed
curl -s http://localhost:8080/api/tasks/<task_id> -H "Authorization: Bearer <token>"
```

**期望**：`retries` 从 0 递增到 3，最终 `failed`；`run_logs` 表里有多条记录（每次重试一条）；`metrics` 的 `gotaskai_task_retries_total` 增加。

```bash
# 观察指标
curl -s http://localhost:8080/metrics | Select-String "gotaskai_task_|gotaskai_llm_"
```

### 9.4 验证 §8.2 的"行复活"

```sql
-- 1) 造一条处于 pending 的任务（提交后立刻暂停 worker，让它停在队列里）
-- 2) 记下 task_id 与 session_id
-- 3) 调用 DELETE /api/tasks/session/{sessionId}
-- 4) 再查一次
SELECT id, status, session_id FROM tasks WHERE id = '<task_id>';
```

**期望（若缺陷成立）**：任务行仍然存在，`status = 'cancelled'`；**期望（设计意图）**：该行应已被物理删除。
→ 若复现成功，修复方向是把 `UpdateTask` 换成"仅当行存在时才更新"的条件写法，或调整顺序为先取消再删除。

### 9.5 验证取消能中断在途调用

```bash
# 1) 提交一个会长时间运行的任务（比如让模型做长文生成）
# 2) 在它处于 processing 时立即取消
curl -s -X POST http://localhost:8080/api/tasks/<task_id>/cancel -H "Authorization: Bearer <token>"
```

**期望**：返回 200；Worker 日志出现 `cancelling in-flight task <id>`（`pool.go:211`）；任务在数秒内变 `cancelled`（而不是等满 2 分钟超时）。
**再试一次**：对已 `completed` 的任务发取消 → 期望返回 **409**。

### 9.6 验证并发安全（条件写回）

```bash
# 提交任务后，在极短时间内同时发出"取消"和等待"完成"，观察是否出现 completed 与 cancelled 互相覆盖
# 更严谨的做法：用 tools/conc_probe.py 采样在途任务数曲线
python tools/conc_probe.py
```

**期望**：任务最终状态唯一，不会出现"先 completed 后 cancelled"的回退（因为终态被条件更新保护）。

## 10. 一页速记（面试/复盘用）

- **架构支柱**：**提交与执行物理分离 + 队列削峰 + 状态机条件写回 + 消息总线跨进程回传**。
- **四个最容易被追问的设计点**：
  1. 为什么重试要回读数据库？（队列重试复用旧 payload，业务级计数会失效）
  2. 为什么用条件 UPDATE 而不是先查后写？（TOCTOU，终态不可被覆盖）
  3. 取消怎么中断已经在跑的模型调用？（NATS 广播 + 进程内 in-flight 取消表）
  4. 消息总线挂了会怎样？（状态照常落库，只是实时推送丢失——正确性与实时性解耦）
- **三个必须说清的事实修正**：优先级是**权重不是抢占**；`queue.capacity` **未生效**；SSE 推送是**任务/工具事件级，不是逐字流式**。
- **一条可量化的证据**：压测（2026-09-07）31 个任务 100% 完成、0 重试，峰值约 6,780 RPS；`llm_calls_total=33`、成本 `$0.01573`——与本模块的 Budget 计量口径一致。
