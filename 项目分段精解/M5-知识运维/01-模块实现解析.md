## 0. 一句话总览

**知识运维 = 让"已入库的知识"随时间保持正确：文件改了要重建、文件删了要清干净、清理失败了要有人兜底。**

前三篇讲的都是"**怎么把知识放进去、怎么取出来**"。这一篇讲反向问题：**怎么把它拿出去，并且拿干净**。

在异步 + 多存储（Milvus / Neo4j / MySQL）架构里，"拿干净"比"放进去"难得多——删除要跨三个存储、每个都可能中途失败、而失败后不清干净就会产生**幽灵知识**（列表显示正常、实际能检索到已删内容）。

## 1. 这个模块解决什么问题

### 1.1 三个用户故事

**故事一：我的文档库是活的**

> "我把知识库指向本地目录 `/data/inbox/papers`。这目录每周会新增论文、也会修订旧论文。我不想每次手动点上传——系统能不能自己定期同步？而且**别重复花钱**：没变过的文件不要再抽一遍图谱。"

→ 需要：**定时扫描 + 内容指纹去重**。

**故事二：删了就得真的没了**

> "我把一份内部草稿上传错了，赶紧删掉。结果同事提问时，答案里竟然还引用了那份草稿的内容。这比查不到更可怕。"

→ 需要：**跨三个存储的失效清理**，且删除后**立刻**对检索不可见。

**故事三：失败不能永久卡住**

> "有个文档一直显示'删除中'，永远不动了。查了下是删除任务重试次数用完了。"

→ 需要：**删除补偿**——重试耗尽后由周期任务兜底重投，实现最终一致。

### 1.2 三块拼图

```
① 定时增量入库    cron 触发 kb:scan → 扫目录 → 指纹比对 → 新建 / 跳过 / 重建
② 三级失效清理    Milvus → Neo4j → MySQL，顺序删、失败可重试、幂等可重入
③ 删除补偿        周期检查卡在 deleting 的行，重新投递，保证最终一致
```

### 3.3 流程三：删除补偿（最终一致的兜底）

```
每次 kb:scan 触发（即使没有配置扫描源也会跑）
   │
   ▼
compensateStaleDeleting()
   ├─ cutoff = now - 10min
   ├─ ListStaleDeletingDocumentIDs(cutoff, 200)
   │     SELECT id FROM documents WHERE status='deleting' AND updated_at < cutoff
   │     ORDER BY updated_at ASC LIMIT 200
   │  → 逐个 EnqueueDocDelete(id)
   └─ ListStaleDeletingKnowledgeBaseIDs(cutoff, 200)
         SELECT id FROM knowledge_bases WHERE status='deleting' AND updated_at < cutoff
      → 逐个 EnqueueKBDelete(id)
```

**为什么补偿一定要挂在 `kb:scan` 上**（`pool.go:1255-1256` 注释原文）：

> 补偿（W3 6.4）：重投因重试耗尽而滞留的删除任务。**即使未配置扫描源也执行，保证删除最终一致。**

这个设计很实在：`kb:scan` 的**主职责**是扫目录，**兜底职责**是删数据。如果补偿逻辑挂在"有扫描源才跑"的分支里，那没配扫描源的部署就永远没有补偿——删除失败即永久卡死。所以 `compensateStaleDeleting()` 被放在函数**最开头**，早于 `scan_sources` 的空值检查。

## 4. 核心机制逐个讲透

### 4.1 定时调度：为什么"只有一个进程能注册"

**问题**：Asynq 的 Scheduler **没有 leader 选举**。谁注册了 cron，谁就在到点时投递任务。而本项目 Worker 是 **supervisor + N 个子进程**模型（`queue.processes`，默认 2）。

若每个子进程各注册一份 cron，"每日 03:00"会同时投递 **N 份** `kb:scan`——同一目录被扫 N 次、重复告警、重复读文件。副本数再放大就变成 `N × 副本数`。

**代码怎么解**（`cmd/worker/main.go:41-58`）：

```go
if os.Getenv(workerChildIndexEnv) == "" {
    runSupervisor(cfg)      // ← 只有 supervisor 走这条路
    return
}
runWorkerProcess(cfg)       // ← 子进程（带 GOTASKAI_WORKER_CHILD_INDEX）走这条路
```

```go
// W2：kb:scan 周期任务只在 worker 主实例（supervisor）注册，
// 避免每个子进程各注册一份导致重复投递（R4）。
if scheduler := startKBScanScheduler(cfg); scheduler != nil {
    defer scheduler.Shutdown()
}
```

**用"进程身份"代替"分布式锁"**：靠环境变量区分 supervisor 与子进程，把注册动作锁在唯一进程里。简单、零依赖，但**只在单副本部署下成立**——设计文档原本要求 `asynq.Unique(ttl)` 或 `TaskID` 做跨副本兜底，**代码里没有实现**（见 §8.5）。

**时区是个隐藏的坑**（`cmd/worker/main.go:140`）：

```go
scheduler := asynq.NewScheduler(db.NewAsynqRedisConnOpt(cfg.Redis),
    &asynq.SchedulerOpts{Location: time.Local})
```

Asynq 默认时区是 **UTC**。不显式指定时，`"0 3 * * *"`（想表达"每日凌晨 3 点"）会在**北京时间 11:00** 触发。

代码用了 `time.Local`——**依赖宿主机的 `TZ` 设置**：

| 运行环境 | `time.Local` 实际值 | `0 3 * * *` 的真实触发时间（北京时间） |
|---|---|---|
| Windows 开发机（时区设为北京） | Asia/Shanghai | 03:00 ✅ |
| Linux 容器（未设 TZ） | **UTC** | **11:00** ❌ |

设计文档明确写的是 `SchedulerOpts{Location: Asia/Shanghai}`（硬编码时区），实现换成了 `time.Local`——**从"确定性"退化为"环境依赖"**。容器化部署前必须显式设 `TZ=Asia/Shanghai`。

**启动期还有一次可读性预检**（`cmd/worker/main.go:122-138`）：

```go
readable := 0
for _, src := range cfg.KB.ScanSources {
    if src.KBID == "" || src.Path == "" {
        slog.Warn("kb:scan source ignored: kb_id and path are required"); continue
    }
    info, err := os.Stat(src.Path)
    if err != nil || !info.IsDir() {
        slog.Warn("kb:scan source unreadable, will be skipped at runtime",
            "path", src.Path, "error", err)
        continue
    }
    readable++
}
if readable == 0 {
    slog.Warn("kb:scan: no readable scan source, only delete compensation will run")
}
```

**为什么值得在启动时查一次**：容器/多节点部署下，"配置里写的本地路径"很可能在运行进程所在节点上**不存在**（配置挂载了但卷没挂上）。启动时报一行 warning，比等到凌晨 3 点任务失败才发现好得多。注意它**只告警不阻断**——扫描源不可读时任务照常注册，因为补偿还要跑。

### 4.2 指纹判据：为什么不用 `mtime`

**三态判定**（`kbimport.go:70-79`）极其简单：

```go
func Decide(existingHash, newHash string) Action {
    switch {
    case existingHash == "":      return ActionCreate    // 库里没这个来源 → 新建
    case existingHash == newHash: return ActionSkip      // 指纹一致 → 跳过（零成本）
    default:                      return ActionRebuild   // 指纹变了 → 先清理再重建
    }
}
```

指纹是**内容 sha256**（`kbimport.go:63-66`）。

**为什么不用文件修改时间 `mtime`**（设计文档 §5.2 给的理由是"`mtime` 在拷贝/同步场景不可靠"）。具体地：

- 从别处 `cp`/`rsync` 过来的文件，`mtime` 可能保留**源文件的旧时间**——内容明明变了，`mtime` 却是老的 → **漏检变更**；
- 某些工具（编辑器、构建脚本）只 `touch` 不写内容——`mtime` 变了但内容没变 → **误判变更** → 白跑一次最贵的图谱抽取；
- 跨时区/跨文件系统迁移时，`mtime` 的精度与时区解释都不一致。

内容 sha256 没有这些问题，代价是要把文件**完整读一遍**。对"每天扫一次、单文件 ≤10MB"的场景，这个代价可以接受。

**为什么变更处理是"先清理后重建"而不是"追加"**（设计文档 §5.2 原文）：

> 追加会让新旧事实并存，污染图谱并给出过时证据。

这指出了图数据库特有的问题：Milvus 里旧 chunk 和新 chunk 并存，只会让某段落被重复召回（影响小）；但 Neo4j 里**旧事实边和新事实边并存**，会让模型同时看到"张三出生于 A 市"和"张三出生于 B 市"——**直接给出矛盾证据**。所以必须整体替换，不能增量追加。

**三态的成本差异是这设计的经济意义**：

| 动作 | LLM 调用 | 向量化 | 说明 |
|---|---|---|---|
| `skip` | 0 | 0 | 绝对零成本，绝大多数文件每天走这一支 |
| `create` | 摘要 1 次 + 向量 N 次 + 图谱抽取 1 次 | 有 | 新文件 |
| `rebuild` | 同 create | 有 | 变更文件；**图谱抽取是最贵的一步** |

所以 `skip` 命中率直接决定这个功能的日常成本。设计文档把它列为风险 R1（"图谱抽取重复付费"），缓解措施是 `content_hash + ontology_version` **双键判定**——但 **`ontology_version` 没有实现**（见 §8.4），所以目前只有内容维度能触发重建，**本体升级后不会自动重抽**。

### 4.3 `create` 路径

```go
// pool.go:1322-1340
doc := &model.Document{
    ID: uuid.New().String(), KBID: kbID,
    Title: filepath.Base(f.Path),          // 标题 = 文件名
    Content: f.Content, ContentHash: f.Hash,
    SourcePath: f.Path,                    // ★ 绝对路径，增量匹配的键
    Status: "pending", GraphStatus: "pending",
}
p.manager.CreateDocument(doc)
p.manager.EnqueueKBBuild(kbID, doc.ID)
```

三个要点：

1. **`SourcePath` 是绝对路径**（`kbimport.go` 用 `filepath.Abs` 归一），因为它是增量匹配的键。若不同轮次扫描得到不同形式的路径（相对/绝对、正反斜杠），就会把同一文件当成新文件反复入库。`ScanDir` 还额外按**绝对路径排序**（`kbimport.go:123`），保证多次扫描顺序稳定。
2. **`CreateDocument` 失败**会被上层 `handleKBScan` 记 `[Worker][ALERT]` 后 `continue`。设计文档 §13.2 把这类路径称为"**噪音型**"：因为库里始终没有这一行，下轮扫描的 `GetDocumentBySource` 仍返回"不存在"，于是**每周期重复读文件、重复失败、重复告警**，文件永久无法入库。不是数据损坏，但会持续刷告警。
3. `GraphStatus` 也初始化为 `pending`，与 `Status` 分开维护（这样"向量成了但图谱没成"能被单独观测）。

### 4.4 `rebuild` 路径：最危险的一段代码

这是整个模块**唯一会产生数据损失**的地方。

```go
// pool.go:1342-1380
default: // ActionRebuild：内容变更，先失效清理再重建。

    // ① 正在删除或已在处理中：本轮跳过，避免重复入队
    switch existing.Status {
    case "deleting", "processing", "pending":
        return kbimport.ActionSkip, nil
    }

    // ② 体积校验前置
    if len(f.Content) > kbimport.MaxFileSize {
        existing.Status = "failed"
        p.manager.UpdateDocument(existing)
        return kbimport.ActionSkip, fmt.Errorf("kbimport: content too large …")
    }

    // ③ 先删旧向量
    if p.ragStore != nil {
        if err := p.ragStore.DeleteByDocID(ctx, existing.ID); err != nil { return action, err }
    }
    // ④ 再删旧图谱边
    if p.kagManager != nil {
        if _, err := p.kagManager.DeleteBySourceDoc(ctx, existing.ID); err != nil { return action, err }
    }
    // ⑤ 覆写正文并清空派生状态
    existing.Content = f.Content
    existing.ContentHash = f.Hash
    existing.Summary = ""          // ★ 内容变了，摘要必须重生成
    existing.ChunkCount = 0
    existing.Status = "pending"
    existing.GraphStatus = "pending"
    if err := p.manager.UpdateDocument(existing); err != nil { return action, err }
    // ⑥ 重新入队建库
    p.manager.EnqueueKBBuild(kbID, existing.ID)
```

#### 为什么顺序必须是"先删后写"

不能反过来（先 `UpdateDocument` 再删旧向量），因为检索是**按 `doc_id` 过滤**的：如果先更新了 MySQL 行（新内容）却还没删旧向量，那么在"更新完成 ~ 删除完成"窗口里，用户检索到的会是**旧内容**，而 MySQL 里显示的已经是新内容——状态与事实不符。更糟的是这个窗口很长（删除要跨两个存储）。

所以**先清空旧的，再写入新的**。代价是：中间失败会留下"两空"状态——即 **"先删后写"窗口**。

#### 这个窗口的具体危害

设计文档 §13.2 定性为"**数据损失型**"，描述准确：

> 一旦 `UpdateDocument` 因溢出失败，**向量与图谱已被清空，而 MySQL 行仍是旧内容、旧 `content_hash`、`status = ready`、`chunk_count > 0`** —— 产生「列表显示 ready、实际一条也搜不到」的幽灵文档，且下轮扫描会重复该过程。

关键点：**MySQL 行还是 `ready`**。因为 `UpdateDocument` 失败意味着第 ⑤ 步写库没成功，状态字段停留在上次成功时的 `ready`。于是：

- 用户看到"就绪"；
- 检索不到任何内容（向量和边都被删了）；
- **下一轮扫描**：`GetDocumentBySource` 拿到旧的 `ContentHash` ≠ 新文件 hash → 又判 `rebuild` → 又删一遍（此时删的是空的，无副作用）→ 又尝试写库 → 又失败。如此循环，**每轮刷告警**。

#### 补丁做了什么（以及一个必须说清的"真相"）

针对该问题，2026-09-13 落了两条改动（设计文档 §13）：

| 改动 | 落点 | 效果 |
|---|---|---|
| `Content` 列 `text` → **`mediumtext`** | `model/document.go:12` | ✅ **这才是真正的修复**：列上限从 65,535 字节提到 16MB，与 10MB 闸门对齐 |
| 体积校验**前置**到两次删除之前 | `pool.go:1351-1357` | ⚠️ 见下 |

⚠️ **必须说清的真相：第 2 条守卫在当前代码里恒不触发。**

```go
// kbimport.go:137（ScanDir 内部，先于返回过滤）
if info.Size() == 0 || info.Size() > MaxFileSize {
    return File{}, fmt.Errorf("kbimport: skip %s (size %d)", path, info.Size())  // 超限文件被跳过
}
```

```go
// pool.go:1352（守卫）
if len(f.Content) > kbimport.MaxFileSize { … }   // ← 永远为 false
```

推理链：

1. `syncScannedFile` 的 `f` 参数**只来自** `kbimport.ScanDir`（全仓唯一调用点 `pool.go:1284`）；
2. `ScanDir` 已跳过所有 `info.Size() > kbimport.MaxFileSize` 的文件；
3. `f.Content` 是文件字节的字符串形式（去 BOM 后更短），故 `len(f.Content) ≤ info.Size() ≤ MaxFileSize`；
4. 两边用的是**同一个常量** `kbimport.MaxFileSize`，所以二者**永远同时成立或同时不成立**。

**结论**：这是一道逻辑上恒为假的校验，只有"`Stat` 之后、`Read` 之前文件突然变大"（TOCTOU）这种极窄场景才可能触发。

那补丁白做了吗？**没有**——真正兜住问题的是**列类型升级**。守卫是"防御性代码"：如果将来有人放宽 `ScanDir` 的上限（比如 50MB），这道守卫会立刻起作用。但**它必须换一个独立常量**，否则"同源常量"会让它继续沉默。

#### 还有一个隐性代价：`Summary` 被清空

第 ⑤ 步把 `Summary` 置空。这会让重建后的文档丢失摘要层——但**建库任务会重新生成**（M4 向量线 §4.6 的摘要逻辑）。所以这里清空是对的：**不清空的话，摘要层会注入"针对旧内容的摘要"，而命中层给的是新内容**——这正是设计文档担心的"过时证据"，只不过发生在摘要层。

### 4.5 三级清理的顺序设计

**删除顺序：Milvus → Neo4j → MySQL 行**。这个顺序不是随意的：

| 步骤 | 为什么在这个位置 |
|---|---|
| ① 先把 MySQL 行置 `deleting`（在 API 侧） | 让"删除意图"**先持久化**。进程崩了也能靠这行状态恢复（补偿只认 `status='deleting'`） |
| ② 删 Milvus 向量 | 这是**检索可见性的关键**。删完之后用户就搜不到内容了（M4 向量线里 `DeleteByDocID` 内含强制 `Flush`，就是为了让"删完立刻不可见"成立） |
| ③ 删 Neo4j 边 | 图谱也是检索来源，同样必须清 |
| ④ **最后**删 MySQL 行 | 行是"墓碑"。只要行还在（`deleting`），补偿就能发现"这个删除没完成"并重投。**行一旦删掉就失去线索了**——所以必须最后删 |

**一句话记忆**：**先断检索（②③），再拆墓碑（④）**。反过来（先删行）就永久失去了"这里还有东西没清"的记录。

**幂等性从哪来**（`handleDocDelete`，`pool.go:1209-1248`）：

```go
if doc, ok := p.manager.GetDocument(docID); !ok {
    return nil            // ★ 文档不存在 → 直接成功返回
}
```

这个**存在性前置检查**是整个删除幂等性的根基：

- 删除任务被重试/被补偿重复投递时，第二次进来发现行已不在 → 直接成功返回，不会报错、不会重复递减 `doc_count`；
- 也让"用户连点两次删除"这类重复请求无害。

**为什么 KB 级删除要"先快照 doc_ids"**（`pool.go:1165-1205`）：

```go
docIDs, _ := p.manager.ListDocumentIDsByKB(t.KBPayload)     // ① 先在删行前取快照
p.ragStore.DeleteByKBID(ctx, kbID)                          // ② 按 kb 整体删向量
for _, docID := range docIDs {
    p.kagManager.DeleteBySourceDoc(ctx, docID)              // ③ 逐个清图谱边
}
p.manager.DeleteDocumentsByKB(kbID)                          // ④ 删文档行
p.manager.DeleteKnowledgeBaseRow(kbID)                       // ⑤ 最后删 KB 行
```

`doc_ids` **必须在第 ④ 步之前取**：图谱清理（③）是按 `doc_id` 逐个做的，而 Neo4j 的边只知道 `source_doc`（= `doc_id`），不知道 `kb_id`。一旦文档行被删掉，就再也枚举不出该文档的 `doc_id`——图谱边将成为**永久残留**。

> 这里体现了一个跨存储的通用原则：**在删除任何"索引型数据"之前，先把需要用到的 ID 快照下来**。

### 4.6 删除补偿：最终一致的最后一道网

**触发条件**（`pool.go:1393-1413`）：

```go
const (
    staleDeletingGrace = 10 * time.Minute   // 滞留多久算"卡住"
    staleDeletingBatch = 200                // 单轮最多补偿多少条
)
cutoff := time.Now().Add(-staleDeletingGrace)
for _, id := range p.manager.ListStaleDeletingDocumentIDs(cutoff, staleDeletingBatch) {
    p.manager.EnqueueDocDelete(id)
}
for _, id := range p.manager.ListStaleDeletingKnowledgeBaseIDs(cutoff, staleDeletingBatch) {
    p.manager.EnqueueKBDelete(id)
}
```

四个细节：

1. **两个粒度都补**：文档级 + 知识库级。只补文档会漏掉"KB 删除中断"的情况。
2. **10 分钟宽限期**：`updated_at < now - 10min`。这个宽限是**必须的**——否则会把"刚刚被请求、正在正常处理中"的删除任务也重投一遍，造成重复劳动甚至重复删除。10 分钟远大于正常删除耗时（秒级），能安全区分"正在做"和"卡住了"。
3. **单轮限 200 条 + `ORDER BY updated_at ASC`**：按最老的先补，防止新卡住的任务永远排在后面。限批量是为了避免一次投递过多任务压垮队列。
4. **补偿是"重投"而不是"自己执行"**：`EnqueueDocDelete` 只投一个任务，实际清理还是由 `handleDocDelete` 做。这样补偿逻辑极简，且天然复用删除逻辑的幂等性。

**为什么这称为"最终一致"**：删除请求返回 202 之后，系统进入"不保证立刻完成、但保证最终完成"的状态。只要 `kb:scan` 还在跑（cron 配了、worker 活着），卡住的删除一定会被重投直到成功。代价是**可能需要最多一个 cron 周期（默认一天）**——即一个删除任务如果在 03:00 之后卡住，要等到次日 03:00 才被补偿。

> 这是个真实的运维含义：**"最终一致"的"最终"在这里可能是 24 小时**。如果要更快的收敛，需要把补偿挪到更频繁的周期任务上（当前没有独立的补偿任务）。

### 4.7 批量保护与故障隔离

**批量保护**（`pool.go:1263, 1298-1303`）：

```go
remaining := kc.ScanBatchSize       // <=0 表示不限制
…
if remaining > 0 {
    remaining -= len(files)
    if remaining <= 0 { break }
}
```

设计意图是"防雪崩"：如果扫描目录里第一次出现 10 万个文件（比如误挂了根目录），全量入队会把队列瞬间打满、把 LLM 成本打爆。`scan_batch_size`（默认 200）把它切成多轮。

**但要注意它的粒度不是精确的**：`remaining -= len(files)` 减的是 `ScanDir` **实际返回的文件数**，而 `ScanDir` 的 `limit` 参数就是 `remaining`——所以单轮最多处理 `ScanBatchSize` 个文件。不过**只有 `ActionSkip` 也占用额度**：目录里已有 200 个未变更文件时，这一轮额度会被全部"浪费"在 `skip` 上，新文件要等下一轮。对每天一次、目录稳定的场景影响不大，但**首次指向一个已有内容的大目录时，增量入库会被拉长到多个周期**。

**故障隔离**（`pool.go:1266-1280`）：三层 `continue`，任一层失败都不影响其它源/其它文件：

| 失败点 | 处理 |
|---|---|
| 源的 `KBID`/`Path` 为空 | `continue`（静默跳过） |
| 该 `KBID` 在库中不存在 | `[Worker][ALERT]` + `continue` |
| 源目录不可读 | `[Worker][ALERT]` + `continue` |
| 单文件同步失败 | `[Worker][ALERT]` + `continue` |

**为什么"知识库不存在"要跳过而不是自动创建**：扫描源配置里写了 `kb_id`，但这个知识库可能已被用户删掉。这时候自动重建一个知识库是**危险的**——用户删库的意图会被系统悄悄撤销。所以只告警跳过，把决定权留给人。

**最后一个细节**（`pool.go:1306`）：

```go
log.Printf("[Worker] kb:scan done: created=%d rebuilt=%d skipped=%d", created, rebuilt, skipped)
```

每轮扫描输出一行统计。这三个数字是运维时最有用的信号：`skipped` 占比高说明增量去重在工作；`rebuilt` 突然很大说明有批量变更（或指纹判据出问题）；`created` 持续非零但 `doc_count` 不涨，就说明 create 路径在失败（对应 §4.3 的"噪音型"问题）。

### 5.2 状态机

```
Document.status

   ┌──────────────── 扫描发现新文件 ────────────────┐
   ▼                                               │
 pending ──(kb:build 开始)──▶ processing ──(成功)──▶ ready
   ▲                              │                  │
   │                              └──(失败)──▶ failed │
   │                                                 │
   └──── 扫描发现内容变更（rebuild）─────────────────┘
                 │
                 │  用户/API 请求删除
                 ▼
             deleting ──(三级清理完成)──▶ 行被物理删除
                 │
                 └── 超过 10 分钟仍为 deleting ──▶ 补偿重投（回到 deleting 循环）

KnowledgeBase.status

   pending ──▶ building ──▶ ready
                  │
                  └──▶ failed
   deleting ──(三级清理完成)──▶ 行被物理删除
        └── 超过 10 分钟 ──▶ 补偿重投
```

**一个容易忽略的细节**：`rebuild` 会把 `status` 从 `ready` 打回 `pending`（`pool.go:1372`）。也就是说**内容变更后文档会短暂回到"待处理"**——这是诚实的，因为它确实还没重建完。用户在列表里会看到状态回落，这是预期行为、不是 bug。

## 6. 依赖与协作

### 6.1 依赖的外部系统

| 依赖 | 用途 | 故障时行为 |
|---|---|---|
| **本地文件系统** | 扫描源目录 | 启动预检告警；运行期该源跳过，其它源不受影响 |
| **MySQL** | 状态、指纹、补偿筛选 | 启动即 Fatal；运行期任务报错 → Asynq 重试 |
| **Milvus** | 向量删除 | `ragStore == nil` 时**跳过删除**（`if p.ragStore != nil`）→ 可能留下残留向量 |
| **Neo4j** | 图谱边删除 | `kagManager == nil` 时**跳过删除** → 可能留下残留边 |
| **Redis / Asynq** | 承载 `kb:scan` / `doc:delete` / `kb:delete` / `kb:build` | 启动即 Fatal |

> ⚠️ 注意中间两条：删除链路里对 `ragStore` / `kagManager` 的调用**都有 nil 判断**（`pool.go:1228, 1233`），即"存储不可用时静默跳过删除"。这保证了删除不会因为依赖不可用而卡死，但也意味着**一次 Milvus 故障期间的删除，会留下永远无人清理的残留**（因为删除任务已经"成功"了，补偿不会重投）。这是一个真实的一致性缺口。

### 6.2 被谁使用

| 使用方 | 用途 |
|---|---|
| `cmd/worker` supervisor | 注册 `kb:scan` 定时器、启动期预检 |
| `api.KnowledgeBaseHandler` | 请求删除（标记 + 入队）、扫描源状态查询 |
| `worker.handleKBBuild` | 重建时被本模块投递（`EnqueueKBBuild`） |
| `M4 向量线 / 图谱线` | 提供 `DeleteByDocID`/`DeleteByKBID`/`DeleteBySourceDoc` 三个能力 |

### 6.3 与 M7 任务底座的关系

本模块**不自建队列，完全复用 M7 的三个队列语义**：

| 任务 | 队列 | 优先级含义 |
|---|---|---|
| `kb:scan` | `low` | 定时批处理，不该抢用户请求资源 |
| `kb:build` | `low` | 建库（含最贵的图谱抽取） |
| `doc:delete` / `kb:delete` | `low` | 清理 |

**注意**：删除和建库同属 `low` 队列，且 M7 里已确认 **Asynq 的 `StrictPriority` 未开启**（M7 §4.3）。所以"用户删了文档希望立刻生效"和一个正在跑的 `kb:build` 之间**没有优先级保护**，会互相排队。这是删除延迟的一个来源。

## 8. 已知缺陷与未验证项

> 本节前半部分是**「设计文档 vs 实际代码」的对照**。设计文档 `docs/tech/技术情报知识平台-改造计划.md`（2026-09-12）经过独立技术审查，明确论证了若干实现要求；实现阶段有部分未落地。**这不是文档错了，而是实现偏离了已审查的方案**——偏离项里有两条（§8.1、§8.2）有实际后果。

### 8.1 高：图谱建模偏离已审查方案，平行边问题被重新引入

这是最需要关注的一条。

**设计文档 §6.2 的结论**（原文摘要）：

> 初稿提出「把 `source_doc` 写进关系属性并放进 MERGE 模式」，该方案**会破坏检索行为**，已废弃。
>
> 问题：`MERGE (a)-[r:REL {source_doc:$doc}]->(b)` 是"含属性全匹配"。同一 `(a, REL, b)` 事实来自两篇文档时会生成**两条平行边**；而 `queryNeighbors` 用 `MATCH (n)-[r]->(m)` 不按 `(src,type,dst)` 去重，平行边会产生**重复事实**，挤占 `GraphTopN` 预算、稀释证据链。
>
> **采用方案：文档节点 + 事实边两级模型**
> ```cypher
> MERGE (a)-[r:REL]->(b)              // 事实边：跨文档唯一，保持单条
> MERGE (d:Document {doc_id: $doc_id})
> MERGE (d)-[:ASSERTS]->(r)           // 溯源边：按文档可枚举
> ```

**实际代码**（`kag.go:113-125`）：

```go
// 有来源时
query = `MERGE (a:Entity {name: $source})
         MERGE (b:Entity {name: $target})
         MERGE (a)-[r:%s {source_doc: $doc_id}]->(b) RETURN id(r)`
```

即**实现的正是被审查否决的单级方案**（`source_doc` 在关系属性上并参与 MERGE）。并且 `retrieve.go` 的 `queryNeighbors` **没有**加 `(src, rel, dst)` 去重防御（设计文档 §6.2 把它列为"配套加固"，要求"无论最终建模如何"都要加）。

**后果**：当同一事实出现在两篇文档中时：

1. Neo4j 里产生**两条平行边**（因为 `source_doc` 不同 → MERGE 模式不匹配 → 新建）；
2. `queryNeighbors` 的 `MATCH (n:Entity {name})-[r]->(m)` 会把两条边都返回；
3. `expandNeighbors` 不去重 → 同一条事实在证据链里出现**两次**；
4. 结果：`graph_top_n = 10` 的预算被重复事实占用，**有效证据条数减半**。

**设计文档还预见了这一点会稀释证据链**——这不是理论推演，是同一个方案被否决的确切原因。

**可验证**：把同一份事实文本放进两个文件、都入同一个 KB，然后在 Neo4j Browser 执行：

```cypher
MATCH (a)-[r]->(b) WHERE a.name = '<实体A>' AND b.name = '<实体B>'
RETURN type(r), r.source_doc;
-- 期望（设计文档方案）：1 条
-- 实际（当前实现）：2 条
```

### 8.2 高：知识库级删除与补偿的粒度不匹配

**设计文档 §6.4 陷阱 4**（原文）：

> **补偿任务可见性**：补偿只认 `status='deleting'` 的文档；KB 级删除必须**先**把该 KB 下所有文档置 `deleting`，否则补偿扫不到。

**实际代码**：`RequestKnowledgeBaseDelete(kbID)` **只把 KB 行置 `deleting`**，其下属的 `documents` 行**状态不变**（仍为 `ready`）。

补偿侧确实有 KB 粒度的分支（`ListStaleDeletingKnowledgeBaseIDs`），所以**KB 行的删除最终会被补偿到**——这一点比设计文档担心的情形要好。但仍然存在两个缺口：

1. **文档行的墓碑缺失**：KB 删除中途失败时，补偿会重投整个 `kb:delete`。此时 `ListDocumentIDsByKB` 若因为文档行已被部分删除而返回不完整列表，**图谱清理（逐个 docID）会漏删**——这正是流程二里"必须在删行前快照"要解决的问题，但重跑时快照质量取决于上一次执行到了哪一步。
2. **补偿周期即 cron 周期**：如 §4.6 所述，"最终一致"的最终可能是 **24 小时**。

### 8.3 中：`(kb_id, source_path)` 唯一键未落地

**设计文档 §6.1 明确要求**（原文）：

> 复合唯一键必须写成 GORM 标签：`kb_id` 与 `source_path` 同带 `uniqueIndex:uk_kb_source`，否则 `AutoMigrate` **不会**建这个键。
>
> `source_path` 用 `*string`（或 `sql.NullString`）以产生真正的 NULL。

**实际代码**：已 grep 核实——全仓 `uniqueIndex` 只出现在 `users.username` 与 `tools.name`；`documents` 的 `source_path` 是 `string` 且只有 `index`。

**后果**：

1. **唯一性只靠应用层的 `GetDocumentBySource` 保证**。两个扫描源配了同一个 `path`（或两个 worker 实例同时扫同一目录的极端情况）会产生**重复文档行**——同一文件两份内容、两套向量、两套图谱边；
2. `source_path` 是 `string`（非 `*string`）→ **手动上传的文档写入空串 `""`**，而不是 NULL。这正是设计文档警告过的：如果将来给这个字段加唯一键，**第二条空串记录会直接唯一键冲突**。也就是说，现在加上唯一键会立刻失败，必须先做数据清理。

### 8.4 中：`ontology_version` 未落地，本体升级不会触发重抽

已 grep 核实：`ontology_version` / `OntologyVersion` **在全仓不存在**。

后果：设计文档的风险 R1 缓解措施（`content_hash + ontology_version` 双键判定）只实现了一半。当本体白名单变更、或抽取 prompt 改进后：

- 存量文档的 `content_hash` 没变 → 扫描判定 `skip` → **永不重抽**；
- 想重抽只能手动改文件内容（触发 rebuild）或直接清库重建。

这是"知识质量升级"路径上的一个真实阻塞点。

### 8.5 中：定时器无跨副本去重

已 grep 核实：无 `asynq.Unique(` / `asynq.TaskID(` 调用。

现状的"单实例"靠**进程身份判断**（supervisor vs 子进程）实现，只在**单副本部署**下成立。一旦部署两个 worker 副本（比如为了 HA）：

- 两个 supervisor 各注册一份 cron → 每轮投递 2 份 `kb:scan`；
- 两份任务并发扫同一目录 → 同一文件可能被两个任务同时判为 `create` → **产生重复文档行**（正好被 §8.3 的"无唯一键"放大）。

### 8.6 中：`doc_count` 用递减而非重算

设计文档 §6.4 陷阱 3 要求：

> `doc_count` 递减不幂等：重复补偿会减到负数。改为删除完成后**重算该 KB 的实际文档数覆盖写**。

实际代码用的是 `DecrementKnowledgeBaseDocCount`（`doc_count - 1`，下限 0）。

**但实际风险比设计文档设想的小**，因为 `handleDocDelete` 开头有存在性检查（§4.5）：文档行已删则直接 `return nil`，**不会二次递减**。所以"重复补偿减到负数"这条路径被堵住了。

残留风险是**累积漂移**：

- 如果 `doc_count` 曾经因为别的原因不准（比如 §4.3 的 create 失败路径、或历史上一次 KB 删除漏了递减），递减只会**保持错误的偏移量**，永远不会自我纠正；
- 重算则是一次性纠偏。

所以这条更准确的定性是：**不是 bug，而是"不自愈"**。列表页显示的文档数可能与真实值有历史偏差。

### 8.7 中：存储不可用时删除静默跳过，残留无人清理

见 §6.1 的注记。`handleDocDelete` / `handleKBDelete` 里对 `ragStore` / `kagManager` 的调用都包了 `!= nil` 判断：

```go
if p.ragStore != nil { p.ragStore.DeleteByDocID(...) }
if p.kagManager != nil { p.kagManager.DeleteBySourceDoc(...) }
```

**后果**：Milvus 故障期间发生的删除，会**跳过向量清理并把任务判为成功**。由于任务成功（不是失败），补偿**不会重投**——于是那条向量成为**永久残留**，且能继续被检索命中。

这正是用户故事二里最怕的情况，只不过触发条件不是"代码逻辑错"，而是"**依赖恰好不可用**"。修法方向（未实施）：nil 时**返回错误**让任务重试，而不是静默跳过。

### 8.8 低：`scan_batch_size` 的额度被 `skip` 占用

见 §4.7。首次指向已有大量内容的大目录时，增量入库会被拉长到多个扫描周期（因为 `skip` 也计入额度）。

### 8.9 低：时区依赖环境（`time.Local`）

见 §4.1。容器未设 `TZ` 时，"每日 03:00"会变成北京时间 11:00。

## 10. 一页速记（面试/复盘用）

- **架构支柱**：**异步删除 + 墓碑状态 + 周期补偿**。删除先持久化意图（`status=deleting`），再跨三存储清理，最后拆墓碑；失败由周期任务重投，实现最终一致。
- **四个最容易被追问的设计点**：
  1. 为什么不用 `mtime` 做变更判据？——`cp`/`rsync` 会保留旧 `mtime`（漏检），`touch` 会改 `mtime` 不改内容（误判，白花最贵的图谱抽取）。用内容 sha256 换准确性。
  2. 为什么删除顺序是 Milvus → Neo4j → **最后** MySQL？——**先断检索，再拆墓碑**。只要有 `deleting` 行在，补偿就能发现"还没清完"；行一删就失去线索。
  3. 变更为什么"先删后写"而不是"追加"？——追加会让图谱里新旧事实并存，**给出矛盾证据**；而向量层只是重复召回（危害小）。所以必须整体替换。
  4. 定时器为什么放在 supervisor 而不是子进程？——Asynq Scheduler **没有 leader 选举**，N 个子进程会各注册一份 → 重复投递。用"进程身份"代替分布式锁。
- **四条必须说清的事实修正**：
  1. **图谱建模偏离了已审查方案**：设计文档明确论证"`source_doc` 进 MERGE 会产生平行边、稀释证据链"并废弃了该方案，但**代码实现的正是这个被废弃的方案**，且 `queryNeighbors` 没加去重防御 → `graph_top_n=10` 的预算会被重复事实占用。
  2. **体积守卫恒不触发**：补丁新加的 `len(f.Content) > kbimport.MaxFileSize` 与 `ScanDir` 用的是**同一个常量**，逻辑上永远为假。真正修复问题的是 `content → mediumtext` 的列升级。
  3. **存储不可用时删除静默跳过**：`ragStore`/`kagManager` 为 nil 时删除被跳过且任务判成功 → 补偿不会重投 → **永久残留向量/边**，且能被检索到。
  4. **设计文档要求的 `(kb_id, source_path)` 唯一键、`ontology_version`、`asynq.Unique` 三项均未落地**（已逐项 grep 核实），分别导致：重复文档行风险、本体升级不重抽、多副本重复投递。
- **一条可量化的证据**：扫描的三态计数 `created / rebuilt / skipped` 直接反映增量去重效果与知识库健康度——`skipped` 占比高 = 去重在工作；`created` 持续非零但 `doc_count` 不涨 = create 路径在失败。
