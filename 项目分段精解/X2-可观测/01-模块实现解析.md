## 0. 一句话总览

**X2 = 用「Prometheus 指标 + 三套日志 + NATS 事件流 + 三张观测表」回答三个问题：系统现在健康吗、这次任务为什么慢、这块花了多少钱。**

可观测的经典三支柱在本项目的落点是：

| 支柱 | 本项目的实现 | 成熟度 |
|---|---|---|
| **Metrics（聚合趋势）** | 13 个 Prometheus 指标，**只在 Worker 里打点** | ⚠️ 缺 HTTP 层与检索层 |
| **Logging（离散事件）** | `slog`(JSON) + `log.Printf`(文本) + Gin access log，**三套并存** | ⚠️ 格式未统一 |
| **Tracing（单请求链路）** | `TraceID` 贯穿 Task → RunLog → ToolCallLog → ToolCallEvent | ⚠️ **主路径未生成** |
| （第四样）**事件流** | NATS 承载任务更新/工具事件/取消指令 | ✅ 与队列解耦，设计清晰 |
| （第五样）**结构化审计** | `run_logs` / `tool_call_logs` 两张表 | ⚠️ **只写不读** |

## 1. 这个模块解决什么问题

### 1.1 一个异步系统不做可观测会瞎成什么样

回到本项目的形态：**提交请求立刻返回 202，真正的执行发生在另一个进程、另一个时刻**。这带来一串"看不见"：

- 用户问"我的任务怎么还没好" → 需要看**队列积压**和**在途任务数**；
- 运维问"今天为什么这么慢" → 需要区分是**队列排队长**、**模型慢**、还是**检索慢**；
- 老板问"这个月花了多少钱" → 需要按**队列/模型**分摊 token 与成本；
- 开发问"这个任务为什么答错了" → 需要知道**它到底检索了没有、用了哪些工具、调了几次模型**。

X2 就是把这四类问题变成"有数据可查"。

### 1.2 本模块的五个数据出口

```
                        ┌─────────────────────────────────────────┐
   一次任务执行  ──────▶ │ ① Prometheus 指标  /metrics             │ 聚合趋势、告警
                        │ ② 日志             stdout / stderr       │ 排障细节
                        │ ③ NATS 事件流      global_*              │ 实时推送（SSE）
                        │ ④ run_logs 表      按任务一行            │ 成本与耗时审计
                        │ ⑤ tool_call_logs 表 按工具调用一行        │ 工具行为回溯
                        └─────────────────────────────────────────┘
                                        │
                                        ▼
                              asynqmon 面板（/admin/tasks）
                              队列级可视化（可浏览/重跑/删除）
```

## 2. 指标：13 个指标的设计与意图

### 2.1 全量清单

`internal/metrics/metrics.go` 用 `promauto`（自动注册到默认 registry）定义了 13 个指标：

| 指标名 | 类型 | 标签 | 设计意图（来自代码注释） |
|---|---|---|---|
| `gotaskai_task_duration_seconds` | Histogram | `status` | 单次任务耗时。**bucket 特意为 LLM 场景定制**：`1,5,10,30,60,120,300`，覆盖默认 120s 超时并留到 300s 长尾 |
| `gotaskai_task_runs_total` | Counter | `status` | **运行次数**（含重试）。注释明确提醒：一次任务重试多次会各记一次，终态数需按 `status` 过滤 |
| `gotaskai_task_retries_total` | Counter | — | 进入重试的次数 |
| `gotaskai_llm_calls_total` | Counter | `queue` | 模型调用次数，**按队列分摊**（`task:process` / `kb:build`） |
| `gotaskai_llm_tokens_total` | Counter | `queue`,`direction` | token 消耗，按队列 + 方向（in/out） |
| `gotaskai_llm_cost_usd_total` | Counter | `queue` | 成本（美元），按队列 |
| `gotaskai_tool_calls_total` | Counter | `status` | 工具调用次数（started/success/failed） |
| `gotaskai_kb_build_total` | Counter | `status` | 文档构建数量（failed/ready） |
| `gotaskai_context_compress_total` | Counter | — | 上下文压缩**尝试**次数 |
| `gotaskai_context_compress_failed_total` | Counter | — | 压缩失败次数。注释点明：**两者相除即失败率** |
| `gotaskai_intent_decisions_total` | Counter | `source` | 意图路由决策次数。注释点明：**各层命中率可直接由 source 分布算出** |
| `gotaskai_intent_route_latency_seconds` | Histogram | — | 路由阶段耗时。bucket `0.01…5`，对应"应该很快"的预期 |
| `gotaskai_intent_retrieval_skipped_total` | Counter | — | 因意图路由跳过 RAG 的次数，注释点明：**用于量化成本节省** |

### 2.2 三个值得学的设计细节

**① `queue` 标签让"成本分摊"成为可能**

```go
metrics.LLMCalls.WithLabelValues("task:process").Add(float64(budget.Calls))     // 对话问答
metrics.LLMCalls.WithLabelValues("kb:build").Add(float64(sumBudget.Calls))      // 知识库构建
```

同一个 `gotaskai_llm_cost_usd_total` 用 `queue` 标签区分了两条完全不同的成本来源。这解决了一个真实困惑：**"这个月 LLM 花了 500 美元"里，多少是用户在聊天、多少是知识库在抽图谱？** 没有这个标签就只能看总数。

**`kb:build` 队列内部还做了进一步拆分**：向量阶段用 `sumBudget`（摘要 LLM 调用）、图谱阶段用 `graphBudget`（抽取 LLM 调用）——两个独立预算、分别累加，所以图谱抽取的成本是可单独观测的。

**② 配对指标算比率（而不是直接打比率）**

```go
CompressTotal  = "上下文压缩尝试次数"
CompressFailed = "上下文压缩失败次数"
// 注释：CompressFailed / CompressTotal 即失败率
```

为什么不在代码里直接算好比率？因为**在分布式计数器上算比率是错的**：Prometheus 是多 target 抓取，`rate()` 必须由查询侧在原始 counter 上计算。把"尝试数"和"失败数"都暴露出来，让 `rate(failed)/rate(total)` 在查询侧成立——这是 Prometheus 的正确用法。

**③ Histogram 的 bucket 是按业务形态选的，不是默认值**

```go
TaskDuration:  Buckets: []float64{1, 5, 10, 30, 60, 120, 300}     // LLM 任务：秒级到分钟级
IntentRouteLatency: []float64{0.01, 0.05, 0.1, 0.25, 0.5, 1, 2, 5}  // 路由：毫秒级（若含 LLM 分类则秒级）
```

这是很容易被忽略但很关键的一步：**默认 bucket 是给 HTTP 请求（毫秒~秒）设计的**，直接用在 LLM 任务上会导致 P95 落在 `+Inf` 桶里、算不出有意义的分位数。这两个指标的 bucket 明显是针对各自场景挑过的。

### 2.3 指标在哪里打点——一个必须先讲清的拓扑问题

`metrics.go` 的包注释第一句就点明了关键约束：

> 各进程独立使用 `prometheus.DefaultRegisterer`，**指标进程内累计**、由各自 `/metrics` 端点暴露。

所以指标不是"全局一份"，而是**每个进程各自一份**。而实际打点位置（全仓 grep `metrics.<Name>` 的结果）：

> **13 个指标，全部只在 `internal/worker/pool.go` 里打点。**

这带来两个直接后果：

**后果一：API 进程的 `/metrics` 里没有业务指标**

```go
// cmd/api/main.go:114-118
r := gin.Default()
...
r.GET("/metrics", gin.WrapH(promhttp.Handler()))     // 挂在 :8080 上
```

`promhttp.Handler()` 服务的是**默认 registry**，而 registry 里的业务 collector 由 `promauto` 在**包初始化时**注册——只有 `internal/metrics` 被 import 才会注册。而用 grep 核对 `cmd/api/main.go` 的 import 列表：

```
internal/api、config、db、events、middleware、model、pkg/kag、pkg/llm、queue
```

**没有 `internal/metrics`，也没有 `internal/worker`。** 所以：

> **`http://<api>:8080/metrics` 只有 Go runtime 与 process 的默认指标（`go_*`、`process_*`），13 个业务指标一个都不在里面。**

这不是 bug（指标在 worker 里打点，本来就该从 worker 抓），但**如果运维习惯性地只抓 API 的 `/metrics`，会以为自己已经监控了系统，实际上一个业务指标都没采到**——这是最危险的形态：**监控看起来是通的，但数据是空的**。

**后果二：Worker 的业务指标分散在多个端口**

```go
// cmd/worker/main.go:228-244
// Worker 子进程使用独立端口（base + childIndex + 1），避免 supervisor 多子进程端口冲突。
func startMetricsServer(cfg config.Config, childIndex int) {
    if cfg.Metrics.Port <= 0 { return }
    port := cfg.Metrics.Port + childIndex + 1
    ...
}
```

而子进程的 `childIndex` 从 0 开始递增（`runSupervisor`，`cmd/worker/main.go:68-73`）：

```go
for i := 0; i < processes; i++ {
    cmd.Env = append(os.Environ(), fmt.Sprintf("%s=%d", workerChildIndexEnv, i))   // i = 0, 1, ...
}
```

按默认配置（`metrics.port: 9100`、`queue.processes: 2`）实际拓扑是：

| 进程 | 监听端口 | `/metrics` 内容 |
|---|---|---|
| API | `:8080` | 仅 `go_*` / `process_*` |
| Worker supervisor | **无** | —（`runSupervisor` 不调用 `startMetricsServer`） |
| Worker child 0 | `:9101` | ✅ 13 个业务指标（该进程的一份） |
| Worker child 1 | `:9102` | ✅ 13 个业务指标（另一份） |
| **配置里的 `9100`** | **无任何进程监听** | —（它只是"基数"） |

**三个必须在部署时注意的点**：

1. **Prometheus 必须配至少两个 target**（9101、9102），且 `processes` 一变就要改配置；
2. **同一指标散在多个 target，查询时必须聚合**（`sum(rate(gotaskai_llm_calls_total[5m])) by (queue)`），否则只能看到某个子进程的一半流量；
3. **再叠加副本数**：`副本数 × processes` 个 target。这是"指标拓扑随部署规模线性增长"的代价，也是本项目 supervisor 多子进程模型（M7 有详述）在运维侧的额外成本。

## 3. 日志：三套格式并存的现状

### 3.1 三套日志的实际去向

| 来源 | 格式 | 去向 | 级别 | 结构化字段 |
|---|---|---|---|---|
| `slog.*`（`slog.SetDefault(JSONHandler)`） | **JSON** | **stdout** | `Info` 及以上 | ✅ 键值对 |
| `log.Printf`（标准库） | **纯文本** | **stderr** | 无级别概念 | ❌ 只有格式化字符串 |
| Gin `Logger()`（来自 `gin.Default()`） | **文本 + ANSI 颜色** | **stdout** | 无级别概念 | ❌ |

配置只有一行：

```go
// cmd/api/main.go:34-35 与 cmd/worker/main.go:36-37（两处完全一致）
logger := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: slog.LevelInfo}))
slog.SetDefault(logger)
```

**这里有一个关键的认知误区**：`slog.SetDefault()` **不会**把标准库 `log` 包的输出重定向到 slog。它只设置 `slog` 包的默认 logger。而 `log.Printf` 仍然走 `log.Default()` → **stderr + 默认文本格式 + `LstdFlags` 时间戳**。

于是同一份运行日志里同时存在：

```json
{"time":"2026-09-13T10:00:00.123+08:00","level":"INFO","msg":"Worker pool started","child_index":0,"workers":5}
```
```
2026/09/13 10:00:00 [Worker] Processing task abc-123 (custom)
2026/09/13 10:00:01 [Worker][ALERT] conversation compress failed, keeping full history: ...
```

**这不是风格问题，是采集问题**：日志采集器（Filebeat/Fluent Bit/Promtail）需要为两条流写**两套解析规则**，一条按 JSON 解析、一条按正则解析；而 `log.Printf` 那条**没有级别字段**，所以 `[Worker][ALERT]` 这种靠约定写在正文里的"级别"无法被自动识别——**告警没法从日志里被规则化地提出来**。

更实际的影响：本系列文档里反复引用的那些 `[Worker][ALERT]` 关键信号（oversized document、compress failed、kb:scan source unreadable、rerank fallback…）**全部走的是 `log.Printf`**，也就是**最不容易被自动告警的那条通道**。

### 3.2 `log.Printf` 还缺一个关键字段：`child_index`

supervisor 把子进程的 stdout/stderr 直接接到自己身上（`cmd/worker/main.go:70-71`）：

```go
cmd.Stdout = os.Stdout
cmd.Stderr = os.Stderr
```

所以两个子进程的日志**混进同一个流**。而：

- `slog` 调用里**有的**手动带 `child_index`（如 `slog.Info("Worker pool started", "child_index", childIndex, ...)`），有的**不带**（如 `slog.Info("metrics server started", "port", port)`）；
- `log.Printf` **完全不带** `child_index`。

后果：看到一行 `[Worker] Processing task abc-123` 时，**无法知道是哪个子进程在处理**。而在排查"任务卡住"这类问题时，这正是最先需要的那个字段。

### 3.3 Gin access log 会把 JWT 写进日志（闭环 M1/M2 的推测）

`cmd/api/main.go:114` 用的是 `gin.Default()`：

```go
r := gin.Default()      // = gin.New() + Logger() + Recovery()
```

`Logger()` 中间件在记录请求时会拼上 **query string**（Gin 的实现是 `path + "?" + Request.URL.RawQuery`）。而 M2 里 SSE 端点的 token 是走 query 的：

```js
// web/src/api/client.js:104-106
export function createTaskStream(token) {
  return new EventSource(buildApiUrl(`/api/tasks/stream?token=${encodeURIComponent(token)}`))
}
```

所以 Gin 的访问日志里会出现完整的一行：

```
[GIN] 2026/09/13 - 10:00:00 | 200 |  1h2m3s |  10.0.0.5 | GET  "/api/tasks/stream?token=eyJhbGciOiJIUzI1NiIs..."
```

**这就把 M1 §7.6 和 M2 §6.3 里"token 走 URL 会进 access log"从推测变成了确定的机制**：不是某个网关的配置问题，而是**应用自己的 access log 就会记下来**。结合 JWT 的 24 小时有效期与"令牌不可吊销"，一次日志读取就等于拿到一张完整的登录票据。

## 4. 事件总线：为什么把实时事件从 Redis 搬到 NATS

### 4.1 动机（代码注释写得很清楚）

```go
// Package events 提供 Worker 与 API 之间实时事件（任务更新、工具事件）的独立消息通道。
//
// 设计动机：实时事件原先与 Asynq 队列、任务/Agent 缓存共用同一个 Redis。
// 为了让任务队列与实时事件通道解耦（避免相互影响、单一 Redis 故障波及全链路），
// 这里改用 NATS：API 进程内嵌启动 nats-server，Worker 与 API 均作为客户端接入。
// Redis 仅保留队列（Asynq）与缓存职责，不再承担事件广播。
```

**这个取舍很值得讲**：原方案（Redis Pub/Sub）的问题不是"不能用"，而是**职责重叠导致的故障域重叠**：

| 组件 | 原职责 | 问题 |
|---|---|---|
| Redis | 任务队列（Asynq）+ 任务/Agent 缓存 + **事件广播** | 三者互相影响：事件量大时挤占队列、缓存刷满内存时可能触发淘汰策略影响事件、Redis 一挂**全链路同时失效** |

拆开之后：

| 组件 | 新职责 | 故障影响 |
|---|---|---|
| Redis | 队列 + 缓存 | 挂了 → 新任务进不来（但已在跑的任务不受影响） |
| NATS | 实时事件 | 挂了 → **只丢实时推送，数据不会错**（状态真相在 MySQL） |

这就是 M7 里讲的"**正确性与实时性解耦**"在基础设施层的体现：**事件的丢失不影响数据正确性**，所以可以把它放到一个独立、更轻、可内嵌的通道上。

### 4.2 三个频道与它们的语义

```go
const (
    SubjectTaskUpdates = "global_task_updates"   // 任务状态更新
    SubjectToolEvents  = "global_tool_events"    // 工具调用过程事件
    SubjectTaskCancel  = "global_task_cancel"    // 任务取消控制指令（广播到所有 worker 进程）
)
```

**频道名刻意与原来的 Redis Pub/Sub 保持一致**（注释："避免破坏消费端语义"）——这是一次**只换传输、不改语义**的替换，好处是消费端代码几乎不用动。

`TaskCancel` 这个频道值得单独看：它是**反向控制流**（API → 所有 Worker 广播），用于实现"取消正在跑的任务"（M7 已详述：命中在途任务后 `cancel()` 中断进行中的模型调用）。它和另外两个"Worker → API 的状态通知"方向相反，共用同一条总线。

### 4.3 内嵌 nats-server 的设计

```go
// StartEmbeddedServer 在当前进程内嵌启动一个 nats-server。
// 固定监听 0.0.0.0（兼容容器网络），端口从地址中解析。
// 返回 server 实例，可用于优雅关闭。仅应由一个进程（目前为 API）调用。
func StartEmbeddedServer(addr string) (*server.Server, error) {
    opts := &server.Options{
        Host: "0.0.0.0", Port: -1, NoLog: false, NoSigs: true,
        MaxConn: 1024, DisableShortFirstPing: false,
    }
    if u, err := url.Parse(addr); err == nil && u.Port() != "" { ... }
    ns, err := server.NewServer(opts)
    ns.Start()
    if !ns.ReadyForConnections(5 * time.Second) { ns.Shutdown(); return nil, errServerNotReady }
    log.Printf("[events] embedded nats-server started at %s (port %d)", addr, opts.Port)
    return ns, nil
}
```

**"内嵌"是个务实的选择**：省掉一个独立的 broker 进程、一套部署与运维（对本地开发尤其友好——不用额外 `docker run nats`）。`config.yaml` 里 `eventbus.embedded: true`，且注释明确"**仅 API 进程应设置为 true**；Worker 作为客户端连接"。

**但这个"内嵌"也埋了一个真实的架构约束**（见 §7.4）：**NATS broker 变成了 API 进程的一部分**——于是"API 挂了"这件事，不再只是"API 不可用"，而是**整个实时事件通道同时消失**。这与 §4.1 想要"解耦故障域"的初衷方向相反。

`ReadyForConnections(5*time.Second)` 是个必要的就绪等待：nats-server 的 `Start()` 是异步的，不等就绪就返回连接地址，客户端可能连不上。这里等不到就 `Shutdown` 并返回明确错误，处理得比较干净。

## 5. TraceID：链路追踪的传递链

### 5.1 传递路径

```
POST /api/tasks/submit（handler.go:164）
   └─ task.TraceID = uuid.New().String()
        │
        ├─▶ 随 Asynq payload 透传 → Worker 读到 t.TraceID
        │
        ├─▶ ToolCallEvent.TraceID   （pool.go:884，SSE 实时推给前端）
        ├─▶ ToolCallLog.TraceID     （pool.go:899，落库）
        └─▶ RunLog.TraceID          （pool.go:993，落库）
```

设计意图（`model/task.go:35` 注释）："分布式追踪 ID，**随 payload 与工具事件透传**"。所以一个 TraceID 能把这三处串起来：

```sql
-- 用 trace_id 把所有观测数据串成一条链
SELECT * FROM run_logs       WHERE trace_id = '<trace>';
SELECT * FROM tool_call_logs WHERE trace_id = '<trace>' ORDER BY created_at;
SELECT * FROM tasks          WHERE trace_id = '<trace>';
```

这是本项目"轻量追踪"的全部实现——**没有引入 OpenTelemetry，只用了一个贯穿的 UUID + 三张表的索引**。对单体 + 一队列的规模来说，这个投入产出比是合理的。

### 5.2 但主路径没有 TraceID

对比三个创建任务的入口：

| 入口 | 是否生成 `TraceID` | 位置 |
|---|---|---|
| `POST /api/tasks/submit` | ✅ `TraceID: uuid.New().String()` | `handler.go:164` |
| `POST /api/tasks/batch-submit` | ✅ `TraceID: uuid.New().String()` | `handler.go:59` |
| **`POST /api/agents/:id/run`** | ❌ **没有该字段** | `api/agent.go:164-177` |

`RunAgent` 构造 Task 时字段列表是：`ID, UserID, AgentID, SessionID, ConversationID, Type, Priority, Payload, Status, MaxRetry, CreatedAt, UpdatedAt`——**没有 `TraceID`**。

**后果**：`/api/agents/:id/run` 是前端"工作台"与"独立大窗对话"**两条主路径**背后的接口（`App.vue` 的 `handleAgentChatSubmit` 与 `handleChatModalSubmit` 都调它）。也就是说：

> **绝大多数真实用户产生的任务，其 `TraceID` 为空** → `ToolCallEvent.TraceID` 空、`ToolCallLog.TraceID` 空、`RunLog.TraceID` 空 → **链路追踪在这些任务上完全失效**，只能退化成用 `task_id` 关联。

`task_id` 当然也能关联（三张表都有 `task_id` 索引），所以**数据没丢**；丢的是"跨任务/跨事件按一次请求串联"的能力——而这个能力在当前系统里本来也没有跨任务场景。所以严重度中等：**不是数据损失，是设计意图未落地**。

## 6. 结构化观测数据：两张表与"只写不读"

### 6.1 `run_logs`（每次任务运行一行）

| 字段 | 含义 |
|---|---|
| `task_id` / `trace_id` / `user_id` / `agent_id` | 四个维度，**全部带索引** |
| `model` | 实际使用的模型（**会读 Agent 覆盖后的值**，见 `pool.go:984-989`） |
| `status` | `completed` / `failed` / `cancelled` / **`pending`** |
| `calls` / `tokens_in` / `tokens_out` / `cost_usd` / `duration_ms` | 本次运行的计量 |
| `error` | 错误信息（text） |

**一个必须注意的语义**：`status` 会出现 `pending`，且**这一行的含义是"本次运行失败、已安排重试"**：

```go
// pool.go:934-945 —— 重试分支
if t.Retries < t.MaxRetry {
    t.Retries++
    metrics.TaskRetries.Inc()
    t.Status = model.StatusPending                    // ← 状态置回 pending
    ...
    p.saveRunLog(&t, model.StatusPending, "", budget, start, t.Error)   // ← 记一行 status=pending
    return err
}
```

所以 `run_logs` 里 `status='pending'` 的行**不是"等待执行"，而是"这一次跑失败了"**。同理，Prometheus 的 `gotaskai_task_runs_total{status="pending"}` 统计的也是**失败待重试的运行次数**，而不是"排队中的任务数"。

> 这是个很容易被误读的语义陷阱：任何按 `status` 分组的看板，都需要先知道这层含义，否则会把"重试"当成"排队"。用 `error != ''` 可以辅助区分。

### 6.2 `tool_call_logs`（每次工具调用一行）

字段与 `RunLog` 平行，多了 `tool_name` / `arguments` / `result`，少了 token 与成本（工具本身不烧 token）。

**`arguments` 与 `result` 都是 `text` 且完整落库**——意味着**工具看到和返回的全部内容都被持久化**。这对排障极有价值（能精确复现"模型当时拿到了什么"），但也是**数据敏感面**：如果工具返回了隐私数据，它会同时存在于 `tool_call_logs`、SSE 事件、以及前端的 `toolEvents`。

### 6.3 两张表都是"只写不读"

全仓 grep 的读取侧结果是：

```
写入：pool.go:896  SaveToolCallLog(...)
       pool.go:990  SaveRunLog(...)
读取：无
```

`TaskManager` 上只有 `SaveRunLog` / `SaveToolCallLog` 两个**写**方法，**没有 `ListRunLogs` / `GetRunLogsByTask` 之类的读方法，也没有任何 API 端点或前端视图**。

后果：

- 这两张表**只能通过 MySQL 客户端（Navicat / `mysql>`）查询**；
- 产品侧完全看不到"这次任务调了几次模型、花了多少钱"——**而这恰恰是最能体现平台专业度的数据**；
- 由于没有读取路径，也就没有"数据保留/清理"策略，表会**无限增长**（每任务一行 + 每工具调用一行，含大 text 字段）。

**这是一个典型的"采集做了、消费没做"**：投入已经沉没，价值没有兑现。把它接到任务详情抽屉里（前端已有 SSE 事件流，只差拉历史）成本并不高。

### 6.4 顺带一个小瑕疵：`saveRunLog` 有个死参数

```go
// pool.go:964-971
log.Printf("[Worker] Completed task %s successfully", t.ID)
p.saveRunLog(&t, model.StatusCompleted, result, budget, start, "")
                                          ↑ 传了 result

func (p *Pool) saveRunLog(t *model.Task, status model.TaskStatus, result string, budget *llm.Budget, start time.Time, errMsg string) {
```

但 `RunLog` **没有 `Result` 字段**（结果存在 `tasks.result`），函数体里也没用到 `result`。所以这是个无用参数，属代码卫生问题（不影响功能，但会让读者以为"结果也进了 run_log"）。

## 7. 成本可观测：Budget 的计量机制

成本可观测的前提是"每次调用都知道烧了多少"。`llm.Budget` 承担这件事（`pkg/llm/budget.go`）：

```go
type Budget struct {
    MaxCalls      int      // 单次运行调用上限（防工具乒乓）
    MaxTotalCalls int      // 跨重试累计上限（防队列级重试放大）

    PriceInUSDPerMTok  float64   // 输入单价（美元/百万 token）
    PriceOutUSDPerMTok float64   // 输出单价

    Calls, TokensIn, TokensOut int          // 本次运行累计
    baseCalls, baseTokensIn, baseTokensOut int   // 历史重试已累计（跨重试续算）
}

func (b *Budget) CostUSD() float64 {
    return float64(b.TokensIn)*b.PriceInUSDPerMTok/1e6 +
           float64(b.TokensOut)*b.PriceOutUSDPerMTok/1e6
}
```

**三层计量链路**：

```
① 每次模型调用 → Record(tokensIn, tokensOut) → Budget 累加（本次运行）
② 每次运行结束 → saveRunLog() →
      ├─ AccumulateTaskUsage(taskID, ...)  → 原子累加到 tasks.total_calls/total_tokens_*  ← 跨重试累计
      ├─ metrics.LLM{Calls,Tokens,Cost}    → Prometheus（按队列）
      └─ SaveRunLog(calls/tokens/cost)     → run_logs 表（按任务）
③ 下次重试开始 → Budget.SetBase(task.TotalCalls, ...) → 续算，使 MaxTotalCalls 生效
```

**三个设计点值得记**：

1. **"本次运行"与"跨重试累计"分开记**：`Budget.Calls` 是本次的（用于 `MaxCalls` 单次上限），`baseCalls+ Calls` 是累计的（用于 `MaxTotalCalls` 跨重试上限）。两个上限对应两类不同的浪费：**工具乒乓**（一次运行内死循环）与**队列重试放大**（重试把成本乘 N）。这是很清晰的分工。
2. **单价可配、未配则为 0**：`cost_per_1m_in` / `cost_per_1m_out`，注释明确"两者未配置（为 0）时 CostUSD 返回 0，表示未启用费用折算"。所以**如果忘了配，成本指标会静默地一直是 0**——不是算错，而是"没算"。看板上的成本曲线会是一条平线，容易被误读为"很省钱"。
3. **`Budget` 是 nil-safe 的**（每个方法开头 `if b == nil { return ... }`）。这让"不传预算"的调用路径不会 panic，但也意味着**漏传 budget 的调用会静默不计费**——这正是 M4 图谱线里 `extractMentions` 的 LLM 调用不进计量的原因（它调的是不带 budget 的 `Generate`）。

## 8. asynqmon：队列级的可视化，与它的访问控制

```go
// cmd/api/main.go:123-129
// 挂载 Asynq 官方的 Web UI 面板
mon := asynqmon.New(asynqmon.Options{
    RootPath:     "/admin/tasks",
    RedisConnOpt: redisOpt,
})
r.Any("/admin/tasks", gin.WrapH(mon))
r.Any("/admin/tasks/*any", gin.WrapH(mon))
```

**从可观测视角，它是本项目最强的可视化能力**（免费获得，不用自己写）：

| 能力 | 说明 |
|---|---|
| 队列浏览 | 各队列的 pending / active / scheduled / retry / archived 计数 |
| **任务级详情** | 点开单个任务看 **payload 与 result**——即用户的原始提问与模型回答 |
| 失败排查 | 重试次数、上次错误、下次执行时间 |
| **人工干预** | **重跑单个/批量任务、删除任务、批量删除** |
| 指标 | asynqmon 自带 Prometheus collector（本项目未启用，见下） |

**从安全视角，它是整个系统最薄弱的环节**（M1 §7.5 已从认证角度记录，这里从可观测角度补充两点）：

1. **它暴露的不是元数据，而是内容**——payload 是用户提问、result 是模型回答，`archived` 队列里还留着历史任务。所以这不是"泄露指标"，而是**全量对话内容的集中泄露点**；
2. **它带写权限**——重跑与删除都是 `r.Any`，包括 `DELETE` 和 `POST`。所以访问者不仅能看，还能**删掉别人的任务记录**。

**另外注意**：asynqmon 的 Prometheus collector（`third_party/asynqmon/metrics_handler.go` 里的 `promQLArchivedTasks` 等）在本项目**没有被启用**——那是 asynqmon 独立 CLI 模式（`third_party/asynqmon/cmd/asynqmon/main.go`）的能力。本项目用的是"作为 handler 挂载"的模式，所以：

> **队列深度（pending/active/retry 计数）不进 Prometheus**，只能在 asynqmon 页面肉眼看。

这直接造成一个监控缺口：**无法对"队列积压"告警**（§9.2 已列为缺失指标）。

## 9. 已知缺陷与未验证项

### 9.1 高：API 进程的 `/metrics` 里没有任何业务指标

见 §2.3。`cmd/api/main.go` 未 import `internal/metrics`，因此 13 个 collector 未注册，`http://<api>:8080/metrics` 只有 `go_*` / `process_*`。

**风险性质不是"功能坏"，而是"监控假象"**——端点有响应、有指标输出、看起来正常，但业务指标一个都没有。如果运维/巡检脚本只检查"`/metrics` 是否 200 且包含 `gotaskai_` 前缀"，能发现；如果只检查 200，则完全发现不了。

**修法**（未实施）：保持无状态（指标仍在 worker 打点），但在 API 侧加一个显式说明或健康检查；或统一让 API 也暴露 `gotaskai_*` 的**零值**（需 import metrics，但会引入"看起来有数据实际为 0"的更糟误导，**不建议**）。

### 9.2 高：缺少三类关键指标，导致核心问题无法告警

**① HTTP 层完全零指标**

没有任何 request count / latency / status code / 在途请求数指标。后果：**无法回答"接口 P95 延迟是多少""错误率有没有上升"**，也无法配置最常见的可用性告警。

**② 队列层零指标**

队列积压（pending / retry 计数）不进 Prometheus（§8）。后果：**无法对"任务堆积"告警**——而这恰恰是异步系统最该告警的信号。用户抱怨"任务没反应"时，运维只能打开 asynqmon 人工看。

**③ 没有任何 Gauge**

13 个指标全是 Counter / Histogram。后果：**看不到任何"当前值"**——在途任务数、当前并发占用量、MCP 连接池大小、Milvus/Neo4j 连接数。Counter 只能算速率，Histogram 只能算分布，**"此刻有多少活儿在手上"这类问题没有指标能回答**。

**④ 检索链路零指标**

RAG 检索、KAG 多跳、embedding、rerank、Milvus 查询、Neo4j 查询——**全都没有延迟/失败指标**。而这是本项目最复杂、最容易慢、也最容易静默降级（如 rerank 失败回退召回序、B2 全文兜底）的链路。当前这条链路的运行状态**只能靠日志**（而日志又缺级别，见 §3.1）。

**⑤ 安全事件零指标**

登录失败次数、401 计数、限流触发次数——都没有。结合 M1 发现的"认证接口完全无限流"与"密码重置可暴力枚举"，这意味着**正在被暴力破解时，监控体系里没有任何信号**。

### 9.3 中：三套日志格式混杂，且关键告警走在最差的通道上

见 §3.1 / §3.2。要点：

- `slog`(JSON/stdout) 与 `log.Printf`(文本/stderr) **并行**，需两套采集规则；
- `log.Printf` **无级别字段**，`[Worker][ALERT]` 这类约定式标记无法被规则化识别；
- **本系列文档里引用的所有关键告警（oversized document、compress failed、kb:scan source unreadable、rerank fallback、图谱连接失败…）全部走 `log.Printf`**；
- `log.Printf` 不带 `child_index`，两个子进程日志混流后**无法区分来源**。

**修法方向**（未实施）：把 `log.Printf` 全部替换为 `slog`（或 `slog.SetDefault` 后统一走 `slog`），并在 handler 里用 `slog.With("child_index", childIndex)` 一次性注入实例级字段。

### 9.4 中：内嵌 NATS 让 broker 与 API 同生共死

`eventbus.embedded: true` 且"仅 API 进程应设置为 true"（`config.yaml:27`）。所以：

| 场景 | 后果 |
|---|---|
| API 进程重启（发版/崩溃/OOM） | NATS broker 一起消失 → 所有 Worker 的**事件发布失败** → 所有前端 SSE 收不到更新 |
| 需要横向扩展 API 副本 | **只能有一个实例 `embedded: true`**，否则多个 nats-server 抢同一端口；其余副本必须改成连远程 (`embedded: false` + 独立 NATS 部署) |

第二点是个**扩容前的隐藏前提**：单副本时一切正常，一旦要加第二个 API 副本就会发现 NATS 起不来。这与 §4.1 想要的"解耦故障域"是相反的——**内嵌省了运维，但把 broker 的可用性绑在了 API 上**。

**修法方向**：生产环境把 NATS 独立部署（`embedded: false`），本地开发保留内嵌。

### 9.5 中：观测数据"只写不读"

见 §6.3。`run_logs` / `tool_call_logs` 无读取方法、无 API、无前端视图 → 只能 SQL 查询，且**无保留策略会无限增长**。

### 9.6 中：`RunAgent` 不生成 TraceID → 主路径无链路追踪

见 §5.2。数据未丢失（`task_id` 可关联），但设计意图未落地。

### 9.7 低：`metrics.port` 的语义容易误配

`9100` 是"基数"而非监听端口（实际监听 `9101`、`9102`），且 supervisor 不监听任何端口。运维若按配置里写的 9100 去抓，会得到"连接拒绝"。建议在配置注释里写明映射规则（当前 `config.yaml:6-7` 的注释提到了 `port + childIndex + 1`，但没说"supervisor 无端口"与"9100 本身不监听"）。

### 9.8 低：成本指标在未配单价时静默为 0

见 §7。`cost_per_1m_in/out` 为 0 时 `CostUSD()` 返回 0 → `gotaskai_llm_cost_usd_total` 恒为 0 → 看板显示"零成本"。**没有"未配置"与"真的为 0"的区分**。

### 9.9 低：`saveRunLog` 的 `result` 参数未使用

见 §6.4。

### 9.10 低：`TaskTotal`/`RunLog` 的 `status=pending` 语义易误读

见 §6.1。`pending` 表示"本次运行失败、已安排重试"，不是"排队中"。

### 9.11 未验证项

| 项 | 说明 |
|---|---|
| API 的 `/metrics` 实际内容 | 已从 import 关系推导（未 import metrics）；**建议实测确认只有 `go_*`/`process_*`** |
| 实际监听端口 | 已从 `base + childIndex + 1` 与 `childIndex ∈ [0, processes)` 推导；**建议实测 `netstat` 确认** |
| Gin access log 是否真含 `?token=` | 已从 Gin `Logger()` 的已知实现推导；**建议实测抓一条 SSE 的访问日志** |
| 指标是否被真正采集 | 取决于部署侧 Prometheus 配置（多 target 聚合），仓库内无配置可查 |
| Prometheus/告警规则 | **仓库内未见任何 Prometheus 抓取配置或告警规则文件**，需确认是否在部署侧另外维护 |

## 10. 怎么验证

### 10.1 验证指标端点拓扑（§2.3，重点）

```bash

curl -s http://localhost:8080/metrics | Select-String -Pattern "^gotaskai_" | Measure-Object

# ③ 配置里的 9100 —— 期望【连接被拒绝】
curl -s -o /dev/null -w "9100: %{http_code}\n" http://localhost:9100/metrics

# ④ 确认实际监听端口

```

**期望**：① 无 `gotaskai_*`；② 9101/9102 各有业务指标；③ 9100 连不上；④ 只有 9101/9102 在 LISTEN。
→ 这四步合起来确认"指标拓扑与直觉不符"这个结论。

### 10.2 验证指标真的在动

```bash
# 提交一个任务，然后对比前后计数
curl -s http://localhost:9101/metrics | Select-String "gotaskai_task_runs_total"
# ...提交任务并等完成...
curl -s http://localhost:9101/metrics | Select-String "gotaskai_task_runs_total"
```

**期望**：`status="completed"` 的计数 +1，`gotaskai_llm_calls_total{queue="task:process"}` 增加。
**同时观察**：如果任务落在 child 1 上，计数会出现在 9102 —— **这正是"多 target 必须聚合"的直观证据**。

### 10.3 验证 `status="pending"` 的语义（§6.1）

```bash
# 造一个必然失败的任务（把 llm.api_key 改错，或让模型地址不可达）
# 等它重试几次后查库
```

```sql
SELECT status, calls, tokens_in, error, created_at
FROM run_logs
WHERE task_id = '<task_id>'
ORDER BY created_at;

SELECT status, retries, max_retry, error FROM tasks WHERE id = '<task_id>';
```

**期望**：`run_logs` 里出现多行 `status='pending'`（每次失败一次），最后一行 `status='failed'`。

## 11. 一页速记（面试/复盘用）

- **一句话定位**：X2 用「13 个 Prometheus 指标 + 三套日志 + NATS 事件流 + 三张观测表」把异步系统里"看不见的部分"变成可查的数据；但**只在 Worker 打点、只覆盖任务与 LLM 成本，HTTP/队列/检索/安全四类都没有指标**。
- **四个最容易被追问的设计点**：
  1. **实时事件为什么要从 Redis 搬到 NATS？**——原方案里 Redis 同时扛队列、缓存、事件广播，**故障域重叠**：Redis 一挂全链路同时失效。拆开后 NATS 挂只丢实时推送，**状态真相仍在 MySQL**，即"正确性与实时性解耦"。
  2. **成本怎么可观测？**——`llm.Budget` 三层计量：每次调用累加（本次运行）→ 运行结束 `AccumulateTaskUsage`（跨重试累计）+ Prometheus（按队列）+ `run_logs`（按任务）；`queue` 标签让"对话成本"与"知识库构建成本"可分开看，`kb:build` 内部还分向量/图谱两个预算。
  3. **怎么追踪一个请求？**——没有 OpenTelemetry，只用**一个贯穿的 `TraceID`** + 三张带索引的表（`tasks` / `run_logs` / `tool_call_logs`）+ SSE 事件。对单体 + 一队列的规模，投入产出比合理。
  4. **配对指标为什么不直接算比率？**——`CompressTotal` / `CompressFailed` 分开暴露，因为**在分布式计数器上算比率是错的**，必须让查询侧用 `rate(failed)/rate(total)`。
- **五个必须说清的事实修正**：
  1. **API 的 `/metrics` 里没有任何业务指标**：`cmd/api/main.go` 未 import `internal/metrics` → 业务 collector 未注册，`:8080/metrics` 只有 `go_*`/`process_*`。**监控看起来是通的，数据是空的**——这是最危险的形态。
  2. **指标只在 Worker 子进程的 9101/9102，且配置里的 9100 无人监听**（`base + childIndex + 1`；supervisor 不启 metrics server）→ 必须配多 target 并**在查询侧聚合**，`processes` 一变就要改抓取配置。
  3. **三套日志格式混杂**：`slog`(JSON→stdout) 与 `log.Printf`(文本→stderr) 并行，Gin access log 又是第三套。而**本系列文档引用的所有关键告警走的都是 `log.Printf`**——无级别字段、无法规则化提取；且不带 `child_index`，两个子进程日志混流无法区分。
  4. **Gin 默认访问日志会把 JWT 写进日志**：`gin.Default()` 的 `Logger()` 会拼接 query，而 SSE 是 `?token=<JWT>` → `[GIN] ... GET "/api/tasks/stream?token=eyJ..."`。这把"token 走 URL"从担忧变成了**应用自身就会产生的确定性泄露**。
  5. **主路径没有 TraceID**：`/api/agents/:id/run`（前端工作台与独立对话窗口背后的接口）构造 Task 时**没有 `TraceID` 字段** → 大多数真实用户任务的链路追踪为空。（数据没丢，可用 `task_id` 关联。）
- **三条可量化的证据**：
  - §10.1：`:8080/metrics` 里 `gotaskai_` 计数为 **0**，而 `:9101` 有 → 确认指标拓扑；
  - §10.5：在 API 日志里 grep 到 `tasks/stream?token=eyJ` → 确认 JWT 落盘；
  - §10.4：`/api/agents/:id/run` 产生的任务 `trace_id` 为**空串**，而 `/api/tasks/submit` 的为 UUID → 确认追踪缺口。
