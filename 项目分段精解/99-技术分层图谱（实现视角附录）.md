### 0.2 运行时真实形态

不是"前后端分离的单体"，而是 **一个前端工程 + 两个后端进程 + 一条消息总线**：

```
浏览器(Vue3) ──HTTP──▶ API Server(cmd/api) ──Asynq/MySQL/Redis──▶ Worker Node(cmd/worker)
     ◀──SSE──── API Server ◀──NATS── Worker Node
```

- **API Server**：接客（鉴权/限流/校验/落库/投递）+ 轻量同步调用（LLM 优化 Prompt、MCP 试连、KAG/RAG 管理接口）+ SSE 推送。
- **Worker Node**：supervisor + N 个子进程（`queue.processes`），每个子进程 `queue.workers` 个并发协程，消费 5 类任务。
- **MCP Server**：Worker 按需拉起的子进程（`bin/search_mcp.exe`），提供 `internet_search`。

### 1.2 为什么这样切

| 判定依据 | 在本项目中的体现 |
|---|---|
| **依赖方向单向** | 上→下：L1 依赖 L2，L2 依赖 L3/L5，L3 依赖 L4/L5，L4 依赖 L5。未发现反向依赖（L5 不 import L4） |
| **进程边界即层边界** | L0 的两个入口各自装配一条独立的依赖链；L3 的 `TaskManager` 被两个进程共用（作为生产者/状态写回方） |
| **变化频率不同** | L4 是算法高变区（本体、检索策略、路由档位），L2 是接口契约区，L5 是数据结构区；分开后改动影响面可控 |
| **可独立灰度的开关集中在下游能力层** | `intent.enabled/mode`、`kb.graph_enabled`、`kb.scan_enabled`、`rerank.enabled`、`compress.enabled` 全部落在 L4/L6，说明 L4 被设计为"可插拔能力" |
| **横切关注单独成层** | `metrics` 被 L3 埋点、被 L0 暴露端点；`events` 是 L3 的跨进程通道，但服务的是 L2 的 SSE |

### 1.3 备选划法的取舍（诚实说明）

- **备选 A：把 `internal/pkg/intent` 归入 L3（编排）而非 L4（能力）**。理由：它直接决定"要不要检索"，是编排语义。**本图谱不采纳**，因为它是无状态的纯分类器、且已被单独评测（`tools/intent_eval`）与灰度开关控制，符合 L4"可插拔能力"特征。
- **备选 B：把 `internal/eval` 归入 L4**。理由：它只测能力。**不采纳**，因为它不参与线上运行，属独立质量保障面。
- **备选 C：把 `events` 归入 L6（基础设施）**。理由：NATS 是中间件。**部分采纳**：`events.go` 作为 NATS 连接与 Subject 契约的封装留在 L3（它是跨进程编排的语义层），NATS **服务端**本身归 L6。

  - 向下：调用 L4 全部能力包 + L5 全部实体。
- **核心流程（`handleTaskProcess`，`pool.go:724-968`，16 步）**
  1. 反序列化 payload → 2. 回读 DB 最新状态、取消短路 → 3. 置 `processing`（条件更新）→ 4. `resolveTools` 解析工具白名单 → 5. 构造 `Budget`（含跨重试基线）→ 6. 解析 Agent 级模型凭证 → 7. **`routeIntent` 意图路由** → 8. 组装 system prompt（默认提示 + 联网强制指令 + RAG 知识注入 + KAG 图谱注入）→ 9. 加载会话历史并按需压缩 → 10. 派生可取消 ctx + `registerInFlight` → 11. 挂 observer（工具事件→NATS+落库）→ 12. **`GenerateWithToolsAndObserver` ReAct 循环** → 13. 生成后再次检查取消 → 14. 错误分支（预算超限不可重试 / 可重试 / 重试耗尽）→ 15. 成功落库 → 16. `saveRunLog`。
- **关键实现点**
  1. **意图路由的真实影响面**：`NeedRAG` 控制是否 `retrieveKnowledge`、`NeedKAG` 控制是否 `RetrieveGraphContext`、`Intent==chat` 控制是否注入联网指令；**`NeedTools` 未生效**。
  2. **上下文闸门**：RAG 与 KAG 共享 `MaxContextChars` 剩余额度（`pool.go:836-845`）。
  3. **渐进式披露**：分数归一化 → 文档摘要层 → chunk 窗口扩展 → 按分截断（`appendKBDocs`/`expandChunks`/`chunkByScore`）。
  4. **图谱阶段不阻断向量**：KAG 抽取失败仅标 `GraphStatus=failed`，不回滚 Milvus（`runGraphStage`）。
  5. **删除补偿机制**：`compensateStaleDeleting` 把卡在 `deleting` 超 10 分钟的记录重新投递（`staleDeletingGrace=10min`，批量 200）。
  6. **`syncScannedFile` 三态**：`skip` / `create` / `rebuild`；rebuild 前**体积校验前置**避免"先删后写"产生幽灵文档。
- **待深挖**：`handleKBBuild` 图谱阶段用信号量限流（`graphQueueConcurrency`）；工具循环**无显式最大轮次**，靠 `Budget.MaxCalls`（默认 15）/`MaxTotalCalls`（默认 30）隐式约束。

### L4 领域能力层（`internal/pkg/*`）

- **边界**：纯能力提供方，**无任务状态、无数据库直写**（除各自负责的外部存储），可被 L3/L0/L7 复用。
- **模块清单**

| 子包 | 文件（行数） | 职责 | 外部依赖 | 接线状态 |

| `ragstore` | store.go(353) schema.go(95) bm25.go(141) | Milvus 建库/索引、chunk 写入、dense+sparse+RRF 检索、按 doc/kb 删除 | Milvus | 投产 |

- **输入**：query 字符串 / 文档 / 文本 / 工具调用参数。
- **输出**：知识上下文字符串、决策结构、三元组、工具调用结果、检索文档列表。
- **上下游交互**：向下依赖 L5 的模型（`kbimport` 无）、外部存储；向上被 L3 编排调用、被 L2 用于管理接口、被 L7 用于评测。
- **关键实现点**
  1. **ragstore 双路召回**：dense(HNSW/COSINE) + sparse(BM25 词频饱和/SPARSE_INVERTED/IP)，各自 `2*topK` 候选 → `HybridSearch` + RRF；**写删后强制 Flush** 保证可见性；**无标量索引**（`kb_id`/`doc_id` 过滤靠表达式）。
  2. **kag 多跳松弛检索**：LLM 抽实体提及 → 精确/归一匹配起点 → 逐跳 BFS（`maxHops=3`）→ 无事实时返回 `[缺失提示]` 而非空串；节点模型为单一 `:Entity(name)`，边为动态关系名。
  3. **本体收敛**：抽取时把白名单注入 prompt，抽取后 `CanonicalizeRelation` 做大小写规范化 + 别名等价类映射。
  4. **intent 三级**：规则层**只有一条**可关闭检索的纯寒暄全串锚定规则；语义层默认只做"正向加速"（`semantic_allow_close=false`）；LLM 层默认二分类；任一失败/低置信/疑似注入 → `FullPipeline` 保守回退。
  5. **Budget 语义**：`MaxCalls` 单次运行上限、`MaxTotalCalls` 跨重试累计上限，超限返回 `ErrBudgetExceeded`（不可重试）。
  6. **rerank 降级**：调用失败回退为召回序前 topK。
- **待深挖**：`EmbedDocuments` 无分批（批大小由调用方决定）；重排一次性提交全部候选；`kag` 无 `:Entity(name)` 索引。
