## 0. 一句话总览

**Agent = 一份持久化的可复用配置**：把「角色设定 + 模型/凭证覆盖 + 能用哪些工具 + 能查哪些知识库」固化成一行记录，每次对话不必重新拼装。

用平台自己的话（`model/agent.go:5-6` 注释）：

> Agent 代表用户构建的一个智能体，即「持久化的可复用配置」。相比每次请求临时拼 Prompt，Agent 把 system_prompt、模型等配置固化下来。

所以 M3 要回答的问题是：**这份配置由哪些字段组成、怎么和工具/知识库建立多对多关系、以及运行期它到底被用上了多少**。

## 1. 这个模块解决什么问题

### 1.1 没有 Agent 的世界

```
每次请求都要带：
  system_prompt = "你是一个只回答金融问题的助手，不确定就说不确定…"   ← 前端得存着
  model = "qwen-max"
  api_key = "sk-xxx"                                              ← 明文在前端流转
  tool_ids = ["...", "..."]
  kb_ids = ["...", "..."]
```

问题：**配置漂移**（同一角色在不同页面写得不一样）、**密钥外泄面扩大**、**无法复用**。

### 1.2 有 Agent 的世界

```
建一次 Agent：
  POST /api/agents        {name, system_prompt, model, api_key, base_url}
  POST /api/agents/:id/tools             {tool_ids: [...]}      ← 工具白名单
  POST /api/agents/:id/knowledge-bases   {knowledge_base_ids: [...]}  ← 知识范围

之后每次只需：
  POST /api/agents/:id/run {payload, session_id}
```

**核心价值在于"边界"**：Agent 是一道**能力围栏**——它只能用你绑定的工具、只能查你绑定的知识库。这既是易用性设计，也是最小权限的落点（理想情况下）。

## 2. 数据模型

### 2.1 一张主表 + 两张绑定表 + 工具表

```
agents（Agent 配置）
  ID           主键 UUID
  UserID       归属用户（多租户隔离）
  Name         显示名
  SystemPrompt ★ 角色设定（gorm: type:text）
  Model        覆盖平台默认模型（空 → 用默认）
  APIKey       覆盖平台默认密钥（空 → 用默认）
  BaseURL      覆盖平台默认接口地址（空 → 用默认）
  Status       ★ active / archived
        │
        ├──< agent_tools（多对多白名单，复合主键 agent_id + tool_id）
        │         └──> tools
        │                 ID / UserID(0=内置) / Name(唯一) / Type(builtin|mcp)
        │                 DisplayName / Description / Config(JSON) / IsBuiltin / Status
        │
        └──< agent_knowledge（多对多，复合主键 agent_id + knowledge_base_id）
                  └──> knowledge_bases
```

### 2.2 三个"覆盖式"字段的设计

`Model` / `APIKey` / `BaseURL` 都是"**为空则回退平台默认**"（`model/agent.go:12-14` 注释）。运行期在 `pool.go:779-786` 实现：

```go
var agentAPIKey, agentBaseURL, agentModel string
if t.AgentID != "" {
    if agent, ok := p.manager.GetAgent(t.AgentID); ok {
        agentAPIKey = agent.APIKey
        agentBaseURL = agent.BaseURL
        agentModel   = agent.Model
    }
}
```

**这个三级回退让"多供应商"成为配置能力而不是代码能力**：平台默认可以是 DeepSeek，某个 Agent 覆盖成 DashScope 或私有部署，不需要改代码、不需要重启。

### 2.3 工具的两类来源

| | 内置工具 | 用户私有 MCP 工具 |
|---|---|---|
| `tools.UserID` | `0`（全局） | 真实用户 ID |
| `tools.IsBuiltin` | `true` | `false` |
| `tools.Type` | `builtin`（`get_current_time`）/ `mcp`（`internet_search`） | `mcp` |
| `tools.Config` | **空字符串** | JSON：`{command,args,url,env}` |
| 注册入口 | `seedBuiltinTools`（API 启动时幂等插入，`cmd/api/main.go:242-276`） | `POST /api/tools` |
| 运行时来源 | worker 侧 `toolregistry.RegisterBuiltins` | `mcpPool.Get` 动态拉起 |

**种子数据只有两个**（`cmd/api/main.go:245-270`）：

```go
{ID: "builtin_current_time",    Name: "get_current_time",  Type: "builtin", IsBuiltin: true}
{ID: "builtin_internet_search", Name: "internet_search",   Type: "mcp",     IsBuiltin: true}
```

注意第二行的 `Type` 是 **`mcp`**，但 **`Config` 是空的**。这不是笔误——它揭示了内置联网搜索的真实来源（见 §5.4）。

### 2.4 可见性规则

```go
// manager.go:564-573 —— 用户能看到「内置全局」+「自己的私有」
m.db.Where("is_builtin = ? OR user_id = ?", true, userID).
    Order("is_builtin desc, created_at asc")
```

内置工具在前、私有工具在后，`created_at` 升序保证**列表顺序稳定**。

而写操作全部带 `IsBuiltin` 保护（`api/tool.go:104, 124, 167`）：

```go
if tool.IsBuiltin || tool.UserID != c.GetUint("userID") {
    c.JSON(http.StatusForbidden, gin.H{"error": "无权删除此工具"})
    return
}
```

**内置工具不可删、不可编辑、不可停用**——这是对的：内置工具是平台资产，让用户改它的 `Type`/`IsBuiltin` 会破坏 `resolveTools` 的匹配语义。

## 4. 核心机制逐个讲透

### 4.1 `resolveTools`：白名单的三条分支

```go
func (p *Pool) resolveTools(ctx context.Context, t model.Task) []toolregistry.Tool {
    if t.AgentID == "" {
        return p.toolRegistry.List()          // 分支①：无 Agent → 全部工具
    }

    bound := p.manager.ListAgentTools(t.AgentID)
    if len(bound) == 0 {
        return nil                            // 分支②：有 Agent 但没绑工具 → 一个都不给
    }

    out := make([]toolregistry.Tool, 0, len(bound))
    for _, bt := range bound {
        if bt.Status == "disabled" {          // 分支③：工具被停用 → 跳过
            continue
        }
        // 优先匹配静态注册（内置 + search_mcp）
        if static, ok := p.toolRegistry.Get(bt.Name); ok {
            out = append(out, static)
            continue
        }
        // 用户私有 MCP 工具：按 config 动态连
        if bt.Type == "mcp" && bt.Config != "" {
            ...
        }
    }
    return out
}
```

**三条分支的语义差异值得单独说**：

| 分支 | 条件 | 结果 | 语义 |
|---|---|---|---|
| ① | 没指定 Agent | **全部工具** | 匿名/直连任务不受限 |
| ② | 有 Agent，但绑定表为空 | **零工具** | 白名单为空 = 什么都不许 |
| ③ | 工具行 `status = disabled` | 跳过该工具 | 平台级停用优先于绑定 |

**分支① 和 ② 放在一起看，会出现一个反直觉的效果**：

> **用户新建了一个 Agent、还没来得及绑工具，就发现"这个 Agent 比我不用 Agent 直连还弱"**——因为直连会拿到全部工具，而新建 Agent 的绑定表是空的，一个工具都拿不到。

从安全角度这是**正确的**（默认拒绝优于默认允许），但对首次使用者来说是个体验陷阱：Agent 创建后是"能力为零"状态，而 UI 上并没有告警。值得在创建流程里给一句提示，或者给 Agent 一个"继承全部工具"的开关。

**`disabled` 检查是运行时的、每次都查**（`bt.Status` 来自刚刚的 DB 查询），所以**停用工具是即时生效的**，不需要重启 worker、也不需要清缓存——这一点比 Agent 自身的配置缓存做得好（见 §4.5）。

### 4.2 静态注册 vs 动态 MCP：两种工具怎么被"接进来"

工具在运行期有两个可能的来源，`resolveTools` 用"**先查静态注册、失败再动态连**"的顺序处理：

```
绑定行 (Name, Type, Config)
   │
   ├─ ① p.toolRegistry.Get(Name) 命中？
   │      └─ 是 → 直接用静态注册的 Tool 实例（进程内已初始化）
   │
   └─ ② Type == "mcp" 且 Config 非空？
          └─ 是 → mcpPool.Get(ctx, ID, command, url, args, env)
                    → NewHTTPWrapper(url) 或 NewWrapperWithEnv(command, env, args…)
                    → wrapper.GetTools(ctx) 拉取该 MCP 服务暴露的工具清单
                    → 每个工具包装成 toolregistry.NewMCPServerTool(wrapper, mt)
```

**静态注册里有什么**（`pool.go:103-113`）：

```go
toolRegistry := toolregistry.NewRegistry()
toolregistry.RegisterBuiltins(toolRegistry)              // → get_current_time
if mcpClient != nil {
    if mcpTools, terr := mcpClient.GetTools(context.Background()); terr == nil {
        for _, t := range mcpTools {
            toolRegistry.Register(toolregistry.NewMCPServerTool(mcpClient, t))   // → internet_search
        }
    }
}
```

所以静态注册区 = `get_current_time` + **worker 启动时从 `bin/search_mcp.exe` 拉到的全部工具**。

**这就解释了 §2.3 里那个"`Type: mcp` 但 `Config` 为空"的内置行**：

> `builtin_internet_search` 在 DB 里没有连接配置，因为它的**运行时来源不是 DB 的 Config，而是 worker 本地的 `bin/search_mcp.exe`**。DB 那一行只是为了让它在 UI 里可见、可绑定。

### 4.3 `resolveTools` 的性能特征：每任务一次 ListTools

`mcpPool.Get` 有缓存（按 tool ID），所以**子进程/连接不会重复创建**。但注意：

```go
wrapper, err := p.mcpPool.Get(ctx, bt.ID, cfg.Command, cfg.URL, cfg.Args, cfg.Env)   // 命中缓存，O(1)
mcpTools, err := wrapper.GetTools(ctx)      // ★ 每次都发一次 MCP ListTools RPC
```

`wrapper.GetTools` **没有缓存**。所以：

> **每执行一个任务，都要对每个绑定的私有 MCP 服务发一次 `ListTools` 往返。**

一轮对话 = 一次任务，所以绑了 3 个私有 MCP 服务的 Agent，**每轮对话开头都有 3 次额外的 MCP RPC**（串行、在 `resolveTools` 里）。这会直接加在首字延迟上。

**工具清单是高度静态的**（一个 MCP 服务的工具集很少变），所以这里完全可以按 `(toolID, configFingerprint)` 缓存工具清单，配合 TTL 或配置变更时失效。**当前没有做**。

### 4.4 MCP 连接池：缓存键不含配置，改配置必须重启

```go
// mcpclient/pool.go:21-41
func (p *Pool) Get(ctx context.Context, id, command, url string, args []string, env map[string]string) (*Wrapper, error) {
    p.mu.Lock()
    defer p.mu.Unlock()

    if w, ok := p.clients[id]; ok {
        return w, nil                    // ★ 命中就直接返回，完全忽略新传入的 command/url/args/env
    }
    ...
    p.clients[id] = w
    return w, nil
}
```

**缓存键只有 `id`**，不含 `command`/`url`/`args`/`env` 的任何指纹。而 `id` 是 tool ID——**改工具的连接配置不会改变 ID**。

于是链路是：

```
用户 PUT /api/tools/:id 改 Config（比如把 command 从 npx 换成 uvx）
  → DB 更新成功 ✅（UpdateTool）
  → resolveTools 下次读到新 Config ✅
  → mcpPool.Get(ctx, 同一个ID, 新command, ...) 
  → 命中缓存 → 返回【旧连接】❌
  → 新配置被静默忽略
```

**结论：修改 MCP 工具配置后，必须重启 worker 才生效**，而且**没有任何提示**。这是一个真实的运维缺口——用户改完配置、测试没变化，会以为"平台坏了"。

**修法方向**（未实施）：把缓存键改成 `id + 配置指纹`（比如配置 JSON 的 sha256），或在 `UpdateTool` 时通过某种跨进程通知失效该 ID。后者需要 worker 与 API 之间的控制通道（项目里已有 NATS 可复用）。

### 4.5 Agent 配置的热更新：Redis 缓存 + 主动失效

这部分**做得比 MCP 好**，可以作为对照：

```go
// manager.go:493-512 —— 读：先缓存，后 DB，再回写
func (m *TaskManager) GetAgent(id string) (*model.Agent, bool) {
    val, err := m.rdb.Get(m.ctx, "agent:"+id).Result()
    if err == nil && val != "" {
        var a model.Agent
        if json.Unmarshal([]byte(val), &a) == nil { return &a, true }
    }
    var a model.Agent
    if err := m.db.Where("id = ?", id).First(&a).Error; err != nil { return nil, false }
    m.cacheAgent(&a)
    return &a, true
}

// manager.go:531-537 —— 写：更新 DB 后【主动删缓存】
func (m *TaskManager) UpdateAgent(a *model.Agent) error {
    if err := m.db.Save(a).Error; err != nil { return err }
    m.rdb.Del(m.ctx, "agent:"+a.ID)          // ★ 主动失效 → 热更新即时生效
    return nil
}

// manager.go:548-554 —— 缓存 TTL 只有 5 分钟，作为兜底
func (m *TaskManager) cacheAgent(a *model.Agent) {
    m.rdb.Set(m.ctx, "agent:"+a.ID, data, 5*time.Minute)
}
```

**双重保障**：主动删（立即生效）+ 短 TTL（5 分钟，防止漏删时长期脏读）。注释也点明了意图："短 TTL，以便配置热更新及时生效"。

`DeleteAgent` 同样清缓存。**所以 Agent 的 model/api_key/base_url 改动是即时生效的**——而 MCP 工具配置不是。这个对比很值得记住。

### 4.6 绑定：全量替换 + 事务

```go
// manager.go:1058-1070
func (m *TaskManager) ReplaceAgentTools(agentID string, toolIDs []string) error {
    return m.db.Transaction(func(tx *gorm.DB) error {
        if err := tx.Where("agent_id = ?", agentID).Delete(&model.AgentTool{}).Error; err != nil { return err }
        for _, toolID := range toolIDs {
            if err := tx.Create(&model.AgentTool{AgentID: agentID, ToolID: toolID}).Error; err != nil { return err }
        }
        return nil
    })
}
```

**语义是"设为"而不是"追加"**：接口叫作 `Replace*`，请求体是完整的 `tool_ids` 数组。这比"逐个 bind/unbind"更不容易产生状态漂移（前端只需提交"最终想要的样子"），配合事务保证不会出现"删完了但没插进去"的中间态。

**同时提供了单条解绑接口**（`DELETE /api/agents/:id/tools/:toolId`）供 UI 做局部操作——但它走的是 `UnbindToolFromAgent`（单条 DELETE），**不在事务里**。两条路径并存时，前端要小心不要混用（比如并发调 Replace 和 Unbind）。

### 4.7 工具发现：自然语言 → LLM → GitHub/npm

这是 M3 里最有意思的一个能力（`api/tool.go:292-323`）：

```
用户输入："一个能查天气的 mcp 工具"
   │
   ├─ ① parseMCPSearchIntent（LLM 解析）
   │      prompt 要求严格输出：{"keywords": "...", "npm_search": "...", "description": "..."}
   │      示例 in prompt："用户说「查天气的mcp工具」 → {"keywords":"weather mcp server",...}"
   │      ★ 容错：用第一个 { 到最后一个 } 截取；解析失败则用原始 query 兜底
   │
   ├─ ② searchNPM(ctx, intent.NpmSearch)
   │      GET https://registry.npmjs.org/-/v1/search?text=...&size=10
   │      过滤：包名或描述里必须含 "mcp"
   │
   ├─ ③ searchGitHub(ctx, intent.Keywords)
   │      GET https://api.github.com/search/repositories?q=<keywords>+mcp&sort=stars&per_page=10
   │      过滤：full_name 或 description 含 "mcp"
   │      Authorization: Bearer $GITHUB_TOKEN（可选，避免匿名限流）
   │
   └─ ④ 合并 + 按 star 降序排序 → 返回可注册的候选（含可直接用的 Config）
```

**几个值得学的地方**：

1. **LLM 只用来"翻译查询词"，不用来判断结果**。搜索本身走确定性 API（GitHub/npm），LLM 幻觉了关键词最坏就是搜不到——**不会凭空造出一个不存在的工具**。这是把 LLM 放在"意图翻译"而非"事实生成"位置的正确用法。
2. **解析失败有确定性兜底**（`tool.go:348-354`）：直接用原始 query 当关键词，流程不中断。
3. **两个方向都强制加 `mcp` 过滤**（`tool.go:372-374, 420-422, 492-494`）：关键词里没有 mcp 时补上，并且对返回结果再做一次"名称或描述须含 mcp"的过滤。防止返回一堆无关高星仓库。
4. **返回的 `Config` 可直接注册**（`{"command":"npx","args":["-y", "<pkg>"]}`），把"发现→注册"的链路缩短成一次点击。
5. **`io.LimitReader(resp.Body, 1<<20)`** 限制了响应体上限（1MB），防止恶意/异常的超大响应打爆内存。

**⚠️ 一处安全提示**：`searchGitHub`/`searchNPM` 返回的 `Config` 是**基于仓库名猜的**（`npx -y <repoName>`），`InstallCommand` 里也写了"具体启动方式以仓库 README 为准"。用户**一键注册后会在 worker 上启动一个 `npx -y <任意包>` 子进程**——这等于允许用户通过"工具发现"在服务器上执行任意 npm 包的代码。当前 `CreateTool` 只校验 `config` 是合法 JSON 且含 `command` 或 `url`，**对 `command` 内容没有任何白名单**。

## 5. 五个必须说清的真相

### 5.1 ⚠️ 高：`Agent.SystemPrompt` 是**死字段**——存了但从不生效

这是 M3 最严重的问题。

**已 grep 全仓核实**：`SystemPrompt` 共 15 处命中，其中与 Agent 相关的只有 3 处，**全部是写入**：

| 位置 | 动作 |
|---|---|
| `model/agent.go:11` | 字段定义 |
| `api/agent.go:51` | `CreateAgent` **写入** |
| `api/agent.go:106` | `UpdateAgent` **写入** |
| — | **没有任何一处读取** |

运行期读的是 **Task** 的字段，不是 Agent 的：

```go
// worker/pool.go:792
systemPrompt := t.SystemPrompt
if systemPrompt == "" {
    systemPrompt = "你是一个有用的 AI 助手。请尽力解答用户的问题或完成用户指定的任务。"
}
```

而 `Task.SystemPrompt` 只在两个地方被赋值：

```go
// ① handler.go:170 —— 通用提交接口：来自【请求体】
SystemPrompt: req.SystemPrompt,      // SubmitRequest.SystemPrompt

// ② api/agent.go:164-177 —— Agent 运行接口：★ 没有赋值！
task := &model.Task{
    ID:             uuid.New().String(),
    UserID:         userID,
    AgentID:        id,
    SessionID:      req.SessionID,
    ConversationID: conversationID,
    Type:           model.TypeCustom,
    Priority:       req.Priority,
    Payload:        req.Payload,
    Status:         model.StatusPending,
    MaxRetry:       3,
    // ← 这里没有 SystemPrompt
}
```

`RunAgentRequest` 里**也没有** `SystemPrompt` 字段（`api/agent.go:33-37`），前端 `runAgent` 传的也只有 `{payload, session_id, priority}`：

```js
// App.vue:429-433
const data = await runAgent(authToken.value, selectedAgentId.value, {
  payload: content,
  session_id: sessionId,
  priority: 2
})
```

**完整结论**：

> 用户在 Agent 里精心写的角色设定，**在运行期被完全丢弃**。任务实际用的是默认的"你是一个有用的 AI 助手"。
> UI 上还能看到它（`App.vue:128` 用它做摘要展示：`activeAgentSummary`），所以**看起来是生效的**——这是最坏的情况：**静默失效 + 界面撒谎**。

**影响范围**：所有通过 `POST /api/agents/:id/run` 发起的对话（也就是前端"工作台"和"独立大窗对话"两条主路径），**全部没有用上 Agent 的角色设定**。

**对比参照**：同一段代码里，Agent 的 `Model`/`APIKey`/`BaseURL` 是**被正确读取并覆盖的**（`pool.go:780-785`）。所以这不是"忘了实现 Agent 覆盖机制"，而是**这一个字段被漏接了**。

**可复现验证**（见 §7.1）：建一个 system_prompt 为"你只能说'喵'"，然后运行它——回答不会变成"喵"。

**修法**（未实施，两行）：`RunAgent` 里给 `Task.SystemPrompt` 赋 `agent.SystemPrompt`；或在 worker 的 Agent 凭证段一并取出 `agent.SystemPrompt` 作为 `t.SystemPrompt` 为空时的回退。

### 5.2 ⚠️ 高：绑定工具/知识库时**不校验对象归属**（BOLA）

两个绑定接口都只校验了 **Agent** 归属，没校验**被绑定对象**的归属：

```go
// api/agent.go:207-223
func (s *AgentHandler) BindTools(c *gin.Context) {
    if _, ok := s.ownedAgent(c); !ok {          // ← 只校验 Agent 是我的
        c.JSON(http.StatusNotFound, gin.H{"error": "Agent 不存在"})
        return
    }
    var req BindToolsRequest
    c.ShouldBindJSON(&req)
    s.manager.ReplaceAgentTools(c.Param("id"), req.ToolIDs)   // ← 不校验每个 tool_id 归属
}

// api/agent.go:244-260  BindKnowledgeBases 结构完全相同：不校验每个 kb_id 归属
```

而读取侧也**没有任何归属复查**：

```go
// manager.go:903-912
func (m *TaskManager) ListAgentKnowledgeBases(agentID string) []*model.KnowledgeBase {
    ids := m.ListAgentKnowledgeIDs(agentID)
    if len(ids) == 0 { return nil }
    var kbs []*model.KnowledgeBase
    m.db.Where("id IN ?", ids).Find(&kbs)        // ← 不按 user_id 过滤
    return kbs
}
```

`resolveTools` 与 `retrieveKnowledge` 都直接使用这些结果，**回退到全局默认凭证运行**。所以后果是：

| 攻击面 | 后果 |
|---|---|
| **绑他人知识库** | 该 Agent 的每一次对话都会检索**别人的知识库**并把内容注入 prompt → **跨租户数据读取** |
| **绑他人私有 MCP 工具** | `resolveTools` 会读取该工具的 `Config`（**含 `Env` 里的密钥**）并**在 worker 上启动它** → 以他人凭证执行、并可能诱导模型输出敏感结果 |

**前提条件**：攻击者需要知道目标对象的 UUID。UUID 不可枚举，但可能通过截图、日志、分享链接、错误信息等渠道泄露。这是典型的 **BOLA（Broken Object Level Authorization）/ IDOR** —— **不应依赖"ID 猜不到"作为授权手段**。

**修法**（未实施）：`ReplaceAgentTools` / `ReplaceAgentKnowledgeBases` 接收 `userID`，在事务内对每个 ID 校验 `(is_builtin = true OR user_id = ?)` / `user_id = ?`；读取侧（`ListAgent*`）同样按 `userID` 过滤作为纵深防御。

> 值得注意：`ListTools`（工具列表）**是正确的**（`is_builtin = true OR user_id = ?`）。所以问题不在"不知道怎么做归属过滤"，而在**绑定路径漏了这一步**。

### 5.3 ⚠️ 中：改 MCP 工具配置后不重启则**不生效**且无提示

见 §4.4。缓存键只有 tool ID，不含配置指纹。用户改完配置测试没变化，没有任何日志或界面提示告诉它"需要重启 worker"。

### 5.4 ⚠️ 中：内置"联网搜索"的运行期依赖是本地文件，缺失时**静默失效**

完整链路（`cmd/worker/main.go:199-208`）：

```go
mcpCtx := context.Background()
mcpServerPath := config.ResolveProjectPath("bin", "search_mcp.exe")    // ★ 依赖编译产物
mcpClient, err := mcpclient.NewWrapper(mcpCtx, mcpServerPath)
if err != nil {
    slog.Warn("Failed to connect to MCP Server, tools will be disabled", "error", err)
    // ★ mcpClient 保持 nil，不返回、不 Fatal
} else {
    slog.Info("Connected to MCP Server successfully")
    defer mcpClient.Close()
}
```

如果 `bin/search_mcp.exe` 不存在（**新克隆仓库还没来得及 build** 是最常见的情况）：

1. `mcpClient == nil` → `pool.go:106` 的 `if mcpClient != nil` 不成立 → `internet_search` **不进静态注册区**；
2. DB 里 `builtin_internet_search` 那行**仍然存在、`status=active`、UI 里可以正常绑定**；
3. `resolveTools` 处理该绑定时：
   - `p.toolRegistry.Get("internet_search")` → **未命中**；
   - 走 `if bt.Type == "mcp" && bt.Config != ""` → **`Config` 是空字符串** → **分支不成立**；
   - **既不加工具，也不打任何日志** → 静默跳过。

**结果**：用户绑定了"联网搜索"，UI 显示已绑定，但 Agent 运行期**没有这个工具**，且模型也收不到"必须搜索"的指令（`pool.go:799` 的 `hasToolName(tools, "internet_search")` 为 false）。**唯一的线索是 worker 启动时那一行 `Warn`**。

**修法方向**：`resolveTools` 里对"绑定行存在但两条分支都未命中"的情况打一条 `[Worker][ALERT]` 日志；或在 API 侧的健康检查里暴露"内置 MCP 是否就绪"。

### 5.5 ⚠️ 中：`Agent.Status` 也是死字段（无归档/停用能力）

已 grep 核实：`archived` 在业务代码里**零命中**（只有 `third_party/asynqmon` 的同名概念，无关）。`CreateAgent` 写死 `Status: "active"`，`UpdateAgent` 不更新该字段，`ListAgents` 也不按它过滤。

**后果**：Agent 没有"停用/归档"能力——要么存在且可用，要么只能删除。删除会连带丢失绑定关系（见 §5.6 的孤儿行问题）。对需要"临时下线一个 Agent 但保留配置"的场景（比如 Agent 出问题要紧急停用），当前只能删掉再重建。

> 这与 M4 向量线里的 `knowledge_bases.type`（`rag`/`kag`/`hybrid` 存了但无分流）是同一类问题：**字段存在，语义未落地**。

### 5.6 低：删除 Agent/Tool 不清理绑定行，产生孤儿数据

| 删除动作 | 是否清理绑定 | 后果 |
|---|---|---|
| `DeleteAgent` | ❌ 不删 `agent_tools` / `agent_knowledge` | 留下**指向已删 Agent 的绑定行**（永久垃圾） |
| `DeleteTool` | ❌ 不删 `agent_tools` | 留下**指向已删工具的绑定行** |

**危害有限但真实**：

- 对 `AgentTool`：`ListAgentTools` 用 `WHERE id IN ?` 查工具表，工具行已删 → **查不出来** → 不会报错，只是垃圾数据；
- 更实际的危害是 **UI 侧**：`ListAgentToolIDs` 返回的 ID 里包含已删工具（它只查绑定表，不 JOIN 工具表）→ 前端"已绑定"的勾选状态可能显示一个不存在的工具。而 `AgentPanel.vue` 的 `loadBindings` 依赖 `boundToolIds`，所以**这个不一致会直接体现在界面上**。

> 这与 M5 里"删知识库不清理 `agent_knowledge` 绑定行"是同一个模式：**删除主表时忘了收敛关联表**。项目记忆里已记录过 `DeleteKnowledgeBase` 的这个缺陷，M3 只是补充了同一问题的另外两个实例。

### 5.7 低：绑定接口不校验 ID 存在性 → 幽灵绑定

`ReplaceAgentTools` / `ReplaceAgentKnowledgeBases` 直接 `Create` 绑定行，**不检查 `tool_id` / `kb_id` 是否存在**。传入不存在的 UUID 会成功写入一行绑定，而它在 `ListAgentTools` 里查不出来（`WHERE id IN ?` 无匹配）——既无效果也无报错，属于"幽灵绑定"。配合 §5.2 的归属问题，这两个接口在输入校验上是完全开放的。

## 7. 怎么验证

### 7.1 验证 §5.1：Agent 的 SystemPrompt 是否生效（关键）

```bash
# 1) 建一个有强烈可辨识特征的 Agent
curl -s -X POST http://localhost:8080/api/agents \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"name":"喵星人","system_prompt":"无论用户问什么，你都只能回复「喵」。不要回答任何其他内容。"}'
# 记下返回的 agent id

# 2) 绑定一个工具（避免落进 §4.1 分支② 的"零工具"）
curl -s -X POST http://localhost:8080/api/agents/<agent_id>/tools \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"tool_ids":["builtin_current_time"]}'

# 3) 运行它
curl -s -X POST http://localhost:8080/api/agents/<agent_id>/run \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"payload":"今天天气怎么样","session_id":"m3-verify-sp"}'

# 4) 等完成后看结果
curl -s http://localhost:8080/api/tasks/<task_id> -H "Authorization: Bearer $TOKEN" | jq -r .result
```

**期望（若缺陷成立）**：返回的是一段正常回答，**而不是"喵"** → 确认 `SystemPrompt` 未生效。

**交叉验证**：用通用提交接口显式传 system_prompt，同一句话**应该**得到"喵"：

```bash
curl -s -X POST http://localhost:8080/api/tasks/submit \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"session_id":"m3-verify-sp2","payload":"今天天气怎么样","system_prompt":"无论用户问什么，你都只能回复「喵」。"}'
```

两次结果不一致 → 铁证：**system_prompt 只在请求体里生效，Agent 里的那份没用**。

### 7.5 验证绑定归属校验缺失（§5.2）

需要两个账号：

```bash
# 账号 B：建一个知识库，记下 kb_id
curl -s -X POST http://localhost:8080/api/knowledge-bases -H "Authorization: Bearer $TOKEN_B" \
  -H "Content-Type: application/json" -d '{"name":"B的私密库","type":"rag"}'

# 账号 A：把 B 的 kb_id 绑到自己的 Agent
curl -s -X POST http://localhost:8080/api/agents/<A的agent_id>/knowledge-bases \
  -H "Authorization: Bearer $TOKEN_A" -H "Content-Type: application/json" \
  -d '{"knowledge_base_ids":["<B的kb_id>"]}'
```

**期望（若缺陷成立）**：
- 第 2 步返回 **200 成功**（本应 403/404）；
- `GET /api/agents/<A的agent_id>/knowledge-bases` 能列出 B 的知识库；
- A 运行该 Agent 提问 B 库里的内容 → **能拿到 B 的内容**。
→ 确认跨租户读取。

**对照组**（证明项目里有正确的写法）：用账号 A 提交**别人的 task id** 查任务，会被拒绝（`GetTaskStatus` 校验 `task.UserID != userID`）。这反衬出绑定路径缺的正是同一层校验。

## 8. 一页速记（面试/复盘用）

- **一句话定位**：Agent 是**持久化的可复用配置 + 能力围栏**（角色设定 / 模型凭证覆盖 / 工具白名单 / 知识库范围）。
- **四个最容易被追问的设计点**：
  1. 白名单语义是什么？——**有 Agent 就只给绑定的**；没 Agent 给全部；绑定了但列表为空 → **零工具**（默认拒绝）。另外 `status=disabled` 的工具即使绑了也不加载，且**运行时每次校验、即时生效**。
  2. Agent 的模型凭证怎么覆盖？——`Model`/`APIKey`/`BaseURL` 三级回退（Agent 有则用 Agent，否则用平台默认），配置存在 Redis（TTL 5 分钟）且**更新时主动删缓存** → 热更新即时生效。
  3. 工具从哪来？——两条来源：**静态注册区**（内置 + worker 启动时从 `bin/search_mcp.exe` 拉到的工具）与**动态 MCP**（读绑定行的 `Config` 拉起 stdio 子进程或连 SSE）。先查静态、再走动态。
  4. 工具发现怎么做？——自然语言 → **LLM 只做"查询词翻译"** → 确定性调用 GitHub/npm 搜索 API → 返回可直接注册的 `Config`。LLM 幻觉最坏是搜不到，不会凭空造工具。
- **五个必须说清的事实修正**：
  1. **`Agent.SystemPrompt` 是死字段**：全仓 3 处命中**全是写入**，读取处为 0；`RunAgent` 也不给 `Task.SystemPrompt` 赋值 → **Agent 的角色设定在运行期被完全丢弃**，任务用默认 prompt 跑。而 UI 还在展示它 —— **静默失效 + 界面撒谎**。
  2. **绑定工具/知识库不校验对象归属（BOLA）**：`BindTools`/`BindKnowledgeBases` 只校验 Agent 是我的，不校验 `tool_id`/`kb_id` 是谁的；读取侧 `ListAgent*` 也不按 `user_id` 过滤 → 可让 Agent 检索**他人知识库**、或以**他人凭证拉起私有 MCP 工具**（其 `Config.Env` 含密钥）。
  3. **改 MCP 工具配置后必须重启 worker**：连接池缓存键只有 tool ID、不含配置指纹 → 新 `command`/`url` 被静默忽略，且无任何提示。
  4. **内置"联网搜索"的运行时依赖是本地 `bin/search_mcp.exe`**：该文件不存在时 `mcpClient` 为 nil → 不入静态注册；而 DB 里那行 `Config` 又是空的 → `resolveTools` **两条分支都不成立，静默跳过**。UI 显示已绑定、运行期不可用。
  5. **`Agent.Status` 也是死字段**：`archived` 在业务代码零命中 → **没有归档/停用能力**，只能存在或删除。
- **两条可量化的证据**：
  - §7.1 的"喵"实验：同一句话，走 `/api/agents/:id/run` 得到正常回答、走 `/api/tasks/submit` 带 system_prompt 得到"喵" → **两次结果不一致即铁证**；
  - §7.5 的双账号实验：A 绑定 B 的 `kb_id` 返回 200 并能读到 B 的内容 → **确认跨租户读取**。
