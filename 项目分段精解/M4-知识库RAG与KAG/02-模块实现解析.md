## 0. 一句话总览

**图谱线 = 把文档里的事实抽成"实体—关系—实体"三元组存进图，提问时沿着关系走几跳，把走过的路径当证据交给模型。**

它要补的是向量线的**结构性盲区**：向量检索只能回答"哪段文字和问题像"，回答不了"这几个实体之间是什么关系"。

---

## 1. 这个模块解决什么问题

### 1.1 向量线回答不了的那类问题

**多跳问题**：*"《某电影》的导演的出生地是哪里？"*

这个问题的答案不在任何一段原文里，它分散在两段事实中：

- 文档 A：`某电影 —[DIRECTED_BY]→ 张三`
- 文档 B：`张三 —[BORN_IN]→ 某市`

向量检索把"问题"和"段落"做语义相似度比对，两段都不"像"这个问题，所以都召不回来（或召回一段，缺另一段）。而只要图里有这两条边，沿边跳两跳就能拼出答案。

### 1.2 图谱线的三段式

```
① 生产期：文档内容 ──LLM 抽取──▶ 三元组 ──MERGE──▶ Neo4j 图
② 检索期：问题 ──LLM 抽实体提及──▶ 起点实体 ──BFS 逐跳──▶ 证据链
③ 注入期：证据链 ──LLM 相关性过滤──▶ 与向量线共享字数闸门 ──▶ 拼进 system prompt
```

## 2. 关键决策：为什么放弃了 Text2Cypher

这是图谱线最值得讲的一段历史，代码注释里留着明确记录。

**旧方案**：让 LLM 一步生成一条 Cypher 查询去查图。

**失败原因**（`retrieve.go:32-33` 注释原文）：

> 替代旧的「LLM 一步生成单条 Cypher」方案：后者在 **744 种关系**下几乎必然生成不一致的关系名而空返回。

也就是说：抽取阶段 LLM 自由发挥，把"总部位于"抽成了 `HEADQUARTERED_IN`、`HEADQUARTERS_IN`、`HEADQUARTER_IN`…… 一共 744 种关系类型。检索阶段 LLM 又凭直觉生成一个关系名，两边**几乎不可能撞上**，查询必然返回空。

**试点实测数据**（`ontology.go:6-7` 注释与项目记忆一致）：

| 假设 | 实测结论 |
|---|---|
| 关系 schema 爆炸是主因 | ✅ 成立：744 种关系类型，58% 是长尾 |
| 实体名大小写/空白碰撞是主因 | ❌ **证伪**：只占节点 1.3% |
| 事后字符串归一化能收敛关系 | ❌ **证伪**：744 → 742，几乎零收益 |

**由此得出的设计原则**（`ontology.go:6-7` 原文）：

> 关系收敛**只能靠抽取侧本体白名单**，故抽取时用白名单约束 LLM、用等价类把变体归一到规范关系。

**新方案 = 三步替换**：

| 环节 | 旧 | 新 |
|---|---|---|
| 关系数量 | 744 种，不可控 | 白名单约 50 个 + 11 条等价类映射 |
| 检索方式 | LLM 生成单条 Cypher | **确定性 BFS 逐跳展开**（不生成查询，只走边） |
| 空结果处理 | 返回空串 | 返回证据链或**缺失提示** |

> **教学点**：遇到"LLM 生成的查询查不到数据"这类问题，第一反应往往是"再让 LLM 聪明点"（比如重试、few-shot）。但这个项目的结论是**反向的**——把不确定性从检索期挪到生产期，在生产期用约束（白名单）掐死，检索期就变成确定性代码，可测、可复现。这个"用约束换确定性"的取舍是图谱线最核心的设计思想。

## 3. 存储模型：极简的图 schema

### 3.1 节点与边

```
(:Entity {name: "张三"})
        │
        ├─[DIRECTED_BY {source_doc: "doc-uuid-1"}]─▶ (:Entity {name: "某电影"})
        └─[BORN_IN    {source_doc: "doc-uuid-2"}]─▶ (:Entity {name: "某市"})
```

- **节点**：只有一种 Label `:Entity`，唯一属性 `name`（`kag.go:115-116`、`:123-124`）。
- **边**：类型就是**规范关系名**（大写），动态生成；属性只有一个可选的 `source_doc`（来源文档 ID）。
- **没有**其它 Label、没有节点属性（没有类型、别名、描述）。

**为什么这么简**：图 schema 越简单，抽取时 LLM 越不容易跑偏。节点只有名字，省掉了"这个实体是人物还是地点"的分类问题。

### 3.2 索引现状

| 索引 | 建了吗 | 位置 |
|---|---|---|
| 关系 `source_doc` 属性索引（每个关系类型一个） | ✅ | `EnsureSourceDocIndex`，`kag.go:201-238` |
| **`:Entity(name)` 节点索引** | ❌ **没有** | 全仓未见 `CREATE INDEX ... ON (n.name)` |

> ⚠️ 这个缺失影响很大，见 §6.4。

### 3.3 `source_doc` 索引的一个运维缺口

```go
// kag.go:198-201
// 关系类型由本体动态生成，故先枚举现有类型再逐个建索引；新建类型需再次调用本方法。
```

`EnsureSourceDocIndex` 的做法是：`CALL db.relationshipTypes()` 枚举**当前已存在**的关系类型，逐个建 `CREATE INDEX ... FOR ()-[r:TYPE]-() ON (r.source_doc)`。

**但它在代码里只在两个地方被调用，都是启动时**：

- `cmd/api/main.go:97`
- `cmd/worker/main.go:194`

**后果**：运行期新出现的某个关系类型**永远没有索引**，直到下次重启。而"删除按 `source_doc` 过滤"恰恰依赖这个索引——所以新关系类型的删除会退化成全图扫描。这是一个真实存在的运维缺口，不是理论问题。

> 另外：Neo4j 的 `CREATE INDEX` 默认是**后台异步填充**，代码建完索引没有等待 population 完成。启动后立刻执行删除，是否真的走索引**未确认**，需实测。

## 4. 生产期：抽取与入图

### 4.1 本体：白名单 + 等价类

`RelationOntology`（`ontology.go:8-13`）两个字段：

```go
type RelationOntology struct {
    Canonical []string          // 白名单规范关系名（统一大写）
    Alias     map[string]string // 语义等价类：变体 -> 规范名
}
```

内置本体（`DefaultRelationOntology`，`ontology.go:40-72`）覆盖 6 类共**约 50 个**规范关系：

| 类别 | 示例 |
|---|---|
| 空间 / 行政归属 | `LOCATED_IN`、`PART_OF`、`CAPITAL_OF`、`COUNTRY_OF` |
| 影视 / 作品 | `DIRECTED_BY`、`STARRING`、`BASED_ON`、`SEQUEL_OF`、`GENRE_OF` |
| 人物 / 机构 | `AUTHOR_OF`、`FOUNDED_BY`、`MEMBER_OF`、`LEADER_OF` |
| 人物属性 | `OCCUPATION`、`NATIONALITY`、`BORN_IN`、`DIED_ON` |
| 亲属 / 社会 | `SPOUSE_OF`、`PARENT_OF`、`SIBLING_OF`、`FATHER_OF` |
| 事件 / 参与 | `PARTICIPATES_IN`、`CONTESTED_OFFICE` |

等价类映射有 **11 条**（`ontology.go:59-71`），例如：

```go
"HEADQUARTERED_IN" -> "LOCATED_IN"
"LOCATED_AT"       -> "LOCATED_IN"
"WORKED_AT"        -> "WORKS_FOR"
"BORN_AT"          -> "BORN_IN"
"PARTICIPATED_IN"  -> "PARTICIPATES_IN"
```

### 4.2 「白名单约束」其实是软约束

这一点必须讲清楚，否则会误以为 schema 已被完全控制。

```go
// kag.go:63-65  抽取时把白名单拼进 system prompt
if hint := k.ontology.whitelistHint(); hint != "" {
    systemPrompt += fmt.Sprintf("\n关系名称必须仅从以下规范关系名中选择（保持大写，不要自创同义词）：\n%s", hint)
}
```

```go
// ontology.go:15-28  抽取后的收敛函数
func (o *RelationOntology) CanonicalizeRelation(rel string) string {
    norm := cleanRelationName(rel)              // 非字母数字→下划线；转大写
    if canon, ok := o.Alias[norm]; ok { return canon }
    return norm                                 // ★ 不在白名单内 → 原样返回
}
```

**关键**：`CanonicalizeRelation` **只做别名映射，不校验白名单**。如果 LLM 吐出一个既不在 `Canonical`、也不在 `Alias` 里的关系名（比如 `HAS_A_NICE_NAME`），它会被**照单全收**写进图。

所以"白名单"是**提示词级的软约束**（靠 LLM 配合），不是**代码级的硬闸门**。这意味着：

- schema 扩散被大幅压制，但**没有归零**；
- 关系类型数量仍会随语料增长而缓慢增加（这正好解释了 §3.3 那个索引缺口为什么是真实问题）。

> 若要变成硬约束，只需在 `CanonicalizeRelation` 里加一句"不在 Canonical 则丢弃或映射到 `RELATED_TO`"——**当前没有这么做**（这是有意的保守：宁可保留信息，也不丢事实）。

### 4.3 抽取流程（`ExtractKnowledgeWithBudget`，`kag.go:54-89`）

```go
systemPrompt := `你是一个知识图谱信息抽取专家。…
提取结果必须严格使用 JSON 数组格式返回…不要使用 markdown 代码块标记。
[
  {"source": "实体A", "relation": "关系名称", "target": "实体B"}
]
注意：请尽可能完整地抽取文本中出现的所有事实三元组，不要遗漏（recall 优先）。`
// + 白名单提示（若有）

resp, err := k.llmClient.GenerateWithBudget(ctx, systemPrompt, userPrompt, budget)  // 单次调用
resp = cleanJSONString(resp)                       // 剥掉可能的 ```json 包裹
json.Unmarshal([]byte(resp), &relations)           // 失败即返回错误
for i := range relations {
    relations[i].Relation = k.ontology.CanonicalizeRelation(relations[i].Relation)
}
```

三个设计取向：

1. **recall 优先**（prompt 里明说"尽可能完整、不要遗漏"）。因为试点结论是"**抽取覆盖不足**是命中率低的主导根因"——"文档里有、图里没有"比"图里多了几条无关边"危害大得多。
2. **只调一次 LLM**：没有分块抽取、没有多轮补抽。长文档一次性喂进去，抽出多少算多少。
3. **`cleanJSONString` 容错**（`kag.go:241-254`）：分别处理 ` ```json `、` ```cypher `、裸 ` ``` ` 三种前缀——`cypher` 分支是旧 Text2Cypher 时代留下的痕迹。

**注意**：抽取结果**不做逐条校验**。`source`/`target` 为空的三元组一路带到入图阶段才被跳过（`kag.go:104-106`）。

### 4.4 入图流程（`IngestGraphWithSource`，`kag.go:98-145`）

```go
for _, rel := range relations {
    if 任一字段为空 { continue }                    // 空值守卫
    relType := cleanRelationName(rel.Relation)

    if sourceDoc == "" {
        query = `MERGE (a:Entity {name: $source})
                 MERGE (b:Entity {name: $target})
                 MERGE (a)-[r:%s]->(b) RETURN id(r)`         // 无归属
    } else {
        query = `MERGE (a:Entity {name: $source})
                 MERGE (b:Entity {name: $target})
                 MERGE (a)-[r:%s {source_doc: $doc_id}]->(b) RETURN id(r)`   // 有归属
    }
    session.ExecuteWrite(...)
    if err != nil { log.Printf("Failed to insert relation …") }   // ★ 只打日志
}
return nil                                                        // ★ 始终返回 nil
```

**三个要点**：

1. **一个三元组一次事务**（`kag.go:131-138` 在 for 循环里）。没有批处理、没有用 `UNWIND` 批量 MERGE。10 条关系 = 10 次事务往返。对离线建库可以接受，但成本随文档规模线性放大。
2. **`source_doc` 参与 MERGE 实现幂等**（`kag.go:121` 注释）：同一个文档重复入图，因为 MERGE 的模式里含 `source_doc`，不会产生重复边。这一点很关键——重建文档时即使重复抽取，也不会把图撑大。
3. ⚠️ **失败被静默吞掉**：`err != nil` 时只打一行日志，循环继续，**函数最终 `return nil`**。调用方（`runGraphStage`）看到 `nil` 会认为"入图成功"，于是把 `graph_status` 记成 `ready`——**而实际上可能一条边都没写进去**。这属于"错误被降级成日志"，是审计与排障上的一个真实缺口。

## 5. 检索期：多跳松弛检索

### 5.1 主流程（`RetrieveGraphContext`，`retrieve.go:34-50`）

```go
const defaultMaxHops = 3      // 硬编码，无配置入口

starts, _ := k.locateStartEntities(ctx, question)     // ① 定位起点
if len(starts) == 0 {
    return "", nil                                     // ★ 起点不在图内 → 直接返回空
}
facts := k.expandNeighbors(ctx, starts, defaultMaxHops, topN)   // ② 逐跳 BFS
return formatGraphContext(starts, facts), nil          // ③ 组装（有事实给证据链，无事实给缺失提示）
```

### 5.2 ① 起点定位（`locateStartEntities`，`retrieve.go:53-65`）

```
问题
 ├─ extractMentions(question)   ← LLM 抽取实体提及（JSON 字符串数组）
 │    └─ 对每个提及 → matchEntity：精确 name 匹配 OR toLower/trim 归一匹配（LIMIT 10）
 └─ 若 LLM 失败 / 无提及
      └─ matchBySubstring(question)：确定性兜底
```

**`matchBySubstring` 的兜底逻辑**（`retrieve.go:119-148`）：

```go
res, _ := tx.Run(ctx, `MATCH (n:Entity) RETURN n.name AS name LIMIT 2000`, nil)
// 把最多 2000 个实体名拉回内存，逐个判断"该名字是否为问题的子串（大小写不敏感）"
```

这是典型的"**用内存换确定性**"：宁可拉 2000 条记录到应用层做子串匹配，也不依赖 LLM。`LIMIT 2000` 是硬上限——图里实体超过 2000 个时，兜底匹配会**看不到后面的实体**（顺序未定义）。

> ⚠️ `extractMentions` 调的是 `Generate`（`retrieve.go:73`），**没有传 budget**——所以这次 LLM 调用**不纳入任务级调用次数与成本上限**，也不进指标。项目记忆里已把这条列为遗留项。而下游的 `IsContextRelevant` 是传了 budget 的（`pool.go:831`），两者不一致。

### 5.3 ② 逐跳展开（`expandNeighbors`，`retrieve.go:151-191`）

标准 BFS，带三处工程细节：

```go
for hop := 1; hop <= maxHops; hop++ {
    for _, name := range frontier {
        for _, nb := range k.queryNeighbors(ctx, name) {
            src, dst := name, nb.Target
            if nb.Incoming { src, dst = nb.Target, name }     // ★ 入边要交换方向
            facts = append(facts, graphFact{Source: src, Rel: CanonicalizeRelation(nb.Rel), Target: dst, Hop: hop})
            if topN > 0 && len(facts) >= topN { return facts } // ★ 达标提前返回
            if !visited[nb.Target] { visited[nb.Target] = true; next = append(next, nb.Target) }
        }
    }
    if len(next) == 0 { break }                                // ★ 无新节点即收敛
    frontier = next
}
```

三处细节的意义：

| 细节 | 为什么需要 |
|---|---|
| **入边交换 source/target** | 图里边的方向是抽取时定的（"张三 —[BORN_IN]→ 某市"）。但检索时"某市"也可能是起点，这时候要能反向走出去。代码取出边和入边两次查询，入边把方向翻正，保证输出格式统一为 `起点 -[REL]-> 终点` |
| **`topN` 提前返回** | `topN` 来自 `context.graph_top_n`（默认 10）。BFS 不设上限时，3 跳在高连接度图上可能爆炸（扇出^3）。topN 是唯一的总量闸门 |
| **`visited` + `break`** | 防环 + 无新增即停，避免在无向环里绕圈 |

**跳数为什么从 1 开始且 `hop` 要标注**：`retrieve.go:16-17` 注释说得很清楚——多跳检索容易"停在中转层"（比如问到第 3 跳的答案，但第 2 跳的中间实体看起来也像答案）。给每条事实标上 `hop=N`，让模型自己判断"这是中间层还是终点"。

### 5.4 `queryNeighbors` 的性能特征（`retrieve.go:194-233`）

```go
session := k.neo4jDriver.NewSession(...)          // 每个实体新建一个 session
collect(`MATCH (n:Entity {name: $name})-[r]->(m:Entity) RETURN type(r) AS rel, m.name AS target`, false)
collect(`MATCH (n:Entity {name: $name})<-[r]-(m:Entity) RETURN type(r) AS rel, m.name AS target`, true)
```

这是本模块**性能上最需要注意的一段**，三个叠加因素：

1. **每个实体一次函数调用 → 新建 session → 2 次 Cypher**。BFS 3 跳、每层若干实体，形成典型的 **N+1 查询**。
2. **`MATCH (n:Entity {name: $name})` 没有索引** → Neo4j 只能做 Label Scan。图里有 N 个实体，每次查邻居就扫 N 个节点。
3. **session 未复用**，逐次建连。

综合起来：图规模小时无感；实体上万后，单次图谱检索会明显变慢。这是"能跑通 vs 能规模化"的分界线。

### 5.5 ③ 组装：宁给提示，不给空串（`formatGraphContext`，`retrieve.go:236-245`）

```go
if len(facts) == 0 {
    return fmt.Sprintf("[缺失提示] 起点实体「%s」已建图，但未发现可达邻接关系（可能为抽取覆盖不足导致事实缺失）。", strings.Join(starts, "、"))
}
// 否则逐行输出
// 张三 -[BORN_IN]-> 某市 (hop=2)
```

这个设计有意思：**"没有事实"和"根本没建图"是两种情况，给模型的信号应该不同**。

- 返回空串 → 模型不知道是"没有这个信息"还是"检索坏了"；
- 返回缺失提示 → 模型知道"这个实体在库里，但关于它的关系没抽出来"，可以据此选择"承认不知道"或"改用常识回答"。

这是把**系统的不确定性显式告诉模型**，而不是藏着。

## 6. 注入期：关联度过滤与总量闸门

### 6.1 注入链路（`pool.go:826-858`）

```go
if p.kagManager != nil && decision.NeedKAG {
    kagResult, err := p.kagManager.RetrieveGraphContext(ctx, t.Payload, config.AppConfig.Context.GraphTopN)  // topN=10
    if err == nil && kagResult != "" {
        // ① 关联度过滤（LLM yes/no）
        if relevant, rerr := p.llmClient.IsContextRelevant(ctx, t.Payload, kagResult, budget); rerr == nil && !relevant {
            kagResult = ""
        }
        if kagResult != "" {
            // ② 与向量线共享剩余额度
            remaining := config.AppConfig.Context.MaxContextChars      // 6000
            if remaining > 0 {
                remaining -= len(kbContext)                            // 减掉向量线已用
                if remaining <= 0 { kagResult = "" }
            }
            if kagResult != "" {
                kagResult = truncateChunk(kagResult, remaining)         // ③ 按剩余额度截断
                systemPrompt += fmt.Sprintf(`…<knowledge_graph_context>%s</knowledge_graph_context>`, kagResult)
            }
        }
    }
}
```

**三道闸门依次收窄**：关联度过滤（内容层）→ 共享额度（预算层）→ 字符截断（硬上限）。

**② 的共享机制值得注意**：图谱上下文不是"额外给 6000 字"，而是和向量知识**抢同一个 6000 字池**。向量线先注入、先占额度；图谱线只能用剩下的。所以：

- 向量线命中很多时，图谱上下文可能被压到极少甚至清零；
- 这是有意的——两条线都是"知识"，加起来必须服从同一个上下文预算，否则 prompt 会膨胀。

**注意一个顺序细节**：`remaining -= len(kbContext)` 减的是**字节数**（`len()` 对 string 返回字节数），而 `truncateChunk` 截断用的是 **rune 数**（`pool.go:573-577` 转 `[]rune`）。中文场景下 1 个汉字 = 3 字节，所以"减字节、截 rune"的口径不一致——剩余 3000 字节时，`truncateChunk(s, 3000)` 会允许 3000 个 rune（可能是 9000 字节）。**图谱上下文实际可能超出共享闸门 3 倍**（中文场景）。这是一个真实的口径漏洞。

### 6.2 `IsContextRelevant` 的子串判定脆弱性（`client.go:444-460`）

```go
r := strings.ToLower(strings.TrimSpace(resp))
if strings.Contains(r, "不相关") || strings.Contains(r, "无关") || strings.Contains(r, "no") {
    return false, nil
}
if strings.Contains(r, "yes") || strings.Contains(r, "是") || strings.Contains(r, "相关") {
    return true, nil
}
return true, nil       // 兜底：无法判定 → 保守注入
```

**设计意图是好的**：判定失败一律返回 `true`（保守注入），宁可多给信息也不误删（`client.go:441-443` 注释明确说明）。

**但判定方式很脆**——用**子串**匹配英文 "no"：

| 模型实际输出 | 含子串 "no"？ | 判定 | 是否正确 |
|---|---|---|---|
| `No, not related` | ✅（`No`） | false | ✅ |
| `not related` | ✅（`not` 里有 `no`） | false | ✅ |
| `I don't know` | ✅（`know` 里有 `no`） | false | ❌ 应为"不确定→保守注入" |
| `No doubt, it is relevant` | ✅（`No`） | false | ❌ 反了 |

也就是说，"no" 作为子串会命中 `not`、`know`、`unknown`、`cannot` 等等。**这是一个概率不高但确实存在的误判路径**。更稳的做法是精确匹配首词或要求严格输出 `yes`/`no` 后 trim 比对。

### 6.3 生产期图谱阶段（`runGraphStage`，`pool.go:1120-1161`）

```go
if !config.AppConfig.KB.GraphEnabled || p.kagManager == nil {
    return "skipped"                              // 开关关闭或无 KAG → skipped
}
if p.graphSem != nil {                            // 信号量限流
    p.graphSem <- struct{}{}
    defer func() { <-p.graphSem }()
}
graphCtx, cancel := context.WithTimeout(ctx, 5*time.Minute)   // 独立 5 分钟超时
graphBudget := &llm.Budget{…}                                 // 独立预算
relations, err := p.kagManager.ExtractKnowledgeWithBudget(graphCtx, doc.Content, graphBudget)
// …指标计量到 "kb:build" 队列…
if err != nil { return "failed" }
if len(relations) == 0 { return "ready" }                     // 抽不出关系也算 ready
if err := p.kagManager.IngestGraphWithSource(graphCtx, relations, doc.ID); err != nil { return "failed" }
return "ready"
```

**四个设计要点**（`pool.go:1114-1119` 注释总结得很准）：

1. **与向量阶段是两个独立失败域**：图谱失败**不回滚已入库的向量**，只记 `graph_status`。这避免了"图谱抽取失败 → 整个任务重试 → 向量重复入库"的连锁问题。
2. **信号量限流**：`graph_queue_concurrency`（默认 2）。因为图谱阶段与向量阶段**共用同一个 `low` 队列**，光靠队列权重压不住图谱抽取的并发（它比向量化慢得多），所以额外加一层信号量。
3. **独立预算与独立指标**：图谱抽取的 LLM 成本计量到 `kb:build` 队列，与 `task:process` 分开观测——不加这一层，"知识库构建烧了多少钱"是不可见的。
4. **空关系也返回 `ready`**：抽不出关系不是错误（可能是文档本身没有事实性内容），标记为 `ready` 而非 `failed`，避免污染失败率指标。

### 6.4 失效清理（`DeleteBySourceDoc`，`kag.go:150-196`）

```go
// 关系类型由本体动态生成，无法按固定类型匹配，故按关系属性 source_doc 过滤
countRes  := `MATCH ()-[r]->() WHERE r.source_doc = $doc_id RETURN count(r) AS c`
delRes    := `MATCH ()-[r]->() WHERE r.source_doc = $doc_id DELETE r`
orphanRes := `MATCH (n:Entity) WHERE NOT (n)--() DELETE n`      // ★ 全局删孤立节点
```

**为什么按属性而不是按类型**：关系类型是动态的（可能几十上百种），没法写 `DELETE (a)-[:TYPE1|TYPE2|…]->(b)`。所以给每条边打 `source_doc` 属性，按属性删。这也正是 §3.3 索引缺口重要的原因。

**孤立节点清理是全局的**（注意 `MATCH (n:Entity) WHERE NOT (n)--()` **不带任何来源过滤**）：删完本文档的边后，把**全图所有无邻接的 Entity 节点**都删掉。

- **好的一面**：本来就应该清理这些无用节点；
- **风险**：如果此刻有其它文档正在入图（边还没建完），或某个节点因为其它原因暂时无邻接，会被**误删**——而这个节点可能马上又要被引用（MERGE 会重新创建，所以不会报错，只是白做一次写入）。属于低概率、低危害但确实存在的竞态。

## 7. 与向量线的关系

```
同一个 kb:build 任务
  ├─ 向量阶段：摘要 → 切分 → 向量化 → Milvus        失败 → doc.status=failed
  └─ 图谱阶段：抽取 → 入图 → Neo4j                   失败 → doc.graph_status=failed
                                            ↑ 互不影响，向量成果保留

检索期
  ├─ 向量线：retrieveKnowledge()    → kbContext
  └─ 图谱线：RetrieveGraphContext() → 过滤 → 截断 → kagContext
                                            ↑ 共享 max_context_chars 预算
注入期
  systemPrompt += <knowledge_base_context>…</knowledge_base_context>
  systemPrompt += <knowledge_graph_context>…</knowledge_graph_context>
```

**两条线的开关是分离的**：向量线只要 Milvus 通就跑；图谱线额外需要 `kb.graph_enabled=true` 且 Neo4j 通。**当前配置下图谱线默认关闭**（`config.yaml:45`）。

## 8. 数据结构与状态

### 8.1 Neo4j 侧

| 元素 | 形态 | 说明 |
|---|---|---|
| 节点 | `(:Entity {name})` | `name` 是唯一业务键；MERGE 依据 |
| 边 | `-[:规范关系名 {source_doc}]->` | 类型动态；`source_doc` 可缺（无归属入图时） |
| 索引 | `FOR ()-[r:TYPE]-() ON (r.source_doc)` | 每个关系类型一个；启动时枚举创建 |
| 边属性 | 仅 `source_doc` | 没有权重、时间、置信度 |

### 8.2 状态字段（MySQL 侧）

`documents.graph_status`（与 `documents.status` **完全独立**）：

```
pending ──▶ ready       抽取并成功入图（含"抽不出关系"）
        ├─▶ failed      抽取失败 / 入图返回错误
        └─▶ skipped     开关关闭 或 未连接 Neo4j
```

> ⚠️ 由于 §4.4 的"入图失败静默返回 nil"，`failed` 实际上只覆盖"**抽取**失败"，不覆盖"**入图**失败"——入图失败会被记成 `ready`。

## 11. 已知缺陷与未验证项

### 11.1 高：入图失败被静默吞掉，`graph_status` 会误报 `ready`

- 事实：`IngestGraphWithSource` 在单条关系写入失败时只 `log.Printf`，循环继续，**函数最终 `return nil`**（`kag.go:140-144`）。
- 后果：`runGraphStage` 收到 `nil` → 返回 `"ready"` → `doc.GraphStatus = "ready"`。**图里可能一条边都没有，但状态显示成功**。失败率、覆盖率类指标全部失真。
- 对照：`ExtractKnowledge` 的失败是**正确返回 error** 的（`kag.go:70-72`）。同一层里两个函数的错误语义不一致。

### 11.2 高：三元组补全（`complete.go`）未接线，且即便启用也会产生"孤儿边"

- 事实 A：全仓检索确认 `GapMine` / `CompleteGraph` **没有任何生产调用点**，只在本文件内定义。
- 事实 B：`CompleteGraph` 调的是 `k.IngestGraph(ctx, missing)`（`complete.go:42`）——即 **`docID = ""` 的版本**，走的是"**无来源归属**"分支（`kag.go:113-119`）。
- 后果：**即使将来启用补全，它补出来的关系也不带 `source_doc`**，于是：
  1. `DeleteBySourceDoc` 删不到它们 → 文档删除后，这些边成为**永久残留**；
  2. 它们不参与"按来源幂等"，重复补全会产生**真正的重复边**。
- 这是"已实现未接线"里危害最隐蔽的一条：**接线的时候如果不改这一行，就会引入数据清理不掉的残留**。

### 11.3 中：`:Entity(name)` 无索引，多跳检索是 N+1 + 全表扫

- 事实：全仓未见节点索引创建；`queryNeighbors`（`retrieve.go:217-220`）与 `matchEntity`（`:95`）都按 `{name: …}` 匹配。
- 叠加 §5.4 的三个因素（N+1、每实体新 session、无索引），图规模上升后检索延迟会明显恶化。
- 需实测：实体数到多少时单次图谱检索延迟超过 1 秒。

### 11.4 中：`source_doc` 索引只在启动时创建，运行期新关系类型永远无索引

见 §3.3。且 `CREATE INDEX` 的异步填充未被等待，"启动后立刻删除是否走索引"**未确认**。

### 11.5 中：白名单是提示词级软约束，schema 未被硬控制

见 §4.2。`CanonicalizeRelation` 不校验白名单，白名单外的关系原样入库。所以关系类型数量仍会缓慢增长——这直接放大了 §11.4 的索引缺口。

### 11.6 中：共享上下文闸门的"减字节、截 rune"口径不一致

见 §6.1。`remaining -= len(kbContext)` 按字节，`truncateChunk(kagResult, remaining)` 按 rune。中文场景下图谱上下文实际可达闸门的约 3 倍。**需实测**：构造"向量命中很多 + 图谱证据很长"的输入，检查最终注入字符数是否超 `max_context_chars`。

### 11.7 中：`IsContextRelevant` 用子串匹配 "no"，存在误判路径

见 §6.2。`not` / `know` / `unknown` / `cannot` 都含子串 "no"。误判方向是"把相关判成不相关"，属于**信息丢失**方向（比反向更危险）。

### 11.8 中：`extractMentions` 的 LLM 调用未纳入预算与指标

- 事实：`retrieve.go:73` 调 `k.llmClient.Generate(ctx, …)`，**未传 budget**。
- 后果：这次调用不计入 `task:process` 的 token/成本统计，也不受 `max_calls_per_task` 约束。也就是说，**图谱检索的这部分成本对任务级熔断不可见**。（下游 `IsContextRelevant` 是计量的，两者不一致。）

### 11.9 低：入图逐条事务，无批量

- 事实：`kag.go:103-143` 每个三元组一次 `ExecuteWrite`。10 条关系 = 10 次网络往返 + 10 次事务。
- 影响：离线建库可接受；文档量级上升后是明确的优化点（可用 `UNWIND` 一条 Cypher 批量 MERGE）。

### 11.10 低：孤立节点清理是全局操作，存在误删竞态

见 §6.4。低概率、低危害（MERGE 会重建），但严格说不是幂等安全的。

### 11.11 低：`matchBySubstring` 的 2000 实体上限无顺序保证

- 事实：`MATCH (n:Entity) RETURN n.name AS name LIMIT 2000`（`retrieve.go:125`）**没有 ORDER BY**。
- 后果：图内实体超 2000 时，兜底匹配只能看到"任意 2000 个"实体，行为不可复现。

### 11.12 未验证项

| 项 | 说明 |
|---|---|
| 图谱线端到端增益 | ✅ 有工具（`tools/graphrag_eval`、`tools/wikihop_eval`、`tools/wikihop_disambig`），❌ **无落盘报告** |
| 本体白名单校准效果 | 目标 ≤120 个规范关系；当前内置约 50 个，**未按业务语料校准** |
| `graphrag_eval` 内注释提到的"关系名大小写不一致" | 该注释针对**已被移除的 Text2Cypher 生成器**，是否仍适用需实测 |

## 13. 一页速记（面试/复盘用）

- **架构支柱**：**用"抽取侧白名单约束"替代"检索侧 LLM 生成查询"**，把不确定性从检索期前移到生产期；检索期退化成确定性 BFS。
- **四个最容易被追问的设计点**：
  1. 为什么放弃 Text2Cypher？——744 种关系类型下，抽取与检索两侧的关系名几乎必然不一致，查询恒空；且事后字符串归一化实测零收益（744→742）。
  2. 多跳怎么防"停在中转层"？——每条事实标 `hop=N`，让模型自己区分中间层与终点；`topN` 提前返回控制总量。
  3. 图谱检索返回空怎么办？——分两种情况：起点不在图里返回空；起点在图但无邻接事实返回**显式缺失提示**，让模型知道是"没抽出来"而不是"没这回事"。
  4. 图谱和向量谁优先？——不优先，**共享同一个 `max_context_chars` 预算**，向量先占，图谱用剩余额度。
- **四个必须说清的事实修正**：
  1. **白名单是软约束**（只注入 prompt，不做后置校验，白名单外的关系照单全收）；
  2. **入图失败被静默吞掉**，`graph_status=ready` 不代表图里真有边；
  3. **补全能力（`complete.go`）未接线**，且它调的是"无来源归属"的入图版本，一旦启用会产生清理不掉的残留边；
  4. **`:Entity(name)` 没有索引**，多跳检索是 N+1 查询 + Label Scan。
- **一条可量化的证据**：`tools/graphrag_eval` / `wikihop_eval` / `wikihop_disambig` 三个工具能在人工集与真实数据集上给出 RAG vs GraphRAG 的命中率对比——但目前**无落盘报告**，跑完请手动留档。
