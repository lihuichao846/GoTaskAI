## 0. 一句话总览

**向量线 = 把文档切碎、算成向量存进 Milvus，提问时再捞出最相关的碎片塞进提示词。**

它要同时解决两件互相拉扯的事：

1. **召回要准**：用户问"盘古怎么解决节点离线"，得命中那一段，而不是命中一堆含"节点"二字的无关段落。
2. **成本要控**：命中了 200 个片段也不能全塞给模型——上下文有长度上限，token 要花钱。

本项目的答案分别是：**稠密 + 稀疏双路召回再融合**（解决"准"），**重排 + 渐进式披露 + 总量闸门**（解决"省"）。

## 1. 这个模块解决什么问题

### 1.1 纯向量检索的三个坑

**坑一：专有名词与精确匹配失灵**

向量是按"语义相似"算的。用户问 `kb_chunks` 这个集合名、或问某个错误码 `1406`、或问人名"奥利维亚"，稠密向量很可能给出"语义相近但并非这个"的结果。这类**字面精确匹配**恰恰是关键词检索的强项。

**坑二：命中了但上下文被切断了**

文档被切成 500 字一块。如果答案横跨两块边界（比如"前半句在块 7、后半句在块 8"），只给块 7 给模型，模型就答不全。

**坑三：命中很多，但只能喂一部分**

`max_context_chars = 6000`。命中 20 个 800 字的片段就是 16000 字，超了一倍多。必须决定"给谁、给多少"。

### 1.2 本模块的四层解法

```
第 1 层【召回】  稠密(HNSW/COSINE) + 稀疏(BM25/IP) 各取 2×topK  → 覆盖语义与字面两种匹配
第 2 层【融合】  RRF（倒数排名融合）把两路排名合成一个排名        → 不用调权重，对分数尺度不敏感
第 3 层【重排】  云端 cross-encoder 对候选逐条精算相关度          → 从 9 条里挑出真正最相关的 3 条
第 4 层【注入】  摘要层 + 窗口扩展 + 按分分层截断 + 总量闸门      → 既补上下文，又不撑爆预算
```

  │                     │                              │─── 投递 ──────▶│ 5 doc.status=processing
  │                     │                              │                │ 6 摘要（LLM，失败不阻断）
  │                     │                              │                │ 7 递归切分 500/50 + 打 chunk_index
  │                     │                              │                │ 8 EmbedDocuments（批量）│
  │                     │                              │                │ 9 稀疏向量（BM25）
  │                     │                              │                │10 Insert + Flush ────▶│ Milvus
  │                     │                              │                │11 status=ready

**关键点**：
- **上传只落库 + 投递**，真正的切分与向量化在 Worker 里跑，所以接口能立刻返回 202。
- **摘要放在建库期生成**，而不是每次检索时现算——这样运行期零额外 LLM 调用。
- **摘要失败不阻断入库**（`pool.go:1052-1057`）：只是少了摘要层，命中层照样能用。

## 4. 核心机制逐个讲透

### 4.1 存储模型：一个 Collection，七个字段

`pkg/ragstore/schema.go:31-62` 建的 Milvus Collection（名字来自 `milvus.collection_name`，默认 `kb_chunks`）：

| 字段 | 类型 | 作用 |
|---|---|---|
| `chunk_id` | Int64，主键，AutoID | Milvus 自己生成 |
| `kb_id` | VarChar(128) | **多租户隔离键**：所有检索都带 `kb_id == "xxx"` 过滤 |
| `doc_id` | VarChar(128) | 归属文档，用于窗口扩展与按文档删除 |
| `chunk_index` | Int64 | 块在原文档中的**有序位置**，窗口扩展的依据 |
| `text` | VarChar(16384) | 块正文（远大于 500 字块长，留余量） |
| `dense` | FloatVector(1024) | 稠密语义向量 |
| `sparse` | SparseVector | BM25 稀疏向量 |

`WithAutoID(true)` + `shards=1`（`schema.go:33, 64`）。

**索引只有两个**（`schema.go:69-84`）：

| 索引 | 参数 | 说明 |
|---|---|---|
| 稠密 | `HNSW(COSINE, M=16, efConstruction=200)` | 建索引时 `efConstruction=200`；检索时 `ef=64`（`store.go:183`） |
| 稀疏 | `SPARSE_INVERTED_INDEX(IP, drop_ratio=0.0)` | 倒排索引 + 内积 |

> ⚠️ **`kb_id` / `doc_id` / `chunk_index` 都没有建标量索引**。它们只出现在过滤表达式里（`kb_id == "..."`、`doc_id == "..."`）。数据量小的时候感觉不到；数据量上来后，这两类过滤会退化成扫描。删除也是按表达式删（`DeleteByDocID`），同样受影响。

**"一个 Collection 装所有知识库"是刻意的取舍**：省去为每个知识库管理 collection 的复杂度，代价是隔离性靠 `kb_id` 过滤保证（不是物理隔离）。

### 4.2 双路召回：为什么要稠密 + 稀疏

**稠密路**（语义匹配）：

```go
denseVec, _ := s.embed.EmbedQuery(ctx, query)          // 调 DashScope 把问题变成 1024 维向量
denseSP, _  := entity.NewIndexHNSWSearchParam(64)      // 检索时搜索宽度 64
milvusclient.NewANNSearchRequest("dense", entity.COSINE, expr,
    []entity.Vector{entity.FloatVector(denseVec)}, denseSP, routeN)
```

**稀疏路**（字面匹配）：

```go
positions, values := s.buildQuerySparse(s.tokenize(query))  // gse 分词 → FNV-1a 哈希 → 权重 1.0
sparseSP, _ := entity.NewIndexSparseInvertedSearchParam(0.0)
milvusclient.NewANNSearchRequest("sparse", entity.IP, expr,
    []entity.Vector{sparseVec}, sparseSP, routeN)
```

两边**各取 2×topK 候选**（`routeN = topK * 2`，`store.go:187`），然后融合：

```go
results, err := s.client.HybridSearch(ctx, s.coll, nil, topK, outputFields,
    milvusclient.NewRRFReranker(), reqs)               // store.go:198
```

**为什么各取 2 倍再收敛**：融合是从两路里挑，候选池太小会导致"某一路的正确答案根本不在池子里"。2 倍是个经验值（配合下一层的 3 倍，最终候选池是 topK 的 6 倍量级）。

**RRF 是什么、为什么用它**：Reciprocal Rank Fusion = 对每个文档，把它在两路里的**排名倒数**相加（`Σ 1/(k+rank)`），按总分排序。它的好处是**只看排名、不看分数**——因为稠密的 COSINE 分数（0~1）和稀疏的 IP 分数（0~数十）根本不在一个量纲上，直接加权求和需要调参，用排名就绕开了这个问题。

### 4.3 BM25 是怎么在 Milvus 里实现的

这段是本模块最"巧"也最容易被误读的部分（`bm25.go`）。

**核心技巧：把"词"哈希成"稀疏向量的位置"**

```go
func tokenPos(token string) uint32 {
    h := fnv.New32a()
    _, _ = h.Write([]byte(token))
    return h.Sum32()          // 词元 → 32 位哈希值 → 稀疏向量的位置下标
}
```

于是"文档的稀疏向量"就是"该文档所有词的哈希位置 → 词权重"的映射；"查询的稀疏向量"就是"查询词的哈希位置 → 1.0"。两者做**内积**，就等于"查询词在文档中的加权出现次数"——也就是 BM25 的检索语义。索引端与查询端用同一个哈希函数，位置才对得上。

**文档侧权重**（`bm25TFWeight`，`bm25.go:62-74`）：

```
w(tf, dl, avgDL) = tf × (k1 + 1) / (tf + k1 × (1 - b + b × dl/avgDL))
其中 k1 = 1.2，b = 0.75
```

这是 BM25 的**词频饱和项**：一个词出现 1 次→3 次，权重涨得快；出现 20 次→22 次，几乎不涨（防"关键词堆砌"）。`dl/avgDL` 是文档长度归一化（长文档天然词多，要打折）。

**查询侧权重**（`buildQuerySparse`，`bm25.go:47-59`）：每个词等权 `1.0`。

**三个必须知道的局限**（这是简化实现，不是完整 BM25）：

| 局限 | 后果 |
|---|---|
| **没有 IDF 项** | 完整 BM25 = TF 饱和 × IDF。IDF 需要全库文档频次统计，这里没有做。所以"的""是"这类高频词和"奥利维亚"这类低频词权重相同，常见词会稀释检索信号 |
| **`avgDL` 是"当前批次"平均，不是全库平均** | `store.go:131-138` 在每次 `AddDocuments` 时按该批 chunk 计算平均词长。同一个文档在不同批次入库，其稀疏权重会不同；重建一个文档会改变同批其它文档的相对权重 |
| **FNV-1a 32 位哈希可能碰撞** | 两个不同词可能映射到同一位置、权重相加。概率低但非零；碰撞时检索结果会轻微失真 |

> 这三点不一定是 bug（这是用现成向量库实现关键词检索的常见工程取舍），但它们决定了：**稀疏路的作用是"补充精确匹配"，不能指望它等价于 Elasticsearch 的 BM25**。

### 4.4 写入与删除都强制刷盘：为了"写完立刻能查到"

```go
// AddDocuments 里（store.go:153-159）
if _, err := s.client.Insert(ctx, s.coll, "", cols...); err != nil { ... }
if err := s.client.Flush(ctx, s.coll, false); err != nil { ... }   // ★ 强制刷盘
```

```go
// deleteByExpr 里（store.go:334-342），注释点明了原因：
// Milvus 删除是异步的：不 Flush 时被删 chunk 仍可能被检索命中（幽灵召回，D1）。
func (s *Store) deleteByExpr(ctx context.Context, expr string) error {
    if err := s.client.Delete(ctx, s.coll, "", expr); err != nil { ... }
    return s.client.Flush(ctx, s.coll, false)                       // ★ 强制刷盘
}
```

**为什么必须这么做**：Milvus 的写入和删除都是"先记日志、后落段（segment）"的异步模型。不 Flush 的话：

- 刚上传的文档，用户立刻提问——**检索不到**（用户会以为上传失败）；
- 刚删掉的文档，**还能被检索命中**——这就是注释里说的"幽灵召回"，比"查不到"更危险，因为它在回答里引用了已删内容。

**代价是吞吐**：每次插入/删除都等一次 Flush，等于放弃了批量合并的机会。对这个项目（知识生产是低频离线动作）是可接受的；如果是高频写入场景，这个设计需要改（改成"写入不刷盘 + 检索端等待可见性"）。

### 4.5 检索全链路：从 topK 到最终注入，一共经过四次变形

这是最容易讲乱的地方，用一次具体检索把它钉死。假设配置为默认值：`rerank.top_n = 3`、`chunk_context_window = 1`、`max_chunk_chars = 800`、`rag_score_threshold = 0.5`、`max_context_chars = 6000`。

```
① 召回候选：rerank 启用 → retrieveK = max(3×3, 5) = 9
   retrieveTopDocs 请求 9 条                            pool.go:588-592

② Milvus 内部再放大：routeN = 2 × 9 = 18
   稠密取 18 条 + 稀疏取 18 条 → RRF 融合 → 返回 9 条    ragstore/store.go:187-198

③ 重排收敛：把 9 条文本整批发给 qwen3-rerank → 返回 3 条   rerank.go:56-118

④ 窗口扩展放大：3 条命中块，每条向前后各扩 1 块
   → 最多 3 × 3 = 9 条（按 doc_id:chunk_index 去重后）    pool.go:427-511

⑤ 注入截断：9 条按 Score 分层
   Score ≥ 0.5 → 每条最多 800 字
   Score < 0.5 → 每条最多 400 字
   总量闸门 6000 字，写满即停                            pool.go:328-334, 549-566
```

**注意第 ④ 步的一个细节**（`pool.go:506-507`）：扩展出来的邻居块，**Score 被强制设成命中块的分数**：

```go
// 邻居块与命中块统一沿用命中块 Score，保持同一分层截断口径。
c.Score = hitScore
```

为什么？如果不这么做，邻居块从 Milvus 查出来时是**没有 Score 的**（`GetChunksByDocID` 用的是 `Query` 不是 `Search`，见 `store.go:268`）。让它 Score=0 的话，第 ⑤ 步就会把它当低分块截成半量——而它明明是"命中块旁边的上下文"，不该被歧视。统一用命中块的分数，等于说"这块和命中块同等待遇"。

**第 ⑤ 步的"分层截断"逻辑**（`chunkByScore`，`pool.go:549-566`）：

```go
full := truncateChunk(doc.PageContent, cc.MaxChunkChars)   // 800
if doc.Score >= cc.RagScoreThreshold {                     // ≥ 0.5
    return full                                            // 高分块：给满 800
}
return truncateChunk(doc.PageContent, cc.MaxChunkChars/2)  // 低分块：只给 400
```

这是一个**"按相关度分配预算"**的策略：高分块值得给全文，低分块给一半意思一下，把省下来的字数留给后面的高分块。

> ⚠️ 但要注意 `normalizeScores` 是**批内 min-max 归一化**（`pool.go:527-547`）：最低分变 0、最高分变 1。所以"Score ≥ 0.5"意味着"排在这批结果的前半段"，而不是"绝对相关度够高"。另外当结果只有 1 条时函数直接返回、不归一化（`pool.go:529-531`），此时 Score 是原始的 RRF/重排分数——口径与多条时不同。

### 4.6 摘要层：用"建库期的一次性成本"换"运行期的零成本"

**问题**：如果每次提问都要先把命中的文档读一遍再让 LLM 总结，那每次提问至少多烧一次 LLM 调用，而且延迟翻倍。

**方案**：在建库时就把摘要算好，存在 `documents.summary` 列。运行期只查一次 MySQL：

```go
func (p *Pool) collectDocSummaries(docs []schema.Document) []string {   // pool.go:399
    // 1. 从命中结果里抽出 doc_id（去重、保持命中顺序）
    // 2. 一次批量查询 GetDocumentSummaries(docIDs) → map[docID]summary
    // 3. 按原顺序返回非空摘要
}
```

注入格式（`pool.go:341-349`）：

```
【产品手册 · 文档摘要】
- 本文介绍盘古系统的分布式存储架构，重点说明大文件分片与节点故障转移机制……
【产品手册 · 片段】
片段 1:
...
```

**"摘要层 + 片段层"两级注入的意义**：摘要让模型先知道"这份文档整体讲什么"，片段给出"具体依据"。如果摘要和问题无关，模型可以据此判断"这段上下文没用"（系统提示词里明确允许它忽略，`pool.go:817-823`）。

**为什么按 doc_id 去重**：3 条命中块可能来自同一份文档，这时候摘要只该出现一次。

### 4.7 存量兼容：B1 / B2 两条降级路径

`chunk_index` 是后加的字段。改造前建的 Collection 没有这一列，而 Milvus 不能直接给已有 Collection 加列。所以代码做了一次**能力探测 + 双路径降级**：

```go
// store.go:72-87
func (s *Store) detectChunkIndex(ctx context.Context) error {
    coll, _ := s.client.DescribeCollection(ctx, s.coll)
    for _, f := range coll.Schema.Fields {
        if f.Name == fieldChunkIndex { s.hasChunkIndex = true; break }
    }
}
```

有了这个标志，后面所有地方都按需分叉：

| 位置 | 有 `chunk_index`（B1 主路径） | 没有（B2 降级） |
|---|---|---|
| 写入（`store.go:150-152`） | 写入该列 | 不写该列 |
| 按文档取块（`store.go:263-265`） | `Query` 取回并按 index 排序 | 直接返回空切片 |
| 窗口扩展（`pool.go:450-474`） | 取相邻块扩展 | 若 `enable_parent_context=true` → 注入 `Document.Content` **全文**兜底 |

**B2 的兜底策略值得注意**：扩不了窗口，就把**整篇文档原文**塞进去（`pool.go:455-464`）。这看起来很奢侈，但逻辑是对的——既然无法定位"命中块周围是什么"，那把整个文档给模型，让它自己找。去重键是 `doc-full:<docID>`，同一文档只注入一次。

`enable_parent_context = false` 时的兜底更保守：直接注入原始命中块（等价改造前行为）。

### 4.8 重排：为什么要多花一次云端调用

```go
// pool.go:582-609
if p.reranker == nil {
    return p.ragStore.SimilaritySearch(ctx, query, kbID, topK)   // 没配重排：召回即结果
}
retrieveK := topK * 3
if retrieveK < 5 { retrieveK = 5 }
candidates, _ := p.ragStore.SimilaritySearch(ctx, query, kbID, retrieveK)
docs, err := p.reranker.Rerank(ctx, query, candidates, topK)
if err != nil {
    // ★ 重排失败不阻断：退回召回序前 topK
    if len(candidates) > topK { return candidates[:topK], nil }
    return candidates, nil
}
```

**为什么值这一次调用**：召回阶段（双路 + RRF）是**双塔模型**——问题和文档**分别**编码成向量，从没"看过"对方。RRF 只用了排名信息。而重排是 **cross-encoder**——把 `(问题, 文档)` 拼在一起送进模型，逐对精算相关度。精度显著更高，代价是慢且贵，所以只对**少量候选**做（这里是 9 条）。

**DashScope 重排的实现细节**（`rerank.go`）：

```go
type rerankRequest struct {
    Model     string   `json:"model"`       // "qwen3-rerank"
    Query     string   `json:"query"`
    Documents []string `json:"documents"`   // ★ 一次性提交全部候选
    TopN      int      `json:"top_n"`
}
```

- 一次性批量提交（`rerank.go:67-77`），**没有分批**；候选只有 9 条时没问题，若把 `top_n` 调大需要留意请求体体积。
- 超时 30 秒（`rerank.go:37`）。
- 非 200 时读前 4096 字节放进错误消息（`rerank.go:95-98`），方便排障。
- 返回值做**越界索引防御**（`rerank.go:107-109`）：`if r.Index < 0 || r.Index >= len(docs) { continue }`——上游返回的 index 不可信，必须校验，否则会 panic。

### 4.9 上传闸门：两道校验

`api/knowledge_base.go` 有两条上传路径，校验强度不同：

| | multipart（文件上传） | JSON（正文直传） |
|---|---|---|
| 体积校验 | ✅ `fh.Size > maxUploadSize(10MB)`（`:214`） | ❌ **只校验非空**（`:151-154`） |
| 类型校验 | ✅ `mimetype.Detect` + `isTextMime` 白名单（`:228-231`） | ❌ 无（本来就是 JSON 字符串） |
| BOM 处理 | ✅ 去 UTF-8 BOM（`:234`） | ❌ 无（BOM 会进正文） |

**文本类型白名单**（`isTextMime`，`:239-258`）：`text/*` 全部放行，加上 `application/json`、`xml`、`x-yaml`/`yaml`、`csv`、`javascript`、`x-httpd-php`、`rtf`，以及任何 `+json` / `+xml` 后缀。

> ⚠️ **JSON 直传分支没有体积闸门**，这是已知遗留（项目记忆里记过）。现在 `documents.content` 列是 `mediumtext`（16MB，`model/document.go:12`），所以 10MB~16MB 之间的正文能写进去；超过 16MB 会撞 MySQL 的 1406 报错（`STRICT_TRANS_TABLES` 下不静默截断）。multipart 路径因为有 10MB 闸门，反而更安全。

### 4.10 同步入库旁路：`/api/admin/rag/ingest`

除了走队列的正式链路，还有一个**同步**的管理接口（`api/rag.go:107-161`），在 API 进程内直接切分并写入 Milvus：

```go
// api/rag.go:122-127
doc := schema.Document{
    PageContent: req.Content,
    Metadata: map[string]any{"source": "web_upload"},   // ★ 只有 source，没有 kb_id / doc_id
}
```

**它和正式链路的三处差异**（都值得知道）：

| | 正式链路（`kb:build`） | 管理旁路（`/api/admin/rag/ingest`） |
|---|---|---|
| 落 MySQL 记录 | ✅ 有 `documents` 行 | ❌ 不写库 |
| 元数据 | `kb_id` + `doc_id` + `chunk_index` | 只有 `source`；`chunk_index` 有、`doc_id` 无 |
| 走队列 | ✅ 异步 | ❌ 同步（请求里等切分+向量化） |

后果：**这条旁路产出的 chunk 没有 `doc_id`**，落进 `default` 知识库（因为 `kb_id` 缺省）。检索到它时，`expandChunks` 里 `docID == ""` 分支会**原样注入不做扩窗**（`pool.go:436-441`）；删除也只能按 `kb_id = "default"` 整批删，无法按文档精确删。

它主要用途是**联调与冒烟测试**，不建议用于正式知识入库。另外注意：它挂在 `/api/admin` 下，**没有鉴权中间件**（见 M2/M7 文档的风险清单）。

### 4.11 为什么是 Milvus：选型答辩口径

> 这一节回答的是面试里最容易被追问的一类问题——"**为什么用这个中间件**"。它的位置放在 §4 末尾是有意的：前面讲的所有机制（双路召回、RRF、Flush）都依赖 Milvus 的特定能力，这一节说明**为什么当初只能这么选**。

#### （a）先说清楚一个事实：仓库里**没有**这个选型的留档

搜遍 `docs/`，**找不到任何"向量数据库选型对比"文档**。留档的只有上一代实现的叙述——那批旧文档（`docs/tech/rag_architecture_guide.md`、`rag_qna_record.md`）描述的是**用 LangChainGo 的 `redisvector` 把向量存 Redis**，并写着"未来将迁移到专门的向量数据库（如 Qdrant、Milvus 或 Chroma）……只需把 `redisvector.New` 换成 `qdrant.New`"。

注意两点：

1. 那里**首先提名的是 Qdrant**，不是 Milvus；
2. 当前代码**完全没用 LangChainGo**——是直接用 `milvusclient` 自己建 schema、自己写检索。

所以：**"从 Redis 迁走"的原因有留档（内存贵、容量受限），但"为什么落在 Milvus 而不是 Qdrant"没有留档。** 下文第（b）节是从代码依赖**反推**出来的技术理由，不是当时的决策记录。**这个区分必须主动说**——否则一被追问"当时的对比文档呢"就答不上来。

#### （b）硬证据：代码到底依赖了 Milvus 的哪些能力

最有力的是这一行（[store.go L186-198](file:///d:/Program%20Files/GoTaskAI/internal/pkg/ragstore/store.go#L186-L198)）：

```go
routeN := topK * 2
reqs := []*milvusclient.ANNSearchRequest{
    milvusclient.NewANNSearchRequest("dense", entity.COSINE, expr, ..., denseSP, routeN),
    milvusclient.NewANNSearchRequest("sparse", entity.IP, expr, ..., sparseSP, routeN),
}
results, err := s.client.HybridSearch(ctx, s.coll, nil, topK, outputFields,
    milvusclient.NewRRFReranker(), reqs)
```

这一行蕴含六项能力，**缺任何一项都得改架构**：

| 代码依赖 | 对应的 Milvus 能力 | 拿掉会怎样 |
|---|---|---|
| `"dense"` 与 `"sparse"` 在**同一个 collection** | 单 collection 多向量字段 | 要么存两份、要么两套库 |
| `FieldTypeSparseVector` + `NewIndexSparseInverted(IP, 0)`（[schema.go L59-83](file:///d:/Program%20Files/GoTaskAI/internal/pkg/ragstore/schema.go#L59-L83)） | **原生稀疏向量 + 倒排索引** | 得额外引一个 Elasticsearch 做关键词那路 |
| `HybridSearch` 一次请求跑两路 | 服务端混合检索 | 两次 RPC + 应用层合并 |
| `NewRRFReranker()` | **服务端 RRF 融合** | 自己实现 RRF，还要处理两路打分不可比 |
| 两路共用一个 `expr`（[L182](file:///d:/Program%20Files/GoTaskAI/internal/pkg/ragstore/store.go#L182) `filterExpr(kbID)`） | 标量过滤**下推到向量检索内** | 多知识库隔离得做两段式查询 |
| `outputFields`（text / kb_id / doc_id / chunk_index） | 标量字段随命中返回 | 每个命中回查一次库 → N+1 |

**一句话**：本模块要的不是"一个向量库"，而是"**一个能同时干稠密检索 + 稀疏检索 + 标量过滤 + 融合排序的库**"。

#### （c）业界通用对照（非本仓库留档，属通用技术事实）

| 能力 | Milvus | Qdrant | pgvector | FAISS |
|---|---|---|---|---|
| 稠密向量索引 | ✅ HNSW / IVF | ✅ HNSW | ✅ HNSW / IVF | ✅ 最全 |
| 稀疏向量**原生类型** | ✅ SparseVector + SPARSE_INVERTED_INDEX | ✅ sparse vectors | ❌（需另用全文索引另起一路） | ❌ |
| 单请求多路混合 + **服务端**融合 | ✅ HybridSearch + RRFReranker | ✅ prefetch + RRF / DBSF | ❌ 两条 SQL 手工融合 | ❌ |
| 标量过滤下推 | ✅ expr | ✅ filter | ✅ WHERE | ❌ |
| 独立服务 / 持久化 | ✅（存算分离：etcd + MinIO） | ✅ | ✅（随 PG） | ❌ 纯索引库 |
| 运维面 | 高（3 容器） | 中（1 容器） | 低（复用 PG） | 极低但功能最少 |

#### （d）代价（讲选型必须一起讲）

为了 Milvus，本模块**多背了三个容器**：

```
milvus:v2.4.4  ──依赖──▶  etcd:v3.5.5（元数据）  +  minio（对象存储）
```

外加三条实打实的摩擦（§4.4 已展开）：**删除非原子、必须 `Flush` 才不再被召回**；**默认一致性 `Bounded`**，写完不一定立刻可见；**schema 变更要重建 collection**（旧方案文档 §2.2 就写着"不改 Milvus schema、不重建 Collection"）。

还有一条**落地反差**值得主动交代：选型看中的是"能力齐备"，但落地时**并没有把性能特性用满**——

- `kb_id` / `doc_id` **没建标量索引**，而删除走 `DeleteByDocID`（按 doc_id 过滤）→ **删除即全扫**（§8.3）；
- 没用 partition / partition key 做多租户隔离，而是用 `kb_id` 标量字段 + `expr`。

**"能力够用是选它的理由，但没吃到它的性能红利是遗留问题"**——这两句话必须同时讲，否则就成了替选型打广告。

#### （e）一个必须澄清的误解：不是"只有 Milvus 能做混合检索"

如果面试官追问"那 Qdrant 不行吗"，**正确答案是"行"**。Qdrant 同样支持稀疏向量、`prefetch` 多路查询 + 服务端 RRF/DBSF 融合、payload 过滤。pgvector 也能做（稀疏那路要借全文索引另起一路，融合得自己写 SQL）；FAISS 是纯索引库，没有持久化、没有标量过滤、删除极难，做知识库要自己包一层。

所以真正立得住的选型理由只有三条，而且都很朴素：

1. **一次替掉两个组件**：稠密向量库 + 关键词检索引擎（否则要 Milvus/Qdrant + ES 两套）；
2. **融合与过滤都在库内完成**：应用层不用维护打分可比性、不用写两段式查询；
3. **存算分离、形态可退可进**：`milvus run standalone` 单机起（本项目就是这么部署的），将来数据长大可换 cluster **而不改应用代码**。

#### （f）可直接照说的答辩话术

> "我们需要的不是单一向量检索，而是**稠密 + 稀疏 + 标量过滤 + 融合排序在同一次请求内完成**。选 Milvus 是为了让这几件事收在一个 collection 里——否则得再引一个 Elasticsearch 做关键词那路，融合逻辑也得挪到应用层自己写。
>
> 代价我清楚：多了 etcd 和 minio 两个依赖，删除要 Flush 才生效，schema 变更要重建 collection。
>
> 而且**这不唯一**——Qdrant 也能做同样的事。我们选 Milvus 更多是成熟度和团队认知度的考量，如果数据规模只有几十万量级，pgvector 的性价比会更高。**另外我们现在有个已知短板**：`doc_id` / `kb_id` 没建标量索引，删除会全表扫，这是下一步要补的。"

最后这段"**承认不唯一 + 主动交代短板**"，比硬说"因为 Milvus 性能最好"要好得多——后者经不起追问，前者显示你真的权衡过。

> ⚠️ `Summary` 仍是 `text`（64KB 上限）；摘要一般远小于此，风险低。

### 5.3 两个状态机

```
KnowledgeBase.status:
   创建 ──▶ pending ──(上传文档)──▶ building ──(构建成功)──▶ ready
                                        │
                                        └──(失败)──▶ failed
   删除请求 ──▶ deleting ──(三层清理完成)──▶ 行被删除

Document.status（单文档，由 kb:build 驱动）:
   pending ──▶ processing ──▶ ready
                   │
                   └──▶ failed（ragStore 不可用 / 切分失败 / 向量写入失败）
   删除请求 ──▶ deleting ──(三段清理完成)──▶ 行被删除

Document.graph_status（图谱线，与上面独立）:
   pending ──▶ ready / failed / skipped
```

**`doc_count` 的增减都是原子表达式**（`manager.go:654-666`、`1000-1009`），避免并发构建同一知识库时读-改-写丢更新。重建场景用 `wasReady` 标志防止重复累加（`pool.go:1026, 1104-1108`）。

## 6. 依赖与协作

### 6.1 依赖的外部系统

| 依赖 | 用途 | 故障时行为 |
|---|---|---|
| **Milvus** | 向量存储与检索 | `ragstore.New` 失败 → Worker 里 `ragStore = nil` → `retrieveKnowledge` 直接返回空串；建库任务置 `failed` |

| **MySQL** | 知识库/文档元数据、摘要 | 启动即 Fatal |
| **DeepSeek** | 建库期生成摘要 | **降级**：摘要缺失，命中层照常可用 |

### 6.2 被谁使用

| 使用方 | 用途 |
|---|---|
| `worker` 的 `retrieveKnowledge` | 对话问答时注入知识（M2 场景一） |

### 6.3 与图谱线的关系（一句话）

同一个 `kb:build` 任务里，**先跑向量线（`pool.go:1060-1094`），再跑图谱线（`pool.go:1099`）**。图谱失败只写 `graph_status=failed`，**不回滚向量**（`pool.go:1117` 注释）。检索时两条线独立触发、独立判分，最后共享同一个 `max_context_chars` 闸门（`pool.go:836-845`）。

## 8. 已知缺陷与未验证项

> 全部基于代码事实并给出行号；标「需实测」的属于运行时行为推断。

### 8.1 中：切分参数在两处硬编码，存在漂移风险

- 事实：`worker/pool.go:1061-1062` 与 `api/rag.go:131-132` 各自写死 `ChunkSize = 500` / `ChunkOverlap = 50`。
- 后果：改一处的切分策略，另一条路径产出的块粒度会不一致——而块粒度直接决定窗口扩展的对齐效果（B1 依赖 `chunk_index` 与块长匹配）。且两条路径产物混在同一个 Collection 里。
- 建议方向（未实施）：抽成 `chunking` 常量或配置项，两处共用。

### 8.2 中：`queryexpand` 整包已实现但未接线

- 事实：全仓检索确认，`internal/pkg/queryexpand/*` 仅被 `tools/queryexpand_eval/main.go:18` 引用；`worker` 与 `ragstore` 均未 import。
- 后果：文档声称的"同义词 / 实体链接 / 语义改写 / 多模态扩展"四类召回增强**当前全部不生效**。检索链路上只有 `SimilaritySearch` 里的"原句 → 向量 + 分词"。
- 影响：这也是"知识库命中率"提升空间里最大的一块未落地能力。

### 8.3 中：Milvus 缺标量索引，过滤与删除全扫

- 事实：`schema.go` 只对 `dense` / `sparse` 建了索引；`kb_id`、`doc_id`、`chunk_index` 都没有。
- 后果：小库无感；数据量上来后，每次检索的 `kb_id == "..."` 过滤、以及按 `doc_id` 的删除/取块都会退化。
- 需实测：多大的数据量开始产生可观测劣化。

### 8.4 中：BM25 为简化实现（无 IDF + 批内 avgDL + 32 位哈希碰撞）

见 §4.3 的三点局限。其中 **`avgDL` 按批次计算**最需要注意：它使同一文档的稀疏权重依赖于"它和谁一起被写入"，导致检索结果不可复现地漂移。重建一份文档会轻微改变同批其它文档的排名。

### 8.5 中：JSON 直传分支无体积闸门

- 事实：`api/knowledge_base.go:145-157` 的 JSON 分支只校验 `Content != ""`；10MB 校验只在 `readUploadedFile`（multipart 专用）里。
- 后果：超过 `mediumtext` 上限（16MB）的正文会撞 MySQL Error 1406；10~16MB 之间能写进去但会把整篇正文存进 MySQL 并整篇切分。
- 项目记忆已记录此遗留（属于 create 路径，失败仅 500，不产生幽灵文档）。

### 8.6 中：`normalizeScores` 是批内相对归一化，跨批次不可比

- 事实：`pool.go:527-547` 做 min-max 到 [0,1]；且结果只有 1 条时**直接返回不归一化**（`pool.go:529-531`）。
- 后果：
  1. `rag_score_threshold = 0.5` 的真实含义是"排这批的前半段"，不是绝对相关度；
  2. 结果数为 1 时 Score 保留原始口径（RRF 分或重排分），与多条时口径不一致，`chunkByScore` 的判断会跳变；
  3. 同一问题在不同批次命中的结果，Score 不可横向比较。
- 需实测：单条命中时的截断行为是否符合预期。

### 8.7 低：管理旁路产物无 `doc_id`，无法参与窗口扩展与精确删除

见 §4.10。另外该接口**无鉴权**（`cmd/api/main.go:133-137`）。

### 8.8 低：EmbedDocuments 无分批

- 事实：`embedder.go:57-79` 把整批 `texts` 一次性放进 `Input`；`AddDocuments` 也是整批传入（`store.go:126`）。
- 后果：单文档块数多时，一次 embedding 请求体可能过大；无重试与退避。
- 需实测：多大文档会触发上游限流或超时。

### 8.9 低：`knowledge_base.type` 字段无实际分流

- 事实：`rag` / `kag` / `hybrid` 三个取值只被存储；检索时 `retrieveKnowledge` 不读 `Type`，是否走图谱只由 `kb.graph_enabled` 与 `decision.NeedKAG` 决定。
- 后果：把一个知识库标成 `kag` 并不会改变它的检索行为。属于"字段存在但语义未落地"。

### 8.10 未验证项

| 项 | 说明 |
|---|---|
| Milvus 一致性窗口 | 已用强制 Flush 规避，但 Flush 的等待边界未实测 |
| 双路召回 vs 单路的实际增益 | 无落盘报告；`tools/t2retrieval_eval` 可量化但未留档 |
| 重排的实际增益 | 同上 |
| 窗口扩展的实际增益 | 同上 |
| `docs/tech/知识库命中率修正-KAG改造实现说明.md` 中「修正后端到端 WikiHop 20 样本重测」 | 仍未执行 |

## 10. 一页速记（面试/复盘用）

- **架构支柱**：**稠密 + 稀疏双路召回 → RRF 融合 → cross-encoder 重排 → 渐进式披露注入**，全程受单一总量闸门约束。
- **四个最容易被追问的设计点**：
  1. 为什么不用纯向量？——字面精确匹配（专有名词、错误码）是稠密的弱项，稀疏路补上。
  2. RRF 相比加权求和好在哪？——只看排名，绕开两路分数尺度不可比的问题，无需调参。
  3. 为什么写删都要强制 Flush？——Milvus 异步落段；不 Flush 会"刚传的查不到、刚删的还能查到"（幽灵召回）。
  4. 邻居块的分数为什么复用命中块的？——扩窗块来自 Query 而非 Search，本身没有相似度分；统一分数才能享受同一分层截断待遇。
- **三个必须说清的事实修正**：
  1. **稀疏路不是完整 BM25**——没有 IDF 项，`avgDL` 按批计算，哈希用 32 位。
  2. **`kb_id`/`doc_id` 没有标量索引**——过滤与删除在数据量大时会退化。
  3. **查询扩展（同义词/实体/多模态）代码已写完但未接线**，当前检索链路上不生效。
- **一条可量化的证据**：`tools/t2retrieval_eval` 可在 C-MTEB T2Retrieval 上给出 recall@K / MRR@K / NDCG@K——但目前**无落盘报告**，这是本模块最大的"待补证据"。
- **一条选型答辩口径**（§4.11）：本模块要的**不是"一次向量检索"，而是"稠密 + 稀疏 + 标量过滤 + 融合排序在同一次请求内完成"**——`HybridSearch(ctx, coll, nil, topK, fields, NewRRFReranker(), reqs)` 这一行就是全部证据，否则得再引一个 Elasticsearch 做关键词那路、融合挪回应用层。代价：多 etcd + minio 两个依赖、删除要 `Flush` 才生效、schema 变更要重建 collection。**且「必须 Milvus」站不住**（Qdrant 同样能做，量小则 pgvector 更划算）；同时主动交代"`doc_id`/`kb_id` 无标量索引 → 删除全扫"这个短板。**注意：该选型在仓库里没有留档**，§4.11 的理由是从代码依赖反推的。
