## 0. 一句话总览

**对话 Agent = 把"每一轮用户输入"做成一个可重试的异步任务；"多轮对话"不是连接的状态，而是执行时从数据库读出来、临时拼给模型的一段历史。**

这句话里藏着本项目对话实现最关键的一个架构决策，值得先讲清楚，因为它决定后面所有设计。

---

## 1. 核心洞察：「对话」不是长连接，是任务流

### 1.1 两种对话实现的对比

主流做法是**连接有状态**：

```
WebSocket 长连接建立
  ├─ 服务端把历史消息 + 新消息一起发给模型
  ├─ 流式返回 token
  └─ 连接生命周期内维护对话数组
```

本项目走的是另一条路 —— **任务有状态，连接无状态**：

```
每一轮用户输入 = 一个独立的 Task 行
   Task.Payload  = 用户这一轮说的话
   Task.Result   = 助手这一轮的回答
   Task.ConversationID = 它属于哪个会话

「多轮对话」在执行时临时拼出来：
   新任务执行 → 查同会话的历史 completed 任务 → 转成 messages 数组 → 一起发给模型
```

### 1.2 这个选择的收益与代价

| | 收益 |
|---|---|
| **可恢复** | 每轮都是一行持久化记录。进程崩了、队列重试、用户刷新页面，上下文都不会丢 |
| **可审计** | 每轮任务都有 `RunLog` + `ToolCallLog` + token 计量（`TotalCalls`/`TotalTokensIn/Out`） |
| **可取消** | 取消就是改一行状态 + 广播事件，不需要维护长连接 |
| **天然异步** | 提交返回 `202`，前端靠 SSE 收结果，HTTP 请求不必挂着等模型 |
| **可水平扩展** | 无粘性会话需求，任何 worker 都能处理任何任务 |

| | 代价 |
|---|---|
| **上下文每次重建** | 历史必须序列化/反序列化，且要显式控制 token 预算 → 需要压缩机制 |
| **粒度是"轮"不是"消息"** | 一轮内部的过程（工具调用中间步骤）不进历史，模型看不到自己上一轮用过什么工具 |
| **无真流式** | 用户看到的是"整段答案落地"，不是逐字蹦出（见 §7.3） |

## 2. 数据模型：Task 兼职 Message

### 2.1 三张表的关系

```
conversations（会话）
  ID             = 会话 ID（兼容策略：复用历史的 session_id，见 §2.3）
  UserID         = 归属用户
  AgentID        = 绑定哪个 Agent（可空）
  Title          = 标题（首轮消息截取 30 字自动生成）
  Summary        = ★ 滚动摘要（压缩产物）
  SummaryCutoff  = ★ 摘要已覆盖到哪一轮（压缩游标）
  CreatedAt / UpdatedAt
        │
        │ 1 : N
        ▼
tasks（既是"任务"，也是"消息"）
  ConversationID = 属于哪个会话
  Payload        = 用户输入  → 组历史时映射为 role=user
  Result         = 助手回答  → 组历史时映射为 role=assistant
  Status         = ★ 只有 completed 的轮次才会进历史
  CreatedAt      = ★ 压缩游标的比较依据
```

**注意：没有独立的 `messages` 表**。`Task` 同时承担三种角色：队列单元、执行记录、对话消息。这是"任务流即对话"的直接结果。

### 2.2 为什么只有 `completed` 进历史

`GetConversationHistory` 的 WHERE 条件是：

```go
m.db.Where("(conversation_id = ? OR id = ?) AND status = ?",
    conversationID, conversationID, model.StatusCompleted)
```

只取 `completed`。三个原因：

1. **`failed` 不进**：错误信息（"抱歉，模型调用超时"）不是有效的对话内容，喂回给模型会污染上下文；
2. **`processing` / `pending` 不进**：正在跑的轮次还没有 `Result`，`taskToMessages` 会产出只有 user 没有 assistant 的残缺轮；
3. **`cancelled` 不进**：用户主动取消的轮次通常是被放弃的，不该影响后续推理。

> ⚠️ 但第 3 条有个体验副作用：**用户取消一轮后重新提问，模型不知道"刚才发生了什么"**。用户会觉得"它怎么忘了我说过的话"。这是"取消即丢弃"的代价，属于设计取舍而非 bug。

### 2.3 兼容策略：`Conversation.ID` 复用 `SessionID`

代码里到处都是这个双条件查询：

```go
"(conversation_id = ? OR id = ?)"     // manager.go:308, 327
```

以及这段回退：

```go
// pool.go:862-864
conversationID := t.ConversationID
if conversationID == "" {
    conversationID = t.SessionID   // 兼容旧数据：无 ConversationID 时回退 SessionID
}
```

**背景**：早期设计没有 `conversations` 表，会话只是 `Task.SessionID` 上一个字符串。后来引入会话模型时，为了**让老数据平滑可用**，采用了"**session_id 直接当 conversation_id 用**"的策略：

```go
// manager.go:773-789
func (m *TaskManager) GetOrCreateConversation(userID uint, agentID, sessionID string) (*model.Conversation, error) {
    if sessionID != "" {
        if conv, ok := m.GetConversation(sessionID); ok && conv.UserID == userID {
            return conv, nil             // 已存在 → 直接复用
        }
        conv := &model.Conversation{ ID: sessionID, ... }   // ★ 用 sessionID 当主键新建
        m.CreateConversation(conv)
        return conv, nil
    }
    conv := &model.Conversation{ ID: uuid.New().String(), ... }   // 没传 sessionID → 新建 UUID
    ...
}
```

所以历史查询必须写成 `(conversation_id = ? OR id = ?)`——`conversation_id` 匹配新数据，`id` 兜底匹配"老任务把会话 ID 存在 session_id 里"的情况。

**还有一个一次性迁移**（`cmd/api/main.go:85` 启动时执行）：

```go
// BackfillConversations 将历史任务的 SessionID 迁移为 Conversation 记录（幂等）。
if err := manager.BackfillConversations(); err != nil { ... }
```

它扫出所有 `session_id <> ''` 且 `conversation_id` 为空的任务，为每个补建会话行并回填 `conversation_id`。幂等（靠 WHERE 条件天然只处理未迁移的），所以每次启动都跑也安全。

> **教学点**：这种"新模型兼容旧数据"的迁移策略，核心是**让新字段的缺失有确定的回退语义**（`conversation_id` 为空 → 用 `session_id`），而不是强制一次性刷库。代价是**这个回退分支会长期留在热路径上**，读代码时必须知道它存在，否则会看不懂那些 `OR` 条件。

**三个细节**：

1. **`resolveConversationID` 吞掉错误**（`conversation.go:31-37`）：

```go
func resolveConversationID(manager *queue.TaskManager, userID uint, agentID, sessionID string) string {
    conv, err := manager.GetOrCreateConversation(userID, agentID, sessionID)
    if err != nil {
        return ""        // ★ 出错返回空串，不阻断提交
    }
    return conv.ID
}
```

这是**刻意的降级**：会话记录创建失败（比如 DB 抖动）不应该导致用户没法提问。返回空串后 `ConversationID` 为空，`loadConversationHistory` 里的回退逻辑会尝试用 `SessionID`——如果 `SessionID` 也为空，这次提问就**没有历史**（单轮问答），但**仍然能正常回答**。可用性优先于上下文完整性。

2. **标题生成是同步的、纯字符串操作**（`conversation.go:40-52`）：截前 30 个 rune、换行替换为空格、超长加 `...`。不调 LLM——标题生成如果调模型会让首轮提交多几百毫秒，得不偿失。

3. **`MaxRetry = 3` 硬编码**，不是配置项（对比 `llm.max_calls_per_task` 是可配的）。

## 4. 上下文组装：顺序就是成本

这是 M2 最需要讲清楚的一段代码（`pool.go:786-868`）。发往模型的 `messages` 是**五段拼接**的结果：

```go
// ① 基础 system prompt（用户自定义，或默认）
systemPrompt := t.SystemPrompt
if systemPrompt == "" {
    systemPrompt = "你是一个有用的 AI 助手。请尽力解答用户的问题或完成用户指定的任务。"
}

// ② 条件：强制联网搜索指令（仅在绑定了 internet_search 工具 且 非纯寒暄时注入）
if p.mcpClient != nil && decision.Intent != intent.IntentChat && hasToolName(tools, "internet_search") {
    systemPrompt += `\n\n[特别指示 - 联网工具强制使用规范]: ...`
}

// ③ 条件：知识库上下文（意图路由判定 NeedRAG 时）
var kbContext string
if decision.NeedRAG { kbContext = p.retrieveKnowledge(ctx, t) }
if kbContext != "" {
    systemPrompt += "\n\n[系统内部提供的本地知识库参考信息]: ...\n<knowledge_base_context>...</knowledge_base_context>"
}

// ④ 条件：图谱上下文（NeedKAG 且关联度过滤通过，且与 ③ 共享字数预算）
if p.kagManager != nil && decision.NeedKAG { ... systemPrompt += "...<knowledge_graph_context>...</knowledge_graph_context>" }

// ⑤ 历史 + 压缩（★ 传入的是"已经拼好的 systemPrompt"）
var historyMessages []openai.ChatCompletionMessage
if conversationID != "" {
    historyMessages = p.loadConversationHistory(ctx, conversationID, systemPrompt, t.Payload)
}

// ⑥ 真正发给模型：system(拼好的) + history + 当前 user
```

### 4.1 顺序为什么这样排

**system prompt 越靠前的内容，模型的注意力越强**（且很多供应商会做 prompt 缓存）。所以排序是**按"可信度 + 稳定性"降序**：

| 位置 | 内容 | 为什么在这 |
|---|---|---|
| 最前 | 用户自定义角色设定 | 决定模型的人格与回答风格，优先级最高 |
| 其次 | 强制联网指令 | 是**行为约束**（必须搜索、禁止抢答），必须比知识上下文更"硬" |
| 再次 | 知识库片段 | 是**参考材料**（prompt 里明说"如果无关请忽略"），属于软信息 |
| 最后 | 图谱关系 | 同样软信息，且比片段更"结构化、更易被误用"，所以放最后 |

**为什么知识上下文放在"历史"之前**：让它紧贴 system 区、远离对话区。如果把知识片段插在对话历史中间，模型容易把片段误当成"之前轮次说过的话"，从而搞错说话人。

### 4.2 一个容易忽略的耦合：知识上下文计入压缩阈值

```go
historyMessages = p.loadConversationHistory(ctx, conversationID, systemPrompt, t.Payload)
//                                                                  ↑ 已是拼好的完整 system
```

`loadConversationHistory` 内部做 token 估算时：

```go
used := llm.EstimateMessagesTokens(systemPrompt, hist, userPrompt)
```

所以**知识库注入的 6000 字（约 2000-3000 token）也算进"当前上下文占用"**。这个行为是对的（它确实占窗口），但带来一个耦合：**知识检索命中越多，越容易触发历史压缩**。极端情况下，一轮知识命中很多，会顺带把历史压掉。

## 5. 对话上下文自动压缩（重点）

这是 M2 最有技术含量的一块。设计目标：**让长会话不爆上下文窗口，同时把成本控制在 O(新增轮次) 而不是 O(全部轮次)**。

### 5.1 完整决策流程

```go
func (p *Pool) loadConversationHistory(ctx, conversationID, systemPrompt, userPrompt) []openai.ChatCompletionMessage {
    cc := config.AppConfig.Compress
    lc := config.AppConfig.LLM

    // ── 第一步：算阈值 ──
    threshold := int(float64(lc.ContextWindow) * lc.CompressThreshold)   // 131072 × 0.7 = 91750
    if lc.ContextWindow <= 0 || lc.CompressThreshold <= 0 {
        threshold = 0            // 未配置 → 永不压缩
    }

    // ── 第二步：配置缺省兜底 ──
    maxHistory := cc.MaxHistory;  if maxHistory <= 0 { maxHistory = 20 }
    keepRecent := cc.KeepRecent;  if keepRecent <= 0 { keepRecent = 6  }
    minTurns   := cc.MinTurns;    if minTurns   <= 0 { minTurns = keepRecent + 2 }

    // ── 第三步：读游标，加载历史 ──
    summary, cutoff := p.manager.GetConversationCompressState(conversationID)
    var turns []*model.Task
    if cc.Enabled {
        turns = p.manager.GetConversationHistorySince(conversationID, cutoff, maxHistory)  // 只取 cutoff 之后
    } else {
        turns = p.manager.GetConversationHistory(conversationID, maxHistory)
    }

    hist := buildHistory(summary, turns)     // [摘要 system 消息] + 最近原始轮次

    // ── 第四步：三层守卫，任一不满足就原样返回 ──
    if !cc.Enabled || threshold <= 0 { return hist }                        // 守卫①：开关/阈值
    used := llm.EstimateMessagesTokens(systemPrompt, hist, userPrompt)
    if used <= threshold { return hist }                                     // 守卫②：未超阈值
    if len(turns) <= keepRecent || len(turns) < minTurns { return hist }     // 守卫③：轮数不足

    // ── 第五步：切分并压缩 ──
    split := len(turns) - keepRecent
    toCompress := turns[:split]      // 最老的
    recent     := turns[split:]      // 最近 keepRecent 轮，永远保留原文

    var toCompressMsgs []openai.ChatCompletionMessage
    for _, t := range toCompress { toCompressMsgs = append(toCompressMsgs, taskToMessages(t)...) }

    metrics.CompressTotal.Inc()
    newSummary, err := p.llmClient.CompressHistory(ctx, "", summary, toCompressMsgs)
    if err != nil {
        metrics.CompressFailed.Inc()
        log.Printf("[Worker][ALERT] conversation compress failed, keeping full history: %v", err)
        return hist                  // ★ 降级：保留全量历史，任务照常跑
    }

    cutoffTime := toCompress[len(toCompress)-1].CreatedAt      // 游标 = 被压缩的最后一轮
    p.manager.SaveConversationSummary(conversationID, newSummary, &cutoffTime)

    log.Printf("[Worker] conversation %s compressed %d historic turns into summary", conversationID, len(toCompress))
    return buildHistory(newSummary, recent)
}
```

### 5.2 滚动摘要：为什么成本是 O(新增) 而不是 O(全部)

关键在 `CompressHistory` 的入参（`client.go:397-424`）：

```go
func (c *Client) CompressHistory(ctx, model string, summaryBase string, turns []openai.ChatCompletionMessage) (string, error) {
    b.WriteString("你是对话历史压缩助手。请把下面的对话内容浓缩成一段简洁、信息完整的摘要；")
    b.WriteString("必须保留：用户的核心目标与诉求、已确认的事实与结论、已完成的关键步骤、以及重要的数字/名称/日期。")
    b.WriteString("对于与主题无关的寒暄、重复内容可略去。\n")

    if strings.TrimSpace(summaryBase) != "" {
        b.WriteString("\n【之前的摘要】\n" + summaryBase + "\n")        // ★ 上一版摘要作为基底
    }
    if len(turns) > 0 {
        b.WriteString("\n【本次待压缩的对话】\n")
        for _, t := range turns { b.WriteString(fmt.Sprintf("%s: %s\n", t.Role, t.Content)) }
    }
    b.WriteString("\n请只输出更新后的摘要正文，不要任何解释、前缀或 markdown 代码块。")
    return c.generate(ctx, model, "", nil, b.String(), nil, nil)
}
```

**它做的是"合并"而不是"重新总结"**：把【上一版摘要】+【本次新增轮次】一起给 LLM，让它产出**新版摘要**。

于是总成本是：`摘要开销 ∝ Σ(每次新增的轮次)`，而不是"每次都把全部历史重读一遍"。第 100 轮时不会比第 10 轮贵 10 倍。这是**滚动摘要**相对"全量重算摘要"的核心优势。

### 5.3 游标机制：`SummaryCutoff` 怎么防止重复压缩

`SummaryCutoff` 记录**摘要已经覆盖到哪一轮**。三个地方配合：

| 环节 | 代码 | 作用 |
|---|---|---|
| 读取 | `GetConversationCompressState` → `(summary, cutoff)` | 拿到上次压到哪 |
| 加载 | `GetConversationHistorySince(conversationID, cutoff, maxHistory)` → `WHERE created_at > cutoff` | **只加载游标之后的新轮次** |
| 写入 | `cutoffTime := toCompress[len(toCompress)-1].CreatedAt` | 游标前移到本次压完的位置 |

**没有这个游标会怎样**：每次加载都会拿到"最近 20 轮"，其中已进摘要的轮次会**重复出现在摘要和原文里两遍**——模型看到重复内容，且每轮都会尝试把同一批轮次再压一次（摘要越压越乱、成本持续浪费）。

### 5.4 三个守卫的设计理由

| 守卫 | 条件 | 为什么需要 |
|---|---|---|
| ① 开关/阈值 | `!cc.Enabled \|\| threshold <= 0` | 允许一键关闭；且 `context_window` 没配时不能瞎猜 |
| ② token 预算 | `EstimateMessagesTokens(...) > threshold` | 这是**唯一的性能触发条件**。没超就不该花压缩调用 |
| ③ 轮数下限 | `len(turns) > keepRecent` 且 `len(turns) >= minTurns` | 见下 |

**守卫③ 的两个条件含义不同**：

- `len(turns) > keepRecent`：**能不能压**。如果轮数 ≤ 6，切分后 `toCompress` 为空，压了也没有"非最近"的内容可压，逻辑上不该动。
- `len(turns) >= minTurns`（默认 8）：**值不值得压**。压缩本身要花一次 LLM 调用 + 几秒延迟，而只压 2 轮省下的 token 抵不上这个成本。而且轮数太少时，被压缩的内容还很"新鲜"，有损摘要的性价比很低。

**`keepRecent`（默认 6）的语义**：**最近 6 轮永远保留原文**。因为对话的**最近上下文最关键**——指代（"它"、"那个"）、省略、语气都依赖它。把最近的内容变成有损摘要，会立刻导致"答非所问"。

### 5.5 为什么"压缩失败"要告警而不是静默（这段注释值得学）

```go
if err != nil {
    // 压缩失败属可告警信号：静默回退全量历史会放大后续 token 成本，需能被观测/告警。
    metrics.CompressFailed.Inc()
    log.Printf("[Worker][ALERT] conversation compress failed, keeping full history: %v", err)
    return hist
}
```

**这段注释体现了很好的工程判断**，值得展开：

- 压缩失败**不是任务失败**——历史照常给模型，回答照常产生。所以**不能**返回 error（否则用户看不到答案，只因为一个优化机制坏了）；
- 但它**必须被观测到**——因为失败的后果是"后续每轮都以全量历史发送"，token 成本持续放大，直到真的撞上窗口上限彻底失败；
- 所以落点是 **`ALERT` 日志 + `CompressFailed` 指标**，并且配套了 `CompressTotal` 来计算**失败率**（`metrics.go:62-69` 注释明确写了"CompressFailed / CompressTotal 即失败率"）。

**"降级但不静默"** —— 这是处理"非关键路径优化"失败的标准姿态：功能可以退，但退化的信号必须发出来。

### 5.6 token 估算为什么自己实现

```go
// EstimateTokens 估算一段文本的 token 数量（轻量、语言感知、无需外部依赖）。
// 中文/日文/韩文（CJK）按约每字 1 个 token；其余字符按每 4 字符约 1 个 token 估算。
// 该估算用于判断何时触发上下文压缩，不追求与真实 token 数完全一致。
func EstimateTokens(text string) int {
    cjk, other := 0, 0
    for _, r := range text {
        if isCJK(r) { cjk++ } else { other++ }
    }
    return cjk + (other+3)/4
}
```

**为什么不调 API 拿准确值**：

1. **不能为了判断"要不要省钱"而先花钱**——一次 token 计数调用本身就有延迟和成本，用它来决策压缩是悖论；
2. **必须同步且零延迟**——这个判断在每轮问答的热路径上；
3. **也不该引入 tokenizer 依赖**——`tiktoken` 之类需要额外依赖和模型文件，且不同厂商的分词策略不同，换来的是"看起来精确"。

**偏差方向是有意选的（高估）**：

| 内容 | 估算 | 真实（以 DeepSeek 类模型为例） | 偏差 |
|---|---|---|---|
| 中文 | 1 字 = 1 token | 约 0.6~0.7 token/字 | **高估 ~40%** |
| 英文 | 4 字符 = 1 token | 约 0.25~0.3 token/字符（≈3.3 字符/token） | 略高估 |

**高估是安全方向**：偏早触发压缩 → 多花一点摘要成本，但**不会撞上窗口上限**。反过来低估会真的超窗口 → 供应商返回 400 / 截断，任务失败。所以宁可贵一点，不可错一次。

## 6. SSE 回传链路

### 6.1 服务端（`StreamTasks`，`handler.go:357-408`）

```go
// ★ EventSource 不支持自定义 Header（如 Authorization），只能通过 URL 参数传 token
tokenStr := c.Query("token")
if tokenStr == "" { c.JSON(401, ...); return }
claims, err := jwt.ParseToken(tokenStr)
if err != nil { c.JSON(401, ...); return }
userID := claims.UserID

// SSE 必需的响应头
c.Writer.Header().Set("Content-Type", "text/event-stream")
c.Writer.Header().Set("Cache-Control", "no-cache")
c.Writer.Header().Set("Connection", "keep-alive")
c.Writer.Header().Set("Access-Control-Allow-Origin", "*")

// 订阅两类事件
ch := h.manager.Subscribe(userID);           defer h.manager.Unsubscribe(userID, ch)
toolCh := h.manager.SubscribeToolEvents(userID); defer h.manager.UnsubscribeToolEvents(userID, toolCh)

ctx := c.Request.Context()
for {
    select {
    case <-ctx.Done():
        return                                    // 客户端断开（关标签页）
    case task := <-ch:
        c.SSEvent("task_update", task); c.Writer.Flush()
    case ev := <-toolCh:
        c.SSEvent("tool_call", ev); c.Writer.Flush()
    }
}
```

**两个设计细节值得注意**：

1. **用 `c.Request.Context()` 而不是 `c.Writer.CloseNotify()`**（注释原文）：

> 用请求上下文取消而非已弃用的 `c.Writer.CloseNotify()`：后者在部分中间件包装后可能不可用，导致客户端断开时无法感知，造成订阅/goroutine 泄漏。

这是个真实的 Gin 踩坑：`CloseNotify` 已被弃用，且在响应被中间件包装（比如 gzip/日志中间件）后可能返回一个永不触发的 channel。一旦如此，**每个断开的连接都会留下一个永久阻塞的 goroutine + 一个永不释放的订阅**——慢速泄漏，很难排查。用请求上下文是标准解法。

2. **`defer Unsubscribe`** 保证退出时释放订阅。配合上面的 ctx 取消，泄漏的两个必要条件都被堵住。

### 6.2 前端（`App.vue:238-276`）

```js
function initTaskStream() {
  closeTaskStream()
  if (!authToken.value) return

  taskEventSource = createTaskStream(authToken.value)     // new EventSource('/api/tasks/stream?token=...')

  taskEventSource.addEventListener('task_update', (event) => {
    const updatedTask = JSON.parse(event.data)
    upsertTask(updatedTask)                               // 按 id 插入或替换
    if (updatedTask.agent_id === selectedAgentId.value) scrollChatToBottom()
  })

  taskEventSource.addEventListener('tool_call', (event) => {
    const ev = JSON.parse(event.data)
    toolEvents.value.push(ev)                             // 工具调用过程展示
    if (ev.agent_id === selectedAgentId.value) scrollChatToBottom()
  })

  taskEventSource.onerror = () => {                       // ★ 断线重连
    closeTaskStream()
    setTimeout(() => { if (authToken.value) initTaskStream() }, 3000)
  }
}
```

**`upsertTask` 是关键**：SSE 是**只推增量**的（推的是变化后的那个 task 对象），前端按 `id` 做"有则替换、无则插入"。所以**前端不依赖推送顺序**，`task_update` 重复到达也是幂等的——这和 M7 里讲的"终态保护"是同一个思想的客户端版本。

**`onerror` 的重连是必要的**：SSE 连接会被网关超时、网络切换、服务重启打断。`EventSource` 自带重连，但这里的 `onerror` 主动关掉再重建（3 秒后），相当于用更可控的方式处理（避免 EventSource 的原生重连退避把状态搞乱）。

### 6.3 ⚠️ token 走 URL 的安全代价

`EventSource` 不支持自定义 Header 是浏览器规范决定的（后来有了 Fetch-based SSE，但 `EventSource` 本身不行），所以只能 `?token=xxx`。代价：

| 风险 | 说明 |
|---|---|
| **接入日志泄露** | nginx / 网关的 access log 默认记录完整 URL（含 query），JWT 会明文落盘 |
| **浏览器历史 / 缓存** | 某些情况下 URL 会进历史记录 |
| **Referer 泄露** | SSE 请求一般不触发 Referer，但同源的其它请求可能带出 |
| **分享链接即泄露** | 用户复制 URL 给他人 = 给出凭证 |

**缓解方向**（未实施）：用一次性短期 ticket 换 token 连流（`POST /api/tasks/stream-ticket` 拿一个 30 秒有效的一次性 token，再 `?ticket=xxx` 连流），并在网关侧对 `/api/tasks/stream` 关闭 query 日志。

## 7. 中断与取消

### 7.1 取消三级链路（链路部分 M7 已详述，这里只讲与对话相关的语义）

```
用户点"停止"
  → POST /api/tasks/:id/cancel
  → 条件更新 MySQL（仅 pending/processing 可取消）
  → 广播 NATS global_task_cancel
  → 命中在途任务 → cancel() 中断进行中的模型调用
```

**对对话语义的影响**：取消后这轮的 `status = cancelled`，而**历史只加载 `completed`**（§2.2），所以这轮**不进后续上下文**。用户会觉得"它忘了我刚才说的"。这是设计取舍，但对体验有实际影响。

### 7.2 超时也是"取消"

```go
// pool.go:870-879
timeout := 2 * time.Minute
if s := config.AppConfig.LLM.TimeoutSeconds; s > 0 { timeout = time.Duration(s) * time.Second }

apiCtx, cancel := context.WithTimeout(ctx, timeout)     // 默认 120 秒
defer cancel()
p.registerInFlight(t.ID, cancel)                        // 登记，供取消指令命中
defer p.unregisterInFlight(t.ID)
```

**关键**：`apiCtx` 是**整个生成阶段**（含工具循环）的总超时，不是"每次模型调用"的超时。所以一个任务如果连续调 15 次工具（`max_calls_per_task`），总时间仍受 120 秒约束——**超时与调用次数是两个独立的上限，谁先到谁生效**。

这个 `cancel` 被登记进 `inFlight` 表，所以**用户取消和超时走的是同一条中断路径**（都是 `cancel()`）——一次中断，两个来源。

### 7.3 为什么"没有真流式"

模型返回的是完整结果，写回 `Task.Result` 后整个推给前端。所以用户看到的是**整段答案一次出现**，而不是逐字蹦。

原因就在 §1 的架构选择：**任务是有状态的，连接是无状态的**。要做真流式，需要"任务执行期间把 token 增量推给某个连接"——那就必然要维护"哪个连接在等哪个任务"的映射，也就回到了连接有状态的模型。

> **这是个诚实的设计边界**：当前实现用"无粘性、可恢复、可水平扩展"换掉了"逐字流式"。如果产品上必须逐字流式，改造点是：在 `generate` 回调里把增量 token 通过 `PublishToolEvent` 类似的通道推给前端，并新增一个 `task_delta` SSE 事件类型——但要注意这样一来"刷新页面后看到的内容"和"正在流式的内容"需要去重。

## 9. 已知缺陷与未验证项

### 9.1 高：`max_history` 会造成**静默的历史丢失**，且丢失部分永远不会进摘要

这是读代码推出来的、我认为最需要说清的一条。

**推理链**：

1. `GetConversationHistorySince(conversationID, cutoff, maxHistory)` 的 SQL 是
   `ORDER BY created_at desc LIMIT 20`，然后反转 → **取的是"cutoff 之后最近 20 轮"**；
2. 压缩只在**已加载的 `turns`** 上发生（`split := len(turns) - keepRecent`，切的是这 20 条）；
3. 压缩的**触发**依赖 `EstimateMessagesTokens` 超过 **91,750 token**；
4. 若某会话"轮数多但每轮很短"（例如 30 轮寒暄，每轮 50 token，合计 1,500 token），则：
   - 永远达不到 91,750 → **压缩永不触发**；
   - 每次只加载最近 20 轮 → **第 1~10 轮永远不出现在上下文里**；
   - 而这 10 轮**也不在 `Summary` 里**（因为没压过）。

**结论**：被 `max_history` 截掉的历史是**永久静默丢失**的——既不在原文窗口，也不在摘要，用户与模型都不会收到任何提示。表现就是"聊久了，模型忘了很早期的约定"。

**为什么"压缩阈值高 + max_history 小"这个组合特别容易踩到**：正常一轮对话约 100~500 token。要让 20 轮累计到 91,750 token，平均每轮需 **约 4,600 token**（相当于每轮都注入满额知识上下文 + 长回答）。**真实对话基本达不到**。所以默认配置下的实际行为是：

> **压缩机制几乎不生效，而 `max_history = 20` 的截断机制一直在生效。**

也就是说，这个精心设计的滚动摘要功能，在默认参数下**基本处于休眠状态**，而起作用的是一条静默截断。

**可复现验证**（见 §10.2）：连发 25 轮短消息，然后问第 1 轮的内容。
**修法方向**（未实施）：把"加载历史"从"固定条数"改成"按 token 预算贪心装载"（从最近往前装，装满预算为止），并给 `max_history` 一个远大于压缩阈值的值（比如 200），让"压缩"而不是"截断"来承担控窗职责。

### 9.2 高：压缩阈值与历史加载上限不匹配（同源问题）

见 §9.1。两个参数分别由不同模块读取（`llm.context_window × llm.compress_threshold` vs `compress.max_history`），**没有任何一致性校验**。把它们配成互相矛盾的值不会有任何警告。

### 9.3 中：压缩不使用 Agent 自己的模型与凭证

```go
// pool.go:705
newSummary, err := p.llmClient.CompressHistory(ctx, "", summary, toCompressMsgs)
//                                              ↑ model 传空
```

```go
// client.go:398-400
if model == "" { model = c.model }     // 回退到全局默认模型
...
return c.generate(ctx, model, "", nil, b.String(), nil, nil)   // 用全局默认 client / api_key
```

对比主生成路径（`pool.go:779-786`）：**Agent 可以配自己的 `api_key` / `base_url` / `model`**，主生成会优先用 Agent 的凭证。

但压缩**固定走全局默认模型与全局 api_key**。后果：

1. **凭证不一致**：Agent 配的是 A 厂商，摘要却发给 DeepSeek（全局默认）；
2. **潜在的数据流向违背预期**：如果某个 Agent 配私有/本地模型正是为了数据不外流，那么它的**对话内容仍会通过压缩发给全局厂商**——这是一个真实的合规风险点，且从配置上看不出来（配置里只有 Agent 的 model/api_key）。

**修法方向**：`loadConversationHistory` 需要拿到 agent 的凭证并透传给 `CompressHistory`。

### 9.4 中：SSE token 走 URL

见 §6.3。JWT 会进网关 access log，且 URL 可被分享即等同泄露凭证。

### 9.5 中：`SummaryCutoff` 用时间戳做游标，存在同刻边界问题

```go
query = query.Where("created_at > ?", *after)          // 严格大于
cutoffTime := toCompress[len(toCompress)-1].CreatedAt  // 游标 = 被压缩最后一轮的时间
```

用单一时间戳做游标有两个隐患：

1. **同一时刻创建的多轮**：若 `created_at` 精度是秒级，同一秒内的多个任务会被一起排除——**可能连带丢掉"本不该被压缩"的同刻轮次**；
2. **游标不是严格单调的**：它依赖"被压缩最后一轮的时间小于后续轮次时间"这个假设。若时钟回拨或多实例时钟不同步，可能出现"新轮次时间 < cutoff" → 该轮次**永久读不到**。

更稳的做法是用复合游标 `(created_at, id)`。是否需要修取决于 `created_at` 列的实际精度——**需实测**（`SHOW CREATE TABLE tasks` 看是否 `datetime(3)`）。

### 9.6 中：历史粒度为"任务"，工具调用过程不进历史

`taskToMessages` 只产出 `user: Payload` + `assistant: Result` 两条。一轮里如果发生了 5 次工具调用，这些中间步骤**不进历史**（它们只存在于 `ToolCallLog` 表和 SSE 的 `tool_call` 事件里）。

后果：模型在下一轮**不知道自己上一轮用过哪些工具、查到了什么**——只知道"我上一轮回答了什么"。对多轮工具型任务（比如"再查一下刚才那个"）会丢失关键线索。

### 9.7 低：取消/失败的轮次不进上下文

见 §2.2 / §7.1。属于设计取舍，但对"取消后重新提问"的体验有可感知影响。

### 9.8 低：`resolveConversationID` 静默吞错

`conversation.go:33-35` 出错返回空串，导致该轮**没有会话归属**（不写 `ConversationID`）。用户看到的是"回答正常，但翻历史看不到这轮"（取决于前端是否按会话过滤）。建议至少打一行日志便于排查。

### 9.9 低：`Summary` 列是 `longtext`，无长度上限

`model/conversation.go:13` 用 `type:longtext`（MySQL 上限 4GB）。滚动摘要理论上会随对话增长而累积（每次合并只增不减）。实际受 LLM 单次输出上限约束，风险低，但缺少"摘要超过 N 字符时二次压缩"的机制。

### 9.10 未验证项

| 项 | 说明 |
|---|---|
| 压缩在真实数据上是否触发过 | 按 §9.1 推导基本不会触发；**`CompressTotal` 指标的实际值需实测确认** |
| `created_at` 列精度 | 决定 §9.5 是否成立（秒级 vs 毫秒级） |
| 压缩的实际质量 | 摘要是否真的保住了"数字/名称/日期"（prompt 里要求了，但无评测） |
| 前端 `onerror` 重连的兜底能力 | 断网 3 秒后恢复是否真能续上、是否会丢事件（丢事件后前端靠什么补齐——看起来没有轮询兜底，**这可能是个真实缺口**） |
| 多 API 实例下的 SSE | 每实例都订阅 NATS 并推给自己本地连接，理论正确；未压测 |

## 11. 一页速记（面试/复盘用）

- **架构支柱**：**任务流即对话**。每轮输入是一个可重试的异步 Task；"多轮"在执行时从 DB 读出历史任务、临时拼成 messages；连接保持无状态，因此可恢复、可审计、可水平扩展。
- **四个最容易被追问的设计点**：
  1. 为什么不用 WebSocket 维护会话？——换取可恢复性、可重试、可审计、无粘性扩展；代价是上下文每轮重建（需压缩）和没有真流式。
  2. 长会话怎么不爆窗口？——**滚动摘要**：`Summary`（上一版摘要）+ 本次较早轮次 → 合并成新摘要；`SummaryCutoff` 游标保证已进摘要的轮次不再加载，成本是 O(新增轮次) 而非 O(全部)。
  3. 最近几轮为什么不压缩？——`keep_recent` 永远保留原文，因为指代、省略、语气都依赖最近的上下文，有损摘要会立刻导致答非所问。
  4. 压缩失败怎么办？——**降级但不静默**：保留全量历史继续回答（不返回 error），但打 `ALERT` 日志 + `CompressFailed` 指标，并配 `CompressTotal` 算失败率。因为失败的后果是 token 成本持续放大。
- **四个必须说清的事实修正**：
  1. **默认参数下压缩几乎不触发，起作用的是一条静默截断**：阈值 `131072 × 0.7 = 91,750` token，而 `max_history = 20` 轮。20 轮要凑到 91,750 token 需平均每轮 ~4,600 token——真实对话达不到。于是 `max_history` 直接截掉更早的轮次，**且被截掉的部分既不进摘要也不进上下文，永久丢失**。
  2. **压缩固定使用全局默认模型与凭证**：Agent 配了自己的 `api_key`/`base_url`/`model`，主生成会用，但**压缩不会**（`CompressHistory(ctx, "", ...)` 传空 model → 回退全局）。若 Agent 配私有模型是为了数据不外流，其对话内容仍会经压缩发给全局厂商。
  3. **历史粒度为"轮"，工具调用过程不进历史**：只映射 `Payload`(user) + `Result`(assistant)，模型下一轮不知道自己上一轮查过什么。
  4. **SSE 的 JWT 走 URL query**：`EventSource` 不支持自定义 Header，只能 `?token=xxx` → 会进网关 access log，且分享 URL 等于泄露凭证。
- **一条可量化的证据**：`compress_total` / `compress_failed` 两个指标 + `conversations.summary_cutoff` 字段，共同回答"压缩到底有没有发生"。按 §9.1 推导，默认配置下 `compress_total` 应长期为 0，而 `summary_cutoff` 长期为 NULL —— **这就是"截断而非压缩"的可观测证据**。
