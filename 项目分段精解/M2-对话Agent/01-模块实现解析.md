## 0. 一句话总览

**对话 Agent = 把"每一轮用户输入"做成一个可重试的异步任务；"多轮对话"不是连接的状态，而是执行时从数据库读出来、临时拼给模型的一段历史。**

这句话里藏着本项目对话实现最关键的一个架构决策，值得先讲清楚，因为它决定后面所有设计。

---

## 1. 核心洞察：「对话」不是长连接，是任务流

### 1.1 两种对话实现的对比

主流做法是**连接有状态**：

```
WebSocket 长连接建立
  ├─ 服务端把历史消息 + 新消息一起发给模型
  ├─ 流式返回 token
  └─ 连接生命周期内维护对话数组
```

本项目走的是另一条路 —— **任务有状态，连接无状态**：

```
每一轮用户输入 = 一个独立的 Task 行
   Task.Payload  = 用户这一轮说的话
   Task.Result   = 助手这一轮的回答
   Task.ConversationID = 它属于哪个会话

「多轮对话」在执行时临时拼出来：
   新任务执行 → 查同会话的历史 completed 任务 → 转成 messages 数组 → 一起发给模型
```

### 1.2 这个选择的收益与代价

| | 收益 |
|---|---|
| **可恢复** | 每轮都是一行持久化记录。进程崩了、队列重试、用户刷新页面，上下文都不会丢 |
| **可审计** | 每轮任务都有 `RunLog` + `ToolCallLog` + token 计量（`TotalCalls`/`TotalTokensIn/Out`） |
| **可取消** | 取消就是改一行状态 + 广播事件，不需要维护长连接 |
| **天然异步** | 提交返回 `202`，前端靠 SSE 收结果，HTTP 请求不必挂着等模型 |
| **可水平扩展** | 无粘性会话需求，任何 worker 都能处理任何任务 |

| | 代价 |
|---|---|
| **上下文每次重建** | 历史必须序列化/反序列化，且要显式控制 token 预算 → 需要压缩机制 |
| **粒度是"轮"不是"消息"** | 一轮内部的过程（工具调用中间步骤）不进历史，模型看不到自己上一轮用过什么工具 |
| **无真流式** | 用户看到的是"整段答案落地"，不是逐字蹦出（见 §9.3） |

## 2. 数据模型：Task 兼职 Message

### 2.1 三张表的关系

```
conversations（会话）
  ID             = 会话 ID（兼容策略：复用历史的 session_id，见 §2.3）
  UserID         = 归属用户
  AgentID        = 绑定哪个 Agent（可空）
  Title          = 标题（首轮消息截取 30 字自动生成）
  Summary        = ★ 滚动摘要（压缩产物）
  SummaryCutoff  = ★ 压缩游标：摘要已覆盖到【哪个时刻】的轮次，精度 datetime(3)
  CreatedAt / UpdatedAt
        │
        │ 1 : N
        ▼
tasks（既是"任务"，也是"消息"）
  ConversationID = 属于哪个会话
  Payload        = 用户输入  → 组历史时映射为 role=user
  Result         = 助手回答  → 组历史时映射为 role=assistant
  Status         = ★ 只有 completed 的轮次才会进历史
  CreatedAt      = ★ 压缩游标的比较依据（GORM 默认 datetime(3)）
```

**注意：没有独立的 `messages` 表**。`Task` 同时承担三种角色：队列单元、执行记录、对话消息。这是"任务流即对话"的直接结果。

> **游标精度为什么必须是毫秒**：`SummaryCutoff` 与 `tasks.created_at` 都是 `datetime(3)`。若游标用秒级 `datetime`，写入时会被**四舍五入**——例如某一轮的 `created_at = 10:00:00.700`，游标被舍成 `10:00:00`，下次加载用 `created_at > cutoff` 就把这一轮判为"已压缩"而**永久跳过**。这是"精度差一个量级 → 静默丢轮次"的典型案例。
>
> **另有一张跨会话的表不在本图中**：`user_memories`（用户向长期记忆）以 `user_id` 而非 `conversation_id` 为归属维度，见 §7。

### 2.2 为什么只有 `completed` 进历史

`GetConversationHistory` 的 WHERE 条件是：

```go
m.db.Where("(conversation_id = ? OR id = ?) AND status = ?",
    conversationID, conversationID, model.StatusCompleted)
```

只取 `completed`。三个原因：

1. **`failed` 不进**：错误信息（"抱歉，模型调用超时"）不是有效的对话内容，喂回给模型会污染上下文；
2. **`processing` / `pending` 不进**：正在跑的轮次还没有 `Result`，`taskToMessages` 会产出只有 user 没有 assistant 的残缺轮；
3. **`cancelled` 不进**：用户主动取消的轮次通常是被放弃的，不该影响后续推理。

> ⚠️ 但第 3 条有个体验副作用：**用户取消一轮后重新提问，模型不知道"刚才发生了什么"**。用户会觉得"它怎么忘了我说过的话"。这是"取消即丢弃"的代价，属于设计取舍而非 bug。

### 2.3 兼容策略：`Conversation.ID` 复用 `SessionID`

代码里到处都是这个双条件查询：

```go
"(conversation_id = ? OR id = ?)"     // manager.go: GetConversationHistory / GetConversationHistorySince
```

以及这段回退（`pool.go: handleTaskProcess` 内）：

```go
conversationID := t.ConversationID
if conversationID == "" {
    conversationID = t.SessionID   // 兼容旧数据：无 ConversationID 时回退 SessionID
}
```

**背景**：早期设计没有 `conversations` 表，会话只是 `Task.SessionID` 上一个字符串。后来引入会话模型时，为了**让老数据平滑可用**，采用了"**session_id 直接当 conversation_id 用**"的策略：

```go
// manager.go: GetOrCreateConversation
func (m *TaskManager) GetOrCreateConversation(userID uint, agentID, sessionID string) (*model.Conversation, error) {
    if sessionID != "" {
        if conv, ok := m.GetConversation(sessionID); ok && conv.UserID == userID {
            return conv, nil             // 已存在 → 直接复用
        }
        conv := &model.Conversation{ ID: sessionID, ... }   // ★ 用 sessionID 当主键新建
        m.CreateConversation(conv)
        return conv, nil
    }
    conv := &model.Conversation{ ID: uuid.New().String(), ... }   // 没传 sessionID → 新建 UUID
    ...
}
```

所以历史查询必须写成 `(conversation_id = ? OR id = ?)`——`conversation_id` 匹配新数据，`id` 兜底匹配"老任务把会话 ID 存在 session_id 里"的情况。

**还有一个一次性迁移**（`cmd/api/main.go:85` 启动时执行）：

```go
// BackfillConversations 将历史任务的 SessionID 迁移为 Conversation 记录（幂等）。
if err := manager.BackfillConversations(); err != nil { ... }
```

它扫出所有 `session_id <> ''` 且 `conversation_id` 为空的任务，为每个补建会话行并回填 `conversation_id`。幂等（靠 WHERE 条件天然只处理未迁移的），所以每次启动都跑也安全。

> **教学点**：这种"新模型兼容旧数据"的迁移策略，核心是**让新字段的缺失有确定的回退语义**（`conversation_id` 为空 → 用 `session_id`），而不是强制一次性刷库。代价是**这个回退分支会长期留在热路径上**，读代码时必须知道它存在，否则会看不懂那些 `OR` 条件。

### 3.2 提交接口（`SubmitTask`，`handler.go:138-188`）

```go
// 默认值兜底
if req.Priority == 0 { req.Priority = model.PriorityNormal }
```

**三个细节**：

1. **`resolveConversationID` 降级但不静默**（`conversation.go`）：

```go
func resolveConversationID(manager *queue.TaskManager, userID uint, agentID, sessionID string) string {
    conv, err := manager.GetOrCreateConversation(userID, agentID, sessionID)
    if err != nil {
        // ★ 补日志：原先这里是纯静默 return ""，出问题时无迹可寻
        log.Printf("[API][WARN] resolveConversationID failed (user=%d agent=%s session=%s): %v",
            userID, agentID, sessionID, err)
        return ""        // ★ 出错返回空串，不阻断提交
    }
    return conv.ID
}
```

这是**刻意的降级**：会话记录创建失败（比如 DB 抖动）不应该导致用户没法提问。返回空串后 `ConversationID` 为空，`handleTaskProcess` 里的回退逻辑会尝试用 `SessionID`——如果 `SessionID` 也为空，这次提问就**没有历史**（单轮问答），但**仍然能正常回答**。可用性优先于上下文完整性。

> **改造点**：返回值语义没变（仍然降级），但补了 `[API][WARN]` 日志。理由与压缩失败告警一致——**功能可以退，退化的信号必须发出来**。否则"这一轮没有会话归属"这种事实在日志里完全不可见，排查时只能靠猜。

2. **标题生成是同步的、纯字符串操作**（`conversation.go: generateTitle`）：截前 30 个 rune、换行替换为空格、超长加 `...`。不调 LLM——标题生成如果调模型会让首轮提交多几百毫秒，得不偿失。

3. **`MaxRetry = 3` 硬编码**，不是配置项（对比 `llm.max_calls_per_task` 是可配的）。

## 4. 上下文组装：顺序就是成本

这是 M2 最需要讲清楚的一段代码。发给模型的 `messages` 由 `generateWithClient` **固定拼成三段**：

```
messages = [ {role: system, content: systemPrompt} ]     ← ① 唯一一条 system
         + history                                       ← ② 历史（首条可能是滚动摘要）
         + [ {role: user, content: t.Payload} ]          ← ③ 当前问题
```

而 `systemPrompt` 本身是**多次累加**出来的，`history` 的首尾又分别挂着摘要与记忆召回块。所以真正喂给模型的是**六块内容**拼出来的：

| # | 内容 | 拼在哪 | 触发条件 |
|---|---|---|---|
| ① | 用户自定义角色设定（或默认人设） | systemPrompt | 总是 |
| ② | 强制联网搜索指令 | systemPrompt 尾 | 绑定了 `internet_search` 且意图非纯寒暄 |
| ③ | 知识库片段 `<knowledge_base_context>` | systemPrompt 尾 | 意图路由判定 `NeedRAG` |
| ④ | 图谱关系 `<knowledge_graph_context>` | systemPrompt 尾 | `NeedKAG` 且关联度过滤通过 |
| ⑤ | **长期记忆 · 用户偏好块** | systemPrompt 尾 | 记忆开启且该用户有偏好类记忆 |
| ⑥ | **长期记忆 · 相关召回块** | history 之后、user 之前（独立 system 消息） | 记忆开启且召回条与当前问题有**词面重叠** |
| — | 滚动摘要 | history 首条（独立 system 消息） | 该会话发生过压缩 |

代码骨架（`pool.go: handleTaskProcess`）：

```go
systemPrompt := t.SystemPrompt
if systemPrompt == "" { systemPrompt = "你是一个有用的 AI 助手。…" }

if p.mcpClient != nil && decision.Intent != intent.IntentChat && hasToolName(tools, "internet_search") {
    systemPrompt += "\n\n[特别指示 - 联网工具强制使用规范]: …"          // ②
}
var kbContext string
if decision.NeedRAG { kbContext = p.retrieveKnowledge(ctx, t) }
if kbContext != "" { systemPrompt += "…<knowledge_base_context>…<knowledge_base_context>" }  // ③
if p.kagManager != nil && decision.NeedKAG { … }                       // ④

// ★ 长期记忆：必须在【装载历史之前】装配——召回块要占用输入 token，
//   其用量要从装载预算里扣除，否则记忆会挤压历史装载额度。
memoryProfile, memoryRecall, memoryHitIDs := p.loadUserMemory(t)
memoryTokens := 0
if memoryRecall != "" { memoryTokens = llm.EstimateTokens(memoryRecall) }
if memoryProfile != "" { systemPrompt += "\n\n" + memoryProfile }      // ⑤

// ★ 超时 ctx 在这里派生：压缩会发起额外 LLM 调用，必须同样受超时与取消约束
apiCtx, cancel := context.WithTimeout(ctx, timeout)
p.registerInFlight(t.ID, cancel)

historyMessages = p.loadConversationHistory(apiCtx, conversationID, systemPrompt, t.Payload,
    cred, tools, memoryTokens, budget)                                 // 摘要 + 原始轮次
if memoryRecall != "" {                                                // ⑥
    historyMessages = append(historyMessages, openai.ChatCompletionMessage{
        Role: openai.ChatMessageRoleSystem, Content: memoryRecall,
    })
}
p.manager.TouchUserMemories(memoryHitIDs)                              // 命中计数（尽力而为）
```

### 4.1 顺序为什么这样排

**system prompt 越靠前的内容，模型注意力越强**（且很多供应商会做 prompt 缓存）。所以排序是**按"可信度 + 稳定性"降序**：

| 位置 | 内容 | 为什么在这 |
|---|---|---|
| 最前 | 用户自定义角色设定 | 决定模型的人格与回答风格，优先级最高 |
| 其次 | 强制联网指令 | 是**行为约束**（必须搜索、禁止抢答），必须比知识上下文更"硬" |
| 再次 | 知识库片段 | 是**参考材料**（prompt 里明说"如果无关请忽略"），属软信息 |
| 再再次 | 图谱关系 | 同样软，但更"结构化、更易被误用"，所以放最后 |
| 最后 | 记忆偏好块 | 与知识同为软信息，但它**对同一用户基本不变**，放尾部对前缀缓存的破坏最小 |

**为什么记忆召回块要"靠后"（history 之后、user 之前）**：

1. 它是**每轮都可能变**的内容（取决于当前问题）。若塞进 systemPrompt 尾部，会把前缀缓存彻底打散——而实测缓存命中价约为未命中价的 **1/120**（见 §6.2），自己把它毁掉不划算；
2. 项目里**已有先例**：滚动摘要就是以"独立 system 消息"的形式注入的，位置形态现成；
3. 放在 user 之前 = 紧贴当前问题，模型更容易把它当成"关于这个问题的背景"，而不是"很久以前说过的话"。

**为什么知识上下文放在"历史"之前而不是中间**：让它紧贴 system 区、远离对话区。如果插在对话历史中间，模型容易把片段误当成"之前轮次说过的话"，从而搞错说话人。

### 4.2 上下文里每一样东西都要"先扣预算"

改造后装载预算的算法（`loadBudgetTokens`）：

```go
budget := int(窗口 × budget_ratio)                        // 1_000_000 × 0.6 = 600_000
if budget > max_load_tokens { budget = max_load_tokens }  // ★ 封顶到 200_000
budget -= EstimateTokens(systemPrompt)                    // 含 ①②③④⑤：人设+联网+知识+图谱+记忆偏好
budget -= EstimateTokens(userPrompt)                      // 当前问题
budget -= EstimateTokens(summary)                         // 滚动摘要（它是一条 system 消息，确实占输入）
budget -= EstimateToolsTokens(tools)                      // 工具 schema（供应商计入输入，估算函数不覆盖它）
budget -= memoryTokens                                    // ⑥ 记忆召回块
budget -= output_reserve                                  // 给模型输出预留（思考模式下要覆盖思维链，见 §6）
```

**这正是原来那个隐式耦合的显式版本**：

- 旧实现是**事后判断**——先用固定 20 轮装载，再看总占用是否超过 `窗口 × 0.7`；于是"知识注入多了"会顺带把历史挤掉，且被挤掉的部分**不进摘要**（见 §11.1 对照表）。
- 新实现是**事前分配**——先把所有固定开销扣光，剩下的额度才用来贪心装载历史（从最近往前装）；装不下的走摘要压缩。

**扣减项的完整性直接决定正确性**：漏掉任何一项，"预算内"就不再等于"上下文内"。历史上就漏过 `summary` 与 tools schema 两项（当时预算只减了 system + user）。

## 5. 上下文自动压缩（重点）

这是 M2 最有技术含量的一块，也是 2026-09-20 这轮改造的核心。设计目标：**让长会话不爆上下文窗口，同时"装不下的旧轮次"是被压缩而不是被悄悄丢掉**。

### 5.0 改造前 vs 改造后（先看这张表）

| | 改造前 | 改造后 |
|---|---|---|
| **装载依据** | 固定条数（`max_history = 20`，同时是 SQL `LIMIT`） | **token 预算**（`min(窗口 × ratio, max_load_tokens)` 扣掉所有固定开销），从最近往前贪心装 |
| **触发判据** | `已装载消息的总 token > 窗口 × 0.7`（事后判断） | **真实溢出**：`COUNT(游标之后全部轮次) − 实际装载轮数` |
| **压缩取材** | 已加载的 20 条里"最早的一段" | 从游标处 **ASC 由旧向新** 分批推进 |
| **游标写入** | 无条件覆盖 | **CAS**：`WHERE summary_cutoff < ?`，`RowsAffected == 1` 才算生效 |
| **丢信息的性质** | 窗口外轮次**永久静默丢失**（既不进摘要也不进上下文） | **有界延迟**（登记在册、可观测、会被逐步压进摘要） |

### 5.1 完整决策流程

```go
func (p *Pool) loadConversationHistory(ctx, conversationID, systemPrompt, userPrompt,
    cred AgentCredential, tools []toolregistry.Tool, memoryTokens int, budget *llm.Budget) []openai.ChatCompletionMessage {

    cc, lc := config.AppConfig.Compress, config.AppConfig.LLM
    // 兜底：maxLoadTurns=200（仅防极端，不再是记忆边界）、keepRecent=6、minTurns=keepRecent+2
    summary, cutoff := p.manager.GetConversationCompressState(conversationID)

    // 压缩关闭 / 未配窗口 → 退化为"按安全上限装载"，不做压缩（等价改造前行为）
    if !cc.Enabled || lc.ContextWindow <= 0 {
        return buildHistory(summary, p.manager.GetConversationHistory(conversationID, maxLoadTurns))
    }

    // ── ① 真实溢出：COUNT 不受装载查询 LIMIT 的影响，能看到"窗口之外"还有多少轮 ──
    totalRemaining := int(p.manager.CountConversationHistorySince(conversationID, cutoff))
    recent := p.manager.GetConversationHistorySince(conversationID, cutoff, maxLoadTurns)

    // ── ② 预算内贪心装载（从最近往前装，keepRecent 是保底轮数） ──
    budgetTok := loadBudgetTokens(systemPrompt, userPrompt, summary, tools, memoryTokens, lc, cc)
    loaded, used := greedyLoad(recent, budgetTok, keepRecent)
    unloaded := totalRemaining - len(loaded)          // ★ 这才是"真实溢出"

    metrics.ContextTotalTurns.Observe(totalRemaining)
    metrics.ContextLoadedTurns.Observe(len(loaded))
    metrics.ContextUnloadedTurns.Observe(unloaded)
    metrics.ContextBudgetUsedRatio.Observe(used / budgetTok)

    if unloaded < minTurns {                           // 溢出很少：容忍不压
        return buildHistory(summary, loaded)
    }

    // ── ③ 由旧向新分批压缩，推进游标 ──
    newSummary, newCutoff, compressed, ok := p.compressForward(
        apiCtx, conversationID, cred, summary, cutoff, unloaded, minTurns, budget)
    if !ok || compressed == 0 {
        // 压缩没取得任何进展：本轮上下文缺少这 unloaded 轮（下次请求会重试）
        log.Printf("[Worker][ALERT] conversation %s compress made no progress, "+
            "this turn loses %d older turns from context", conversationID, unloaded)
        return buildHistory(summary, loaded)
    }

    // ── ④ CAS 写入：只有游标严格前进才生效 ──
    if !p.manager.SaveConversationSummaryCAS(conversationID, newSummary, newCutoff) {
        // 并发的另一轮已把游标推得更远 → 丢弃本次摘要，按最新状态重新装载
        s2, c2 := p.manager.GetConversationCompressState(conversationID)
        recent2 := p.manager.GetConversationHistorySince(conversationID, c2, maxLoadTurns)
        loaded2, _ := greedyLoad(recent2, loadBudgetTokens(systemPrompt, userPrompt, s2, tools, memoryTokens, lc, cc), keepRecent)
        return buildHistory(s2, loaded2)
    }

    // ── ⑤ 摘要变长后要按【新摘要】重算预算并重新装载 ──
    budgetTok2 := loadBudgetTokens(systemPrompt, userPrompt, newSummary, tools, memoryTokens, lc, cc)
    recent2 := p.manager.GetConversationHistorySince(conversationID, &newCutoff, maxLoadTurns)
    loaded2, _ := greedyLoad(recent2, budgetTok2, keepRecent)
    return buildHistory(newSummary, loaded2)
}
```

### 5.2 三个必须这样做的机制

#### (a) 为什么必须用 `COUNT` 而不是 `len(turns)`

旧实现的溢出判断是 `EstimateMessagesTokens(已装载的 20 条) > 阈值`——**它只能在"已经装进来的轮次"里判断**。窗口之外的轮次对这段代码**完全不可见**，于是永远不会被压缩，也就永久丢失。

```go
// 旧：溢出只在 SQL 窗口内可见
used := EstimateMessagesTokens(systemPrompt, hist, userPrompt)
if used <= threshold { return hist }        // ← 20 条之外的轮次在这里被无视

// 新：COUNT 独立的、不受 LIMIT 影响的查询
totalRemaining := COUNT(created_at > cutoff)   // 游标之后到底还有多少轮
unloaded := totalRemaining - len(loaded)       // 真实溢出
```

> **一句话**：`LIMIT` 决定"看得见多少"，`COUNT` 才能回答"还有多少"。用前者判断后者，必然漏掉窗口外的部分。

#### (b) 为什么压缩方向必须是"由旧向新"（ASC）

旧实现是在**已加载的轮次**里切"最早的一段"（`turns[:len-keepRecent]`）。而加载本身是 `ORDER BY created_at DESC LIMIT 20`——**压缩窗口永远在"最近 20 轮"内部滑动**，压完一批，下一轮又从这 20 轮里重新切。游标推不动，进度不累积。

新实现从**游标处**开始，按 ASC 取最旧的一批压缩，游标因此**单调前进**：

```
游标位置 ──►  [ 这批要压 ]  [ ... ] [ 最近 keepRecent 轮永远保留原文 ]
                     ↑ 压完把游标推到这批末尾
```

**代价（诚实）**：渐进压缩期会出现"中间空洞"——一个上万轮的会话不可能一次压完（受单批输入上限与单次运行批数上限约束），需要多轮请求逐步收敛。在收敛之前，中间那段轮次**不在上下文里**。但它是**有界延迟**而非永久丢失：它被 `unloaded` 计数、被指标观测、且会在后续请求中被继续压进摘要。

#### (c) 为什么游标写入必须 CAS

```go
// manager.go: SaveConversationSummaryCAS
res := m.db.Model(&model.Conversation{}).
    Where("id = ? AND (summary_cutoff IS NULL OR summary_cutoff < ?)", id, cutoff).
    Updates(map[string]any{"summary": summary, "summary_cutoff": cutoff, ...})
return res.RowsAffected == 1        // ★ GORM 影响 0 行不报错，必须用它判定
```

同一会话可能被并发处理（asynq 多协程 / 多 worker 子进程），而"读游标 → 压缩 → 写回"是典型的**读改写**。若无条件覆盖，后写者会覆盖先写者的摘要，且游标可能**倒退** → 已压缩轮次被重复压缩、进度丢失、摘要越压越乱。

`RowsAffected == 0` 的语义是"别人已经把游标推得更远了"——此时**丢弃本次摘要**、按最新状态重新装载，是正确的处理（而不是报错）。

### 5.3 装载：`greedyLoad` 与 `keepRecent` 的"最低保障"

```go
func greedyLoad(turns []*model.Task, budgetTok int, keepRecent int) ([]*model.Task, int) {
    // 从最近往前装，直到装不下为止
    for i := len(turns) - 1; i >= 0; i-- {
        cost := EstimateMessagesTokens("", taskToMessages(turns[i]), "")
        if used+cost > budgetTok && len(reversed) >= keepRecent {
            break                                   // 预算用尽，且已保住最近 keepRecent 轮
        }
        reversed = append(reversed, turns[i]); used += cost
    }
    // 反转为时间升序（大模型 prompt 的阅读顺序）
    // 硬容忍带：keepRecent 保底可能使装载量突破预算（例如最近几轮本身极长），
    // 超过 1.5 倍时从最旧的轮次开始裁剪，并打 WARN
}
```

**`keepRecent`（默认 6）的语义是"最低保障轮数"，不是"上限"**：

- 作为**装载保底**：即便预算被 system / 知识 / 图谱 / 记忆 / 工具 schema 吃光，也至少保留最近 6 轮——否则模型看不到直接上文；
- 作为**压缩保留**：压缩时最近 6 轮永远保留原文。因为对话的最近上下文最关键——指代（"它"、"那个"）、省略、语气都依赖它，变成有损摘要会立刻导致答非所问。

**这个设计有一个自带的矛盾**：保底轮数可能自己就把预算撑爆（比如最近几轮都是超长回答）。处理方式是"**硬容忍带**"：允许突破预算到 1.5 倍，超过才从最旧开始裁，并打 `WARN` 日志——即**优先保正确性（看得到上文），其次保预算**。

### 5.4 滚动摘要：为什么成本是 O(新增) 而不是 O(全部)

压缩入口是 `CompressHistoryAs`（`client.go`），提示词结构与"合并"语义如下：

```go
func (c *Client) CompressHistoryAs(ctx, apiKey, baseURL, model, summaryBase string,
    turns []openai.ChatCompletionMessage, budget *Budget) (string, error) {

    // 辅助调用：压缩只需提炼与合并，不需要推理 → 关闭思考模式（见 §6）
    ctx = auxThinkingCtx(ctx)

    b.WriteString("你是对话历史压缩助手。请把下面的对话内容浓缩成一段简洁、信息完整的摘要；")
    b.WriteString("必须保留：用户的核心目标与诉求、已确认的事实与结论、已完成的关键步骤、以及重要的数字/名称/日期。")
    if strings.TrimSpace(summaryBase) != "" {
        b.WriteString("\n【之前的摘要】\n" + summaryBase + "\n")        // ★ 上一版摘要作为基底
    }
    b.WriteString("\n【本次待压缩的对话】\n" + 本轮批次)
    b.WriteString("\n请只输出更新后的摘要正文，不要任何解释、前缀或 markdown 代码块。")

    return c.generateWithClient(ctx, client, model, "", nil, prompt, nil, nil, budget, nil)
}
```

**它做的是"合并"而不是"重新总结"**：把【上一版摘要】+【本次新增轮次】一起给 LLM，产出**新版摘要**。于是总成本 ∝ Σ(每次新增的轮次)，第 100 轮不会比第 10 轮贵 10 倍。

> **三个改造点**（原来这一块有三个问题）：
> 1. **走 Agent 自己的凭证**——`model/apiKey/baseURL` 由调用方从 Agent 配置透传（`AgentCredential`），而不是固定回退全局默认。原实现里"Agent 配了私有模型，但压缩仍把对话发给全局厂商"的合规漏洞已封（见 §11.1 对照表）。
> 2. **关思考模式**——压缩是提炼任务，开思考会白付一段思维链（同一问题上实测：开启 4943 输出 token、其中 4653 是 reasoning；关闭后 605）。
> 3. **独立预算 + 计量并入主账本**——压缩有自己的一次性调用上限（不占用任务的 `max_calls_per_task`），但它的 token 通过 `budget.AddUsage` 计入任务账本，避免 `CostUSD` 系统性低估。

### 5.5 分批压缩：三个上限 + 一次精简

`compressForward` 把"待压缩的全部轮次"分批处理，每批 = 一次 LLM 调用。三个上限缺一不可：

| 上限 | 默认 | 作用 | 缺了会怎样 |
|---|---|---|---|
| `max_compress_input_tokens` | 30000 | 单批请求的输入上限（含已有摘要与提示词模板） | **待压缩的全部轮次自己就可能超窗**，一次压完必然失败 → 所以必须分批 |
| `max_compress_turns` | 50 | 单批轮数上限 | 防止单批拼出超长输入 |
| `max_compress_rounds` | 10 | 单次任务运行内最多压几批 | 防止一次请求无限压缩，把单次任务拖垮 |

**单轮内容本身就超预算时的兜底**：`truncateMessages` 按 token 把该轮截断——否则极端长的一轮会把整批撑爆，使"单批输入上限"形同虚设。

**摘要自身的长度收敛**：`max_summary_tokens`（默认 3000）限制摘要长度。滚动摘要每次只增不减，长期会持续膨胀，所以超限时触发一次**精简**；如果精简后没有变短，就计 `SummaryCompressIneffective` 指标（说明该收敛判据没生效，需要人工介入）。

### 5.6 "压缩失败"与"压缩没进展"：降级但不静默（这段判断值得学）

```go
if !ok || compressed == 0 {
    // 压缩未取得任何进展：本轮上下文缺少这 unloaded 轮（下次请求会重试）
    log.Printf("[Worker][ALERT] conversation %s compress made no progress, "+
        "this turn loses %d older turns from context", conversationID, unloaded)
    return buildHistory(summary, loaded)
}
```

**这个判断的工程价值在于区分了三种"坏"**：

- **压缩失败**（LLM 调用出错）→ 不是任务失败。历史照常给模型、回答照常产生，所以**不能返回 error**（否则用户看不到答案，只因为一个优化机制坏了）；
- **压缩没进展**（跑完了但游标没动）→ 更隐蔽：任务看起来正常，但**上下文里那 unloaded 轮就是没有**。必须用 `ALERT` 把它显式说出来，否则"模型忘了早期约定"这类现象无从归因；
- **压缩没触发**（溢出 < `minTurns`）→ 正常容忍，不算异常。

落点是三种信号一起给：`ALERT` 日志 + `CompressFailed`/`CompressTotal`（失败率）+ `ContextUnloadedTurns`（溢出是否在收敛）。

> **"降级但不静默"** —— 这是处理"非关键路径优化"失败的标准姿态：功能可以退，但退化的信号必须发出来。同类做法在本项目里还有 `resolveConversationID` 补日志（§3.2）与 `IngestGraph` 失败计数（M4）。

### 5.7 token 估算为什么自己实现

```go
// EstimateTokens 估算一段文本的 token 数量（轻量、语言感知、无需外部依赖）。
// 中文/日文/韩文（CJK）按约每字 1 个 token；其余字符按每 4 字符约 1 个 token 估算。
func EstimateTokens(text string) int {
    cjk, other := 0, 0
    for _, r := range text {
        if isCJK(r) { cjk++ } else { other++ }
    }
    return cjk + (other+3)/4
}
```

**为什么不调 API 拿准确值**：

1. **不能为了判断"要不要省钱"而先花钱**——一次 token 计数调用本身就有延迟和成本，用它来决策压缩是悖论；
2. **必须同步且零延迟**——这个判断在每轮问答的热路径上；
3. **也不该引入 tokenizer 依赖**——`tiktoken` 之类需要额外依赖与模型文件，且不同厂商分词策略不同，换来的是"看起来精确"。

**偏差方向是有意选的（高估）**：

| 内容 | 估算 | 真实（DeepSeek 类） | 偏差 |
|---|---|---|---|
| 中文 | 1 字 = 1 token | 约 0.6~0.7 token/字 | **高估 ~40%** |
| 英文 | 4 字符 = 1 token | 约 3.3 字符/token | 略高估 |

**高估是安全方向**：偏早触发压缩 → 多花一点摘要成本，但不会撞窗口上限；低估会真的超窗 → 供应商 400 / 截断，任务失败。**宁可贵一点，不可错一次。**

改造后这套估算函数扩成了一族（都在 `client.go`）：

| 函数 | 用途 |
|---|---|
| `EstimateTokens(text)` | 单段文本 |
| `EstimateMessagesTokens(system, history, user)` | 按消息列表估算（每条附加 +4 的协议开销，工具消息更多） |
| `EstimateMessagesTokensRaw(messages)` | 直接对 `[]ChatCompletionMessage` 估算（**循环内**溢出校验用） |
| `EstimateToolsTokens(tools)` | 工具 schema 的估算——供应商会计入输入，但前两个函数**不覆盖它**，必须单独扣 |
| `TruncateToTokens(s, n)` | 按 token 截断（超长单轮兜底） |

**以及一道之前不存在的硬校验**：每次发请求前（含工具循环内的**后续**请求）都会校验

```go
inTok := EstimateMessagesTokensRaw(messages) + EstimateToolsTokens(tools)
if inTok + req.MaxTokens > window {
    return "", fmt.Errorf("%w: …", ErrContextOverflow)
}
```

它把"超窗"从"供应商报 400/静默截断"变成了**一个我们自己能识别、能降级处理**的错误——`handleTaskProcess` 捕获 `ErrContextOverflow` 后会用"收紧预算 + 去掉保底轮次"重新装载再试一次（并在重装时**保留记忆召回块**，见 §7.4）。

## 6. 思考模式：同一件事，按场景开关

### 6.1 事实：模型默认在"想"，而思维链要花钱

`deepseek-v4-pro` **默认开启思考模式**，且有两个容易被忽略的后果：

1. **思维链（reasoning）与正式回答共享同一份输出预算**——`max_tokens` 卡住时，思维链会先把预算吃光，正式回答变成**空字符串**；
2. **思考模式下 `temperature` / `top_p` 不生效**——采样参数在思考模式下形同虚设。

官方参数长相是 `{"thinking": {"type": "enabled" | "disabled"}}`（另有 `reasoning_effort`），**它不是 OpenAI 标准字段**。这决定了实现方式（§6.3）。

### 6.2 实测：开与不开差多少

同一道需要推理的题，走**本项目的 `Client → thinkingDoer → DeepSeek` 全链路**：

| 模式 | 耗时 | 输入 tok | 输出 tok | 回答字符 | 折算成本 |
|---|---|---|---|---|---|
| disabled | **3.2s** | 47 | 138 | 208 | ≈ $0.000136 |
| enabled | **64.8s**（另一轮同题 >150s 未返回） | 126 | 3690 | 456 | ≈ $0.00315 |

**结论：同题开启思考约 23 倍成本、20 倍以上时延**，换来更完整的回答。这是"质量换成本"的**显式取舍**，不是免费优化。

> **顺带测到的一个成本杠杆**：DeepSeek 的缓存命中价约为未命中价的 **1/120**（官方 0.025 : 3 元/百万）。这解释了两件事：为什么"保持提示前缀稳定"值得单独做；以及为什么 §4.1 要把"每轮都可能变"的记忆召回块放到 system prompt **之外**。

### 6.3 SDK 没有透传入口 → 在 HTTP 层注入

三层约束叠在一起：

1. go-openai 的 `ChatCompletionRequestExtensions` 只提供了 vLLM 的 `guided_choice`，**没有通用透传入口**；
2. `Config.HTTPClient` 在 v1.41.2 里是 `openai.HTTPDoer` **接口**（只有 `Do` 一个方法），**不能直接替换 `Transport`**；
3. 换 SDK 的代价远大于收益。

所以落点是在 `HTTPDoer` 这一层做包装：

```go
type thinkingDoer struct{ base openai.HTTPDoer }

func (d *thinkingDoer) Do(req *http.Request) (*http.Response, error) {
    req, err := injectThinking(req)      // 按 ctx 标记改写请求体
    if err != nil { return nil, err }
    return d.base.Do(req)
}
```

`injectThinking` 的**三条不变量**（都是"不做就出事"的类型）：

| 不变量 | 为什么 |
|---|---|
| 未标记的请求**完全透传** | 不改动任何既有调用行为；没配置思考模式就等于没有这层 |
| 非 `chat/completions` 路径透传 | embedding 请求也走同一个 client，不能把 `thinking` 塞进去 |
| 解析/序列化失败**原样发回** | 绝不因"注入失败"破坏请求本身——注入是增强，不是前置条件 |

**还有一条优先级规则：ctx 中已有标记时，不覆盖。** 因为调用链上存在"先标记者更具体"的情况——压缩摘要先把自己标成 `disabled`，随后要经过按"主对话"处理的 `generate` 入口；若入口处的配置（`thinking_mode: enabled`）覆盖了它，辅助调用就会被重新打开思考模式，白付一段思维链。

> 这条规则是本轮改造中**我自己引入又修掉的一个回归**：最初标记是布尔值（只表达"关闭"），改成"携带模式字符串"后就有了覆盖能力，行为随之变化。现在由 `TestApplyThinkingModePrecedence` 单测守住两个方向。

### 6.4 场景划分

| 场景 | 入口 | 开关 | 理由 |
|---|---|---|---|
| 主对话 | `GenerateWithToolsAndObserver(Sampling)` / `generate` | `llm.thinking_mode`（默认 enabled） | 需要推理质量 |
| 压缩摘要 | `CompressHistory` / `CompressHistoryAs` | `llm.thinking_aux_mode`（留空 = disabled） | 只需提炼与合并 |
| 相关性判定 | `IsContextRelevant` | 同上 | 只需 yes/no |
| 意图分类 | `ClassifyRetrieval` | 同上 | 只需分类标签 |
| 文档摘要 | `SummarizeText` | 同上 | 建库期批量作业 |
| 图谱抽取 | `GenerateWithBudget` | 同上 | 结构化 JSON 输出；思考既贵，又更易在 JSON 之外多输出解释性文字 |

**留空语义**：`thinking_mode` 留空 = 沿用供应商默认（即开启）；`thinking_aux_mode` 留空 = 按 `disabled` 处理（辅助调用不该有思考）。

### 6.5 连带修正：两个"静默失败"被修掉

实测把两个既有问题暴露出来了：

1. **`max_output_tokens: 4096` 会让复杂问题的回答为空**。实测 `max_tokens=2000` 时，2000 个 completion token 全部消耗在思维链上、**正式回答 0 字符**、`finish_reason=length`；不设置则同题正常产出（回答 1106 字符、`stop`）。→ 已改回**不设置**（`max_output_tokens: 0`），并保留 `output_reserve: 8192` 作为装载预算侧的预留。
2. **空回答原先会被当成成功**。`generateWithClient` 原来只要 `len(msg.ToolCalls) == 0` 就 `return msg.Content, nil`——于是 `content=""` 会被当成正常结果：任务置 `completed`、`Result` 为空，事后**无法区分"模型没答"与"答了空"**。现在在返回前显式拦截：

```go
if len(msg.ToolCalls) == 0 && strings.TrimSpace(msg.Content) == "" {
    finish := resp.Choices[0].FinishReason
    if finish == openai.FinishReasonLength {
        return "", fmt.Errorf("AI produced no answer: output budget exhausted (finish_reason=length); " +
            "reasoning tokens of thinking mode likely consumed the whole max_tokens")
    }
    return "", fmt.Errorf("AI returned empty content without tool calls (finish_reason=%s)", finish)
}
```

3. **`timeout_seconds` 从 120 提到 300**：它约束的是**整个任务运行**（含工具循环的多次调用与压缩调用），而思考模式下单次调用就可能 65~150s → 沿用 120s 时，带工具调用的任务必然超时。详见 §9.2。

## 7. 用户向长期记忆（Phase A）

> **状态**：Phase A 已实现，**默认关闭**（`memory.enabled: false`），DB 级实测待环境（见 §12.7）。

### 7.1 三种"记忆"的分工（先划清边界）

"RAG 不就是长期记忆吗"是最常见的混淆。准确的分工是：

| | 组织知识 | 会话内上下文 | **用户向长期记忆（本节）** |
|---|---|---|---|
| 存的是什么 | 关于**世界**的文档知识 | 这场对话里说过的话 | 关于**这个用户**的状态（偏好/事实/经历） |
| 存储 | Milvus `kb_chunks` + Neo4j | `conversations.summary` + `tasks` | MySQL `user_memories` |
| 写入方 | 离线文档管道（对话**不能写**） | 执行时自动生成 | 显式写入（Phase A）/ 离线抽取（Phase B） |
| 归属维度 | 知识库（属于用户/Agent） | 会话 | **用户**（跨会话） |
| 召回方式 | 语义相似（RAG）+ 图谱多跳（KAG） | 全量装载 + 摘要压缩 | 类型 + 词面重叠 |
| 注入位置 | systemPrompt 尾 | history | 偏好块进 system、召回块靠后 |

关键区别在于**写入权**：RAG 的写入是人工/离线的，对话内容进不去；而"记忆"的核心特征就是**由交互自动写入**。"Agent 记不住"的根因通常不是检索不到，而是**根本没地方写**。

### 7.2 表结构：双时间轴 + 一个"只容一条生效"的唯一键

```go
type UserMemory struct {
    ID      string
    UserID  uint   // 归属维度，也是隐私边界
    AgentID string // 空 = 该用户全局；非空 = 只在该 Agent 的对话里召回
    MemKey  string // 归一化的「主体::谓词」，如 preference::answer_style
    ActiveKey *string // 生效时 = MemKey；失效时 = NULL
    Type    string // semantic / preference / episodic / procedural
    Content string // varchar(1024)，与写入闸门 max_content_chars 同源
    Confidence float64
    Status  string // active / superseded / archived

    ValidFrom    time.Time  // ┐ 现实时间轴：事实何时为真
    ValidUntil   *time.Time // ┘
    SupersededAt *time.Time // ┐ 系统时间轴：系统何时认定它被取代
    CreatedAt    time.Time  // ┘

    SourceConversationID, SourceTaskID string // 溯源
    HitCount int; LastHitAt *time.Time
}
```

两个设计点值得单独说：

**(a) 冲突"关窗"而不是删除**。同 `MemKey` 写入新事实时，旧记录被置为 `status=superseded` + `valid_until=now` + `active_key=NULL`，**不删行**。于是"现在是什么"和"当时是什么"都能回答，这正是 Graphiti 双时间轴的核心思想（借鉴的是数据模型，不是它的框架）。

**(b) `ActiveKey *string` 是唯一键的核心技巧**：

```go
ActiveKey *string `gorm:"uniqueIndex:idx_mem_active,priority:3"`
// 组合唯一索引 = (user_id, agent_id, active_key)
```

- 生效时 `active_key = mem_key` → 同一用户/Agent/键**只能有一条生效记录**；
- 失效时置 **NULL** → MySQL 唯一索引**允许多个 NULL**，所以历史记录可以留任意多条。

**不能用空串代替 NULL**：空串会与其它失效行互相撞唯一键，第二条失效记录就写不进去了（与 `documents.source_path` 踩过的坑同源）。

### 7.3 召回语义：偏好无条件，事实看重叠

Phase A **没有向量检索**，选材靠两条规则：

| 块 | 类型 | 是否判断相关性 | 额度 |
|---|---|---|---|
| 偏好块 | `preference` | **不判断**——偏好对任何问题都成立 | `max_profile_tokens`（400） |
| 召回块 | `semantic` / `episodic` / `procedural` | **判断**：与当前问题的**词面重叠为 0 就丢弃** | `max_recall_tokens`（800）+ `max_recall_items`（8） |

**为什么必须有一道相关性判断**：没有它，召回就退化成"把这个用户所有记忆都塞进上下文"。而**注入无关记忆（记忆污染）比不注入更糟**——模型会把不相关的信息当成当前语境。

实现是一个可单测的纯函数 `memoryRelevance`：把文本切成**ASCII 词（长度 ≥2）+ CJK 二元组**，算去重后的命中比例，零重叠即 0 分。这不是好算法，但它零依赖、可解释，且**明确是 Phase C 语义召回要替换掉的东西**。

**排序**：DB 侧 `confidence desc, updated_at desc` 取候选 → 内存中按（相关性 → 置信度 → 更新时间）重排。

> **诚实短板**：候选由 DB 的 `LIMIT`（`max_items × 4`）先截断、再做相关性过滤，因此"高相关但低置信"的记忆可能进不了候选集。这也是 Phase C 引入向量召回的第一个动机。

### 7.4 注入位置与预算（与 §4 呼应）

- **偏好块** → 拼进 `systemPrompt` 尾部。它**对同一用户基本不变**，对前缀缓存的破坏最小；
- **召回块** → 作为一条**独立 system 消息**插在 `history` 之后、`user` 之前。它每轮都可能变，放 system 尾部会打散缓存；
- **两者都占用输入 token**，因此都必须参与装载预算扣减：偏好块通过 `EstimateTokens(systemPrompt)` **天然**被扣，召回块则把 `memoryTokens` 显式传进 `loadBudgetTokens`。

`memoryTokens` 在**全部 4 处**预算计算上都参与扣减：正常装载、压缩后的重装载、CAS 失败后的重装载、溢出收紧重试。**少任何一处，记忆就会挤掉历史装载额度**（等于把 §5 改造的收益吃掉）。这条约束由两条单测锁死。

**命中计数只记"按相关性召回的"**：`TouchUserMemories` 只收到召回块的 ID，偏好块不计。原因是偏好块无条件注入、每轮都会出现——把它算作命中，`hit_count` 会随轮次线性自增，这个字段就再也回答不了"这条记忆到底被用过几次"。

### 7.5 隐私契约：记忆必须 fail-closed（与 RAG 相反）

这是本模块**最不能出错**的一条，值得对照 RAG 讲：

| | RAG（`retrieveKnowledge`） | 记忆（`RecallUserMemories`） |
|---|---|---|
| 作用域 | 按 `kb_id` 过滤 | 按 `user_id`（+ 可选 `agent_id`）过滤 |
| 拿不到作用域时 | **回退公共知识检索**（`kb_id = "default"`） | **返回空 + 告警计数**（`fail_closed_total`） |
| 语义 | **fail-open**：公共知识本来就该共享 | **fail-closed**：宁可什么都不注入，也绝不回退到任何"公共"集合 |

原因很直白：**文档知识召回错了只是答案不准确；用户记忆召回错了是把张三的事安到李四头上**。所以：

- 所有记忆查询的作用域条件都由一个纯函数 `memoryScopeWhere(userID, agentID)` 构造，`userID == 0` 时直接返回 `ok=false`；这个函数存在的唯一目的，就是让"查询必带 `user_id`"这条契约**可以被单测直接断言**（漏掉 `user_id` 是这类代码最危险、也最难在联调中发现的一类 bug）；
- API 侧的归属校验与更新/删除写在**同一条 SQL 的 WHERE**（`id + user_id`）里，消除"先查后改"之间的越权窗口；
- **删除不受写入开关约束**——`memory.write_enabled: false` 只是不让人写，但用户的删除权不能被运维开关挡住。

### 7.6 API

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/memories` | 写一条（需 `write_enabled`）；同 `mem_key` 已有生效记录则**关窗旧记录**再插入 |
| GET | `/api/memories?agent_id=&status=&page=&page_size=` | 列出当前用户的记忆（默认只看 active） |
| PUT | `/api/memories/:id` | 改正文/`mem_key`（`mem_key` 冲突返回 409） |
| DELETE | `/api/memories/:id` | 删除一条（不受写入开关约束） |
| DELETE | `/api/memories` | 清空当前用户全部记忆 |

写入闸门（服务端）：内容非空 + 字符数 ≤ `max_content_chars` + `type` 在白名单内 + 条数未超 `per_user_limit`。

### 7.7 Phase A 的边界（诚实声明）

| 已做 | 未做（Phase B 起） |
|---|---|
| 显式写入 + 结构化召回 + 注入 + 预算扣减 | **自动抽取**（任务完成后离线抽取 + 闸门） |
| 双时间轴 + 取代关窗 + 幂等键 | **冲突消解的 LLM 四操作**（ADD/UPDATE/INVALIDATE/NOOP） |
| fail-closed 隐私契约 + 单元测试锁定 | 语义召回（新 Milvus collection + `memstore` 包） |
| 删除权 + 命中计数 + 4 个指标 | 生命周期（TTL 淘汰、条数上限淘汰到 `archived`、删除对账） |
| — | **Agent 经验记忆**（原料是 `RunLog`/`ToolCallLog`，零 LLM 的聚合统计） |
| — | 中文评测集（跨会话召回/知识更新/抗污染/隐私隔离） |

**已知的语义局限**：Phase A 的召回依赖词面重叠，因此"换个说法问同一件事"可能召回不到（例如记忆写"用户常用 Go"，问"我平时写代码用什么语言"）。这不是 bug 而是**没有向量检索的必然结果**，也是 Phase C 的立项理由。

## 8. SSE 回传链路

### 8.1 服务端（`StreamTasks`）

```go
// ★ EventSource 不支持自定义 Header（如 Authorization），只能通过 URL 参数传 token
tokenStr := c.Query("token")
if tokenStr == "" { c.JSON(401, ...); return }
claims, err := jwt.ParseToken(tokenStr)
if err != nil { c.JSON(401, ...); return }
userID := claims.UserID

// SSE 必需的响应头
c.Writer.Header().Set("Content-Type", "text/event-stream")
c.Writer.Header().Set("Cache-Control", "no-cache")
c.Writer.Header().Set("Connection", "keep-alive")
c.Writer.Header().Set("Access-Control-Allow-Origin", "*")

// 订阅两类事件
ch := h.manager.Subscribe(userID);           defer h.manager.Unsubscribe(userID, ch)
toolCh := h.manager.SubscribeToolEvents(userID); defer h.manager.UnsubscribeToolEvents(userID, toolCh)

ctx := c.Request.Context()
for {
    select {
    case <-ctx.Done():
        return                                    // 客户端断开（关标签页）
    case task := <-ch:
        c.SSEvent("task_update", task); c.Writer.Flush()
    case ev := <-toolCh:
        c.SSEvent("tool_call", ev); c.Writer.Flush()
    }
}
```

**两个设计细节值得注意**：

1. **用 `c.Request.Context()` 而不是 `c.Writer.CloseNotify()`**（注释原文）：

> 用请求上下文取消而非已弃用的 `c.Writer.CloseNotify()`：后者在部分中间件包装后可能不可用，导致客户端断开时无法感知，造成订阅/goroutine 泄漏。

这是个真实的 Gin 踩坑：`CloseNotify` 已被弃用，且在响应被中间件包装（比如 gzip/日志中间件）后可能返回一个永不触发的 channel。一旦如此，**每个断开的连接都会留下一个永久阻塞的 goroutine + 一个永不释放的订阅**——慢速泄漏，很难排查。用请求上下文是标准解法。

2. **`defer Unsubscribe`** 保证退出时释放订阅。配合上面的 ctx 取消，泄漏的两个必要条件都被堵住。

### 8.2 前端（`App.vue`）

```js
function initTaskStream() {
  closeTaskStream()
  if (!authToken.value) return

  taskEventSource = createTaskStream(authToken.value)     // new EventSource('/api/tasks/stream?token=...')

  taskEventSource.addEventListener('task_update', (event) => {
    const updatedTask = JSON.parse(event.data)
    upsertTask(updatedTask)                               // 按 id 插入或替换
    if (updatedTask.agent_id === selectedAgentId.value) scrollChatToBottom()
  })

  taskEventSource.addEventListener('tool_call', (event) => {
    const ev = JSON.parse(event.data)
    toolEvents.value.push(ev)                             // 工具调用过程展示
    if (ev.agent_id === selectedAgentId.value) scrollChatToBottom()
  })

  taskEventSource.onerror = () => {                       // ★ 断线重连
    closeTaskStream()
    setTimeout(() => { if (authToken.value) initTaskStream() }, 3000)
  }
}
```

**`upsertTask` 是关键**：SSE 是**只推增量**的（推的是变化后的那个 task 对象），前端按 `id` 做"有则替换、无则插入"。所以**前端不依赖推送顺序**，`task_update` 重复到达也是幂等的——这和 M7 里讲的"终态保护"是同一个思想的客户端版本。

**`onerror` 的重连是必要的**：SSE 连接会被网关超时、网络切换、服务重启打断。`EventSource` 自带重连，但这里的 `onerror` 主动关掉再重建（3 秒后），相当于用更可控的方式处理（避免 EventSource 的原生重连退避把状态搞乱）。

### 8.3 ⚠️ token 走 URL 的安全代价

`EventSource` 不支持自定义 Header 是浏览器规范决定的（后来有了 Fetch-based SSE，但 `EventSource` 本身不行），所以只能 `?token=xxx`。代价：

| 风险 | 说明 |
|---|---|
| **接入日志泄露** | nginx / 网关的 access log 默认记录完整 URL（含 query），JWT 会明文落盘 |
| **浏览器历史 / 缓存** | 某些情况下 URL 会进历史记录 |
| **Referer 泄露** | SSE 请求一般不触发 Referer，但同源的其它请求可能带出 |
| **分享链接即泄露** | 用户复制 URL 给他人 = 给出凭证 |

**缓解方向**（未实施）：用一次性短期 ticket 换 token 连流（`POST /api/tasks/stream-ticket` 拿一个 30 秒有效的一次性 token，再 `?ticket=xxx` 连流），并在网关侧对 `/api/tasks/stream` 关闭 query 日志。

## 9. 中断与取消

### 9.1 取消三级链路（链路部分 M7 已详述，这里只讲与对话相关的语义）

```
用户点"停止"
  → POST /api/tasks/:id/cancel
  → 条件更新 MySQL（仅 pending/processing 可取消）
  → 广播 NATS global_task_cancel
  → 命中在途任务 → cancel() 中断进行中的模型调用
```

**对对话语义的影响**：取消后这轮的 `status = cancelled`，而**历史只加载 `completed`**（§2.2），所以这轮**不进后续上下文**。用户会觉得"它忘了我刚才说的"。这是设计取舍，但对体验有实际影响。

> **与长期记忆的关系（值得注意）**：记忆的召回块**不受此影响**（它按 `user_id` 召回，与任务状态无关）；但如果 Phase B 的自动抽取挂在"任务完成"这个钩子上，那么**被取消的轮次里用户说过的话就不会被记住**。是否要改成"只要用户说了就抽"，需要在 Phase B 决策。

### 9.2 超时也是"取消"

```go
// pool.go: handleTaskProcess
timeout := 2 * time.Minute
if s := config.AppConfig.LLM.TimeoutSeconds; s > 0 { timeout = time.Duration(s) * time.Second }  // 当前 300s

// ★ 必须在【历史装载/压缩之前】创建（记忆召回之后）：压缩会发起额外 LLM 调用，
//   若在超时 ctx 之外执行，既不受超时约束、也不受取消指令影响
apiCtx, cancel := context.WithTimeout(ctx, timeout)
defer cancel()
p.registerInFlight(t.ID, cancel)                        // 登记，供取消指令命中
defer p.unregisterInFlight(t.ID)
```

**三个关键点**：

1. `apiCtx` 是**整个任务运行**（含工具循环与压缩调用）的总超时，**不是"每次模型调用"的超时**。一个任务如果连续调 15 次工具（`max_calls_per_task`），总时间仍受这个上限约束——**超时与调用次数是两个独立的上限，谁先到谁生效**。
2. **ctx 的创建位置在本轮改造中被前移了**：现在放在历史装载/压缩**之前**（记忆召回之后）。因为压缩会发起额外的 LLM 调用——若它在超时 ctx 之外执行，这段调用既不受超时约束、也不受取消指令影响（用户已点停止，压缩还在跑）。
3. `cancel` 被登记进 `inFlight`，所以**用户取消与超时走同一条中断路径**——一次中断，两个来源。

**为什么默认值从 120s 提到 300s**：思考模式下单次模型调用就可能 65~150s（§6.2 实测），而这里限制的是**整个运行**。沿用 120s 会让"带工具调用"或"触发压缩"的任务**必然超时失败**——注意这不是"慢一点"，而是任务直接失败。

### 9.3 为什么"没有真流式"

模型返回的是完整结果，写回 `Task.Result` 后整个推给前端。所以用户看到的是**整段答案一次出现**，而不是逐字蹦。

原因就在 §1 的架构选择：**任务是有状态的，连接是无状态的**。要做真流式，需要"任务执行期间把 token 增量推给某个连接"——那就必然要维护"哪个连接在等哪个任务"的映射，也就回到了连接有状态的模型。

> **这是个诚实的设计边界**：当前实现用"无粘性、可恢复、可水平扩展"换掉了"逐字流式"。如果产品上必须逐字流式，改造点是：在 `generate` 回调里把增量 token 通过 `PublishToolEvent` 类似的通道推给前端，并新增一个 `task_delta` SSE 事件类型——但要注意这样一来"刷新页面后看到的内容"和"正在流式的内容"需要去重。

## 11. 已知缺陷与未验证项

> 本节在 2026-09-20 做过一次**全面复核**。原来列为"高"的三条（静默截断、阈值与上限不匹配、压缩不用 Agent 凭证）**已经全部修掉**，所以拆成"已修复"与"仍存在"两节——否则读者会拿着已经过期的结论去判断系统。

### 11.1 已修复（保留记录，便于对照旧代码/旧文档）

| 原问题 | 现状 |
|---|---|
| **高**：`max_history = 20` 造成**静默的历史丢失**——被截掉的轮次既不进上下文也不进摘要 | **已修**：装载改为 token 预算驱动、用 `COUNT` 测真实溢出、压缩改由旧向新推进游标（§5.0 / §5.2）。被"装不下"的轮次现在是**有界延迟**，且被 `ContextUnloadedTurns` 观测 |
| **高**：压缩阈值（`窗口 × 0.7`）与加载上限（`max_history`）互相矛盾且无校验 | **已修**：不再存在两个各自为政的参数——装载额度由同一个 `loadBudgetTokens` 统一计算 |
| **中**：压缩**不使用 Agent 自己的模型与凭证**（Agent 配私有模型时，对话内容仍会经压缩发给全局厂商） | **已修**：`CompressHistoryAs` 透传 `AgentCredential`（§5.4） |
| **中**：`SummaryCutoff` 用秒级时间戳做游标，同刻轮次可能被跳过 | **已缓解**：`summary_cutoff` 明确为 `datetime(3)`。但 `tasks.created_at` 的**实际精度仍需实测**（§11.3） |
| **中**：知识上下文隐式计入压缩阈值，命中越多越容易挤掉历史 | **已修**：改为"事前扣预算"——知识/图谱/工具 schema/记忆/输出预留全部先扣，剩下的才是历史额度（§4.2） |
| **低**：`resolveConversationID` 静默吞错 | **已修**：补 `[API][WARN]` 日志（§3.2） |
| **低**：`Summary` 无长度上限、只增不减 | **已缓解**：`max_summary_tokens` 超限触发一次精简，并用 `SummaryCompressIneffective` 观测"精简是否真的变短" |
| **新增修复**：空回答被当成成功（任务 `completed` + `Result` 空，无从排查） | **已修**：返回前显式拦截并区分 `finish_reason`（§6.5） |

### 11.2 仍存在

#### 11.2.1 中：历史粒度为"轮"，工具调用过程不进历史

`taskToMessages` 只产出 `user: Payload` + `assistant: Result` 两条。一轮里如果发生了 5 次工具调用，这些中间步骤**不进历史**（它们只存在于 `ToolCallLog` 表和 SSE 的 `tool_call` 事件里）。

后果：模型在下一轮**不知道自己上一轮用过哪些工具、查到了什么**——只知道"我上一轮回答了什么"。对多轮工具型任务（比如"再查一下刚才那个"）会丢失关键线索。

> 这一条与 §7.7 列为 Phase B 待办的 **Agent 经验记忆**（利用 `ToolCallLog` 做统计）是**同一个数据源的两个不同用途**：一个是"让模型看到过程"，一个是"让它知道哪种做法更有效"。前者代价高（历史会膨胀），后者代价低。

#### 11.2.2 中：SSE token 走 URL

见 §8.3。JWT 会进网关 access log，且 URL 可被分享即等同泄露凭证。

#### 11.2.3 低：取消/失败的轮次不进上下文

见 §2.2 / §9.1。属于设计取舍，但对"取消后重新提问"的体验有可感知影响。

#### 11.2.4 低：渐进压缩期存在"中间空洞"

这不是新缺陷，而是新机制的**固有代价**：上万轮的会话无法一次压完（受单批输入上限与单次运行批数上限约束），收敛之前，中间那段轮次确实不在上下文里。

与旧问题的本质差别：**它被计数（`unloaded`）、被观测（`ContextUnloadedTurns`）、且会在后续请求中被继续压进摘要**——是"有界延迟"而不是"永久丢失"。但仍需注意：**长期不收敛**（unloaded 长期不下降）说明压缩能力不足，应告警。

#### 11.2.5 低：记忆召回依赖词面重叠（Phase A 的局限）

见 §7.3。换个说法问同一件事可能召回不到；候选集还被 DB 的 `LIMIT` 先行截断。

#### 11.2.6 低：并发压缩会重复劳动

`COUNT → 压缩 → CAS` 之间，多个 worker 可能同时压同一段（CAS 只保证**写入**只有一个胜出，不保证**不做重复的 LLM 调用**）。代价是偶发的重复摘要成本，不损害正确性。彻底解决需要分布式锁或"预占游标"，属 Phase B 之后的优化。

### 11.3 未验证项（诚实声明）

| 项 | 说明 |
|---|---|
| `tasks.created_at` 与 `conversations.summary_cutoff` 的**实际列精度** | `SHOW CREATE TABLE` 确认是否都是 `datetime(3)`；以及 `AutoMigrate` 能否把已有列从 `datetime` 改成 `datetime(3)`（MySQL 上属类型变更，可能重建表） |

| 并发 CAS 是否生效 | 需同会话并发提交后轮询 `summary_cutoff` 是否**单调不减** |

### 12.2 核心判据 A2：装不下的轮次**是被压缩，还是被丢掉**

这是本次改造的**核心判据**——比"能不能答出早期内容"更能区分机制。造一个"轮数多、总量不小"的会话：旧实现下压缩几乎不触发（因为触发条件与装载窗口错配）而轮次被静默截断；新实现下它**会因为预算装不下而推进压缩游标**。

```bash
# 连发 30 轮较长消息（每轮 300+ 字），第 1 轮埋一个特殊数字
for i in $(seq 1 30); do
  curl -s -X POST http://localhost:8080/api/tasks/submit \
    -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
    -d "{\"session_id\":\"m2-verify-2\",\"payload\":\"第 $i 句：请记住这一段……（此处 300+ 字）\"}"
  sleep 8
done

# 第 31 轮：追问第 1 轮埋的数字
curl -s -X POST http://localhost:8080/api/tasks/submit \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"session_id":"m2-verify-2","payload":"我最开始让你记的那个数字是多少？"}'
```

**期望**：

| 检查点 | 期望 | 说明 |
|---|---|---|
| `conversations.summary_cutoff` | **非 NULL 且随每轮前进** | 压缩真的在推进游标（不是 NULL，也不是原地不动） |
| `LENGTH(summary)` | 非 0 | 摘要真的被写入 |
| `context_unloaded_turns` | **单调下降** | 溢出在被逐步压进摘要——"有界延迟"的直接证据 |
| 第 31 轮回答 | 能答出第 1 轮的数字 | 端到端有效 |
| worker 日志 | 出现 `compressed N older turns into summary` | 与指标一致 |

```sql
SELECT LENGTH(summary) AS summary_len, summary_cutoff FROM conversations WHERE id = 'm2-verify-2';
```

```bash
curl -s http://localhost:9100/metrics | grep -E \
  'context_total_turns|context_loaded_turns|context_unloaded_turns|context_budget_used_ratio|context_compress'
```

**怎么读这个结果**：

- `summary_cutoff` 长期 NULL 且 `context_unloaded_turns` 长期 >0 → **压缩没生效**，上下文里长期缺着那一段（这正是旧实现的行为，可用来判断改造是否真的落地）；
- 日志出现 `compress made no progress` → 触发了压缩但游标没前进，去查压缩调用是否失败、CAS 的 `RowsAffected` 是否为 0。这条 `ALERT` 就是为"任务看起来正常、但上下文缺内容"这种隐蔽情况准备的。

### 12.3 强制触发压缩（快速验证压缩链路本身是通的）

把**装载预算**压到极小，让"装不下"必然发生：

```yaml
# config/config.yaml
compress:
  budget_ratio: 0.5
  max_load_tokens: 800     # ★ 装载预算封到 800 token —— 两轮稍长的对话就装不下
  keep_recent: 2           # 保留少一点，让切分容易发生
  min_turns: 3             # 溢出门槛降低
```

> 注意：现在**没有"压缩阈值"这个配置**了——触发条件是"预算装不下"，而不是"占用超过窗口比例"。所以强制触发的方式是**调小装载预算**（`max_load_tokens`），而不是调阈值。

重启 worker，然后发 6~8 轮稍长的对话（每轮几百字）。

## 13. 一页速记（面试/复盘用）

- **架构支柱**：**任务流即对话**。每轮输入是一个可重试的异步 Task；"多轮"在执行时从 DB 读出历史任务、临时拼成 messages；连接保持无状态，因此可恢复、可审计、可水平扩展。

- **四个最容易被追问的设计点**：
  1. 为什么不用 WebSocket 维护会话？——换取可恢复性、可重试、可审计、无粘性扩展；代价是上下文每轮重建（需压缩）和没有真流式。
  2. 长会话怎么不爆窗口？——**token 预算装载 + 滚动摘要**：先用 `min(窗口×比例, 上限)` 扣掉所有固定开销得到装载额度，从最近往前贪心装；装不下的旧轮次按 **由旧向新** 压成摘要，`summary_cutoff` 游标单调前移，成本是 O(新增轮次) 而非 O(全部)。
  3. 最近几轮为什么不压缩？——`keep_recent` 既是**最低保障轮数**也是压缩保留量：指代、省略、语气都依赖最近的上下文，有损摘要会立刻导致答非所问。
  4. 压缩失败怎么办？——**降级但不静默**：保留现有历史继续回答（不返回 error），但打 `ALERT` 日志 + `CompressFailed` / `ContextUnloadedTurns` 指标。因为失败的后果是"上下文缺内容"或"token 成本持续放大"，两者都必须可见。

- **本轮改造的三个机制级要点**（最能体现工程判断的部分）：
  1. **判据要能看见窗口之外**——旧实现用 `EstimateMessagesTokens(已装载的 N 条)` 判断溢出，只能在 SQL 窗口内自证；换成 `COUNT(游标之后全部轮次)` 才看得见"还有多少"。**`LIMIT` 决定看得见多少，`COUNT` 才能回答还有多少。**
  2. **压缩方向决定进度是否累积**——在 `DESC LIMIT` 的装载结果里切"最早一段"，压缩窗口永远在同一区间滑动；改成从游标处 **ASC** 推进，游标才会单调前进。
  3. **游标写入必须 CAS**——`WHERE summary_cutoff < ?` + `RowsAffected == 1`。否则并发写会让游标**倒退**，已压轮次被重复压缩、摘要越压越乱。

- **五个必须说清的事实**（前两条是本轮**修掉**的历史缺陷，讲的时候要说清"改造前是什么、现在是什么"）：
  1. ~~默认参数下压缩几乎不触发，起作用的是一条静默截断~~ → **已修**：装载改预算驱动、溢出改 `COUNT` 判定、压缩改 ASC 推进。装不下的轮次现在是**有界延迟**（被计数、被观测、会被逐步压进摘要），不再是永久丢失。**代价**：渐进压缩期存在"中间空洞"，需要多轮请求收敛。
  2. ~~压缩固定使用全局默认模型与凭证~~ → **已修**：`CompressHistoryAs` 透传 Agent 自己的 `api_key/base_url/model`，并关闭思考模式、把压缩的 token 通过 `AddUsage` 计入任务账本。
  3. **历史粒度为"轮"，工具调用过程不进历史**：只映射 `Payload`(user) + `Result`(assistant)，模型下一轮不知道自己上一轮查过什么。
  4. **SSE 的 JWT 走 URL query**：`EventSource` 不支持自定义 Header，只能 `?token=xxx` → 会进网关 access log，且分享 URL 等于泄露凭证。
  5. **思考模式下"省钱"的最大杠杆不在输入而在输出**：同题开启思考约 **23 倍成本、20 倍以上时延**（实测 3.2s/138 tok vs 64.8s/3690 tok），且思维链会吃掉 `max_tokens` 导致**正式回答为空**。所以"按场景关思考（辅助调用全关、主对话可配）+ 不显式设 `max_tokens` + `output_reserve` 覆盖思维链"是三条必须一起做的措施。

- **三条可量化的证据**：
  1. `context_total_turns` / `context_loaded_turns` / `context_unloaded_turns` 共同回答"有没有丢轮次"——**`unloaded` 长期不下降即为告警信号**；
  2. `context_compress_total` / `context_compress_failed` + `conversations.summary_cutoff` 共同回答"压缩有没有发生、游标有没有前进"；
  3. `memory_recall_fail_closed_total` 是记忆的**安全阀读数，应恒为 0**——一旦 >0，说明调用链丢了用户身份（fail-closed 被触发），属必须立刻排查的信号。
