## 0. 先对齐：两种视角的关系

| | 功能模块视角（本文档） | 技术分层视角（99 号附录） |
|---|---|---|
| 回答的问题 | 系统**能做什么**、用户怎么用 | 代码**怎么组织**、改动落在哪 |
| 划分单位 | 业务能力（如"知识库 RAG 与 KAG"） | 技术层（如"接口层、编排层"） |
| 适合谁 | 产品理解、面试讲架构、新人熟悉系统 | 开发定位改动、代码走读、排障 |
| 一个模块 | 会**横跨**多个技术层 | 一层含**多个**业务功能 |

**关系举例**："知识库 RAG 与 KAG"这个功能模块，横跨 5 个技术层：

```
知识库 RAG 与 KAG（功能模块）
├─ 前端页面        → 技术分层 L1 表现层
├─ 上传/管理接口   → 技术分层 L2 接口与网关层
├─ 建库编排        → 技术分层 L3 应用编排层（kb:build 任务）
├─ 切分/向量/检索/抽图谱 → 技术分层 L4 领域能力层（kbimport/ragstore/rerank/kag）
└─ 落库与状态      → 技术分层 L5 数据与存储层
```

两套视角的完整对照见 §6。

## 1. 三大使用场景（一眼看懂这个系统）

```
场景一【对话问答】    用户提问 ──▶ 检索知识（向量 + 图谱）──▶ 大模型生成答案
                      （M2 对话 Agent + M4 知识库 RAG 与 KAG）

场景二【知识生产】    丢进文档 ──▶ 切分向量化 + 抽实体关系 ──▶ 变成可检索的知识
                      （M4 知识库 RAG 与 KAG）

场景三【知识运维】    文件改了/删了 ──▶ 自动增量重建 + 失效清理，防幽灵知识
                      （M5 知识运维）

支撑以上三者的"装配台"与"底座"：
  装配台 → M3 Agent 平台（把模型+提示词+工具+知识库打包成 Agent）
           M6 工具与 MCP 生态（给 Agent 装外部能力）
  底座   → M7 任务调度中心（所有耗时操作异步化 + 实时回传进度）
           X1 意图路由（决定这次要不要检索，控成本 + 防注入）
           M1 用户与认证（账号与边界）
           X2 可观测 / X3 前端应用
```

| 编号 | 模块 | 一句话定位 | 状态 |

## 3. 按场景拆解

### 场景一：对话问答（用户问一句话，拿到有依据的回答）

**用户故事**：我在工作台选一个 Agent，输入"盘古系统怎么解决大文件存储和节点离线问题？"，几秒后拿到答案，并能在界面上看到"调用了哪些工具、命中了哪些知识"。

**涉及模块**：X3 → M1 → M7 → X1 → M2 →（M4 / M6）→ X3

| 步骤 | 做什么 | 所在模块 | 代码落点 |
|---|---|---|---|
| 1 | 登录拿到凭证，前端存本地 | M1 / X3 | `web/src/App.vue`、`internal/api/auth.go` |
| 2 | 提交问题（创建任务） | M7 | `internal/api/handler.go:138` |
| 3 | 任务落库 + 缓存，投递到优先级队列 | M7 | `internal/queue/manager.go:190-223` |
| 4 | Worker 取任务，置为执行中 | M7 | `internal/worker/pool.go:744-748` |
| 5 | **判断要不要检索** | X1 | `pool.go:790` → `internal/pkg/intent/router.go:92` |
| 6a | 命中知识库 → 向量双路召回 + 重排 + 窗口扩展 | M4 | `pool.go:810-824`、`pool.go:583-610` |
| 6b | 命中图谱 → 多跳关系检索 | M4 | `pool.go:826-858`、`kag/retrieve.go:34` |
| 6c | 需要外部信息 → 调工具（联网搜索） | M6 | `pool.go:913` → `llm/client.go:168-317` |
| 7 | 组装上下文（知识 + 图谱 + 历史）→ 调大模型 | M2 | `llm/client.go:134` |
| 8 | 状态回写 → NATS → API → SSE → 前端刷新 | M7 / X3 | `manager.go:351-370`、`handler.go:356-407` |

**关键机制**：
- 会话带多轮记忆，超长会自动压缩（阈值 `0.7 × 131072` token）。
- 界面上的"实时"是**任务状态与工具调用事件**级，**不是逐字流式输出**。
- 检索走**渐进式披露**：文档摘要 → 命中片段 → 向上下扩展窗口 → 按分数决定给多少。

### 场景二：知识生产（把文件变成可检索的知识）

**用户故事**：我在知识库页上传一份 Markdown，系统自动切分、向量化、抽实体关系，之后提问就能命中它。

**涉及模块**：X3 → M1 → M4 → M7

| 步骤 | 做什么 | 所在模块 | 代码落点 |
|---|---|---|---|
| 1 | 上传文档（文件或 JSON 正文） | M4 | `internal/api/knowledge_base.go:117` |
| 2 | 落库为文档记录，知识库置为"构建中" | M4 | `knowledge_base.go:168-176` |
| 3 | 投递建库任务（低优先级队列） | M7 | `manager.go:1045-1055` |
| 4 | 【向量线】生成文档摘要（失败不阻断）→ 切分 500/50 | M4 | `pool.go:1045-1087` |
| 5 | 【向量线】向量化 → 写入 Milvus（稠密 + 稀疏双路） | M4 | `pool.go:1089`、`ragstore/store.go:104` |
| 6 | 【图谱线】LLM 抽三元组（本体约束）→ 写 Neo4j | M4 | `pool.go:1120-1161` |
| 7 | 文档计数 +1，知识库置为就绪 | M4 | `pool.go:1105`、`manager.go:654-666` |

**关键机制**：
- **向量与图谱解耦**：图谱抽取失败只标状态，**不回滚已入库的向量**。
- 图谱阶段有并发信号量限流（`kb.graph_queue_concurrency`，默认 2）。
- 建库阶段的模型调用有独立预算与独立指标（`kb:build` 队列分别统计）。
- ⚠️ **查询扩展（同义词/实体/多模态改写）代码已写完但未接进生产链路**，目前只在离线评测里跑。

### 场景三：知识运维（知识会过期，怎么持续保持正确）

**用户故事**：我把知识库指向一个本地目录，文件被改了、加了、删了，系统按计划自动同步，并把旧向量和旧图谱边清干净，不会出现"文件删了但还能被检索到"。

**涉及模块**：M5（+ M4 / M7）

| 步骤 | 做什么 | 所在模块 | 代码落点 |
|---|---|---|---|
| 1 | 定时触发扫描（cron，只在 worker 主实例注册一次） | M5 | `cmd/worker/main.go:109-152` |
| 2 | **先做删除补偿**：卡在"删除中"超 10 分钟的记录重新投递 | M5 | `pool.go:1393-1413` |
| 3 | 递归扫描目录（跳过隐藏/不支持类型/空文件/超 10MB） | M5 | `kbimport/kbimport.go:84` |
| 4 | 用内容指纹判定三态：跳过 / 新增 / 重建 | M5 | `kbimport.go:70`、`pool.go:1319` |
| 5a | 新增 → 建文档记录 + 投递建库 | M5 → M4 | `pool.go:1327-1339` |
| 5b | 重建 → **先校验体积** → 删旧向量 → 删旧图谱 → 覆盖正文 → 重建 | M5 → M4 | `pool.go:1345-1379` |
| 6 | 删除知识库/文档 → 三级清理：Milvus → Neo4j → MySQL | M5 | `pool.go:1165-1248` |

**关键机制**：
- **"先删后写"窗口**：重建必须先删旧数据再写新数据，中间失败会产生"幽灵文档"。代码把**体积校验前置**到删除之前来堵这个洞。
- **删除补偿**：删除任务重试耗尽后，靠定时任务兜底重投，避免永久卡住。
- **本能力默认关闭**（`kb.scan_enabled=false`）。

### 场景四（支撑）：Agent 装配与工具接入

**用户故事**：我把"某模型 + 某段系统提示词 + 联网搜索工具 + 两个知识库"存成一个 Agent，之后每次提问都用这套配置。

**涉及模块**：M3 + M6（+ M4）

| 步骤 | 做什么 | 所在模块 | 代码落点 |
|---|---|---|---|
| 1 | 建 Agent，可覆盖模型/密钥/接入地址 | M3 | `internal/api/agent.go:40` |
| 2 | 绑定工具（多对多，全量替换） | M3 / M6 | `agent.go:208`、`manager.go:1057-1070` |
| 3 | 绑定知识库（多对多，全量替换） | M3 / M4 | `agent.go:245`、`manager.go:1072-1085` |
| 4 | 运行时按绑定白名单解析工具 | M6 | `pool.go:217-261` |
| 5 | 运行时按绑定知识库逐个检索并分行注入 | M4 | `pool.go:369-389` |
| 6 | 发现新工具：自然语言描述 → 搜 GitHub/npm → 试连 → 注册 | M6 | `tool.go:294,211` |

**关键机制**：
- 工具**运行时动态装配**：内置工具 + 启动时连上的 MCP 工具 + 按 Agent 绑定现拉的私有 MCP 工具。
- MCP 连接有**连接池**，避免每个任务都重启子进程。
- ⚠️ 工具按意图"裁剪"的设计存在，但**实际未生效**（`NeedTools` 只写日志，工具在路由前就已解析）。

## 4. 模块档案

### M1 用户与认证

| 项 | 内容 |
|---|---|
| **定位** | 账号注册登录、凭证签发与校验、写接口限流 |
| **子功能** | 注册（bcrypt 单向哈希）｜登录（签发 24h JWT）｜忘记密码（6 位验证码存 Redis，5 分钟，用后即删）｜鉴权中间件｜用户维度固定窗口限流（提交 3/分、批量 1/分、优化提示词 3/分） |
| **入口** | 登录/注册页；`POST /api/auth/*` |

| **风险** | 签名密钥硬编码在源码；校验时未断言签名算法；验证码只打印控制台；限流在 Redis 异常时降级放行 |

### M4 知识库 RAG 与 KAG

> 本模块内含两条**并行的知识线**，入库时同一条流水线里先后执行，检索时分别独立触发。

| 项 | 内容 |
|---|---|
| **定位** | 把文档变成"回答时可用的依据"：向量线负责语义相似，图谱线负责关系推理 |
| **子功能（流水线）** | 知识库 CRUD｜文档上传（文件/正文）｜递归切分（500/50）｜生成文档摘要｜向量化（1024 维）｜双路写入（稠密 + 稀疏）｜LLM 三元组抽取（本体白名单约束）｜关系名规范化 + 别名收敛｜入图（幂等合并 + 来源文档归属）｜按来源失效清理 |
| **子功能（检索）** | 混合召回（稠密 + 稀疏 + 融合）｜云端重排｜上下文窗口扩展｜按分截断注入｜多知识库分行注入｜多跳松弛检索（最多 3 跳）｜图谱关联度过滤｜缺失时返回提示而非空 |
| **入口** | 知识库视图；`/api/knowledge-bases/*`、`/api/admin/rag/ingest`、`/api/admin/kag/ingest` |
| **代码** | `internal/api/knowledge_base.go`(259)、`rag.go`(161)、`kbimport`(153)、`ragstore`(353+95+141)、`rerank`(118)、`kag`(264+73+258+85) |
| **关键机制** | 稠密（HNSW/COSINE）+ 稀疏（BM25 词频饱和）各取 2×topK → 融合 → 重排到 topK；**写删后强制刷盘**保证立即可见；标量过滤字段**无索引**；图谱与向量共享上下文总量闸门；**查询扩展与三元组补全未接线** |
| **状态** | 向量线 ✅ 投产；图谱线 ⚠️ 抽取与检索已投产但默认关闭（`kb.graph_enabled=false`） |

### M5 知识运维

| 项 | 内容 |

## 8. 状态与待确认

### 8.1 模块划分依据

- 口径：**按"用户能感知到的业务能力"**切分，而非按代码目录或技术层。
- 每个模块满足：有明确用户价值、有可指认的功能入口、有独立生命周期（可单独开发/灰度/下线）。
- 支撑性能力（意图路由、任务调度）虽用户不直接感知，但因**可独立灰度、有独立评测**，仍单独成模块。
- **M4 合并 RAG + KAG**：同一条入库流水线、共享上下文总量闸门、服务同一目标，仅在"检索方式"上分叉。
