## 1. 一句话说清这个系统的形状

**GoTaskAI 是一个"一个前端 + 两个 Go 进程 + 两条消息通道 + 四个存储"的 Agent 平台。**

理解它只需要抓住一句话：

> **API 只负责"接客"，Worker 只负责"干活"，中间靠队列解耦。**

这个形状不是设计洁癖的产物，而是一条硬约束推出来的：**LLM 调用的耗时以秒到分钟计**。如果让 HTTP 请求线程直接等模型返回，连接会长时间占着、超时难以控制、重试无法幂等、并发一上来就被拖垮。所以整个系统被切成两半——

| | 谁在做 | 特征 |
|---|---|---|
| **接客** | `cmd/api` | 秒级返回、无状态、可水平扩展 |
| **干活** | `cmd/worker` | 分钟级执行、有状态（任务终态保护）、重试与取消 |

剩下的一切（队列、事件总线、四个存储、意图路由、工具生态）都是为了让这两半能可靠地对话。

### 1.1 一段话讲清整条链路怎么转

> 用户在前端点下「发送」，浏览器带着 JWT 把问题 POST 给 Nginx，反代到宿主机上的 API 进程——**API 只做三件轻活**：验明身份、查出这个 Agent 绑定了哪些工具与知识库、把任务连同绑定关系写成 MySQL 里的一行 `pending` 记录，随即返回 `202` 与 `task_id`，**它从头到尾不等模型**。任务被投进 Redis 上的 Asynq 队列（按优先级进 `high`/`default`/`low`），与此同时浏览器已挂好 SSE 长连接在等消息；真正干活的 worker 子进程从队列抢到这个任务，**先用一条条件 UPDATE 抢下执行权**（若该行已是 `cancelled` 就直接丢弃），然后才开跑：先问意图路由「这题要不要查资料」，要查就走 Milvus 双路召回加 Neo4j 图谱多跳，在共享的字数预算内拼出上下文，再带上工具进入模型的工具调用循环，边生成边调工具，直到模型不再要求调工具为止。这期间每一次状态变化与工具调用，worker 都写回 MySQL（**那是唯一的真相**），并顺手往 NATS 广播一条事件；API 一直订阅着这些事件，收到即经 SSE 推给浏览器，界面于是实时亮起来——但要记住**推送只负责「快」不负责「对」**：事件丢了、API 重启了都无妨，刷新页面照样能从 MySQL 读到权威状态。所以整条链路的骨架就是一句话：**API 接客、队列解耦、worker 干活、MySQL 存档、NATS 报信**。

## 2. 架构总览：四层骨架

> **看图入口**：[架构图/01-总体架构.html](file:///d:/Program%20Files/GoTaskAI/项目分段精解/M0-全局认知与场景总览/架构图/01-总体架构.html)
> 用浏览器打开即可：支持明暗主题切换、缩放平移、节点搜索、关系追踪，内置 4 个导览章节（同步请求 / 异步任务 / 检索与生成 / 事件与实时推送）。

把架构图读成一张分层表：

| 层 | 组件 | 进程/位置 | 核心职责 | 明确不做的事 |
|---|---|---|---|---|
| **接入层** | Nginx | 容器 `gotaskai_nginx`，`:80` | 静态资源托管、`/api/` 反代、为 SSE 单独关闭缓冲 | 不做鉴权、不做业务 |
| **编排层** | `cmd/api` | 宿主机进程 `:8080` | 接客、JWT 鉴权、投递任务、推送 SSE、暴露 `/metrics` | **不执行任何 LLM 调用** |
| **消息层** | Redis + Asynq | 容器 `:6379`（+2 副本 +3 Sentinel） | 投递任务、重试、三队列分流 | 不存业务真相 |
| | NATS | **内嵌在 API 进程内** | 任务状态/工具事件/取消广播 | 不保证送达（可丢） |
| **执行层** | `cmd/worker` | 宿主机进程（supervisor + N 子进程） | 消费队列、检索、调模型、跑工具、回写状态 | 不直接对外提供 HTTP |
| **存储层** | MySQL 8.0 | 容器 `:3307`→`:3306` | **状态真相**、元数据、用户/Agent/知识库 | 不做向量与图查询 |
| | Milvus 2.4.4 | 容器 `:19530` | 向量召回（dense + sparse 双路） | 不存正文 |
| | Neo4j 5.18 | 容器 `:7687` | 知识图谱 KAG（实体-关系多跳） | 不做全文检索 |
| **外部** | LLM / Embedding / Rerank | 云端 | DeepSeek + 阿里云 DashScope | — |
| | `search_mcp` | **worker 的 stdio 子进程** | 联网搜索（SerpApi） | — |

> 注意最后一行：`search_mcp` 不是独立服务，而是 **worker 拉起的一个子进程**，通过 stdio 说 MCP 协议。这一点在 M6 里会展开。

## 3. 部署视图：容器里到底跑了什么

这部分常被含糊带过，但面试里最容易问"你的中间件版本/端口是什么"。[docker-compose.yml](file:///d:/Program%20Files/GoTaskAI/docker-compose.yml) 的实际布局：

```
宿主机                                     Docker 网络 gotaskai_net (172.28.0.0/16)

│  cmd/worker     supervisor    │         │   ├─ /api/tasks/stream → 缓冲关闭(SSE)    │
│    ├─ child 0   :9101/metrics │         │   └─ /admin/tasks/ → asynqmon 面板       │

         │  │  │  │                        │  mysql:8.0       172.28.0.2   :3307      │
         │  │  │  └────────────────────────▶  redis-stack     172.28.0.10  :6379      │
         │  │  │                           │   ├─ replica_1  172.28.0.11            │
         │  │  │                           │   ├─ replica_2  172.28.0.12            │

         │  │                               │  neo4j:5.18.1    172.28.0.30  :7687      │
         │  └──────────────────────────────▶│  milvus:v2.4.4   172.28.0.52  :19530     │
         └──────────────────────────────────▶│   ├─ etcd:v3.5.5  172.28.0.50 :2379    │
                                              │   └─ minio        172.28.0.51 :9000    │
                                              └──────────────────────────────────────────┘
```

**必须记住的三个"反直觉点"：**

1. **`api` 与 `worker` 不在 Docker 里**。它们是宿主机上直接跑的 Go 进程；Nginx 靠 `extra_hosts: host.docker.internal:host-gateway` 才能反向代理到宿主机 8080。所以 `docker compose up -d` 只起了中间件，业务进程要另起（`run_microservices.bat`）。
2. **MySQL 映射到宿主机的 3307 而不是 3306**，`:3306` 是容器内端口。`config.yaml` 里的 DSN 写的就是 `127.0.0.1:3307`。
3. **etcd 与 minio 没有对外端口**。它们是 **Milvus 的依赖**（etcd 存元数据、minio 存对象），不是本项目的组件——读架构图时不要把这两个算进"我们的存储"。

**worker 的进程模型**（[cmd/worker/main.go](file:///d:/Program%20Files/GoTaskAI/cmd/worker/main.go)）：`worker` 启动时先判断自己是不是 supervisor（看环境变量 `workerChildIndexEnv` 是否为空，L41）。是 supervisor 就 `exec.Command(os.Args[0])` 拉起 N 个子进程（L67-78，N = `queue.processes`，默认 2），然后自己退居"管理者"角色；子进程（L155 起）才是真正消费队列的 worker pool。

由此推出两个容易被考的结论：

- **指标端口随子进程编号递增**：`metrics.port(9100) + childIndex + 1`（L230）→ 第一个子进程 `:9101`、第二个 `:9102`。Prometheus 需要按进程数配多个 target，**`:9100` 本身没人监听**。
- **周期任务只在 supervisor 注册**（L57，`kb:scan`），子进程不注册——否则 N 个子进程会各投一份，导致重复入库。这是"单实例投递"的朴素实现（没有分布式锁，靠"谁是 supervisor"这个身份）。

## 4. 两条消息通道：为什么不用一个

这是本项目最值得讲的一个设计决策。

**表面上**：Redis 既能做队列（Asynq）也能做 Pub/Sub，那实时事件推送也放 Redis 不就行了？改造前就是这么干的。

**实际上**：同一份 Redis 同时承担"任务队列"和"实时事件广播"，意味着——

- 一次 Redis 抖动/主从切换，**同时**打击任务投递与前端实时刷新；
- 大 key、慢查询、内存压力会互相干扰；
- 两者对可靠性的要求完全不同：任务**丢一条就少干一件事**，事件**丢一条只是界面晚刷新一次**。

所以 [internal/events/events.go](file:///d:/Program%20Files/GoTaskAI/internal/events/events.go#L1-L7) 的开头把动机写得很直白：改用 NATS 让两条通道解耦，**Redis 只保留队列与缓存职责**。

| | Redis + Asynq | NATS 事件总线 |
|---|---|---|
| 管什么 | **任务**（要干活） | **事件**（要知道） |
| 三个频道/队列 | `high` / `default` / `low` | `global_task_updates` / `global_tool_events` / `global_task_cancel` |
| 语义 | 至少一次、可重试 `MaxRetry(3)`（删除类 5 次） | 发完即忘、可丢 |
| 谁发布 | API（投递） | Worker（更新）+ API（取消） |
| 谁订阅 | Worker | API（→ SSE 推前端）、全部 Worker（取消广播） |
| 部署形态 | 独立容器 + 副本 + Sentinel | **内嵌在 API 进程内** |
| 源码 | [manager.go L205-221](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L205-L221) | [events.go L25-29](file:///d:/Program%20Files/GoTaskAI/internal/events/events.go#L25-L29) |

**三个必须一起讲清的细节：**

1. **三队列是"权重"不是"抢占"**。`PriorityHigh/Low/Default` 只决定任务进哪个队列（L205-213），而 Asynq Server 默认 **不开启 `StrictPriority`**——所以 `high` 队列里堆积的任务**不会**抢占正在跑的 `low` 任务，只是被更早取到。这是"优先级"这个词最容易被误解的地方（详见 M7）。

2. **NATS 内嵌的代价**。省了一个进程、省了一次网络跳数，但：**API 进程挂了，事件通道就断了**（worker 发不出状态，前端 SSE 也失去数据源）。设计上用 `RetryOnFailedConnect(false)` + 失败时降级为进程内广播来兜底（[main.go L53-64](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L53-L64)）。【需实测】降级路径的实际表现。

3. **取消指令走的是 NATS 而不是队列**。因为取消必须"广播到所有 worker"，而不是"被某一个 worker 消费掉"——这是 pub/sub 与 queue 的本质区别（M7 §取消）。

## 5. 四个存储：谁说了算

新手最容易犯的错是"哪个快就用哪个存状态"。本项目的边界划得很清楚：

| 存储 | 存什么 | 是否"真相" | 丢了会怎样 |
|---|---|---|---|
| **MySQL** | 用户、Agent、知识库、文档、任务状态、RunLog、ToolCallLog | ✅ **是** | 数据永久丢失，不可恢复 |
| **Redis** | Asynq 队列、任务/Agent 缓存、限流计数、验证码 | ❌ 否 | 队列任务需重投；缓存可重建；**限流与验证码短期失守** |
| **Milvus** | 文档切片的向量（dense + sparse） | ❌ 副本 | 可从 MySQL 的 `Document.Content` 重新切分重建 |
| **Neo4j** | 实体-关系三元组（KAG） | ❌ 派生 | 可从文档重新抽取。**但抽取会花 LLM 的钱** |

三条推论：

- **状态真相与"快"是分离的**：任务状态先写 MySQL，再经 Redis/NATS 广播出去。所以"界面没刷新"不等于"任务没跑完"——刷新页面从 MySQL 一查就知道。
- **终态保护写在 MySQL 层的条件 UPDATE 里**（`UpdateTaskIfActive`），不是靠 Redis 锁。`RowsAffected == 0` 就说明任务已被取消/终态，本次结果直接丢弃。这是 M7 的核心机制。
- **Milvus / Neo4j 都是"可以重建"的**，这是能放心对它们做"先删后写"（有风险）或"重试即重建"的前提。但重建的代价不同：Milvus 重建只花 CPU 与 embedding，Neo4j 重建要重跑 LLM 抽取——**所以图谱才是那个"不能随便删"的**。

## 6. 四条端到端主线

把架构讲活的唯一方法是走一遍数据流。以下四条覆盖了 90% 的提问场景。

### 6.1 主线一：提交一个问题，拿到答案

```
①  浏览器           POST /api/tasks {agent_id, payload}
       │               Authorization: Bearer <JWT>
       ▼
②  Nginx             location /api/  →  host.docker.internal:8080
       │
       ▼
③  cmd/api           鉴权 → 解析 Agent 绑定（工具/知识库）→ 写 MySQL 任务行
       │              立刻返回 202 Accepted + task_id
       ▼
④  Redis/Asynq       Enqueue("task:process", Queue=high|default|low, MaxRetry=3)
       │
       ▼
⑤  cmd/worker(子进程) 消费 → UpdateTaskIfActive 抢到执行权 → 开始干活
       │
       ├─ X1 意图路由：要不要检索？（规则 → 语义 → LLM，默认关闭）
       ├─ 检索：Milvus 双路召回 → RRF 融合 → 云端重排 → 渐进式披露注入
       ├─ 图谱：Neo4j 多跳松弛检索（可选，与向量共享上下文总量闸门）
       ├─ 工具：MCP stdio 子进程 / 内置工具（受 MaxCalls=15 约束）
       └─ 生成：LLM Chat Completions
       │
       ▼
⑥  cmd/worker       写回 MySQL（状态、Token 用量、RunLog）
       │             同时 Publish 到 NATS：global_task_updates
       ▼
⑦  cmd/api          订阅到事件 → 通过 SSE 推给浏览器
       │
       ▼
⑧  浏览器            task_update 到达 → 更新界面
```

**关键点**：③ 是同步的、⑤~⑧ 全是异步的。**API 从头到尾没有等过模型。**

### 6.2 主线二：把一批文档变成可检索的知识

这条线比第一条长得多，因为它要同时喂两个检索系统：

```
选目录 → 投递 kb:build（low 队列，MaxRetry=3）
   │
   ├─ 扫描：按 MaxFileSize 闸门过滤（10MB）
   ├─ 建文档行：DeleteByDocID(可重入) → 切分 → 逐块写 Milvus（写后 Flush）
   │
   └─ W1 图谱阶段（kb.graph_enabled，默认 false）：
        抽取实体关系 → 本体归一（白名单 + 等价类）→ 入 Neo4j
        并发由 graphSem 信号量限制（kb.graph_queue_concurrency=2）

W2 定时增量（kb.scan_enabled，默认 false）：supervisor 注册 kb:scan 周期任务
```

两个设计点值得单独记住：

- **写删后强制 Flush**：Milvus 的删除不是原子的、默认一致性是 `Bounded`，不 Flush 就可能"删了还能被召回"。所以本项目在写/删之后都强制 Flush（M4 向量线）。
- **`kb.graph_enabled` 与 `kb.scan_enabled` 默认都是 false**：图谱抽取按 LLM 计费，所以是灰度开关。**默认配置下，知识入库只喂 Milvus，不喂 Neo4j**——这一点在讲"图谱能力"时必须说清，否则容易夸大。

### 6.3 主线三：一次带检索的生成（上下文是怎么拼出来的）

```
t.Payload（用户问题）
   │
   ├─ X1 意图路由 → Decision{NeedRAG, NeedKAG, NeedTools, Source}
   │
   ├─ NeedRAG → retrieveKnowledge()
   │     ├─ 双路召回：HNSW(dense, ef=64) ∥ SPARSE_INVERTED_INDEX(sparse)
   │     ├─ RRF 融合 → 取 3×topK 候选 → qwen3-rerank 重排
   │     ├─ 渐进式披露：文档摘要层 + 命中片段层（≥0.5 给 800 字，<0.5 给 400）
   │     └─ 块窗口扩展（chunk_context_window）补回相邻上下文
   │
   ├─ NeedKAG → RetrieveGraphContext()
   │     └─ 多跳松弛 BFS（默认 3 跳）→ 带 hop=N 标注 → 关联度过滤（计入 Budget）
   │
   ├─ 总量闸门：RAG 与 KAG **共享** max_context_chars（默认 6000 字），KAG 按剩余量截断
   │
   ├─ 会话历史：loadConversationHistory()（按 token 预算加载，超阈值滚动摘要）
   └─ 拼成 system_prompt + messages → RunAgent（工具调用循环）
```

**这里最该讲透的一句话**：RAG 与 KAG 不是"各注入一段"，而是**共享同一个字数预算**。所以图谱信息多了，向量片段就会被挤掉。这个"总量闸门"是 M4 两条线交汇的地方。

### 6.4 主线四：取消一个正在跑的任务

```
① 浏览器  POST /api/tasks/:id/cancel
② cmd/api 条件 UPDATE 把状态置为 cancelled（MySQL，真相）
③ cmd/api Publish global_task_cancel（NATS 广播到所有 worker）
④ 目标 worker 命中 inFlight 表 → 调用该任务的 cancelFunc
⑤ 在途的 LLM HTTP 请求随 context 取消而中断
⑥ 任务后续的回写被 UpdateTaskIfActive 拦下（RowsAffected==0 → 丢弃）
```

**为什么需要⑤而不是只靠②？** 因为"数据库里标记为取消"和"正在跑的模型调用停下来"是两件事。不掐断在途调用，那次调用的钱照样花掉，而且结果回来还得再被丢弃一次。

## 7. 九个关键架构决策（附代价）

面试里"你为什么这么设计"的问题，答案都在这一节。**每条都写了代价**——只讲收益不讲代价的设计是不成立的。

| # | 决策 | 收益 | 代价 / 遗留 |
|---|---|---|---|
| 1 | **API / Worker 双进程** | 接客与干活隔离；各自独立扩缩；HTTP 永不阻塞在模型上 | 部署复杂度上升；需额外保证消息投递可靠 |
| 2 | **Asynq（Redis）而非直接 goroutine** | 可重试、可持久化、可跨进程、可观测（asynqmon） | 多一跳 Redis；队列成为新的失败点 |
| 3 | **NATS 与 Redis 分开** | 单一 Redis 故障不再同时打击队列与推送 | 多一个组件；NATS 内嵌在 API 里 → API 挂则推送断 |
| 4 | **状态真相只在 MySQL** | 前端刷新即可拿到权威状态；Redis 可随意丢弃 | 每次状态回写都要落库，写放大 |
| 5 | **条件 UPDATE 做终态保护** | 用一条 SQL 同时解决并发写与取消竞态（防 TOCTOU） | 所有回写路径都必须走这套封装，漏一处就出 bug |
| 6 | **supervisor + N 子进程** | 进程级隔离，故障域收窄到 1/`processes`；**天然提供一个"单实例身份"**，周期任务只在 supervisor 注册，不必引分布式锁 | **supervisor 不重启子进程**（只打日志）→ 全部子进程退出后会变成"僵尸 supervisor"：进程活着、队列在堆（见 M7）；指标端口分裂（9101/9102/…）；该"单实例"只在单机内唯一，多节点部署仍会重复投递 |
| 7 | **Milvus 双路召回 + 云端重排** | 稠密语义 + 稀疏关键词互补，重排提升精度 | 链路长（embedding → 检索 → rerank → 关联度 LLM）；BM25 是简化实现（无 IDF） |
| 8 | **意图路由默认关闭（`intent.enabled=false`）** | 零新增调用、行为与改造前逐字节一致，可安全灰度 | **当前配置下这套优化完全不生效**；且 `enable_tool_routing` 开启是纯亏（见 X1 §8.2） |
| 9 | **选 Milvus 而非"单向量库 + 独立关键词引擎"** | 稠密 + 稀疏 + 标量过滤 + 融合排序**在一次请求内**完成（`HybridSearch` + 服务端 `RRFReranker`），省掉一个 Elasticsearch 与应用层融合代码 | 多 etcd + minio 两个依赖；删除需 `Flush` 才可见；schema 变更要重建 collection。**且不唯一**——Qdrant 同样能做，数据量小的话 pgvector 更划算。**已知短板**：`doc_id`/`kb_id` 无标量索引，删除全扫（见 M4 §8.3）。完整答辩口径见 M4 §4.11 |

> 第 9 条是**事后从代码依赖反推**的，不是仓库留档的决策记录——`docs/` 下没有任何向量库选型对比文档。这个区分在面试里要主动说清（展开见 [M4 §4.11](file:///d:/Program%20Files/GoTaskAI/项目分段精解/M4-知识库RAG与KAG/01-模块实现解析.md)）。

## 10. 一页速记

**形状**：一个前端 + 两个 Go 进程 + 两条消息通道 + 四个存储。

**四个数字**：进程 2 个（`api` / `worker`）、Asynq 队列 3 条（`high`/`default`/`low`）、NATS subject 3 个（`global_task_updates`/`global_tool_events`/`global_task_cancel`）、真相存储 1 个（MySQL）。

**一条铁律**：**状态真相只在 MySQL**；Redis 与 NATS 只负责"快"，不负责"对"。

**两条通道的分工**：Asynq 管**任务**（可靠、可重试、被一个 worker 消费）；NATS 管**事件**（实时、可丢、广播给所有人）。分开是为了不让一次 Redis 故障同时打断两者。

**四个存储的边界**：MySQL 不可丢（真相）；Redis 可丢（重建队列/缓存）；Milvus 可重建（重新切分向量化）；Neo4j 可重建**但要花 LLM 的钱**。

**三个别记错的细节**：
1. `api` 与 `worker` 是**宿主机进程**，不在 docker-compose 里；compose 只起中间件。
2. MySQL 宿主机端口是 **3307**，不是 3306。
3. `metrics.port=9100` 只是基数，**真正的指标在 9101/9102…**；`:9100` 无人监听。

**四个默认关闭的开关（讲能力时务必先说明）**：`kb.graph_enabled`、`kb.scan_enabled`、`intent.enabled`、`intent.enable_tool_routing`。

**三条交叉引用**：想看队列与状态机 → M7；想看检索链路怎么拼上下文 → M4（两篇）；想看"要不要检索"这层开关 → X1。

## 11. 面试 STAR 口述稿

> 这一节是**可以整段背下来直接说**的版本。它把前面十节压成一条叙事线，按 **Situation → Task → Action → Result** 推进。所有数字都锚定仓库实测，**没有编造任何百分比**。

### 11.1 完整版（约 90 秒）

> **（S 背景）** 这个项目是企业内部的技术情报知识平台，核心场景是"把海量文档变成可检索的知识，再让 Agent 用这些知识回答多跳问题"。**（T 任务）** 我接手后判断有两个真问题：一是 LLM 调用动辄几十秒，放在 HTTP 请求里同步等，并发一上来就被拖垮、超时与重试也无法幂等；二是知识库检索命中率低，但**低在哪里没有数据支撑**，团队当时的直觉是"实体名大小写不统一"，我并不信这个判断。**（A 行动）** 于是分两条线做。架构线上，我把系统拆成"接客"和"干活"两个 Go 进程——`api` 只做鉴权、解析 Agent 绑定、落一行 MySQL 任务记录就返回 `202`，**绝不碰模型**；`worker` 从 Redis 上的 Asynq 队列消费，把状态与工具调用都写回 MySQL 作为**唯一真相**，再用一条**条件 UPDATE** 抢执行权，杜绝"任务已被取消、结果却又写回来"的竞态；跨进程的实时推送我走了 NATS 而不是复用队列，因为状态上报是"被一个消费者处理"、取消广播是"被所有 worker 听到"，**两种语义混在同一条 Redis 上，一次抖动会同时打断投递与推送**。数据线上，我先做归因再改代码：实测发现实体大小写碰撞只占节点 **1.3%**，真正的问题是图谱关系 schema 爆炸到 **744 种、近六成是长尾**，于是放弃"让模型自由生成 Cypher"的路线，改成**本体白名单约束抽取 + 等价类归一 + 多跳松弛检索**；向量侧用 Milvus 稠密+稀疏双路召回、RRF 融合后过云端重排，注入上下文时做渐进式披露与总量闸门。**（R 结果）** 最能拿出手的是一个**可量化的成本开关**：我先把它做成默认关闭、可灰度，再用 100 条种子集做三档对照实测——只靠规则准确率 **0.72**、误检索率高达 **0.62**；加上语义层与 LLM 分类后准确率到 **0.97**、漏检率 **1.82%**（安全红线 2%）、**多次运行零抖动**，这组数据反过来证明了"单靠关键词规则不够"。图谱那条线的价值则在于**证伪**——用数据推翻了"归一化能救命中率"的假设，避免在几乎零收益的方向上继续投入。**诚实地说**，这条改造的端到端重测还没跑完，需要真实 LLM 与图库环境。

### 11.2 STAR 结构与证据对应

| 环节 | 讲了什么 | 支撑证据（均为实读） |
|---|---|---|
| **S** | 技术情报知识平台：文档 → 知识 → 多跳问答 | 项目定位（`docs/tech/技术情报知识平台-改造计划.md`） |
| **T** | 两个真问题：**LLM 阻塞 HTTP**、**命中率低但归因不明** | 双进程架构的起因（§1）；归因结论 744 种关系 / 58% 长尾 / 1.3% 碰撞（§7 第 7 行、M4 §4） |
| **A** | 架构线（双进程 + 队列解耦 + 条件 UPDATE + NATS 分流）／数据线（本体约束抽取 + 双路召回 + 渐进式披露） | `queue/manager.go`、`worker/pool.go`、`kag/ontology.go`、`kag/retrieve.go`、`ragstore/store.go` |
| **R** | 意图路由三档实测（0.72 → **0.97**，漏检 1.82%，零抖动）；KAG 侧**证伪旧假设** | `tools/intent_eval/` 100 条种子集报告（X1） |

### 11.3 这条稿子的三个设计点

1. **T 里埋了"我不信直觉"**。这比"我优化了性能"值钱得多——面试官问"你怎么定位问题的"时，你已经有答案：**先归因，再动手**。
2. **A 用"两种语义不能混"收尾**。一句话同时讲清"为什么有两条通道"和"取消为什么不能走队列"，是最能体现架构判断力的地方（§4）。
3. **R 拆成"可量化"与"证伪"两部分**。前者给结论，后者给方法论——**花时间证明某个方向没用，本身就是一种能力展示**。

### 11.4 一条红线：这句话不能说

**不要说"检索命中率提升了 X%"。** KAG 改造的端到端 WikiHop 重测**未执行**（缺真实 LLM + Neo4j 环境），这是仓库里的事实。

如果面试官追问"改造后命中率涨了多少"，正确回答是：

> "归因是数据驱动的，机制也重构完了，但**端到端重测还没跑**——这是我们下一步要补的第一件事。我不想拿一个没测过的数字糊过去。"

**主动交代这一点，比编一个漂亮数字安全得多**：前者显得诚实且有工程纪律；后者一旦被追问测试集和基线，就会当场崩掉。
