## 0. 一句话总览

**M1 = 用"用户名 + bcrypt 密码"换一张 24 小时有效的 HS256 JWT，之后每个受保护接口靠这张票据里的 `user_id` 做多租户隔离。**

整个模块只有三件事：**发票据（登录）、验票据（中间件）、按票据归属数据（各业务模块）**。

---

## 1. 这个模块解决什么问题

### 1.1 它要守住的三条线

| 线 | 要求 | 落点 |
|---|---|---|
| **身份真实性** | 密码不能明文存、不能明文比 | bcrypt 哈希 + `CompareHashAndPassword` |
| **请求可归属** | 每个业务请求必须知道"我是谁" | JWT `user_id` → `c.Set("userID")` → `c.GetUint("userID")` |
| **数据不越界** | A 看不到 B 的数据 | 各业务 handler 自校验（**注意：不是中间件统一保证**，见 §5.3） |

第三条是理解本模块边界的关键：**M1 只负责"你是谁"，不负责"你能看什么"**。归属校验被下放到了每个业务 handler 里——这直接决定了后续那些越权缺陷（M3 的绑定 BOLA）为什么会发生。

### 1.2 一句话数据流

```
POST /api/auth/login  ──(bcrypt 校验)──▶  GenerateToken(user.ID)
                                              │
                                              ▼  前端存 localStorage
            每个请求：Authorization: Bearer <token>
                                              │
                                              ▼
                    AuthMiddleware ──(HS256 验证)──▶ c.Set("userID", claims.UserID)
                                              │
                                              ▼
                              业务 handler：c.GetUint("userID") → 查自己的数据
```

## 2. 数据模型

### 2.1 `users` 表——只有三个字段

```go
// internal/model/user.go
type User struct {
    ID        uint      `json:"id" gorm:"primaryKey"`
    Username  string    `json:"username" gorm:"uniqueIndex;type:varchar(50);not null"`
    Password  string    `json:"-" gorm:"type:varchar(255);not null"`
    CreatedAt time.Time `json:"created_at"`
}
```

三个值得注意的点：

1. **`Password` 用 `json:"-"`**——注释写得很清楚："确保密码不会在转成 JSON 时暴露给前端"。这是个**低成本、高收益**的防护：哪怕某个 handler 误把整个 user 对象返回，密码哈希也不会出去。
2. **`Username` 有 `uniqueIndex`**——这是注册接口"先查再插"竞态的**最终兜底**（见 §5.6）。
3. **没有 `UpdatedAt`、没有 `Role`、没有 `Status`、没有邮箱/手机号**。
   - 没有 `Role` → **所有用户平权**，系统里不存在"管理员"这个角色（但路由里却有 `/admin/*`，见 §5.3）；
   - 没有 `UpdatedAt` → 没有"密码最后修改时间"的概念，也就无法实现"改密后踢下线"（见 §8.6）。

### 2.2 多租户的"弱关联"设计

`User.ID` 被各业务表用 **`user_id uint` + `index`** 引用，但**没有外键约束**（全项目未见 `foreignKey` 标签）。例如 `agents.UserID`、`knowledge_bases.UserID`、`tasks.UserID`。

取舍很清楚：**换取了写入性能与部署灵活性**（无需处理删除用户时的级联），代价是**删除用户会留下大量孤儿数据**（而项目里也确实没有"删除用户"接口）。

## 3. 端到端流程

### 3.1 注册

```
前端                      API 进程                        MySQL
 │                          │                              │
 │ POST /api/auth/register  │                              │
 ├─────────────────────────▶│ ① ShouldBindJSON 校验          │
 │   {username, password}   │    username: 3-20 位           │
 │                          │    password: >= 6 位           │
 │                          │ ② Count(username) ───────────▶│ SELECT COUNT(*)
 │                          │ ③ bcrypt.GenerateFromPassword │
 │                          │    (DefaultCost = 10)         │
 │                          │ ④ Create(user) ──────────────▶│ INSERT users
 │◀── 200 "注册成功，请去登录"─┤                              │
 │                          │                              │
 │   若用户名已存在 → 409 "该用户名已被注册"                     │
 │   若并发下撞 uniqueIndex → 500 "创建用户失败"                 │
```

**注意 ② 与 ④ 之间存在 TOCTOU 窗口**：两个并发注册同名用户时，两次 `Count` 都可能返回 0，随后一个 `Create` 成功、另一个撞 `uniqueIndex` 失败 → 返回 `500 创建用户失败`（而不是语义正确的 `409`）。属于体验瑕疵，不是安全漏洞（DB 兜住了）。

### 3.2 登录

```
前端                       API 进程                       MySQL / JWT
 │                           │                             │
 │ POST /api/auth/login      │                             │
 ├──────────────────────────▶│ ① ShouldBindJSON            │
 │                           │ ② First(username) ─────────▶│ 查不到 → 401 "用户名或密码错误"
 │                           │ ③ bcrypt.CompareHashAndPassword
 │                           │       失败 → 401 "用户名或密码错误"（与②同一句）
 │                           │ ④ jwt.GenerateToken(user.ID)
 │                           │      HS256, exp = now + 24h
 │◀── 200 {token, username} ──┤                             │
```

**② 和 ③ 返回完全相同的错误信息**，代码里还专门加了注释：

```go
// 注意：为了安全，不要明确提示是"用户名不存在"还是"密码错误"，统一返回相同信息
c.JSON(http.StatusUnauthorized, gin.H{"error": "用户名或密码错误"})
```

这是防**用户名枚举**的标准做法。但——**同一个文件里的另外两个接口把这个防护破坏了**（见 §8.2）。

### 3.3 受保护请求的鉴权

```
任意受保护请求
   │  Authorization: Bearer eyJhbGciOi...
   ▼
AuthMiddleware（middleware/auth.go）
   ├─ ① Authorization 头为空？        → 401 "未提供认证 Token，请先登录"
   ├─ ② SplitN(" ", 2)，parts[0] == "Bearer"？
   │      不满足                      → 401 "Token 格式错误，应为 Bearer <token>"
   ├─ ③ jwt.ParseToken(parts[1])
   │      失败/过期                   → 401 "Token 无效或已过期，请重新登录"
   └─ ④ c.Set("userID", claims.UserID) → c.Next()
```

### 3.4 密码重置（两段式）

```
第 1 段：申请验证码
  POST /api/auth/forgot-password/request-code {username}
     ├─ Count(username)；不存在 → 404 "该用户不存在"   ← ★ 用户名枚举点
     ├─ code = fmt.Sprintf("%06d", rand.Intn(1000000))  ← ★ math/rand，6 位数字
     ├─ Redis SET reset_code:<username> = code, TTL 5min
     └─ fmt.Println("...验证码是: %s...")               ← ★ "模拟发送"：只打控制台

第 2 段：提交新密码
  POST /api/auth/forgot-password/reset {username, code, new_password}
     ├─ GET reset_code:<username>；不存在/为空 → 400 "验证码已过期或不存在"
     ├─ savedCode != code → 401 "验证码错误"            ← ★ 无尝试次数限制
     ├─ DEL reset_code:<username>                      （防重复使用）
     ├─ bcrypt 加密新密码
     └─ UPDATE users SET password = ? WHERE username = ?
```

**这条链路是本文最需要关注的部分**——它同时具备三个弱点，组合成一条完整的账号接管路径（见 §8.2）。

### 3.5 前端会话保持与登出

```js
// App.vue:25-26 —— 启动时从 localStorage 恢复
const authToken = ref(localStorage.getItem(tokenKey) || '')
const username  = ref(localStorage.getItem(usernameKey) || '')

// App.vue:161-166 —— 登录成功后持久化（token 明文存 localStorage）
function persistAuth(token, currentUsername) {
  authToken.value = token
  username.value = currentUsername
  localStorage.setItem(tokenKey, token)
  localStorage.setItem(usernameKey, currentUsername)
}

// App.vue:168-182 —— 登出 = 只清本地
function clearAuth() {
  closeTaskStream()          // 关闭 SSE
  authToken.value = ''
  ... 清空所有内存状态 ...
  localStorage.removeItem(tokenKey)
  localStorage.removeItem(usernameKey)
}
```

**关键：登出是纯客户端行为**。不发请求、服务端无任何记录变更——因为 JWT 是无状态的，服务端**没有"注销这张票"的能力**（见 §8.6）。

## 4. 核心机制逐个讲透

### 4.1 JWT 的签发与校验

```go
// internal/pkg/jwt/jwt.go

// 在生产环境中，这个密钥应该从环境变量读取。这里为了演示硬编码在代码里。
var SecretKey = []byte("gotaskai-super-secret-key")

type Claims struct {
    UserID uint `json:"user_id"`
    jwt.RegisteredClaims          // 内嵌：ExpiresAt / IssuedAt / （可选）Subject 等
}

func GenerateToken(userID uint) (string, error) {
    claims := Claims{
        UserID: userID,
        RegisteredClaims: jwt.RegisteredClaims{
            ExpiresAt: jwt.NewNumericDate(time.Now().Add(24 * time.Hour)),  // ★ 有效期 1 天
            IssuedAt:  jwt.NewNumericDate(time.Now()),
        },
    }
    token := jwt.NewWithClaims(jwt.SigningMethodHS256, claims)
    return token.SignedString(SecretKey)
}

func ParseToken(tokenStr string) (*Claims, error) {
    token, err := jwt.ParseWithClaims(tokenStr, &Claims{}, func(token *jwt.Token) (interface{}, error) {
        return SecretKey, nil            // ★ keyfunc 不校验算法
    })
    if err != nil { return nil, err }
    if claims, ok := token.Claims.(*Claims); ok && token.Valid { return claims, nil }
    return nil, errors.New("invalid token")
}
```

**JWT 的本质**：一张**自包含、服务端不存储**的票据。好处是**无状态**（任何 API 副本都能独立校验，不需要共享 session 存储）；代价是**发出去就收不回来**——这正是 §8.6 那些问题的根源。

**载荷里只有一个 `user_id`**，不含 username、不含角色。所以：

- 校验不查库 → 鉴权是 **O(1) 无 IO**，性能好；
- 但**改了用户名/密码/角色后，旧票据的载荷不会变**——服务端也没有"票据版本号"来作废它们。

### 4.2 中间件与上下文传递

```go
// internal/middleware/auth.go
func AuthMiddleware() gin.HandlerFunc {
    return func(c *gin.Context) {
        authHeader := c.GetHeader("Authorization")
        if authHeader == "" {
            c.JSON(http.StatusUnauthorized, gin.H{"error": "未提供认证 Token，请先登录"})
            c.Abort()                       // ★ 必须 Abort，否则会继续执行下游 handler
            return
        }
        parts := strings.SplitN(authHeader, " ", 2)       // ★ SplitN 限 2 段，token 里含空格也不会切坏
        if len(parts) != 2 || parts[0] != "Bearer" { ... c.Abort(); return }

        claims, err := jwt.ParseToken(parts[1])
        if err != nil { ... c.Abort(); return }

        c.Set("userID", claims.UserID)
        c.Next()
    }
}
```

三个细节：

1. **`c.Abort()` 不可省**：Gin 里中间件不 Abort 的话，`c.Next()` 之后下游 handler 仍会执行——那就是"校验失败但接口照跑"，属于典型的鉴权绕过写法。这里三处都正确 Abort 了。
2. **`strings.SplitN(authHeader, " ", 2)`** 比 `strings.Split` 更稳：JWT 的 payload 段是 base64url，不含空格，但用 `SplitN` 限段数可以避免"多余空格导致 parts 长度不对"的边界错误。
3. **`c.Set("userID", claims.UserID)` 的类型是 `uint`**，下游必须用 `c.GetUint("userID")`。**注意 `GetUint` 在 key 缺失时返回 `0`**——所以如果某个路由**忘了挂中间件**，handler 拿到的 `userID` 就是 `0`。所幸多数查询是 `WHERE user_id = 0`（查不到数据）或 `task.UserID != 0`（拒绝），**降级方向是安全的**；但这是"忘记挂中间件"不会立刻暴雷的原因，也是它更容易长期潜伏的原因。

### 4.4 限流：设计意图与一个实现缺陷

```go
// middleware/ratelimit.go —— 基于 Redis 固定窗口
func RateLimitMiddleware(rdb *redis.Client, maxRequests int, window time.Duration) gin.HandlerFunc {
    return func(c *gin.Context) {
        var key string
        if userID, exists := c.Get("userID"); exists {
            key = "rate_limit:user:" + fmt.Sprint(userID)     // ★ key 里【没有路由维度】
        } else {
            key = "rate_limit:ip:" + c.ClientIP()
        }

        count, err := rdb.Incr(ctx, key).Result()
        if err != nil {
            c.Next()          // ★ Redis 异常 → 降级放行
            return
        }
        if count == 1 { rdb.Expire(ctx, key, window) }        // 首次请求才设窗口
        if int(count) > maxRequests {
            c.JSON(http.StatusTooManyRequests, gin.H{"error": "您的操作太频繁啦，请稍后（最多1分钟）再试"})
            c.Abort()
            return
        }
        c.Next()
    }
}
```

挂载情况（`main.go:150-152`）：

```go
tasksGroup.POST("/submit",          middleware.RateLimitMiddleware(redisClient, 3, time.Minute), handler.SubmitTask)
tasksGroup.POST("/batch-submit",    middleware.RateLimitMiddleware(redisClient, 1, time.Minute), handler.BatchSubmitTasks)
tasksGroup.POST("/optimize-prompt", middleware.RateLimitMiddleware(redisClient, 3, time.Minute), handler.OptimizePrompt)
```

**正确的地方**：

- **用 `INCR` 保证并发安全**（注释也点明了）；
- **首次请求才 `Expire`**，避免每次 INCR 都刷新 TTL 把窗口变成"永不结束"；
- **Redis 故障降级放行**，注释说明了取舍（可用性优先）。

**缺陷：限流 key 不含路由维度**（`rate_limit:user:<id>`）。三个端点各自 `new` 了中间件实例（各带自己的 `maxRequests`），但**共用同一个 Redis key**。后果：

| 场景 | 实际结果 |
|---|---|
| 窗口内先调 1 次 `submit`，再调 `batch-submit` | 计数 = 2 > 1 → **429**（batch-submit 本意是"1 次/分钟"，但它被别人的调用吃掉了额度） |
| 窗口内调 3 次 `submit`，再调 `optimize-prompt` | 计数 = 4 > 3 → **429**（prompt 优化被任务提交挤掉） |
| 三个端点合计 | **额度被压缩成三者的最小值**，而不是各自独立 |

也就是说：**这三个接口实际上是"共享一个 3 次/分钟的总配额"，且 `batch-submit` 在同一窗口内只要发生过任何一次请求就必然 429**。

**修法**（未实施）：`key += ":" + c.FullPath()`（或路由模板），使每个端点独立计数。

### 4.5 CORS 策略

```go
// middleware/cors.go
func CORSMiddleware() gin.HandlerFunc {
    return func(c *gin.Context) {
        origin := c.GetHeader("Origin")
        if origin != "" {
            c.Header("Access-Control-Allow-Origin", origin)         // ★ 反射任意 Origin
            c.Header("Vary", "Origin")                             // ✔ 正确声明缓存维度
            c.Header("Access-Control-Allow-Headers", "Authorization, Content-Type, Accept, Origin, Cache-Control")
            c.Header("Access-Control-Allow-Methods", "GET, POST, PUT, PATCH, DELETE, OPTIONS")
            c.Header("Access-Control-Expose-Headers", "Content-Length, Content-Type")
        }
        if c.Request.Method == http.MethodOptions {
            c.AbortWithStatus(http.StatusNoContent)                 // ✔ 预检直接短路
            return
        }
        c.Next()
    }
}
```

**做对的两件事**：

1. **`Vary: Origin`**——很多人会漏。不写的话，中间缓存（CDN/反向代理）可能把"给 A 站点的 CORS 响应"复用给 B 站点，造成跨站数据泄露。这是 CORS 实现的必答项。
2. **预检 `OPTIONS` 直接 204 短路**，不走业务中间件。

**没做的是白名单**：`Allow-Origin` 直接回显请求里的 `Origin`，等于**允许任意站点跨域调用**。文件头注释说明了为什么这里风险可控：

> 当前项目使用 JWT Header 和 SSE query token，不依赖 Cookie 凭证。

这是准确的判断：**因为没有用 Cookie，浏览器不会自动携带凭证**——恶意站点即使发起跨域请求，也拿不到用户的 `Authorization` 头（它存在 localStorage 里，跨域读不到）。所以这不是一个可直接利用的 CSRF。

但仍应收紧（未实施）：维护 `CORS_ALLOWED_ORIGINS` 白名单；否则一旦将来引入 Cookie 会话或某个页面出现 XSS，反射 Origin 会立刻从"配置不卫生"升级成"可直接利用"。

**另外注意**：SSE 端点硬编码了 `Access-Control-Allow-Origin: *`（`handler.go:379`），与中间件的"反射 Origin"策略不一致——同一份响应上可能出现两个 `Access-Control-Allow-Origin` 头（一个来自中间件，一个来自 handler），浏览器会因"多值"而拒绝。这是个潜在的行为不一致，值得实测确认。

### 4.6 密码存储

```go
hashedPassword, err := bcrypt.GenerateFromPassword([]byte(req.Password), bcrypt.DefaultCost)
...
if err := bcrypt.CompareHashAndPassword([]byte(user.Password), []byte(req.Password)); err != nil { ... }
```

**为什么用 bcrypt 而不是 SHA-256**：普通哈希（MD5/SHA）是**为速度设计**的，GPU 每秒可算数十亿次，配合彩虹表/字典，弱密码几乎秒破。bcrypt 是**为"慢"设计**的：

| 特性 | 作用 |
|---|---|
| **可调 cost（默认 10）** | 单次哈希约几十到上百毫秒。攻击者暴力枚举的成本被抬高若干个数量级，而正常登录只多花一次 |
| **内置随机 salt** | 同一个密码每次哈希结果都不同 → **彩虹表完全失效**，且两个用户用同一密码也看不出 |
| **哈希串自包含参数** | `$2a$10$<22位salt><31位hash>`，校验时从串里读 cost 和 salt，无需另存 |

**代价**：bcrypt 是 CPU 密集操作。如果登录接口被高频冲击，单机 CPU 会被打满（这既是防护也是 DoS 面）——所以**登录接口本该配限流**（见 §8.1）。

**一个必须知道的细节**：**bcrypt 只使用输入的前 72 字节**，超出部分被静默忽略。而 `AuthRequest` 只校验 `min=6`、**没有 max**。所以用户设一个 100 字符的密码，实际只有前 72 字节参与哈希——**密码强度被截断，且用户不知情**。

## 7. 已知缺陷与未验证项

### 7.1 高：认证接口完全无限流

`main.go:139-145` 的 `authGroup` **没有挂任何限流中间件**：

```go
authGroup := apiGroup.Group("/auth")
{
    authGroup.POST("/register", authHandler.Register)
    authGroup.POST("/login", authHandler.Login)
    authGroup.POST("/forgot-password/request-code", authHandler.RequestResetCode)
    authGroup.POST("/forgot-password/reset", authHandler.ResetPassword)     // ← 无限次尝试
}
```

对比 `tasksGroup` 里三个端点都配了限流——**限流能力是有的，只是没用在最需要它的地方**。后果：

| 端点 | 无限流的后果 |
|---|---|
| `/login` | **可无限次暴力猜密码**。bcrypt 提供天然限速（每次约几十~上百毫秒），单连接约 10–20 次/秒、多连接可叠加。对弱密码字典仍然可行 |
| `/register` | 可批量注册账号（刷库、占用用户名） |
| `/request-code` | 可无限请求，反复覆盖 Redis 里的验证码；同时是用户名枚举的探针（§7.2） |
| `/reset` | **可无限次尝试验证码** → 见 §7.2 的爆破链 |

**修法**（未实施）：给 `/login` 加 `(5, time.Minute)` 级别的 IP+用户名双维度限流；给 `/reset` 加严（如 `(5, 5*time.Minute)`），并在 Redis 里对 `reset_code:<username>` 维护**失败尝试计数**，超过 N 次直接作废该验证码。

### 7.2 高：密码重置链路可组合成**完整的账号接管路径**

这是把四个独立弱点串起来看的结果，也是我认为 M1 最严重的发现：

```
步骤 1 ── 枚举有效用户名
          POST /api/auth/register {username: 猜测}  → 409 "该用户名已被注册" ⇒ 存在
          POST /api/auth/forgot-password/request-code {username} → 404 "该用户不存在" ⇒ 不存在
          ⚠️ 与登录接口刻意统一错误信息的做法【互相矛盾】

步骤 2 ── 为目标账号申请验证码
          POST /api/auth/forgot-password/request-code {username: 目标}
          → 验证码写入 Redis（TTL 5 分钟），服务端只打印到控制台（§7.3）
          → 攻击者看不到码，但码【已在 Redis 里且有效】

步骤 3 ── 暴力枚举 6 位验证码
          POST /api/auth/forgot-password/reset {username, code: 000000..999999, new_password}
          ⚠️ 无尝试次数限制、无限流、无锁定
          空间 = 10^6；但无需穷举 —— 期望命中约 5×10^5 次
          5 分钟窗口内需要 ~1667 req/s 才能覆盖全空间，单机并发【在工程上可行】

步骤 4 ── 命中后接口直接把密码改成攻击者指定的值 → 账号接管
```

**四个弱点缺一不可**（所以这也是"为什么单看每个接口都不算致命"的原因）：

1. `request-code` 与 `register` 泄露用户名是否存在（**枚举**）；
2. 验证码只有 **6 位数字**（空间 10⁶，而不是足够的熵）；
3. `reset` **没有尝试次数上限**（也没有限流）；
4. 验证码比对用的是**普通字符串比较**（`savedCode != req.Code`，非恒定时间）——在无限次尝试下这条不是瓶颈，但属于同类问题。

**修法方向**（未实施）：`request-code` 对不存在的用户也返回 `200`（统一文案）；把 `reset` 的失败次数记进 Redis（`reset_attempt:<username>`），超过 5 次即删除验证码并锁定一段时间；给 `reset` 加限流。

### 7.3 中：密码重置的"发送"只是控制台打印

```go
// api/auth.go:138-142
// 模拟发送邮件或短信的行为：将验证码打印到终端控制台
fmt.Println("\n=======================================================")
fmt.Printf("[模拟短信/邮件] 账号 %s 的密码重置验证码是: %s\n", req.Username, code)
fmt.Println("请在 5 分钟内输入验证码完成重置。")
fmt.Println("=======================================================")
```

接口的响应里也直说了：`{"message": "验证码已发送，请检查控制台输出"}`。

两点影响：

1. **功能上：用户根本拿不到验证码**（真实用户看不到服务器控制台）→ 这条链路对正常用户是**不可用**的；
2. **安全上**：验证码被写进了**日志/标准输出**。容器化部署时 stdout 通常被收集到日志系统（Loki/ELK 等），于是**验证码会随日志扩散到更多可能被更多人访问的地方**。日志的重要度提升了。

综合 §7.1/§7.2/§7.3：**这条链路当前对正常用户不可用，但对攻击者是可利用的**——这是最坏的组合（添了风险、没给功能）。

### 7.4 中：JWT 密钥硬编码 → 可为任意用户伪造票据

```go
// jwt.go:10-11
// 在生产环境中，这个密钥应该从环境变量读取。这里为了演示硬编码在代码里。
var SecretKey = []byte("gotaskai-super-secret-key")
```

**因为密钥在源码里，任何拿到源码的人都可以离线签出一张 `user_id` 为任意值的合法 token**，从而绕过全部鉴权、访问任意用户的数据。

```
HS256 的签名 = HMAC-SHA256(base64url(header) + "." + base64url(payload), SecretKey)
知道 SecretKey ⇒ 可以对任意 payload 产生合法签名 ⇒ 可伪造 user_id = 1, 2, 3 ...
```

**且系统里没有 `role` 概念**，所以伪造 `user_id = 1` 就是"第一个用户"的身份（在自部署场景里往往就是部署者本人）。

**修法**（未实施）：改为从环境变量/密钥管理服务读取（`JWT_SECRET`），启动时**校验非空且长度足够**（如 < 32 字节直接 Fatal）；轮换时支持新旧双密钥并行校验。

**顺带一个加固项**：`ParseToken` 的 keyfunc 只 `return SecretKey, nil`，**没有用 `jwt.WithValidMethods([]string{"HS256"})` 限定算法**。当前仅用 HMAC，直接利用面有限（攻击者仍需知道同一密钥才能换算法重签），但**"限定算法"是 JWT 校验的必写项**，建议补上。

### 7.5 中：无鉴权的运维面板与写入接口（四处）

| 端点 | 位置 | 风险 |
|---|---|---|
| **`/admin/tasks`（asynqmon Web UI）** | `main.go:124-129` | **最严重**：可浏览所有队列（包括 `archived`）中的任务，**任务 payload 是用户的原始提问、result 是模型回答** → 全量用户对话内容泄露；且该 UI 支持**删除任务 / 重跑任务** |
| `/api/admin/rag/ingest` / `/api/admin/kag/ingest` | `main.go:133-137` | 可**匿名向向量库与图谱写入数据**，污染所有知识库的检索结果 |
| `/metrics` | `main.go:118` | 暴露内部指标（任务量、错误率、成本等），属信息泄露 |

**为什么 `/admin/tasks` 尤其要紧**：它不是"路径名字里有 admin 所以有人以为有权限"，而是 **asynqmon 是一个功能完整的运维控制台**——能看、能删、能重跑。项目把它 `r.Any` 挂到公网可达的 `r`（根路由）上，没有任何中间件。

**修法**（未实施）：至少加一层鉴权；更稳的做法是把 asynqmon 只绑内网/仅开发环境启用（`if cfg.Server.Mode != "release"`）。

### 7.6 中：令牌不可吊销 → 登出是"假的"

JWT 无状态带来的必然结果：

| 场景 | 当前行为 |
|---|---|
| 用户点"退出登录" | **只清 localStorage**（`App.vue:168-182`），服务端无任何动作。票仍在有效期内可继续使用 |
| 用户改了密码 | **旧 token 依然有效**。因为 token 里没有"密码版本号"，服务端也不在每次请求时查库 |
| token 被泄露（含 M2 的"SSE token 走 URL 进 access log"） | 攻击者可用满 **最长 24 小时**，且无任何手段提前作废 |
| 被盗号后想"踢下线" | **做不到** |

**修法方向**（未实施，按成本递增）：

1. **最简**：`Claims` 里加 `pwd_v`（密码版本），用户表加 `pwd_version`；改密时自增。中间件比对——代价是**每次请求多一次查库/缓存查询**（可用 Redis 缓存缓解）；
2. **标准**：引入 Redis 黑名单（登出/改密时把 token 的 `jti` 写入黑名单，TTL = 剩余有效期）；
3. **彻底**：改用短期 access token（15 分钟）+ refresh token（存 Redis，可吊销）。

### 7.7 低：前端只有一处处理 401

```js
// App.vue:278-293 —— 只有 refreshTasks 做了 401 处理
} catch (error) {
    if (error?.status === 401) {
        clearAuth()
        setMessage('登录状态已失效，请重新登录', 'error')
    } else { ... }
}
```

其余调用（提交任务、Agent/Tool/知识库操作、`handleAgentChatSubmit` 等）**只把错误显示出来，不清理登录态**。所以 token 过期后用户会进入一种尴尬状态：**界面看起来仍是已登录的**（顶栏有用户名、能点按钮），但每个操作都报错，直到用户手动点"退出"或刷新页面。

**修法**：在 `apiRequest`（`client.js:20-33`）里统一拦截 `401` → 触发一个全局登出事件。这也顺带解决了"每个调用方都要记得处理 401"的重复问题。

### 7.8 低：其他细节

| 项 | 说明 |
|---|---|
| **bcrypt 72 字节截断** | `AuthRequest.Password` 只校验 `min=6`、无 max。超过 72 字节的密码**后半段被静默忽略**，密码强度被截断且无提示。建议加 `max=72`（或先做预哈希） |
| **注册的 TOCTOU** | 并发注册同名用户时，第二个请求撞 `uniqueIndex` 返回 `500 创建用户失败`，语义上应为 `409`。DB 兜住了正确性，仅体验瑕疵 |
| **`math/rand` 生成验证码** | 非密码学安全随机源。对 6 位验证码而言熵本身就不足（§7.2），换 `crypto/rand` 收益有限但成本也低；另外 `rand.Seed()` 自 Go 1.20 起已废弃（运行时自动播种），该行属于冗余 |
| **固定窗口限流** | 窗口边界处可产生约 2 倍突发（`t=59s` 用满 3 次，`t=61s` 又是新窗口） |
| **限流 key 含用户 ID 而非 IP** | 已登录用户换账号即可重置额度；未登录/未挂中间件的路由才会走 IP 分支（但那些路由本来也没挂限流） |
| **无角色/无权限模型** | 所有用户平权。`/admin/*` 只是路径名，无权限语义 |
| **无"删除用户"接口** | 结合无外键约束，用户数据无法清理（也避免了级联删除问题） |

### 7.9 未验证项

| 项 | 说明 |
|---|---|
| 验证码爆破的**实际可行性** | 已从代码确认"无尝试限制"，但未实测 5 分钟窗口内的实际吞吐（取决于 BCrypt 无关的重置接口耗时、Redis 往返、网络） |
| **CORS 头冲突** | 中间件反射 Origin + SSE handler 硬编码 `*` → 同一响应可能有两个 `Access-Control-Allow-Origin`。**建议实测确认浏览器行为** |
| asynqmon 的可访问性 | 需在真实部署下确认 `/admin/tasks` 是否被网关/反代拦住（代码层面确定没拦） |
| Token 过期后的前端行为 | 只有 `refreshTasks` 处理 401，其它入口的实际表现需实测 |
| 限流 key 共享的实际影响 | 已从代码推导（三端点共用计数器），建议实测确认（见 §8.3） |

## 8. 怎么验证

### 8.1 验证登录链路与防枚举（预期正确的部分）

```bash
# 注册
curl -s -X POST http://localhost:8080/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username":"m1_alice","password":"pass123456"}'
# 期望：200 {"message":"注册成功，请去登录"}

# 重复注册 → 409（同时是用户名枚举点）
curl -s -X POST http://localhost:8080/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username":"m1_alice","password":"pass123456"}'
# 期望：409 {"error":"该用户名已被注册"}

# 密码太短 → 400
curl -s -X POST http://localhost:8080/api/auth/register \

# 登录成功

  -H "Content-Type: application/json" \

```

### 8.2 验证鉴权中间件

```bash
TOKEN=...   # 上面的 token

# 无 token → 401
curl -s http://localhost:8080/api/tasks
# 期望：401 "未提供认证 Token，请先登录"
```

## 9. 一页速记（面试/复盘用）

- **一句话定位**：M1 只解决"**你是谁**"（bcrypt 存密码 + HS256 JWT 发身份），**不解决"你能看什么"**——归属校验被下放到每个业务 handler，这正是后续越权缺陷的结构性原因。
- **四个最容易被追问的设计点**：
  1. 为什么用 bcrypt 而不是 SHA-256？——普通哈希为速度设计、可被 GPU 批量爆破；bcrypt **可调 cost + 内置随机 salt**，把单次成本抬到几十毫秒，且彩虹表失效。
  2. JWT 为什么无状态、代价是什么？——任意 API 副本都能独立校验（O(1) 无 IO、无共享 session），代价是**发出去收不回来**：无吊销、改密不失效、登出只是前端行为。
  3. 登录失败为什么统一提示"用户名或密码错误"？——防**用户名枚举**。但注册（409）与申请验证码（404）把这个防护破坏了，两者自相矛盾。
  4. 限流怎么做的？——Redis `INCR` + 首次 `Expire` 的**固定窗口**；Redis 故障时**降级放行**（可用性优先）。但**key 只含 userID、不含路由** → 三个端点共用计数器，互相吃额度。
- **五个必须说清的事实修正**：
  1. **密码重置链路可组合成完整的账号接管路径**：枚举用户名（404/409 泄露存在性）→ 申请验证码 → **无限次暴力枚举 6 位码**（无尝试上限、无限流、无锁定）→ 重置密码 → 接管账号。而这条链路**对正常用户反而不可用**（验证码只 `fmt.Println` 到控制台）。
  2. **JWT 密钥硬编码在源码里**（`jwt.go:11`，注释自己承认应该走环境变量）+ **全系统无角色概念** → 拿到源码即可为任意 `user_id` 伪造合法票据，绕过全部鉴权。
  3. **认证接口完全没有限流**：`authGroup` 未挂任何限流中间件（而 `tasksGroup` 挂了）→ 登录可无限爆破、注册可批量刷库、验证码接口可无限尝试。
  4. **四处端点无鉴权**：`/admin/tasks`（**asynqmon 运维控制台**，可浏览/删除/重跑全部用户任务，payload 就是用户对话原文）、`/api/admin/rag/ingest` 与 `/kag/ingest`（可匿名向向量库/图谱写入）、`/metrics`。**"路径叫 `/admin`" ≠ "有权限控制"**。
  5. **CORS 反射任意 Origin（无白名单）**：因凭证走 `Authorization` 头而非 Cookie，暂不构成可直接利用的 CSRF，但属于应收紧的配置卫生问题（且已正确设置 `Vary: Origin`）。
- **三条可量化的证据**：
  - §8.3：窗口内先调 1 次 `submit` 再调 `batch-submit` → 期望 **429**（证明限流 key 共享）；
  - §8.4：不带 token 请求 `/admin/tasks` → 期望 **200**（证明运维面板无鉴权）；
  - §8.6：改密码后用**旧 token** 访问 → 期望 **200**（证明令牌不可吊销）。
