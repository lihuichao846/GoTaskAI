# 上下文感知分块改造方案（路线 B：上下文检索 / 窗口扩展）

> 交付类型：**改造方案评审稿（不落地代码）**。经确认，采用「B 上下文检索/窗口扩展」路线。
> 目标：解决现有「按字符硬切 500 rune + 注入只给命中块」导致的**跨句实体/关系割裂**问题（阶段一实测：KAG 开放域 +0.0pp 的主要诱因之一），在不改变主链路切分策略、不大幅增加成本的前提下，把「上下文」补回到检索注入阶段。

---

## 一、背景与问题定位

### 1.1 现状（代码级）
| 环节 | 位置 | 现状 |
|---|---|---|
| 切分 | [pool.go#L858-L870](file:///d:/Program%20Files/GoTaskAI/internal/worker/pool.go#L858-L870) | `RecursiveCharacter`，ChunkSize=500 / Overlap=50，按 **rune** 计数 |
| 入库 | [store.go#L111-L117](file:///d:/Program%20Files/GoTaskAI/internal/pkg/ragstore/store.go#L111-L117) | 仅 5 列：`kb_id / doc_id / text / dense / sparse` |
| 检索 | [store.go#L131-L204](file:///d:/Program%20Files/GoTaskAI/internal/pkg/ragstore/store.go#L131-L204) | 双路召回 + RRF → 返回命中块本身 |
| 注入 | [pool.go#L272-L276](file:///d:/Program%20Files/GoTaskAI/internal/worker/pool.go#L272-L276) | 对每个命中块做 `chunkByScore` 截断后独立注入，**不补上下文** |

### 1.2 核心缺口
1. **块间无顺序/无归属关系**：Milvus 只存 `doc_id`，未存 `chunk_index` / `parent_id` / `section`，因此**无法在命中后定位其在原文档的相邻块**。
2. **注入是「孤岛」**：命中块只带自身 `text`，跨句/跨段依赖（前文主语、后文结论、上下文消解）在切分时已被截断，注入后无法重建。
3. **Document 表已有全文但未利用**：`Document.Content` 存了完整文本，检索侧从未用它做扩展或定位。

### 1.3 阶段一关联
WikiHop 评测暴露的「KAG 开放域 +0.0pp」中，`ExtractKnowledge` 是基于**整篇 supports 文本**抽取的，而向量检索注入的却是**碎片化 chunk**——两者天然不一致。上下文感知（窗口/父段）能部分弥合这一割裂。

## 二、目标与不做什么

### 2.1 目标
- 命中一个 chunk 时，能**补回它在原文档中的相邻上下文**（父段落或前后 N 个相邻块），作为注入上下文的一部分。
- 上下文总量仍受现有 `MaxContextChars`（6000）与 `MaxChunkChars`（800）门禁约束，**不失控**。
- 不改切分主链路策略（仍 RecursiveCharacter 500/50），**不引入 LLM 分块或句子级嵌入**（属于 C/D，本次不做）。

### 2.2 不做
- ❌ 语义分块（路线 C）：需句子级嵌入，多一次嵌入请求，提升成本、稳定性存疑。
- ❌ LLM 驱动分块（路线 D）：慢且贵，仅适合离线建库。
- ❌ 重建 Milvus Collection 全量迁移（除非必须加列，见 §五 schema 方案）。

## 三、技术方案选型（B 的两个子实现）

「上下文检索/窗口扩展」有两种落地口径，**推荐 B1，B2 作为低侵入兜底**：

### 3.1 B1：命中块 → 按 doc_id 拉取该文档 chunk 序列，取「命中位置 ± 窗口」注入（推荐）
- 依赖新增字段 `chunk_index`（int，块在文档内的顺序），建库时写入。
- 检索命中 `topK` 个块后，收集这些命中块的 `doc_id`，在 Milvus 侧**按 doc_id 批量查询该文档的全部 chunk**（`Query` 接口按 `expr: doc_id == 'x'` + 按 `chunk_index` 排序），得到文档的有序块序列。
- 以命中块的 `chunk_index` 为中心，取前后 **W** 个相邻块（窗口），拼接为一段**该文档的局部连续上下文**注入；注入仍受 `MaxContextChars` 截断。
- 优点：上下文连续、语义连贯，直接重建被切分截断的跨句依赖。

### 3.2 B2：命中块 → 直接引用 Document.Content 全文（低侵入兜底）
- 不改 Milvus schema，不改切分数，仅在注入时为每个命中 doc 拉取 `Document.Content`（已有字段）做**父段落/上下文兜底**。
- 缺点：全文直接注入容易超 `MaxContextChars`；要定位命中块在全文的位置需依赖 `chunk_index` 或文本匹配，精度不如 B1。
- **结论**：B2 单独用价值有限，**应作为 B1 未建 `chunk_index` 时（存量数据）的降级路径**，不单独作为主方案。

> **结论：主方案 = B1，B2 仅作为存量数据/异常降级。**

## 四、改造点清单（B1）

### 4.1 建库侧：为每个 chunk 打 `chunk_index`
- **位置**：[pool.go#L858-L878](file:///d:/Program%Files/GoTaskAI/internal/worker/pool.go#L858-L878) `handleKBBuild` 与 [rag.go#L128-L133](file:///d:/Program%Files/GoTaskAI/internal/api/rag.go#L128-L133)。
- **动作**：`SplitDocuments` 返回有序 `chunks []schema.Document`，在写库前对每个 chunk 的 `Metadata` 注入：
  ```go
  for i := range chunks {
      chunks[i].Metadata["chunk_index"] = i        // 块序号
      chunks[i].Metadata["doc_id"] = doc.ID        // 已存在
      chunks[i].Metadata["kb_id"] = payload.KBID   // 已存在
  }
  ```
- **存储侧**：[store.go#L111-L117](file:///d:/Program%Files/GoTaskAI/internal/pkg/ragstore/store.go#L111-L117) 需从 metadata 读取并新增一列：

### 4.2 Milvus schema 变更（新增一列）
| 列 | 类型 | 来源 | 说明 |
|---|---|---|---|
| `chunk_index` | Int64 | 上一步 metadata | 块在文档内的顺序，用于窗口扩展 |
- **变更方式**：Milvus 加列需重载/新建 Collection。**可选两种**：
  1. 新建带 `chunk_index` 的 Collection（改名或新版本），存量数据用 B2 降级；新写入走 B1。→ 推荐，**避免破坏存量**。
  2. 对现有 Collection `AddColumn`（Milvus SDK 支持 `AddColumn`）后重建索引。
- **注意**：`AddColumn` 会重载 collection，需在低峰执行；若嵌入模型已变更需 `DropCollection` 全量重建（[store.go#L65-L71](file:///d:/Program%Files/GoTaskAI/internal/pkg/ragstore/store.go#L65-L71)）。

### 4.3 检索侧：按 doc_id 批量取该文档有序 chunk 序列
- **位置**：[store.go#L131-L204](file:///d:/Program%Files/GoTaskAI/internal/pkg/ragstore/store.go#L131-L204)。
- **新增方法** `GetChunksByDocID(ctx, docID) ([]schema.Document, error)`：
  - 用 Milvus `Query`（非 `Search`）按 `expr: doc_id == "..."` 过滤，`output_fields: [text, chunk_index]`，按 `chunk_index` 升序返回，带 `MaxContextChars` 内截断。
- 在 `retrieveTopDocs` 之后（[pool.go#L388-L415](file:///d:/Program%Files/GoTaskAI/internal/worker/pool.go#L388-L415)）或注入前，对每个命中的 doc_id 调该方法，得到有序块序列。

### 4.4 注入侧：块级窗口扩展
- **位置**：[pool.go#L272-L276](file:///d:/Program%Files/GoTaskAI/internal/worker/pool.go#L272-L276) `appendKBDocs` 中。
- **动作**：对每个命中块，取其在文档 chunk 序列中的 `chunk_index`，向前后各扩展 W 块（配置项 `chunk_context_window=1` 起步），合并为一段局部连续文本；再经 `chunkByScore` + `MaxContextChars` 双层截断后注入。
- **去重**：同一 doc 多个命中块会重复扩窗，需按 `doc_id + 窗口区间` 用 `seen` 去重（复用现 [pool.go#L315](file:///d:/Program%Files/GoTaskAI/internal/worker/pool.go#L315) 的 `seen` 思路，扩展为窗口区间去重）。
- **新增配置项**（[config.yaml#L80-L84](file:///d:/Program%Files/GoTaskAI/config/config.yaml#L80-L84)`context` 字段下）：
  ```yaml
  context:
    chunk_context_window: 1   # 命中块前后各扩展的相邻块数（0=关闭，等价现状）
    enable_parent_context: true  # 是否启用上一级文档上下文兜底
  ```

### 4.5 成本评估
- **新增嵌入请求**：无。B1 复用已存储的 `text`/`dense`，按 doc_id 取回有序块，**不新增任何 LLM/嵌入调用**。
- **Milvus Query 请求**：每个命中 doc_id 一次 Query（topK ≤3~5，可控）。
- **注入体积**：受 `MaxContextChars=6000` 门禁约束，窗口扩展只是**换内容**而非**增体积**，超限自动停止（[pool.go#L246-L252](file:///d:/Program%Files/GoTaskAI/internal/worker/pool.go#L246-L252)），不会泄露。

## 五、风险与应对
| 风险 | 等级 | 应对 |
|---|---|---|
| **Milvus 加列需重载 Collection** | Medium | 采用「新建带 chunk_index 的 Collection + 存量走 B2 降级」，避免破坏存量；低峰执行 |
| **窗口扩展引入无关上下文、污染注入** | High | 窗口默认 W=1 起步保守；仍走 `chunkByScore` 分层 + `MaxContextChars` 截断；用 RAG 分层阈值剔除低分 |
| **同一 doc 多命中块重复扩窗导致冗余** | Medium | `seen` 按 `doc_id+窗口区间` 去重 |
| **增量数据先 B1、存量先 B2 的一致性** | Medium | 提供降级标志；监控注入质量，随后续数据重建逐步迁移为 B1 |
| **上下文过长失控** | Medium | 强依赖 `MaxContextChars` / `MaxChunkChars` 门禁，单位测试覆盖 |

## 六、回归验证方法
1. **跨句依赖断言**：构造「主语在前块、谓语/宾语在后块」的文档，验证 B1 扩窗后注入包含完整三元组（现状为割裂）。
2. **上下文总量不超**：复用现有 `MaxContextChars` 门禁测试，确保窗口开启后注入不超上限。
3. **去重正确性**：同一 doc 多命中块场景下，断言不重复注入同一窗口区间。
4. **门禁（非功能性）**：`go test ./...` + `go vet ./...` 全绿；确认零新增嵌入/LLM 调用。
