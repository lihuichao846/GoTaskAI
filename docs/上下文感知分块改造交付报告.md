落实的功能项（对照方案「改造点清单」）：

- 建库侧：为每个 chunk 注入 `chunk_index`（服务建库与 API 上传两条入口一致）。
- 存储侧：Milvus Collection 新增 `chunk_index`（Int64）列；写入条件化；检索输出带回。
- 检索侧：新增 `GetChunksByDocID` 按 `doc_id` 有序还原 chunk 序列。
- 注入侧：以命中块为中心做前后 ±`chunk_context_window` 块级窗口扩展，按 `doc_id:chunk_index` 去重，沿用命中块归一化分数统一截断口径，受 `max_context_chars` 总量门禁。
- 配置：新增 `context.chunk_context_window` 与 `context.enable_parent_context`。
- 兼容：存量 Collection 缺 `chunk_index` 列时自动降级（B2），不影响既有数据检索。

### 2.2 变更要点

**建库侧（B）**
- 在 `textsplitter.SplitDocuments` 之后，为每个 chunk 的 `Metadata` 写入 `chunk_index`（= 切分后下标），作为其在原文档中的有序位置。Worker 的 `handleKBBuild` 与 API 的 `Ingest` 两处保持一致。

**存储侧（C）**
- schema 新增 `chunk_index` 列（`FieldTypeInt64`），仅在新 Collection 创建时写入。
- `Store` 新增 `hasChunkIndex` 标记；`New` 中通过 `DescribeCollection` 检测字段是否存在（存量 Collection 无此列 → `hasChunkIndex=false`）。
- `AddDocuments` 仅在 `hasChunkIndex=true` 时追加 `entity.NewColumnInt64(fieldChunkIndex, ...)`；存量 Collection 忽略该列，走 B2 降级。
- `SimilaritySearch` 在 `hasChunkIndex=true` 时向 `outputFields` 追加 `chunk_index`，并在构造 `schema.Document.Metadata` 时解析回填。

**检索侧（D）**
- 新增 `GetChunksByDocID(ctx, docID)`：`client.Query(...{text, kb_id, chunk_index}, expr=doc_id=="...")`，按 `chunk_index` 升序 `sort.SliceStable` 返回。
- 存量 Collection（`hasChunkIndex=false`）时直接返回空切片，由上层走 B2 全文兜底，避免对无该列的集合发起非法查询。

**注入侧（E）**
- `expandChunks`：当 `ChunkContextWindow <= 0` 时直接返回原始命中块（等价改造前行为）；否则对每个带 `doc_id` 的命中块经 `GetChunksByDocID` 取该文档有序块序列，交给 `addWindowChunks` 做窗口扩展。
- `addWindowChunks`：在有序序列中定位命中块 `chunk_index`，`windowRange` 计算前后 ±window 区间，按 `doc_id:chunk_index` 去重追加；邻居块 Score 统一置为命中块归一化分数，保证与命中块同一分层截断口径。
- B2 降级：取块失败或无 `chunk_index` 且 `EnableParentContext=true` 时，回退为 `Document.Content` 全文（单文档一次，按 `doc-full:<docID>` 去重）。
- `chunkByScore` 分层截断、`max_context_chars` 总量门禁保持既有语义，与窗口扩展叠加。

**配置（F）**
- `context.chunk_context_window`（默认 1）：命中块前后各扩展的相邻块数；`<=0` 关闭。
- `context.enable_parent_context`（默认 true）：B2 降级时是否回退 `Document.Content` 全文兜底。

### 3.3 性能基准

命令：`go test -run=NONE -bench=. -benchmem ./internal/worker/`（i9-13980HX）

| 基准 | ns/op | B/op | allocs/op | 说明 |
| --- | --- | --- | --- | --- |
| `BenchmarkWindowRange` | 0.14 | 0 | 0 | 窗口区间计算（含边界裁剪） |
| `BenchmarkAddWindowChunks` | 581 | 320 | 9 | 单次命中窗口 1（±1 邻居 + 命中块），O(window) 阶 |
| `BenchmarkAddWindowChunks_Dedup` | 19447 | 12998 | 130 | 100 块文档上 19 次命中逐次去重（去重 map 覆盖 19 个窗口区间） |
| `BenchmarkChunkByScore` | 2.45 | 0 | 0 | 单块分层截断 |

**结论**：单命中窗口扩展为亚微秒级；去重 map 在多命中/大文档场景下的整体开销仍为毫秒以下，且该路径仅在检索命中后触发，不会影响查询主链路吞吐。满足方案「性能优化指标」。

## 六、后续建议（超出本次改造范围，供参考）

- **存量数据迁移脚本**：如需对既有 `kb_chunks` 启用窗口扩展，建议提供「读出 `doc_id` 文本 → 按序重打 `chunk_index` → 重新入库」的迁移工具。
- **窗口大小动态化**：可按命中块与中心块的语义距离或分数衰减动态调节 `chunk_context_window`，而非固定 1。
- **跨块去重增强**：当前按精确 `chunk_index` 去重；若未来引入「父子块」结构，可扩展为按原文片段哈希去重。
