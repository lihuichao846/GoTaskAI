# HTTP 与 HTTPS 核心原理解析

在 Web 开发与面试中，HTTP 与 HTTPS 的区别以及握手过程是极其高频的知识点。本文档采用“对比法”和“生活比喻”，用最通俗易懂的方式为你梳理这些核心概念。

## 一、 HTTP 与 HTTPS 的核心区别

HTTP（超文本传输协议）是明文传输的，而 HTTPS（安全超文本传输协议）在 HTTP 的基础上加入了 SSL/TLS 协议层，实现了数据的加密传输、身份验证以及数据完整性保护。

我们可以用**“寄信”**来做通俗对比：
*   **HTTP（明文传输）：** 就像寄**明信片**。邮递员、快递中转站的任何人都能直接看到你写在上面的内容。如果有人偷偷篡改了内容，收信人也完全无法察觉。
*   **HTTPS（加密传输）：** 就像把信装进了一个**密码箱**，并且密码箱上还有官方认证的**防伪印章**。只有拥有专属钥匙的收信人才能打开看，中途任何人拿到密码箱都看不到里面的内容，也无法伪造印章。

### 核心区别速查表

| 维度 | HTTP | HTTPS |
| :--- | :--- | :--- |
| **安全性** | 明文传输，极易被窃听和篡改 | 密文传输，防窃听、防篡改、防伪装 |
| **默认端口** | 80 | 443 |
| **证书要求** | 不需要 | 需要向 CA 机构申请 SSL 证书（通常需要付费或定期续期） |
| **建立连接耗时** | 较短（只需 TCP 三次握手） | 较长（需 TCP 握手 + TLS 加密握手） |
| **SEO 影响** | 搜索引擎排名权重较低 | 搜索引擎（如 Google）优先收录并给予更高权重 |

## 二、 握手过程详解

要理解 HTTP 的连接过程，我们必须先知道 HTTP 是基于 TCP 协议的。因此所谓的“HTTP 握手”，本质上是底层的 **TCP 三次握手**。而如果是 HTTPS，在 TCP 握手之后，还会多出一步 **TLS 握手（协商加密）**。

### 1. TCP 三次握手（建立连接通道）

无论是 HTTP 还是 HTTPS，通信的第一步都是建立 TCP 连接通道。为了确保双方都能正常收发数据，需要进行“三次握手”。

**📞 通俗比喻：打电话**
*   **第一次握手（Client -> Server）：** 客户端发送 `SYN` 报文。
    *   *（客户端：“喂，听得到吗？我想跟你说话。”）*
*   **第二次握手（Server -> Client）：** 服务端收到后，回复 `SYN + ACK` 报文。
    *   *（服务端：“听得到！那你听得到我说话吗？”）*
*   **第三次握手（Client -> Server）：** 客户端收到后，回复 `ACK` 报文。
    *   *（客户端：“我也听得到！那我们开始说正事吧。”）*

> **❓ 面试常问：为什么是三次握手，不是两次？**
> **答：** 主要是为了防止**已失效的连接请求报文**突然又传到了服务端，产生错误。如果是两次握手，服务端回复“听得到”之后就单方面认为连接建立了，开始分配内存资源等待接收数据。但如果客户端当时只是网络卡顿发出的历史无效请求，客户端实际上并不会发送数据，服务端的资源就白白浪费了。三次握手确保了**双方都确认了对方具备收发能力**。

### 2. TLS 握手（HTTPS 专属的加密准备）

在 TCP 三次握手成功后，HTTP 就可以直接发送数据了。但 HTTPS 不行，它还需要协商加密方式和交换密钥，这就是 TLS 握手过程（通常分为 4 步）。

**🔐 通俗比喻：对暗号与交换密码箱钥匙**
1.  **Client Hello（客户端打招呼）：** 客户端向服务端发送自己支持的加密算法列表，以及一个**客户端生成的随机数 A**。
2.  **Server Hello & Certificate（服务端回应并出示证件）：** 服务端选择一种双方都支持的加密算法，并发送自己的**数字证书（内含公钥）**，以及一个**服务端生成的随机数 B**。
3.  **Client Key Exchange（客户端验证并发送密钥材料）：** 客户端验证证书是真的后（确认服务端身份），生成一个新的**随机数 C（Pre-Master Secret）**，用服务端的**公钥**把 C 加密，发给服务端。
    *   *此时，客户端和服务端都拥有了随机数 A、B、C。双方使用协商好的算法，将这三个随机数混合，生成了最终的**“对称加密密钥”**（即会话密钥）。*
4.  **Finished（加密通信开始）：** 双方互发消息确认：“以后我们就用这个新生成的对称密钥来加密所有聊天内容啦！”

> **❓ 面试连环炮：如果证书颁发的机构不权威（比如自己伪造的证书），连接还能不能建立？**
> **答：** **连接在技术上是可以建立的，但浏览器会拦截并发出红色严重警告。**
> *   **原理**：在上述第 3 步（客户端验证证书）时，浏览器会拿着服务端发来的证书，去自己操作系统内置的**“受信任的根证书颁发机构 (CA) 列表”**里比对。
> *   如果你用的是自己用代码签发的证书（自签证书），或者颁发机构是个野鸡机构，浏览器在本地列表里查不到它的“担保人”，就会认定这是一个“不安全”的证书。
> *   **表现**：此时，浏览器（如 Chrome）会弹出一个极其显眼的红色警告页面，提示“您的连接不是私密连接”。**但如果用户（也就是你）手动点击了“高级 -> 继续前往（不安全）”**，浏览器就会强行信任这个证书，继续用它里面的公钥进行后续的 TLS 握手步骤，连接依然能够成功建立并加密通信。

> **💡 核心设计巧妙之处：非对称加密 + 对称加密 的结合**
> *   **非对称加密（公钥/私钥）：** 极度安全，但运算极其缓慢。所以在 HTTPS 中，**只在握手阶段**用它来安全地传递“对称加密密钥”（随机数 C）。
> *   **对称加密：** 运算速度极快。在握手完成后，后续所有海量的 HTTP 请求和响应数据，都使用协商好的“对称加密密钥”进行加密传输。
> 这种结合既保证了绝对的安全性，又兼顾了极高的性能。
