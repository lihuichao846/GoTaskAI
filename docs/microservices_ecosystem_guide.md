# 微服务生态与核心技术栈全景指南

当你把一个单体应用（Monolith）拆分成微服务（Microservices）后，虽然解决了“局部计算卡死全局”的问题，但也打开了潘多拉魔盒：**分布式系统的复杂性**。

以前调用一个函数只需 1 纳秒，现在变成了一次网络请求（可能超时、丢包）；以前查日志直接看控制台，现在日志散落在 10 台不同的机器上。
为了治理这些复杂性，业界演进出了一套完整的“微服务技术栈”。面试中如果聊到微服务，以下**七大核心技术领域**是必考内容。

---

## 1. 服务间通信机制 (Service Communication)

拆分后的微服务分布在不同的物理机上，它们之间怎么聊天？
*   **同步通信 (RESTful HTTP vs gRPC)**：
    *   **RESTful API**：基于 HTTP 协议，JSON 格式。优点是人类可读、跨语言方便；缺点是 JSON 序列化慢、体积大。
    *   **gRPC**：Google 开源的 RPC 框架，基于 HTTP/2 和 Protobuf（Protocol Buffers）。传输的是高度压缩的二进制数据，速度比普通 HTTP 快数倍，是目前内部微服务同步通信的**绝对主流**。
*   **异步通信 (Message Queue)**：
    *   为了彻底解耦，不要求对方立刻回应。比如本项目中 API 把任务扔进 **Redis (Asynq)**，或者大型项目中使用 **Kafka / RabbitMQ / RocketMQ** 进行事件驱动通信。

## 2. 服务注册与发现 (Service Discovery & Registry)

*   **痛点**：API Server 想调用 Worker，但 Worker 随时可能扩容成 50 台，或者因为宕机 IP 发生变化。API 怎么知道该请求哪个 IP？
*   **解决方案**：引入一个“通讯录”。所有 Worker 启动时，把自己当前的 IP 登记到通讯录里。API 调用前，先去通讯录查一下目前哪些 Worker 活着。
*   **主流技术选型**：
    *   **Nacos**（阿里开源，目前国内 Go/Java 生态最火）
    *   **Consul**（HashiCorp 开源，支持多数据中心）
    *   **Etcd**（K8s 的底层存储，强一致性）
    *   **Zookeeper**（老牌组件，偏重型）

## 3. 统一 API 网关 (API Gateway)

*   **痛点**：微服务有几十个（用户服务、订单服务、AI 服务），前端不可能去记住每一个服务的不同域名和端口。而且如果在每个服务里都写一遍 JWT 鉴权和防刷限流代码，太冗余了。
*   **解决方案**：在所有微服务前面挡一个“大门”（API 网关）。前端只和网关打交道，网关负责把请求路由（转发）到对应的微服务，并集中处理鉴权、跨域、限流。
*   **主流技术选型**：
    *   **Kong**（基于 Nginx/OpenResty，性能极高）
    *   **APISIX**（Apache 顶级项目，动态高性能网关）
    *   *注：本项目中的 `cmd/api` 实际上就扮演了一个定制化的轻量级业务网关角色。*

## 4. 可观测性 (Observability) - 极其重要

微服务排错是地狱级的，必须有“天眼”。可观测性分为三大支柱：
1.  **链路追踪 (Distributed Tracing)**：
    *   **作用**：一个请求经过了 A -> B -> C 三个服务，到底在哪一步变慢了？链路追踪会给这个请求打上一个唯一的 `TraceID`，串联全过程。
    *   **技术栈**：**Jaeger**, **SkyWalking**, **OpenTelemetry**（目前的行业标准规范）。
2.  **指标监控 (Metrics)**：
    *   **作用**：监控系统的宏观健康状态：CPU 占用率、当前排队任务数、每秒 QPS。
    *   **技术栈**：**Prometheus**（采集数据） + **Grafana**（炫酷的数据大屏展示）。
3.  **集中式日志 (Logging)**：
    *   **作用**：把散落在 100 台机器上的日志全部收集到一个池子里，支持全文搜索。
    *   **技术栈**：**ELK** 栈 (Elasticsearch + Logstash + Kibana) 或 **EFK** 栈 (Filebeat/Fluentd)。

## 5. 服务容错与降级 (Fault Tolerance)

*   **痛点**：微服务存在“雪崩效应”。如果底层的大模型 API 卡死了，会导致等待它的 Worker 全部卡死，进而导致调用 Worker 的 API Server 连接数耗尽，最终整个系统全线崩溃。
*   **解决方案**：
    *   **熔断 (Circuit Breaking)**：如果发现大模型 API 连续 10 次超时，直接“拉闸”（断路器打开）。接下来 1 分钟内的请求不再真正发起调用，而是直接返回“服务繁忙”，保护系统。
    *   **限流 (Rate Limiting)**：超过系统承受能力的请求直接拒绝（本项目已实现）。
*   **主流技术选型**：**Sentinel** (阿里开源)、**Hystrix** (Netflix，已停更)。

## 6. 分布式配置中心 (Configuration Management)

*   **痛点**：系统有 50 台机器，如果数据库密码变了，或者想调整限流的阈值，难道要一台台登录进去改 `config.yaml` 然后重启吗？
*   **解决方案**：引入配置中心。所有服务启动时去配置中心拉取配置；如果在配置中心网页上修改了值，它会**热更新**推送到所有机器的内存中，无需重启。
*   **主流技术选型**：**Apollo** (携程开源)、**Nacos** (兼具注册中心和配置中心功能)。

## 7. 容器化与服务编排 (Container Orchestration)

*   **痛点**：微服务数量多，部署极其复杂，如何做到一键发布、挂了自动拉起、高峰期自动增加服务器？
*   **解决方案**：
    *   **Docker**：把代码和运行环境打包成集装箱（镜像），保证本地和线上环境绝对一致。
    *   **Kubernetes (K8s)**：集装箱的调度平台。它可以监控你的服务，一旦发现 CPU 超过 80%，自动帮你从 2 台机器扩容到 10 台机器；流量下来后自动缩容。

## 💡 结合 GoTaskAI 项目谈微服务

如果面试官问：“你的 GoTaskAI 项目用到了哪些微服务技术？”

你可以这么回答：
> “目前 GoTaskAI 项目完成了**微服务演进的第一阶段：业务边界的拆分与解耦**。
> 1. 我们将架构物理拆分为了 API Gateway 和 Worker Node 两个服务。
> 2. 在**通信机制**上，我们使用了 Redis Asynq 作为消息队列进行异步解耦，并使用了 Redis Pub/Sub 事件总线实现了跨进程的 SSE 状态推送。
> 3. 在**服务容错**上，我们在 API 层面实现了限流中间件，并在队列层面实现了任务的重试与状态机机制。
> 
> 如果未来项目要支撑更大规模的流量，我会考虑引入 **gRPC** 优化内部通信，接入 **Nacos** 做服务发现，并全面拥抱 **OpenTelemetry + Prometheus** 来补齐分布式系统最核心的**可观测性**短板。”
