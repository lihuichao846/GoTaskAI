## 一、项目概述（面试开场白）

### 1. 一句话介绍

> 一个用 **Go + Gin + Vue3** 构建的**异步 AI 任务调度与 GraphRAG 对话平台**——后端按「接入层 / 计算层」拆成 API Server 与 Worker Node 两个进程，以 Redis 承担缓存与 Asynq 队列、以独立 NATS 通道承担跨进程实时事件，围绕 **Agent、知识库、MCP 工具**三大可配置能力，实现高并发下的削峰填谷、故障重试与跨进程实时推送。

### 2. 30 秒自我介绍话术（可直接背）

> 我做了一个叫 GoTaskAI 的平台，先讲它解决的真实业务问题：团队的知识都散落在文档、Wiki、聊天记录里，员工想查个资料、跑个流程，要么翻文档要么问人，效率低、口径还不统一。我把它做成一个「**私有知识 + 大模型 + 外部工具**」的问答与任务执行平台——用户上传文档建知识库、创建自己的 Agent、再挂上外部工具，然后像聊天一样提问或派任务，平台自动检索知识、调用工具、执行，并实时反馈进度。但落地时撞上三个硬问题：**大模型不懂私有知识，只有通用常识；它只会「光说不动手」；而且调用耗时长、并发低，用户不能干等**。所以我先把后端拆成两个进程：**API Server** 负责接请求、鉴权、限流，把用户请求变成任务；**Worker Node** 负责消费任务、按 Agent 组装工具与知识（RAG 向量检索补文本 + KAG 图谱检索补关系）、再调大模型。最关键的设计是**异步解耦**：API 一收到请求就把任务丢进 Redis 的 Asynq 队列、立刻返回 202，由 Worker 慢慢消费，实现流量削峰；任务完成后 Worker 通过 **NATS 广播**任务/工具事件，API 订阅后再用 **SSE 推给前端**，打通跨进程的实时状态同步。在此基础上，我把它做成一个**多维可配置平台**：用户能创建 Agent（固化人设与模型）、上传文档进知识库（RAG/KAG 双路召回）、注册并绑定 MCP 外部工具（联网搜索、飞书等），让同一套后端服务不同风格的智能体。技术栈用了 Gin、GORM、Asynq、NATS、Neo4j、MCP。

### 3. 项目边界（已做 / 未做）

**已实现**：用户认证、Agent 管理、知识库（RAG/KAG 双路召回）、MCP 工具平台、会话管理、任务管理、Agent Harness 护栏（六项目标）。

**未实现（可主动说明，显得边界清晰）**：多租户组织模型（当前只有单用户 `user_id` 归属）、计费系统（`CostUSD` 仅为观测计量，无账单）、输出 Schema 强校验（Task/Agent 无输出表达字段）。

### 4. 非功能性需求（面试「怎么保证 X」的回答索引）

| 维度 | 实现方式 |
|---|---|
| 性能 | API 秒回 202 + Asynq 异步削峰 |
| 可用性 | Redis Sentinel + 限流 fail-open + 工具/检索降级回退 |
| 可扩展 | Worker 多子进程 supervisor + 多 worker 并发 |
| 可观测 | RunLog/ToolCallLog + Prometheus + /metrics |
| 安全 | JWT + bcrypt + 资源归属校验 |
| 成本 | 预算熔断（单次/跨重试双上限 + token 计量） |

## 三、系统架构

### 1. 运行态进程（面试核心，务必先讲清）

```
┌─────────────── API Server（接入层，IO 密集型）───────────────┐
│  接 HTTP、JWT 鉴权、Redis 限流、托管前端、建任务/会话/Agent、SSE 推送   │
└─────────────┬──────────────────────────────────┬─────────────┘
              │ ① 任务入队（Asynq）                │ ④ 订阅事件→SSE 推送
              ▼                                  ▲
    ┌─────────── Redis ───────────┐      ┌─────────── NATS ───────────┐
    │     缓存 + Asynq 消息队列      │      │     跨进程实时事件总线       │
    └──────────────┬─────────────┘      └──────────────┬─────────────┘
              │ ② 消费任务                               │ ③ 发布任务/工具事件
              ▼                                          │
┌─────────────── Worker Node（计算层，CPU/网络密集）─────────────┐
│  消费队列、RAG/KAG 检索、组装 MCP 工具、调 LLM、更新状态、检查取消    │
└────────────────────┬──────────────────────────────────────────┘
                     │  可按 processes 配置拉起多个子进程；
                     │  亦可按需拉起 MCP Server 子进程（stdio）

  前端 SSE 流：API Server 订阅 NATS 后，将 task_update / tool_call
  事件通过 SSE 推送给浏览器（即 ④ -> API -> 浏览器，见上方 API 侧）
```

### 2. 一条完整请求的生命周期（必背）

1. 前端登录拿到 JWT，存 localStorage。
2. 前端 `POST /api/tasks/submit`（或 `POST /api/agents/:id/run`）携带 Bearer Token。
3. 中间件鉴权 + Redis 限流（INCR+EXPIRE，超限 429）。
4. `SubmitTask`：查或建会话（`resolveConversationID`）、空标题自动生成（`ensureConversationTitle`），构造 Task（UUID、默认普通优先级、`MaxRetry=3`、状态 `pending`）。
5. `AddTask`：写 MySQL → 写 Redis 缓存（24h TTL）→ 入 Asynq 队列（high/default/low 优先级）。
6. 立即返回 `202 Accepted`（关键：不等待结果）。
7. Worker 从队列取任务 → 先检查是否已被取消 → 置 `processing`。
8. `resolveTools` 按 Agent 白名单动态加载工具（过滤 `disabled`，私有 MCP 工具走连接池懒加载）。
9. 组装 `systemPrompt`：默认人设 + （绑定了 `internet_search` 时注入强制搜索指令）+ RAG 知识库上下文 + KAG 图谱上下文。
10. 拼装历史消息：按 token 预算加载会话历史（`max_history=20`），超上下文阈值自动把最早轮次压缩为滚动摘要（保留最近 `keep_recent=6` 条原始消息）。
11. 调 LLM（支持 Agent 级覆盖 model/api_key/base_url；每次调用前校验运行级/任务级预算，超限熔断不可重试；失败指数退避重试，超过 `MaxRetry=3` 置 `failed`）。
12. 调用工具时通过 `PublishToolEvent` 经 NATS 广播工具调用事件。
13. 以 asynq 传入的 ctx 为父派生可取消上下文（叠加配置超时 `timeout_seconds`），登记进 Worker 的 in-flight 注册表；收到 NATS `global_task_cancel` 取消指令即 `cancel()` 中断进行中的 LLM 调用。
14. 成功后通过 `UpdateTaskIfActive`（CAS 条件写回 `WHERE status NOT IN ('cancelled','completed')`）置 `completed`；0 行受影响即视为已被并发取消，丢弃结果并记录日志；否则写 MySQL + 写 Redis 缓存 + **经 NATS 发 `global_task_updates`**。
15. API 订阅 NATS → 转 SSE 推送：`task_update`（任务状态）/ `tool_call`（工具调用过程）两个事件。
16. 前端收到事件，更新任务列表与工具调用轨迹。

## 四、核心模块与技术点（按「是什么→为什么→怎么做→面试怎么答」）

### 1. 微服务拆分（API + Worker）

- **是什么**：把「接客」和「干活」拆成两个独立进程，`cmd/api/main.go` 与 `cmd/worker/main.go` 两套入口。
- **为什么**：AI 任务慢、重、易阻塞；HTTP 接口要求快、稳、抗并发。放一个进程会互相拖累。
- **怎么做**：API 与 Worker 通过「Redis（Asynq 队列 + 缓存）」与「NATS（实时事件）」两条通道协作，并以 MySQL 作为共享持久化状态；Worker 支持 `queue.processes` 配置拉起多个子进程。
- **面试答**：核心是「接入层与计算层解耦」，接入层只做轻量操作快速返回，计算层独立扩容、故障隔离。

### 2. Asynq 消息队列（削峰 + 优先级 + 重试）

- **是什么**：基于 Redis 的异步任务队列。
- **为什么**：大模型调用慢，用队列把「瞬时洪峰」蓄起来，Worker 匀速消费。
- **怎么做**：
  - 三优先级队列 `high:6 / default:3 / low:1`。
  - `AddTask` 三步：落 MySQL → 写缓存 → 入队；队列满返回 503。
  - 失败返回 error 给 Asynq 自动指数退避重试，`MaxRetry: 3`；处理函数里手动维护 `retries` 计数。
- **面试答**：一句话「API 快速收单 + 队列削峰填谷 + Worker 并发消费」。

### 3. Cache-Aside 缓存（MySQL + Redis 双写）

- **怎么做**：读先查 Redis，未命中查 MySQL 再回写；写先更新 MySQL 再更新 Redis 缓存（任务 24h TTL，Agent 5min TTL）。
- **面试答**：这是旁路缓存模式，用 TTL 兜底保证最终一致性；追问可延伸到「删除 vs 更新缓存」「延时双删」「Canal 订阅 Binlog」。

### 4. SSE + NATS（跨进程实时推送）

- **为什么**：任务进度是单向数据流（后端→前端），SSE 比 WebSocket 轻、比轮询省。
- **怎么做**：Worker 更新状态时 `eventBus.PublishJSON("global_task_updates")`，API 进程 `eventBus.Subscribe` 后广播给对应用户的 channel，`StreamTasks` 用 `c.SSEvent` + `Flush` 推送。
- **关键细节**：SSE 用 URL 参数传 token（EventSource 无法自定义 Header）；实时事件走独立 NATS 通道，与 Asynq 队列 / Redis 缓存彻底解耦。
- **面试答**：这是微服务解耦的关键——「Worker 不直接连前端，而是 Worker → NATS → API → SSE → 浏览器」。

### 5. 认证体系（JWT + bcrypt）

- 注册：bcrypt 单向哈希存密码。
- 登录：查库比对密码 → 签发 JWT（HS256，24h）。
- 鉴权：`AuthMiddleware` 解析 Bearer Token → 把 `userID` 注入 Gin Context。
- 忘记密码：验证码存 Redis（5 分钟）模拟短信。
- **面试答**：无状态 JWT 适合分布式，中间件统一注入身份，Handler 只关心「当前是谁」。

### 6. Redis 限流（防刷）

- 用 Redis `INCR` + `EXPIRE` 实现固定窗口限流，Key 优先用 userID，降级用 IP。
- 超限返回 429。
- **面试答**：INCR 原子操作保证并发安全，Redis 故障时降级放行保证可用。

### 7. Agent 平台（可复用智能体配置）

- **是什么**：把人设（system_prompt）、模型、Key 等固化成一个可复用的 `Agent` 实体（`system_prompt/model/api_key/base_url/status`）。
- **怎么做**：
  - 创建/编辑/删除/列表/详情（`POST/GET/PUT/DELETE /api/agents...`），`status` 取值范围 `active/archived`（当前无独立启停端点，创建默认 active）。
  - `POST /api/agents/:id/run` 等价于「提交一个绑定该 Agent 的任务」，会自动解析会话 ID。
  - 绑定白名单：`BindTools/ListAgentTools/UnbindTool`（工具）、`BindKnowledgeBases/ListAgentKnowledgeBases/UnbindKnowledge`（知识库）。
  - 运行时：Worker 按 Agent 取其工具与知识库，并支持 Agent 级覆盖 `model/api_key/base_url`。
- **面试答**：Agent 是「用户可配置的智能体模板」，把「每次拼 Prompt」升级为「一次配置、处处复用」，并从中引出工具白名单与知识库绑定两个关键设计。

### 8. 知识库与 RAG / KAG（GraphRAG 双路召回）

- **知识库模型**：`KnowledgeBase`（`type: rag/kag/hybrid`，`status: pending/building/ready/failed`）；`Document`（`status/chunk_count`）。
- **入库流程（异步入库）**：上传文档（`POST /api/knowledge-bases/:id/documents`，multipart 或 JSON，10MB 限制，仅限文本类）→ KB 置 `building` + `EnqueueKBBuild`（已收口 `asynq.MaxRetry(3)`）→ Worker `handleKBBuild`：分块（RecursiveCharacter，`ChunkSize=500`、`ChunkOverlap=50`）→ 生成 per-doc 摘要（摘要层，供运行期渐进披露）→ Qwen3-Embedding（text-embedding-v4，1024 维）dense 向量 + gse 中文分词构建 BM25 sparse 向量 → 写入 Milvus Collection `kb_chunks`（**按 `kb_id` 字段隔离**）→ 文档置 `ready` + 记录 `chunk_count`，KB 置 `ready` + `doc_count++`。
- **RAG 检索**：问题向量化 → Milvus HybridSearch 双路召回（dense COSINE + sparse BM25，每路取 2×topK 候选，RRF 融合）→ 可选 Ollama rerank（qwen3-reranker）重排取 topK（失败回退召回序）→ 注入 `systemPrompt` 的 `<knowledge_base_context>`。
- **KAG 检索**：LLM 抽取三元组 → Neo4j `MERGE` 入库；检索时 `RetrieveGraphContext` 走 LLM Text2Cypher 生成查询语句 → 执行 → 结果注入 `<knowledge_graph_context>`。
- **面试答**：RAG 是「搜文本」，KAG 是「查关系」，两者结合实现「双路召回」，既解决知识盲区又支持关系推理、降低幻觉。

### 9. MCP 工具平台（插件化工具市场，本项目的核心亮点）

- **是什么**：一套「工具管理平台」，让 Agent 不只有内置工具，还能按需注册、绑定外部 MCP 工具（联网搜索、飞书、GitHub 等）。
- **为什么**：LLM 能力受限于「内置工具」，而外部能力分散在各 MCP Server 上；通过统一抽象 + 白名单绑定，实现工具像插件一样动态接入，且只对显式绑定的 Agent 开放。
- **怎么做（四层）**：
  1. **统一抽象**：自定义 `Tool` 模型（`name/type(builtin|mcp)/display_name/description/config(JSON)/is_builtin/status(active|disabled)`）+ `toolregistry.Registry`；内置工具与 `MCPServerTool`（转发到 mcpgo 的 CallTool）都统一注册，`List()` 返回给 Worker 用。
  2. **动态加载**：Worker 的 `resolveTools` 按任务绑定的 Agent 从 `agent_tools` 白名单取工具；用户私有 MCP 工具按 `config`（`command/args/url/env`）通过 `mcpPool` 连接池**懒加载**拉起 stdio 子进程或远程 URL（SSE/HTTP），`GetTools` 拿到工具列表再注册，避免每个任务都重新拉起子进程。
  3. **发现与接入**：`POST /api/tools/search` 用自然语言 → LLM 解析为结构化意图（keywords/npm_search/description）→ 调 GitHub/npm 搜索 API 返回候选；飞书作为官方预置（`@larksuiteoapi/lark-mcp`，可 OAuth 用户身份）一键接入。
  4. **生命周期管理**：注册/编辑（`UpdateTool`，限制非内置且归属当前用户）/测试连接/启停（`UpdateToolStatus`，仅 `active|disabled`）/删除；`resolveTools` 会过滤 `status == disabled`，做到停用的工具**运行时彻底不可用**。前端「工具管理」页按 Tab 分组（工具列表 / 添加工具），并反查展示每个工具被哪些 Agent 绑定（`ListToolAgents`）。
- **底层连接池**：`mcpclient.Pool` 按工具 id 缓存 `Wrapper`，`Get` 命中缓存直接复用、未命中才拉起 stdio 子进程或远程连接（懒加载 + 复用），避免高频任务反复拉起进程。（当前为全局串行懒加载，高并发下是已知优化点，见「难点」末尾技术债）
- **亮点细节**：针对 Qwen2.5 不标准输出 `tool_calls` 的问题，用正则从 Content 提取 JSON 工具调用；工具调用过程通过 `PublishToolEvent` → SSE `tool_call` 实时展示。
- **面试答**：MCP 赋予模型「外挂工具」的 Agent 能力；我把工具做成「可发现、可注册、可绑定、可启停」的平台，并通过连接池规避了「每个任务拉起子进程」的性能坑。

### 10. 会话管理与多轮对话记忆

- **会话模型**：`Conversation`（`id/user_id/agent_id/title`），每个会话关联一个用户与某个 Agent（可空）。
- **管理**：创建/列表/详情/删除（`POST/GET/DELETE /api/conversations...`）；提交任务时自动「查或建会话」。
- **标题**：会话标题为空时用首次消息内容自动生成（`generateTitle` 截取前 30 个字符、去换行）。
- **记忆**：Worker 按 token 预算加载会话历史（`max_history=20`），估算 token 达到上下文窗口阈值（`context_window × compress_threshold`，默认 70%）时，自动把最早轮次压缩为滚动摘要并持久化（`Conversation.summary/summary_cutoff`），仅保留最近 `keep_recent=6` 条原始消息；压缩失败走可告警信号（Prometheus `compress_failed`）而非静默回退。
- **面试答**：以「会话」为单位组织多轮对话，用「滑动窗口 + 滚动摘要」双层记忆，既保留短期原文又压缩远期上下文，控制 Token 消耗与长对话成本。

### 11. Redis Sentinel 高可用

- 代码支持 `standalone` / `sentinel` 双模式（`config.redis`），`UseSentinel()` 决定连接方式。
- 本地搭了 1 主 + 2 副本 + 3 Sentinel（`docker-compose` 的 `redis/redis_replica_1/2/redis_sentinel_1/2/3`），完成故障切换演练。
- **面试答**：Redis 承担缓存与 Asynq 队列这两条核心数据链路太关键，所以第一步上 Sentinel（主从 + 自动 failover），后续可演进 Cluster；实时事件走独立 NATS 通道，不受 Redis 切主影响。

### 12. 取消任务（NATS 广播 + CAS 条件写回）

- **控制通道**：`POST /api/tasks/:id/cancel` 先经 `CancelTaskIfActive`（`WHERE status IN ('pending','processing')` 才置 `cancelled`），再经 `PublishTaskCancel` 向 NATS `global_task_cancel` 广播取消指令；所有 Worker 进程订阅该主题，命中本进程 in-flight 注册表时调用 `cancel()` 中断进行中的 LLM 调用。
- **可取消上下文**：Worker 以 asynq 传入的 ctx 为父（而非 `context.Background()`）派生可取消上下文并叠加配置超时，取消指令或 asynq 取消都会在下一次 socket 读时中断 LLM HTTP 调用。
- **正确性保证**：Worker 一切终态/中间态回写统一走 `UpdateTaskIfActive`（CAS 条件更新 `WHERE status NOT IN ('cancelled','completed')`），0 行受影响即视为任务已被并发修改，丢弃本次结果并记录日志——「取消任务不会被回写 completed」由机制保证而非措辞承诺。
- **面试答**：这是「跨进程控制 + 并发安全」的组合拳——控制走 NATS 广播（免服务发现、契合多子进程架构），正确性靠 CAS 条件写回兜底，替代了原先未生效的 gRPC 桩（已删除）。

### 13. Agent Harness 工程化护栏（六项目标落地）

> 把 GoTaskAI 从「异步任务调度平台」补齐为「可验证、可控制、可计量、可观测、可回归」的 Agent Harness。

| # | 目标 | 落地要点 |
|---|---|---|
| 1 | 验证循环 | 修复工具参数解析静默失败缺陷（失败改以 tool 角色错误消息回传 LLM + observer，杜绝孤儿 `tool_calls`）；MCP 工具入参走 JSON Schema 校验，非法同样回传 LLM 自修正 |
| 2 | 成本预算与熔断 | `llm.Budget` 注入 `generateWithClient` 模型调用循环，覆盖单任务单次上限（`max_calls_per_task`）与跨重试累计上限（`max_total_calls_per_task`）；从 `resp.Usage` 计量 token，`AccumulateTaskUsage` 原子累加 + 缓存失效；CostUSD 按模型单价折算；`kb:build` 显式 `asynq.MaxRetry(3)` 收口；超时配置化 `timeout_seconds` |
| 3 | 可观测性 | 新增 `RunLog`/`ToolCallLog` 观测表 + `trace_id` 透传；Prometheus 9 组指标（任务耗时/次数/重试、LLM 调用/token/成本按队列、工具调用、kb:build、压缩尝试/失败率），API 与 Worker 分别暴露 `/metrics` |
| 4 | 确定性控制 | 见核心模块十二：可取消 ctx 派生 + NATS 广播控制 + `UpdateTaskIfActive`/`CancelTaskIfActive` CAS 条件写回 |
| 5 | 上下文渐进式披露 | RAG 按 min-max 归一化 Score 分层注入（高分全文、低分减半）；KAG 按 `graph_top_n` 条数上限 + LLM 关联度过滤（单独判据，不共用阈值）；摘要层在 kb:build 构建期生产 per-doc 摘要；命中片段 `max_chunk_chars` 截断 + 两路共享 `max_context_chars` 总量上限 |
| 6 | Agent 评估 harness | `internal/eval`：用例 = 问题 + 期望工具 + 期望答案；固定采样（`Sampling{Temperature,TopP}`）+ 每例独立运行 N=5 次，输出工具命中率/答案相似度的均值、方差、95% CI（半宽裁剪）；`cmd/eval -threshold` 以非零退出码作为 CI 回归闸门；embedding 失败单列 `EmbeddingErrors` 不静默记 0 分 |

## 五、项目亮点（面试最值得讲的 3-5 个点）

1. **异步解耦 + 削峰填谷**：API 秒回 202，队列蓄洪，Worker 匀速消费，天然抗高并发。
2. **GraphRAG 双路召回 + 渐进披露**：RAG（Milvus dense + sparse BM25 双路 + RRF 融合 + rerank 重排）+ KAG（图谱）混合检索，按 Score/关联度分层注入 + 摘要层，既解决知识盲区又控制上下文成本。
3. **跨进程实时推送**：NATS + SSE 打通 Worker→API→前端，实现真正的微服务解耦，且能实时展示工具调用过程。
4. **分层消息架构**：Redis 承担缓存 + Asynq 队列，NATS 独立承担跨进程实时事件与取消控制，队列与事件通道解耦，避免单一 Redis 故障波及全链路（并可上 Sentinel 高可用）。
5. **MCP 工具市场（插件化）**：把工具做成「可发现、可注册、可绑定、可启停」的平台，支持联网搜索、飞书等外部 MCP 工具，并通过连接池动态加载、按 Agent 白名单隔离。
6. **Agent Harness 工程化护栏**：验证循环（Schema 校验）、成本预算熔断、Prometheus 可观测、CAS 确定性控制、评估 harness 回归闸门，让 Agent 能线上长期稳定运行。

## 六、难点与挑战（体现思考深度）

1. **大模型输出不规范**：Qwen2.5 不按标准 `tool_calls` 输出，需要正则从 Content 里提取工具调用 JSON 做兼容。
2. **取消任务的并发安全**：多 Worker 共享 MySQL/Redis 状态源，先以可取消 ctx 派生 + NATS 广播中断进行中的 LLM 调用，再用 `UpdateTaskIfActive`（`WHERE status NOT IN ('cancelled','completed')`）条件写回兜底，把「取消不被回写 completed」从措辞承诺变为机制保证。
3. **SSE 鉴权**：EventSource 无法自定义 Header，改用 URL 参数传 token。
4. **Redis Sentinel 改造**：切主有短暂重连抖动窗口，Sentinel 返回内网地址对宿主机不可达，需要固定 IP 监控。
5. **缓存一致性**：任务状态高频变化，用 Cache-Aside + TTL 兜底。
6. **MCP 连接生命周期管理**：MCP stdio 是子进程，若每个任务都拉起会开销巨大且并发失控，于是用 `mcpclient.Pool` 连接池做懒加载 + 复用（按 id 缓存）；工具调用失败要降级为「工具返回错误」回传 LLM，而非拖垮整个任务。
7. **双层重试的成本放大**：业务级 `Task.MaxRetry` 与 asynq 队列级重试互不知情，`kb:build` 还默认约 25 次重试；通过预算对象（单任务单次 + 跨重试累计）+ `EnqueueKBBuild` 显式 `MaxRetry(3)` 收口。
8. **跨重试累计计量的缓存失效**：预算累计字段写入 MySQL 后若不失效 Redis 缓存，下次重试读到过期计数导致熔断失效，故 `AccumulateTaskUsage` 累加后显式 `Del` 缓存。
9. **LLM 输出非确定的评测**：答案评测 embedding 失败若静默记 0 分会污染质量基线，改为单列 `EmbeddingErrors`，CI 半宽裁剪到 [0,1]。

### 项目不足与技术债（被追问「项目有什么不足」时主动讲）

> 主动讲不足比被问出来更显真实，配合「已识别 + 有改进方向」的回答结构。

| 技术债 | 现状 | 改进方向 |
|---|---|---|
| JWT 密钥硬编码 | `gotaskai-super-secret-key` 写在代码里 | 改环境变量 + 显式校验签名算法 |
| `/api/admin/*` 未鉴权 | RAG/KAG 手动入库端点无鉴权 | 挂 AuthMiddleware 或独立管理鉴权 |
| 限流覆盖不全 | 仅 3 个任务提交端点限流 | 统一限流覆盖全部写接口 |
| 输出 Schema 强校验未落地 | Task/Agent 无输出表达字段 | 先设计输出 Schema 再结构化生成 |
| MCP 连接池全局串行 | `Get` 全程持锁懒加载 | 分段/分片锁 + 空闲回收 |
| 前端无路由/状态管理 | `activeView` ref 手动切换 | 引入 Vue Router + Pinia |

**回答话术**：「项目现在能跑、也做了护栏，但我知道有几处需要补：安全上 JWT 密钥还没外置、admin 写入端点缺鉴权；工程上 MCP 连接池是全局串行懒加载，高并发会成瓶颈，后续要分片锁 + 空闲回收。」

## 八、简历项目描述模板（可直接改）

**项目二 · GoTaskAI（异步 AI 任务调度与 GraphRAG 对话平台，2026-02 ~ 2026-05）**

一句话定位：基于 Go 的高性能异步 AI 任务调度与 GraphRAG 对话平台，解决大模型 API 调用耗时、高并发资源浪费与私有知识缺失三大痛点。

**核心亮点**

- **GraphRAG 混合检索**：突破传统 RAG，基于 Milvus 双路召回（dense 向量 + sparse BM25 + RRF 融合 + rerank 重排）与 Neo4j 图谱检索（LLM 抽取三元组 + Text2Cypher），并按 Score/关联度分层注入，降低幻觉、控制上下文成本。
- **异步任务调度与重试**：基于 Asynq（Redis）构建多级优先级队列，实现指数退避重试 + 完整状态机（pending/processing/completed/failed/cancelled），保障高并发下任务可靠执行。
- **多轮对话与上下文管理**：基于 Conversation 的多轮历史 + 滚动摘要自动压缩（token 预算触发）；集成 MCP 协议与 Agent 工具调用引擎（连接池懒加载 + 白名单隔离），实现可追溯链路（trace_id + SSE）。
- **并发流控与稳定性**：Redis 固定窗口限流防刷，防止接口被恶意请求打垮、Token 资源被恶意消耗。
- **企业级工程化**：RESTful + JWT 鉴权、Worker 与 HTTP 服务优雅退出防任务丢失、NATS + SSE 跨进程实时可视化、Redis Sentinel 高可用。
- **Agent Harness 工程化护栏**：补齐验证循环（工具参数 Schema 校验）、成本预算熔断（单任务/跨重试双上限 + token 计量 + CostUSD）、可观测（Prometheus + RunLog/ToolCallLog 落表）、确定性控制（CAS 条件写回）、上下文渐进披露、评估 harness 回归闸门。

**技术栈**：Go、Gin、GORM、Asynq、Redis（Sentinel）、NATS、MySQL、Milvus、Neo4j、GraphRAG、MCP、SSE、JWT、Prometheus、Vue3。
