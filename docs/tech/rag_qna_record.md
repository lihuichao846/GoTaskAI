# RAG 与大模型对话系统：核心问题与实战记录 (FAQ)

本文档专门用于记录 GoTaskAI 项目中关于 RAG（检索增强生成）和 LLM（大语言模型）对话机制的核心问题、原理解析以及架构演进思路。

## 1. 介绍一下 RAG，以及 RAG 的具体过程？

**什么是 RAG (Retrieval-Augmented Generation)**：
RAG（检索增强生成）是一种通过外挂“私有知识库”，让大语言模型（LLM）能够在回答专业问题时做到“有据可查”、“照本宣科”的技术。它解决了大模型存在的“幻觉”以及“无法获取实时/私有数据”的痛点。

**RAG 的核心过程（两阶段）**：

**阶段一：数据入库 (Data Ingestion)**
1. **文档接收**：系统接收用户上传的文本或文档（如 Markdown、TXT 等）。
2. **文本切分 (Chunking)**：大模型无法一次性吃下整本书，需要使用切分器（如 `LangChainGo` 的 `RecursiveCharacterTextSplitter`）将长文档切成带有一定重叠的小块（Chunk）。
3. **向量化 (Embedding)**：将切分好的每个文本块发送给 Embedding 模型（如 `bge-m3`），将其转换为机器可计算的高维浮点数数组（向量）。
4. **向量入库 (Storage)**：将文本块的内容、元数据和生成的向量数据一起存入向量数据库（本项目中为 `Redis Stack` / `RedisVector`）。

**阶段二：检索与生成 (Retrieval & Generation)**
1. **用户提问向量化**：将用户在聊天框输入的问题，通过相同的 Embedding 模型转换成一个“查询向量”。
2. **相似度检索 (Similarity Search)**：拿着查询向量去向量数据库中进行 K-NN（K近邻）搜索，计算余弦相似度，找出与问题最相关的 Top K（如前 3 个）文本块。
3. **Prompt 动态拼接 (Context Injection)**：这是 RAG 的核心魔法。系统在后台将检索到的这 3 个文本块，通过 `<knowledge_base_context>` 等标签偷偷拼接到发给大模型的 System Prompt 中。
4. **大模型生成 (Generation)**：大模型阅读包含私有知识的完整 Prompt，根据参考资料生成精准的答案并流式返回给用户。

## 2. RAG 的底层大模型选了什么？

在本项目中，RAG 流程中涉及到的两种核心模型（向量化模型和生成模型）都统一采用了本地部署的开源模型，并通过 **Ollama** 引擎进行驱动。

1. **向量化模型 (Embedding Model)**：
   * **选型**：选择了 **`bge-m3`**。
   * **原因**：BGE (BAAI General Embedding) 是目前开源界非常优秀的中文/多语言向量模型。它负责将切分好的文本块以及用户的提问转换成高维向量（浮点数数组），以便在 RedisVector 中进行相似度检索。
   * **代码位置**：在 `api/rag.go` 和 `worker/pool.go` 中，均通过 `ollama.WithModel("bge-m3")` 进行了硬编码初始化配置。

2. **对话生成模型 (Generation LLM)**：
   * **选型**：当前默认配置为 **`qwen2.5:latest`** (通义千问 2.5)。
   * **原因**：Qwen 2.5 在中文理解、指令遵循以及代码能力上表现极佳，非常适合作为 RAG 的最终生成引擎。它负责阅读检索到的背景资料，并生成最终的答案。
   * **代码位置**：这部分是可配置的。在 `config/config.yaml` 中通过 `model: "qwen2.5:latest"` 进行了配置，底层通过 `go-openai` 库去调用 Ollama 提供的兼容 API（`http://127.0.0.1:11434/v1`）。

**总结**：
本项目实现了 100% 的私有化/本地化部署。无论是把私密文档变成向量（`bge-m3`），还是最终生成回答（`qwen2.5`），所有数据都不会离开你的本地服务器，这在企业级私有知识库场景中是极其重要的安全考量。

## 3. RAG 知识库的文本切割是怎么实现的？

**实现方式**：
项目中使用了 `LangChainGo` 框架提供的 `RecursiveCharacterTextSplitter`（递归字符切分器）。

**核心参数**：
*   **ChunkSize = 500**：限制每块文本最大长度为 500 字符，确保模型输入窗口的注意力聚焦。
*   **ChunkOverlap = 50**：相邻文本块保留 50 个字符的重叠部分。这就像“胶水”一样，防止在生硬切分时把一句话从中间截断（语境截断），保证了语义的连贯性。

**切分策略（递归）**：
它不会单纯按字数死板切割，而是按照优先级（段落 `\n\n` -> 句子 `\n` -> 空格 -> 字符）逐级尝试切分，最大程度保证切出来的每一块都是完整的句子或段落。

## 4. RAG 中的向量数据库具体是怎么存储的？

当面试官问到：“你说你把切分好的文本块存进了 Redis 向量数据库，那底层到底存了些什么？是怎么存的？”你可以这样回答：

在本项目中，我们使用了 `Redis Stack`（内部集成了 RediSearch 和 RedisVector 模块）作为向量数据库。当调用 `AddDocuments` 入库时，底层实际上存储了三个维度的核心数据：

**1. 向量数据 (Embeddings - 核心)**
*   **长什么样**：大模型（如 `bge-m3`）将一段文本计算后，返回的是一个定长的**高维浮点数数组**（例如 1024 维：`[0.123, -0.045, 0.887, ...]`）。
*   **怎么存**：在 Redis 底层，这串浮点数数组会被转换为连续的二进制字节流（BLOB）存储在内存中。并且为了支持极速的相似度搜索，Redis 会为这些向量构建 **HNSW（分层导航小世界）** 或 **FLAT（暴力枚举）** 索引算法树。

**2. 原始文本内容 (PageContent/Document)**
*   光存浮点数是不够的，因为当我们通过相似度算出了最匹配的浮点数数组后，必须要把对应的“人类能看懂的文字”拿出来喂给大模型。
*   所以在 Redis 的同一条记录（通常使用 Hash 结构存储）中，还会保存这段向量对应的原始文本块内容。

**3. 元数据 (Metadata - 附加属性)**
*   除了文本和向量，通常还会附带一个 JSON 格式的元数据字段。
*   比如存入 `{"source": "user_guide.md", "page": 1, "author": "admin"}`。
*   **作用**：在检索时支持**混合过滤查询 (Hybrid Search)**。比如你可以要求系统：“请帮我找出与问题最相似的向量，但前提是 `author` 必须等于 `admin`”。

**总结存储结构：**
在 Redis 内部，每一条切片后的知识库记录，其实就是一个包含了 `[向量二进制数据] + [原始文本片段] + [JSON元数据]` 的复合体，它们被包裹在一个唯一的 Key（如 `doc:uuid`）下，并被加入了 HNSW 向量索引中。如果你使用 Redis 客户端查看，它在底层通常是以 **Hash（哈希）** 的数据结构存储的，Hash 的各个字段分别保存了上述内容。

## 5. 向量数据库的存储会一直存放在 Redis 中吗？

**答案**：不会。Redis 适合前期的 MVP（最小可行性产品）阶段，但不适合海量数据的生产环境。

**为什么初期选 Redis**：
因为项目中为了做高并发缓存和 Asynq 队列，已经必须存在一个 Redis 实例。开启 Redis Stack 的向量模块可以做到“零额外组件部署成本”，对新手友好，且纯内存检索速度极快。

**为什么后期要换**：
*   **内存成本极高**：高维向量（如 1024 维的浮点数数组）体积庞大，存入 Redis 会极其消耗服务器最昂贵的内存资源。
*   **重启恢复慢**：虽然有 AOF/RDB 持久化保证数据不丢，但每次重启 Redis 时，必须把庞大的向量数据全部重新加载进内存才能对外服务，耗时极长。

**演进方案**：
未来将迁移到专门的向量数据库（如 Qdrant、Milvus 或 Chroma），它们基于磁盘（Mmap）或混合存储，成本更低。得益于 `LangChainGo` 的高度抽象，未来只需将初始化代码从 `redisvector.New` 替换为 `qdrant.New` 即可，底层的入库和检索核心业务流**完全不用改**。

## 6. 系统是如何解决对话的上下文（记忆）机制的？

**核心原理**：客户端维护状态，服务端拼接记忆。
大语言模型本身是无状态的（Stateless），它记不住你说过的话。因此，必须在每次提问时，把之前的聊天记录打包发给它。

**具体工程实现（GoTaskAI 项目方案）**：
1.  **前端（客户端）维护状态**：前端为每次连续对话生成并维护一个唯一的 `Session ID`。用户在同一个窗口下发送的每一句话，都会在 Payload 中携带这个 ID。
2.  **后端（服务端）拼接记忆**：Asynq Worker 在处理任务前，会根据这个 `Session ID` 去 MySQL 数据库中查询最近 6 条状态为 `Completed`（已完成）的历史任务。限制 6 条是为了防止上下文过长导致 Token 超限或费用飙升。
3.  **动态组装 Prompt**：将查出的历史任务反转排序（最老的在前，最新的在后），映射为标准的 `User` 和 `Assistant` 消息数组：
   *   `Role: "user", Content: ht.Payload` (用户的历史提问)
   *   `Role: "assistant", Content: ht.Result` (大模型历史的回答)
   这组历史消息会被夹在 System Prompt（系统设定及 RAG 检索出的背景知识）和当前新问题之间，最后通过 `openai.ChatCompletionMessage` 格式一并发送给大模型。

## 7. 业界常见的上下文记忆处理方式有哪些？

除了我们项目中采用的“滑动窗口”机制外，业界在处理大模型长上下文记忆时，通常会根据业务场景的复杂度和成本考虑，采用以下几种主流方案：

**1. 滑动窗口机制 (Sliding Window Memory) —— 本项目使用**
*   **原理**：只保留最近的 N 轮对话（如最近 6 条），丢弃更早的记录。
*   **优点**：实现简单，Token 开销极低，响应速度快，不会触发大模型的 Context Limit。
*   **缺点**：大模型会像“金鱼”一样，彻底忘记 N 轮之前讨论过的细节。

**2. 摘要记忆机制 (Summary Memory)**
*   **原理**：当对话轮数或 Token 数量达到阈值时，不直接丢弃老记录，而是**在后台悄悄调一次大模型**，让它把之前的长对话“总结”成一段几百字的摘要（Summary）。
*   **存储方式**：
    *   **持久化**：通常在数据库中新增一张 `SessionSummary` 表（字段如 `SessionID`, `SummaryText`, `LastTaskID`），或者直接在现有的 `Task` 会话中维护一个全局的 Summary 字段。
    *   **注入过程**：当生成了新摘要后，下次用户再提问，系统会从数据库查出这段 `SummaryText`，并将其作为 System Prompt 的一部分（如：“这是之前对话的摘要：xxx”）发给大模型，同时清空或折叠旧的原始对话记录。
*   **优点**：能以较小的 Token 开销保留长期的核心语境。
*   **缺点**：会丢失对话的具体细节，且后台需要额外的 API 调用开销。

**3. 向量检索记忆 (Vector Store Memory / Zep)**
*   **原理**：把用户的每一句聊天记录，都当作 RAG 里的知识块，计算出 Embeddings 向量并存入 Redis 或 Qdrant 等向量数据库中。当用户提问时，去向量库里搜索与当前问题语义最相关的历史聊天记录，拼接到上下文中。
*   **存储方式**：
    *   将 `{"role": "user", "content": "帮我写一个快速排序算法"}` 作为一个 Document，计算其 Embedding 向量。
    *   在底层数据库（如 Redis Stack）中，会以 **Hash（哈希）** 的数据结构存储这条记录，其中包含了 `原始对话文本`、`生成的浮点数向量数组 (Blob)` 以及 `SessionID 等元数据`，并为其建立 HNSW 向量索引。存入专门的 `ChatHistoryVectorStore` 中。
*   **优点**：可以实现“无限长”的长期记忆，哪怕是几个月前提到过的一个词也能被检索出来。
*   **缺点**：架构极其复杂（相当于把 RAG 流程套嵌在日常聊天里），语义检索的准确率直接决定了记忆的准确性。

**4. 令牌截断机制 (Token Buffer Memory)**
*   **原理**：不按“轮数”截断，而是通过引入 `tiktoken` 等分词器算法，精确计算每一句话消耗的 Token 数。始终保留刚好不超过阈值（如 4000 Tokens）的最大上下文量。
*   **存储方式**：依然存在 MySQL/Redis 等常规数据库中，只是在“拉取”和“组装 Prompt”时，多了一步 `CalculateTokens()` 的动态截断计算。
*   **优点**：是对大模型输入窗口利用率最高、最极致的做法。
*   **缺点**：需要引入专门的 Tokenizer 库，计算开销稍大。

## 8. AI 回答有没有做流式传输？如何做流式传输？

在当前的 GoTaskAI 项目中，我们**实现了任务状态的实时流式推送（SSE）**，但对于大模型生成文字本身的“打字机”流式传输（Token by Token），我们在底层 API 调用时选择了**整体返回（非流式）**。

### 为什么当前没有做大模型的 Token 流式传输？
在 `internal/pkg/llm/client.go` 的 `Generate` 方法中，我们调用大模型时使用的是 `client.CreateChatCompletion` 而非 `CreateChatCompletionStream`。主要原因如下：
1.  **架构限制与 MCP 工具调用**：我们的 Worker 可能会触发多次 LLM API 调用（比如先调用一次判断是否需要使用 `internet_search` 搜索工具，拿到搜索结果后再调用第二次进行最终总结）。在处理多轮工具调用时，如果开启 Token 流式传输，会导致前台看到大量中途的分析过程和工具调用的乱码，极大增加代码处理的复杂度。
2.  **异步队列的设计初衷**：我们的任务是推入 Asynq 队列交由后台 Worker 异步慢慢处理的，Worker 处理完毕后才会把完整的 `Result` 保存到 MySQL 数据库中。这种“后台静默处理”的机制天然更适合整块生成和持久化。

### 系统不是使用了 SSE 吗？
是的，系统确实使用了 SSE（Server-Sent Events）。但需要明确：**SSE 只是一个传输通道，通道里传输什么数据是由业务决定的。**
*   **在我们项目中**：前端建立 SSE 连接后，后端通过这个通道推送的是**宏观的任务状态变更**（比如从 `pending` 变成了 `processing`，最后变成带有完整回答的 `completed`），所以你能看到前端页面上状态的无刷新自动跳动。
*   **在 ChatGPT 中**：SSE 通道里推送的是大模型吐出来的**每一个单字（Token）**。

### 如果要做大模型文字的流式传输，应该怎么做？
如果面试官问到流式传输的原理和做法，你可以从以下几个层面来回答：

**1. 大模型 API 层面（调用方）**
在使用 `go-openai` 或 `LangChainGo` 时，需要将普通的请求切换为 Stream 模式（如 `CreateChatCompletionStream`）。它会返回一个数据流对象（Stream），你需要写一个 `for` 循环不断读取 `stream.Recv()`，每次只能拿到 1~2 个字（Token）。

**2. 后端推送层面（Server-Sent Events, SSE）**
一旦后端一个个字拿到了大模型的回复，如何实时推给前端呢？这里必须使用 **SSE（Server-Sent Events）** 技术。
在 Gin 框架中，这很容易实现：
*   设置 HTTP 响应头：`Content-Type: text/event-stream`、`Cache-Control: no-cache`、`Connection: keep-alive`。
*   使用 `c.SSEvent("message", 那个字)` 把字发出去。
*   **最关键的一步**：每次发送后必须立刻调用 `c.Writer.Flush()`，把缓冲区里的这一个字强制冲刷给前端浏览器，否则 Nginx/Gin 会把字攒够一大坨才发。

**3. Nginx 代理层面（运维配置）**
这是新手最容易踩的坑！如果你的后端挂在 Nginx 后面，Nginx 默认会开启缓冲（Buffer）。也就是说，后端虽然是一个字一个字 `Flush` 出来的，但 Nginx 会觉得“一个字发一次太浪费网络”，它会把字拦截下来，攒够一个数据包再发。
*   **解决方案**：必须在 Nginx 配置对应的 location 中明确关闭缓冲：
    ```nginx
    proxy_buffering off;
    proxy_cache off;
    ```

**4. 前端接收层面**
前端不再使用传统的 `fetch` 或者是 `axios` 去接收完整的 JSON。
需要使用浏览器原生的 `new EventSource('/api/chat/stream')`，或者使用 `fetch` 配合 `ReadableStream` 去一点点读取流式数据，并将每次收到的字拼接到屏幕上，实现“打字机”效果。

## 9. LangChainGo 框架和 Python/JS 版本的 LangChain 是一样的吗？

在 GoTaskAI 项目中，我们使用的是 `github.com/tmc/langchaingo` 框架来构建 RAG 工作流。

**答案**：它们是**同宗同源的生态实现，但不是同一个代码库**。

**详细解析**：
1. **概念与架构的一致性**：
   `LangChainGo` 完美复刻了原版（Python 版）`LangChain` 的核心架构思想和组件抽象。你在 Python 版里熟悉的那些概念，比如 `LLMs`（模型接口）、`Embeddings`（向量化）、`Document Loaders`（文档加载器）、`TextSplitters`（文本切分器，如本项目用的 `RecursiveCharacterTextSplitter`）以及 `VectorStores`（向量存储，如本项目用的 `RedisVector`），在 `LangChainGo` 中都有几乎一模一样对应名称的接口和实现。
2. **语言生态的差异**：
   原版 `LangChain` 是用 Python（也有官方的 JS/TS 版本）编写的，生态极其繁荣，支持的第三方模型和数据库插件最多，迭代速度最快。而 `LangChainGo` 是 Go 社区的开源实现，专门为 Go 语言的高并发、强类型和编译型特性打造。
3. **为什么本项目选择 LangChainGo**：
   * **统一技术栈**：我们的后台业务逻辑（路由、高并发队列、数据库操作）都是 Go 语言写的，如果硬要在架构里塞一个 Python 的 LangChain 服务，就需要维护两种语言的微服务，增加跨语言调用的 RPC/HTTP 延迟和运维成本。
   * **接口解耦带来的红利**：正如我们在第 4 个问题（向量库演进）中提到的，因为 `LangChainGo` 提供了高度抽象的 `VectorStore` 接口，这让我们的业务代码与底层的具体组件彻底解耦。今天我们初始化的是 `redisvector.New`，明天换成 Qdrant 时只需改一行代码为 `qdrant.New`，核心业务流（切分、入库、相似度检索）完全不用改。这就是使用标准编排框架的最大意义。

## 10. 面试常问：LangChain 到底是什么？它的核心组件有哪些？

如果面试官问你：“你项目中用到了 LangChainGo，那你能通俗地介绍一下 LangChain 到底是个什么框架吗？它解决了什么痛点？”

**核心一句话回答**：
LangChain 是一个**大语言模型（LLM）应用开发的标准编排框架**。它的本质是把那些零散的、各自为战的 AI 接口和工具（如 OpenAI API、各种向量数据库、各种文本加载器）封装成了**统一的抽象接口**，让开发者可以像搭积木一样把它们串联起来。

**生活化比喻（通俗易懂版）**：
你可以把开发 AI 应用想象成开一家“餐厅”。
如果没有 LangChain，你（老板）必须亲自跑到菜市场去买白菜（调用文档加载 API）、跑去肉联厂买猪肉（调用向量数据库 API）、跑去调料店买盐（调用 OpenAI 接口），不仅每家的规矩都不一样，而且如果你明天想把猪肉换成牛肉，你还得重新找门路，极其繁琐。
**LangChain 就像是一个“超级厨房中控台”**。它帮你把所有原材料供应商的接口都标准化了。你只需要下指令：“给我切菜、给我炖肉、出锅”。底下到底用的是 OpenAI 还是 Ollama，是 Redis 还是 Qdrant，你完全不需要关心。

**LangChain 解决的痛点（为什么要用它）**：
如果没有 LangChain，今天你想接 OpenAI，明天想换成本地的 Ollama，后天想把向量库从 Redis 换成 Qdrant，你每次都要看不同的 API 文档，重新写一遍 HTTP 请求和数据解析代码。
有了 LangChain，你只需要操作它定义好的统一接口（比如 `llm.Generate()` 或 `vectorstore.SimilaritySearch()`），底层随便怎么换，上层业务代码一行都不用改。（也就是**解耦**）。

**LangChain 的核心组件（六大基石）**：
1. **Models (模型抽象)**：统一了各种 LLM（大语言模型）和 Embeddings（向量化模型）的调用接口。
2. **Prompts (提示词模板)**：提供了动态拼接、格式化提示词的工具（比如给大模型注入 RAG 的背景知识模板）。
3. **Retrieval (检索系统 - RAG的核心)**：包含 `Document Loaders`（加载 PDF/Word）、`Text Splitters`（文本切分器）、`Vector Stores`（向量数据库封装），专门用于从私有数据中检索知识。
4. **Chains (链)**：把上面这些组件像流水线一样串起来。比如：输入提问 -> 检索向量库 -> 拼接 Prompt -> 调用 LLM -> 返回结果，这一整套动作就是一个 Chain。
5. **Memory (记忆)**：大模型是无状态的，Memory 组件专门负责把历史聊天记录保存并注入到新的 Prompt 中（就像我们用 `Session ID` 在 MySQL 里做的那样）。
6. **Agents (智能体)**：最前沿的功能。让大模型根据用户的复杂意图，**自己决定**去调用哪些外部工具（比如自己决定去调 Google 搜索 API、去执行 Python 脚本），最后综合结果返回给用户。

## 11. 面试常问进阶：LangChain 和 LangGraph 有什么区别？

如果面试官看你对 LangChain 很了解，可能会抛出一个非常前沿的进阶问题：“那你听说过 LangGraph 吗？它和 LangChain 是什么关系，解决了什么新痛点？”

**核心一句话回答**：
**LangChain 是一条单向的流水线（Chain），而 LangGraph 是一个带循环和条件判断的复杂流程图（Graph），它是专门为了开发复杂的多智能体（Multi-Agent）系统而生的。**

**详细解析与痛点对比**：

1. **LangChain 的局限性（为什么会有 LangGraph？）**
   * 在早期的 AI 应用（比如最基础的 RAG）中，我们的执行逻辑是一条**直肠子（DAG，有向无环图）**：提问 -> 检索 -> 组装 Prompt -> 调大模型 -> 输出。这就是典型的 **Chain（链）**。
   * 但当我们想做一个高级的 **Agent（智能体）** 时，直肠子行不通了。比如让 AI 写代码，真实的流程应该是：写代码 -> 运行测试 -> **如果报错，把报错信息喂给大模型重写** -> 再测试 -> 直到成功为止。
   * 这种**“如果...就返回重做（循环/While Loop）”**的逻辑，传统的 LangChain 极难实现，它的代码组织会变得像面条一样混乱且难以调试状态。

2. **LangGraph 是怎么解决的？**
   * LangGraph 是 LangChain 官方推出的一个底层库（可以说是 LangChain 的进化版或高级插件）。
   * 它把应用抽象成了**图（Graph）**结构，由节点（Nodes）和边（Edges）组成。
   * **Nodes（节点）**：就是一个个干活的函数。比如一个节点负责写代码，一个节点负责跑测试。
   * **Edges（边）**：这是最强大的地方！它支持**条件边（Conditional Edges）**。你可以定义规则：测试节点的输出如果带有 error，连线就指回写代码节点；如果是 success，连线就指向输出节点。
   * **状态保存（State）**：LangGraph 在整个图流转的过程中，会维护一个全局的 State（状态字典）。这就相当于大模型在循环做任务时的“草稿本”，极其方便调试和保存断点进度。

**总结生活比喻**：
*   **LangChain** 像是一条**工厂流水线**。原料（问题）放进去，经过几道固定的工序（检索、生成），最后吐出产品（答案），绝不回头。
*   **LangGraph** 像是一个**带部门流转的公司**。策划部写完方案交个审核部，审核部觉得不行可以**打回**给策划部重写，来来回回拉扯（循环），直到老板满意了才发布。

## 12. KAG 知识库系统和 RAG 知识库系统的区别是什么？

如果面试官考察你对 AI 检索技术的最新发展趋势的了解，可能会问：“现在的 RAG 有什么痛点？听过 KAG 吗，它们有什么区别？”

**核心一句话回答**：
**RAG 是基于“文本切片 + 向量相似度”的模糊匹配检索；而 KAG 是基于“知识图谱 (Knowledge Graph) + 逻辑推理”的结构化精准检索。KAG 是对 RAG 在复杂逻辑推理场景下的终极升级。**

**详细痛点与区别对比**：

### 1. RAG 的核心逻辑与痛点
*   **RAG 怎么工作的**：像我们 `GoTaskAI` 项目里做的那样，把一整本说明书切成 500 字的小块，把这些小块变成一堆浮点数向量存进 Redis。用户提问时，算一下哪个切片的向量和问题的向量“长得最像”（余弦相似度），就把那个切片拿出来喂给大模型。
*   **致命痛点**：它只能做**字面语义上的模糊匹配**，缺乏宏观的逻辑推理能力。
    *   *举个例子*：文档 A 写了“张三是李四的爸爸”，文档 B 写了“李四是王五的爸爸”。
    *   如果你问大模型：“张三是谁的爷爷？”
    *   **RAG 会崩溃**。因为知识库里没有任何一个切片包含了“张三”和“爷爷”这两个词的相似向量。RAG 检索不出相关切片，大模型就回答不上来。

### 2. KAG (Knowledge Graph Augmented Generation) 是怎么解决的？
KAG 把 RAG 里的“向量数据库”换成了（或结合了）**知识图谱数据库 (如 Neo4j、NebulaGraph)**。
*   **KAG 怎么入库数据的**：在录入文档时，大模型会先阅读全文，把文本里的信息抽丝剥茧，提取成一个个的“实体”和“关系”，存成网状图。比如：`(张三) --[父亲]--> (李四) --[父亲]--> (王五)`。
*   **KAG 怎么检索数据的**：当用户问“张三是谁的爷爷”时，系统会把问题转换成图数据库的查询语句（Cypher / Gremlin）。图数据库顺着张三的节点往下跳两步，精准地找到了“王五”。
*   **优势**：KAG 不依赖模糊的文本相似度，而是依赖**严谨的网状关系推理**。它非常适合处理“医药成分溯源”、“公司股权穿透图”、“复杂人物关系”等需要逻辑跨度推理的场景。

**总结**：
*   **RAG** 就像在图书馆里用**全文关键字搜索**，适合找定义、找规章制度。
*   **KAG** 就像在公安局的**线索关系网**上顺藤摸瓜，适合找因果、找隐藏逻辑链。
在未来的企业级应用中，通常会采用 **RAG + KAG 的混合检索架构 (GraphRAG)**，既能回答文本细节，又能进行逻辑推理。

### 3. KAG (GraphRAG) 的具体落地实现流程

如果面试官追问：“如果让你在现有项目中把 RAG 升级为 KAG (GraphRAG)，你会怎么实现？”
你可以按照以下工程步骤来回答：

**第一步：基础设施准备 (图数据库)**
首先，我们需要引入一个支持图结构的数据库，比如 **Neo4j**（业界最主流）、**NebulaGraph**，或者如果是云服务可以使用阿里云的 Graph Compute 等。

**第二步：知识抽取与入库 (Knowledge Extraction - 最难的一步)**
这一步不再是简单地用 `TextSplitter` 切片了，而是要利用大模型的能力来“榨干”文本：
1. 我们需要写一段 Prompt（比如：“你是一个实体关系抽取专家。请阅读以下文本，提取出所有的 `[实体A, 关系, 实体B]` 三元组”）。
2. 让 LLM（如 Qwen2.5）阅读所有原始文档，输出结构化的 JSON 数据（比如 `{"source": "张三", "relation": "father_of", "target": "李四"}`）。
3. 将这些三元组通过图数据库的 API 写入数据库中，构建出庞大的节点（Nodes）和边（Edges）。

**第三步：意图识别与图检索 (Graph Retrieval)**
当用户在前端提问时（比如：“张三的孙子是谁？”）：
1. **Text2Cypher**：我们不再是把问题转成向量，而是先把问题发给 LLM，让 LLM 把用户的自然语言“翻译”成图数据库能听懂的查询语句（比如 Neo4j 的 `Cypher` 语句：`MATCH (a:Person {name: '张三'})-[:father_of]->()-[:father_of]->(grandson) RETURN grandson`）。
2. **执行查询**：拿着这句代码去查图数据库，数据库会顺着图的连线瞬间找到答案节点。

**第四步：混合生成 (Hybrid Generation)**
最后，把图数据库里查出的精准结构化关系（张三->李四->王五），连同传统的 RAG 查出的文字片段，一起丢进大模型的 Context 中，让大模型润色成一句人类听得懂的话输出给用户。

## 13. 什么时候使用消息队列？它主要是用来做什么的？

在 GoTaskAI 这种涉及大模型调用的项目中，引入消息队列（本项目采用 Asynq）是架构演进的必然结果。如果你在面试中被问到这个问题，请牢记消息队列的三大核心作用口诀：**异步、解耦、削峰**。
*   **痛点**：用户在页面提交一个问题，大模型需要思考 20 秒才能给出答案。如果使用同步调用，用户的浏览器会一直转圈卡死，HTTP 连接甚至可能因为超时（Timeout）而断开。
*   **MQ 的作用**：引入消息队列后，用户的请求只需要 0.01 秒就可以存入队列。后端立刻给用户返回一个“任务已受理，排队中”的响应。用户可以去干别的，等后台的 Worker 慢慢把 20 秒的任务跑完后，再通过 SSE 或短信/邮件通知用户。这极大地提升了用户体验。

### 2. 流量削峰 (Traffic Shaving / Peak Clipping)
*   **痛点**：假设双十一或者突发热点事件，一瞬间有 10000 个人同时向你的服务器发起了对话请求。你的服务器 CPU 和大模型的 API 接口根本扛不住这么高的并发，会瞬间宕机或触发 429 限流报错。
*   **MQ 的作用**：消息队列就像水库的“大坝”。无论外面涌来多大的洪水（10000 个请求），都先被大坝（Redis/Kafka）挡住存起来。大坝底下的发电机（Worker Pool）只按照自己能承受的速度（比如设置 `Concurrency: 5`，即同时只处理 5 个任务）匀速地从水库里放水处理。这样就保护了脆弱的下游服务不被压垮。

### 3. 服务解耦 (Decoupling)
*   **痛点**：假设用户注册成功后，你需要做三件事：发欢迎邮件、发新手优惠券、调用大模型生成用户画像。如果这三件事都写在注册接口里，任何一个环节报错（比如邮件服务器挂了），都会导致注册失败。
*   **MQ 的作用**：注册接口只需要把“用户A注册了”这条消息扔进队列里，就直接返回“注册成功”。至于发邮件的服务、发券的服务、大模型的服务，它们各自去队列里订阅这条消息并执行。互相之间没有任何代码依赖，某个服务挂了也完全不影响主流程。

### 本项目 (GoTaskAI) 中的具体体现：
在我们的架构中，大模型调用是典型的“高耗时、易限流”操作。
1.  我们利用 Asynq 实现了**削峰**：前端海量请求全部变成 Payload 扔进 Redis 队列，Worker 按照 `Workers: 5` 的并发度慢慢消费。
2.  我们利用 Asynq 实现了**容错与重试**：大模型 API 经常由于网络波动而失败。如果不走队列，失败了前端就只能看到报错；走队列后，Worker 执行失败会抛出 error，Asynq 会捕获它并进行**指数退避重试**（第一次等几秒，第二次等十几秒），实在不行再放进死信队列（Dead Queue）等待人工介入，确保了用户的任务“绝对不丢”。
