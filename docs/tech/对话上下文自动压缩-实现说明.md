# 对话上下文自动压缩（大模型摘要）实现说明

> 面向零基础读者的教学文档。我会尽量用大白话讲清楚：**为什么需要这个功能、它解决了什么问题、我们是怎么实现的、每一步代码在做什么**。
> 如果你读完还有不理解的地方，随时可以追问。

---

## 0. 一句话总结

在 GoTaskAI 里，每次用户和 AI 对话，系统会把「**之前聊过的历史内容**」一起发给大模型，让 AI 知道「我们刚才聊到哪了」。

但现在这套做法**太简单**：它只 `取最近 6 轮`，一旦对话很长，6 轮往往装不下关键信息；而且它**完全没有考虑 token 数量**，对话一多就很容易把大模型的「上下文窗口」撑爆。

我们这次做的功能是：

> **当历史内容占到大模型上下文窗口的 70% 时，就自动把「比较早的内容」用大模型压缩成一段「摘要」，只保留最近几轮的原始对话。** 这样既能记住关键信息，又不会让输入爆炸。

---

## 1. 先弄清几个基础概念（很重要）

### 1.1 什么是「上下文窗口」？
大模型一次能"看"的文本量是有限的，这个上限叫 **上下文窗口（Context Window）**，单位是 **token**。你可以把 token 理解为"模型的最小文字单位"：
- 一段英文，大约 4 个字母 = 1 个 token；
- 一个汉字，大约 = 1 个 token。

比如 `deepseek-v4-pro` 的上下文窗口我们按 `128K token` 计算（配置里是 `131072`）。

### 1.2 为什么会有"70%"这个说法？
因为**不能等完全满了才处理**。一旦塞满，大模型要么报错、要么截断、要么忘掉前面的内容。所以我们制定一条规则：
> 当已用的 token 数占到窗口的 **70%** 时，就提前"清理"一下，把旧内容压缩成摘要，腾出空间。

128K × 70% ≈ 89.6K token，也就是说大约用到 9 万 token 时开始压缩。

### 1.3 什么是"摘要压缩"？
不是简单地把旧对话删掉（那样就丢信息了），而是**再调用一次大模型**，让它读一遍旧对话，用一段精炼的话概括出「关键信息」。这段概括叫**滚动摘要（Rolling Summary）**。

滚动摘要会一直存在数据库里，随着对话越来越长，摘要会不断被"更新、合并"，始终代表"更早之前聊过什么"。

## 2. 改造前的问题（我们为什么要改）

改造前，代码在 `internal/worker/pool.go` 里是这样加载历史的：

```go
historyTasks := p.manager.GetConversationHistory(conversationID, 6) // 硬编码：只看最近 6 轮
```

问题清单：
1. **硬编码 6 轮**：不管对话多长、多重要，永远只带最近 6 轮，更早的关键信息会被无情丢掉。
2. **没有 token 预算**：完全不关心用了多少 token，也不知道模型窗口还有多少空间。
3. **无法处理超长对话**：一旦某一次聊天内容特别长（比如贴了一大段代码），即使只有几轮，也可能把窗口挤爆。

一句话：**"固定 6 轮"和"看 token 占用率"是两回事。我们要做的是后者。**

## 3. 关于 langchain 的调研结论（我们为什么自己实现）

你的需求里提到"先看看 langchain 框架有没有这个功能"。我们查了 Go 版 langchain（包名 `github.com/tmc/langchaingo`，项目用的是 `v0.1.14`）：

✅ **有**：它的 `memory` 包里有个 `SummaryMemory`，功能就是"token 超阈值时自动把旧对话总结成摘要"。

❌ **但不好接入本项目**，原因有三个：
1. `SummaryMemory` 需要一个 `llms.LLM` 接口对象，而本项目是直接用 `sashabaranov/go-openai` 直连大模型的，**根本没有 `langchaingo/llms` 这个子包**，得额外写一层适配器。
2. `SummaryMemory` 的摘要**存在自己的内存缓冲区里**，而本项目的对话历史是**存在 MySQL 的 `tasks` 表**里，两套"记忆"对不上，会打架。
3. 它不了解本项目 system prompt 里额外塞进去的**知识库检索内容、知识图谱、工具调用循环**，无法把这些也纳入 token 预算。

所以结论：**自己实现**，这样最贴合我们的架构，也能精准控制 token 预算。

## 4. 整体设计

### 4.1 一句话流程
```
每次用户发消息 → 从数据库取出"摘要 + 最近N轮历史" → 估算 token
  ├─ 没到 70% → 直接发给大模型 ✅
  └─ 到了 70% → 把"较早的轮次"交给大模型压缩成摘要 → 存回数据库
                → 只保留"最近6轮原始消息 + 摘要"再发给大模型 ✅
```

### 4.2 关键设计点
| 设计点 | 选择 | 原因 |
|--------|------|------|
| 触发时机 | 上下文窗口的 70%（128K × 0.7 ≈ 89.6K） | 提前腾空间，防爆 |
| 估算 token | 轻量语言感知估算（中文≈1字/token，英文≈4字符/token） | 不引入新依赖，够用即可 |
| 摘要存哪 | 存在 `conversations` 表新增的 `summary` 字段 | 与会话一一对应，最简洁 |
| 避免重复压缩 | 新增 `summary_cutoff` 字段记录"摘要已覆盖到哪" | 防止旧内容被反复压缩、摘要重复膨胀 |
| 保留最近几轮 | 6 轮 | 沿用你原来的习惯，上下文连贯 |

## 6. 配置文件（config.yaml）

在 `config/config.yaml` 的 `llm` 段和新增的 `compress` 段里，我们加了这些配置：

```yaml
llm:
  # ...上面的 api_key / base_url / model 不动...
  # 新增：上下文窗口大小（token 数）
  context_window: 131072
  # 新增：触发压缩的占用比例，0.7 即 70%
  compress_threshold: 0.7

# 新增：对话上下文自动压缩配置
compress:
  enabled: true        # 是否开启压缩
  max_history: 20      # 单次任务最多加载多少轮历史（避免一次取太多）
  keep_recent: 6       # 压缩时保留最近多少轮的原始消息
  min_turns: 8         # 历史轮数少于这个值就不做压缩（防止对很短的对话也压缩）
```

> `config/config.docker.yaml` 也同步加了同样的配置。

这些配置最终会被读取到 `internal/config/config.go` 里。我们看看：

```go
// internal/config/config.go
type LLMConfig struct {
```

## 7. 数据库模型（Conversation 表）

会话（conversation）是"一次对话的壳"，里面没有聊天正文，正文都在 `tasks` 表里。这次给 `conversations` 表加了两列：

```go
// internal/model/conversation.go
type Conversation struct {
    ID        string    `json:"id" gorm:"primaryKey;type:varchar(36)"`
    UserID    uint      `json:"user_id" gorm:"index"`
    AgentID   string    `json:"agent_id" gorm:"index;type:varchar(36)"`
    Title     string    `json:"title" gorm:"type:varchar(255)"`
    Summary   string    `json:"summary" gorm:"type:longtext"`            // 新增：滚动摘要
    SummaryCutoff *time.Time `json:"summary_cutoff,omitempty" gorm:"type:datetime"` // 新增：摘要已覆盖到的最早任务时间
    CreatedAt time.Time `json:"created_at"`
    UpdatedAt time.Time `json:"updated_at"`
}
```

**`summary`**：存压缩后的摘要文本（很长，所以用 `longtext`）。
**`summary_cutoff`**：存一个时间点，表示"摘要已经覆盖到这里的任务为止了"。它的作用是**防止下一次又把旧内容重复压缩一遍**（后面细讲）。

> 这两列不需要手动建。项目在 `cmd/api/main.go` 里调用了 GORM 的 `AutoMigrate(&model.Conversation{}, ...)`，它会自动把模型里新增的列同步到数据库。

## 8. 数据库读写层（manager.go）

`internal/queue/manager.go` 负责所有数据库操作。我们新增了 3 个方法：

### 8.1 读取摘要 + cutoff
```go
func (m *TaskManager) GetConversationCompressState(id string) (summary string, cutoff *time.Time) {
    if id == "" { return "", nil }
    var c model.Conversation
    if err := m.db.Select("summary", "summary_cutoff").Where("id = ?", id).First(&c).Error; err != nil {
        return "", nil
    }
    return c.Summary, c.SummaryCutoff
}
```
从数据库里拿出这个会话当前的摘要和 cutoff。

### 8.2 保存摘要 + cutoff
```go
func (m *TaskManager) SaveConversationSummary(id string, summary string, cutoff *time.Time) error {
    if id == "" { return nil }
    updates := map[string]any{
        "summary":    summary,
        "updated_at": time.Now(),
    }
    if cutoff != nil {
        updates["summary_cutoff"] = *cutoff
    }
    return m.db.Model(&model.Conversation{}).Where("id = ?", id).Updates(updates).Error
}
```
压缩完后，把新摘要和 cutoff 一起写回数据库。

### 8.3 按 cutoff 之后取历史（避免重复压缩）
```go
func (m *TaskManager) GetConversationHistorySince(conversationID string, after *time.Time, limit int) []*model.Task {
    // ... 查询逻辑，额外加一句 Where("created_at > ?", *after)
}
```
它和原来的 `GetConversationHistory` 几乎一样，只多了"只取 `created_at` 晚于 cutoff 的任务"这个条件。

**为什么要有 cutoff？** 假设我们压缩了第 1~20 轮变成摘要。如果下一轮还是用原来的方式"取最近 6 轮"，可能又会把第 15~20 轮（刚压缩过）再取出来、再压一遍，摘要就会重复膨胀。有了 cutoff，我们就能记录"摘要已覆盖到第 20 轮"，下次只取第 20 轮**之后**的新内容。

## 9. LLM 客户端（client.go）

`internal/pkg/llm/client.go` 负责真正调用大模型。我们加了两个东西：

### 9.1 token 估算函数
```go
func EstimateTokens(text string) int {
    if text == "" { return 0 }
    cjk, other := 0, 0
    for _, r := range text {
        if isCJK(r) { cjk++ } else { other++ }
    }
    return cjk + (other+3)/4   // 中文每字≈1 token，其他字符每4个≈1 token
}

func isCJK(r rune) bool {
    return unicode.Is(unicode.Han, r) || unicode.Is(unicode.Hiragana, r) ||
        unicode.Is(unicode.Katakana, r) || unicode.Is(unicode.Hangul, r)
}

func EstimateMessagesTokens(systemPrompt string, history []openai.ChatCompletionMessage, userPrompt string) int {
    // 把 system + history + user 身上的文字分别 EstimateTokens 再累加，每条消息额外加几个 token 作为"角色标记"开销
}
```

这个 `EstimateMessagesTokens` 会用来判断"当前这条消息一共用了多少 token，是否到了 70%"。

> 这里用的是"估算"而不是 100% 精确，因为要在不引入第三方分词库的前提下快速判断。对判断"是否到 70%"来说，误差完全可以接受。

### 9.2 摘要压缩方法
```go
func (c *Client) CompressHistory(ctx context.Context, model string, summaryBase string, turns []openai.ChatCompletionMessage) (string, error) {
    // 1. 拼一段系统提示词，告诉模型要做什么（保留目标、结论、关键步骤、数字/名称/日期）
    // 2. 把"之前的摘要"+ "本次待压缩的对话" 拼成一个 user 消息
    // 3. 调用生成方法，只取模型输出的摘要文本
    return c.generate(ctx, model, "", nil, prompt, nil, nil)
}
```

它本质上就是"**再问一次大模型**"：请你把这段旧对话概括成一段摘要。之前的摘要也一起给它，让它做"合并更新"（旧摘要 + 新增对话 → 新摘要）。

## 10. Worker 核心逻辑（pool.go）—— 最关键

`internal/worker/pool.go` 是"接任务、调 AI"的入口。我们把原来那 6 行"硬编码取 6 轮"的代码，替换成一个新方法 `loadConversationHistory`。

### 10.1 替换处（handleTaskProcess 里）
原来是：
```go
historyTasks := p.manager.GetConversationHistory(conversationID, 6)  // 硬编码6轮
```
现在是：
```go
historyMessages = p.loadConversationHistory(ctx, conversationID, systemPrompt, t.Payload)
```

### 10.2 新方法 loadConversationHistory 做了什么
我把它拆成几张"步骤图"来讲。

**第 1 步：算阈值**
```go
threshold := int(float64(lc.ContextWindow) * lc.CompressThreshold)
// 131072 × 0.7 ≈ 91750，即约 9.1 万 token 就触发压缩
```

**第 2 步：取配置默认值（兜底）**
```go
maxHistory := 20 // 单次最多取20轮
keepRecent := 6  // 压缩后保留最近6轮原始消息
minTurns  := 8   // 少于8轮不压缩
```

**第 3 步：取摘要 + 取历史**
```go
summary, cutoff := p.manager.GetConversationCompressState(conversationID) // 读出之前的摘要和已压缩到哪
turns := p.manager.GetConversationHistorySince(conversationID, cutoff, maxHistory) // 取 cutoff 之后的最近若干轮
```

**第 4 步：组装消息**
```go
hist := buildHistory(summary, turns)
// 如果 summary 不为空，就在最前面加一条 system 消息："以下是此前对话的压缩摘要..."
// 然后把每轮任务转成 user/assistant 两个消息追加在后面
```

**第 5 步：判断是否到阈值**
```go
used := llm.EstimateMessagesTokens(systemPrompt, hist, userPrompt)
if used <= threshold {
    return hist  // 没到70%，直接返回，不用压缩
}
```

**第 6 步：压缩旧内容**
```go
split  := len(turns) - keepRecent  // 比如取到20轮，保留6轮，则前14轮要压缩
toCompress := turns[:split]        // 要压缩的旧轮次
recent     := turns[split:]        // 要保留的最近6轮

newSummary, err := p.llmClient.CompressHistory(ctx, "", summary, toCompressMsgs) // 让大模型压缩
```

**第 7 步：存回数据库 + 返回**
```go
cutoffTime := toCompress[len(toCompress)-1].CreatedAt  // 记录"最后被压缩那一轮"的时间
p.manager.SaveConversationSummary(conversationID, newSummary, &cutoffTime) // 持久化
return buildHistory(newSummary, recent)  // 用"新摘要 + 最近6轮"继续
```

### 10.3 一个具体例子
假设某一轮任务，我们取到了最近 **20 轮**历史，估算 token 为 **95,000**，超过阈值 91,750：

1. 保留最近 **6 轮**（第 15~20 轮）。
2. 把第 **1~14 轮**交给大模型压缩成一段摘要（合并之前的摘要）。
3. 把新摘要存回数据库，同时记录 cutoff = 第 14 轮的时间。
4. 组装后的消息 = **[摘要 system 消息] + [第15~20轮的原始对话]** + 本次用户输入。
5. 下次再聊，因为有 cutoff，系统只会取"第 14 轮之后"的新内容，不会把第 1~14 轮再取出来重复压缩。

## 11. 如何验证这个功能

1. **重启服务**：改的是编译期代码，需要重新编译并重启 worker 服务（`go build ./...` 已经通过）。
2. **确认配置生效**：看 worker 启动日志里是否有 "Configuration loaded successfully"。
3. **看压缩日志**：当某次对话触发压缩时，worker 会打印：
   ```
   [Worker] conversation <id> compressed N historic turns into summary
   ```
4. **查数据库**：压缩后，去 `conversations` 表看 `summary` 字段是否被写入、`summary_cutoff` 是否更新。

> 因为默认窗口是 128K、阈值 70%，普通短对话**不会触发压缩**，这是正常的。想快速看到效果，可以把 `config.yaml` 里 `context_window` 临时调小（比如 `4096`），再故意聊很多轮即可触发。

## 12. 常见疑问（Q&A）

**Q：为什么用估算而不是精确 token？**
A：精确分词需要引入第三方库（比如 tiktoken），而且还不一定 100% 匹配 DeepSeek 的分词。这里是"判断是否到 70%"，估算误差完全够用，也省去了新依赖。

**Q：摘要会越滚越大吗？**
A：不会无限膨胀。每次压缩都会让大模型把"旧摘要 + 新增内容"合并成一段更精炼的新摘要；而且 cutoff 保证了旧内容不会被重复压缩。极端长对话下摘要确实会缓步变长，但远比保留全部原始对话要短得多。

**Q：压缩失败怎么办？**
A：失败就回退到"原始历史顺序"照常发给大模型，不阻塞用户。日志会打印 `conversation compress failed`。

**Q：改了数据库结构，需要手动迁移吗？**
A：不需要。项目的 `AutoMigrate` 会自动为新字段建列。但如果 `conversations` 表已经很大，建议确认迁移日志正常。
