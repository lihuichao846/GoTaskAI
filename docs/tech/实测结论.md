# GoTaskAI 实测结论报告

> 目的：针对「检索准确率 GraphRAG vs 传统 RAG」「高并发下 API 成本 / 吞吐」两个问题，在本机真实环境（Docker 拉起 Milvus / Neo4j / MySQL / Redis + 本地 API(8080) + Worker(9101/9102)）下**实际测试**给出结论。所有数字均为实测，非估算。

---

## 一、测试环境

| 项 | 值 |
|---|---|
| 向量库 | Milvus `kb_chunks`（dense COSINE + sparse BM25/IP 双路召回 + RRF 融合） |
| 图数据库 | Neo4j（本地 `neo4j://localhost:7687`） |
| RAG 重排 | Ollama `qwen3-reranker:4b` |
| LLM | DeepSeek `deepseek-v4-pro`，`in=0.27$ / 1M`、`out=1.10$ / 1M` |
| Worker | `queue.workers=5` × 2 子进程 = 10 并发；asynq 队列 high:6 / default:3 / low:1 |
| 成本上限 | `MaxCallsPerTask=15`，`MaxTotalCallsPerTask=30` |

---

## 二、结论一：检索准确率 GraphRAG vs 传统 RAG

**方法**：使用独立 collection `kb_chunks_eval`（不触碰生产 `kb_chunks`）。人工构造「单关系文档」入库 Milvus 作向量侧；ground-truth 三元组直接写入 Neo4j 作图谱侧。问题分两类：

- **单跳**：向量召回可命中。
- **多跳/跨链**：需沿 ≥2 条关系链推理，向量召回难以命中。

判定标准 = ground-truth 答案实体是否出现在被召回的内容（RAG 命中片段 / KAG 图谱上下文）中。

> **样本量说明**：初版仅 8 题（单跳4/多跳4），子集样本过小（1 题即 ±25pp），结论统计不稳。为客观起见，**扩充到 20 题（单跳10/多跳10）** 后重测，下方结论以 20 题为准。

**实测结果（N=20：单跳 10，多跳/跨链 10）**：

| 指标 | 传统 RAG（Milvus 双路召回） | GraphRAG（RAG + KAG 图谱检索） | 相对提升 |
|---|---|---|---|
| 整体准确率 | **16/20 = 80.0%** | **20/20 = 100.0%** | **+20.0 个百分点** |
| 仅多跳/跨链子集 | 7/10 = 70.0% | 10/10 = 100.0% | **+30.0 个百分点** |

> 对比（N=8 小样本时的旧数据：整体 87.5% vs 100%，多跳 75% vs 100%）。扩样本后整体回落到 80%，多跳回落至 70%，反映了小样本高估；但 KAG 在 20/20 全部命中，相对提升结论不变且更稳健（≥±30pp 的相对优势在 10 题多跳上是真实的）。

**典型案例**：「王七的爷爷是谁？」
- RAG-only：向量召回命中「赵六是王七的父亲」「李明是李小月的父亲」等散布片段，但**未命中**正确实体 `王五` → miss。
- RAG+KAG：图谱沿 `王七 → 父亲 赵六 → 父亲 王五` 遍历，正确返回 `王五` → hit。

**结论**：GraphRAG（RAG+KAG 双路）比传统 RAG 在整体检索准确率上**提升约 20 个百分点**（80%→100%）；在需要跨关系链推理的多跳问题上**提升约 30 个百分点**（70%→100%）。提升主要来自多跳/跨链场景，因为向量召回只能命中局部片段、无法跨链聚合，而图谱遍历天然支持多跳推理。

## 三、结论二：高并发下 API 成本 / 吞吐

**方法**：注册 `bench_user` 登录取 JWT；创建无工具单轮 `bench_fast` Agent；`/api/tasks/batch-submit` 批量压测，同时读取 Worker metrics（9101/9102）的 `gotaskai_llm_*`、`gotaskai_task_runs_total`。成本增量 = 压测后 metrics − 压测前基线。

### 3.1 受理层：并发接收与削峰（无瓶颈）

| 观测 | 结果 |
|---|---|
| 批量提交 22 任务 | HTTP 202，dispatcher 延迟 **572ms**，22/22 全部入队 |
| 单任务并发突增（12 波） | **峰值在途 12 个**，全部任务在 ~1s 内被 worker 并行拉起，**超过配置的 10 并发** |
| 突发 8 连发 `/submit` | **202 收 2~3 个**（p50≈36ms，均值 36~44ms），**429 拒 5~6 个**（均值 7~16ms） |

**结论**：受理/派发层不构成瓶颈——批量 202 快速入队、队列并行拉满（≥10 在途）。限流（Redis 固定窗口，`submit` 3/min、`batch-submit` 1/min）在**突发时主动削峰**，以 429 拒绝超额请求，保护下游 LLM 不被突发打爆。

### 3.2 成本：每任务极低，被预算/检索压到接近下限

「单波 22 任务」干净波成本增量：

| 指标 | 值 | 说明 |
|---|---|---|
| 模型调用/任务 | **1.00 次** | 无工具循环，单轮即答 |
| 输入 tokens/任务 | 777 | 注入 RAG/图谱上下文后的一轮输入 |
| 输出 tokens/任务 | 122 | 简洁回答 |
| 成本/任务 | **≈ $0.00034** | `777×0.27e-6 + 122×1.10e-6` 验证一致 |

**成本控制对比（倍数）**：
- 实测每任务 **1.0 次 LLM 调用**，仅为单次运行调用上限 `MaxCallsPerTask=15` 的 **~6.7%**。
- 若工具型 agent 触发工具乒乓打满 15 次调用，成本将达 `15 × $0.00034 ≈ $0.0051/任务`，即实测成本的 **~15 倍**。
- 因此**成本降低倍数上限 ≈ 15×**（相对单任务 15 次调用的护栏上限）；同时 RAG + 图谱用「廉价向量/图检索替代长链条 LLM 推理」换取输入 token 更低、且命中更准（见结论一）。

注：本波 `calls=22`、`in=17094`、`out=2682`、`cost=$0.007566`，单个基准 token 平衡，成本主要由配置的 `CostPer1MIn/Out` 决定。

### 3.3 吞吐：受上游 LLM 时延约束，系统并发已饱和

| 指标 | 值 |
|---|---|
| 单波 22 任务排空 | **76.6s** → **0.29 tasks/sec** |
| 单波 12 任务排空 | **57s** |
| Worker 直方图（LLM 段耗时） | 聚合均值 ~4~11s，p50≈4s，p95≈<10s |
| 真实端到端单任务（客户端观测） | 从 processing 到 completed 约 **20~55s** |

**结论**：系统内部无串行瓶颈（在途峰值 ≥10，配置并行度已拉满）。**吞吐上限由「上游 LLM 每次生成的时延」决定**（DeepSeek 单次生成在并发下从 ~8s 到 ~50s 波动），而非排队或派发。提升吞吐需**加 worker 并行度**或**换更快/流式模型**，而不是优化队列。

> 口径说明：`task_duration` 直方图只计时 LLM 调用段（计时点在检索/图谱/历史装载之后），故比客户端观测的端到端耗时低；客户端观测值才是用户感知的真实延迟。

### 3.4 高并发成本/吞吐小结

- **并发接收**：系统可同时接收并拉起 **≥10（实测 12）** 个任务，较单槽串行处理器约 **10~12× 并发受理提升**。
- **单任务成本**：被预算护栏 + RAG/图谱替代压到 **≈$0.00034、1 次调用**，较「打满 15 次调用」护栏上限约 **15× 成本降低空间**。
- **吞吐瓶颈**：并发已饱和，实际 tasks/sec 受上游 LLM 单次生成时延约束，为 **0.29~0.40 tasks/sec**（N=20~22）。

## 四、附：实测发现的线上 Bug（重要）

**Bug 1：Neo4j 关系名大小写敏感，导致生产 KAG 图谱检索恒为空。**

- 生产 `IngestGraph` 使用 `cleanRelationName()` 将中文关系名（如「父亲」）**强制转大写**为 `FATHER_OF` 并剥离非法字符；而 Cypher 生成器输出的关系名是**小写** `father_of`。
- Neo4j 关系名**大小写敏感**，二者永不匹配 ⇒ 生产链路 `RetrieveGraphContext` 返回空 ⇒ **KAG 图谱上下文实际上从未注入过**。
- 实测验证：查询 `father_of` 返回 `[]`，查询 `FATHER_OF` 返回正确实体。
- 结论：**当前线上 KAG 检索层整体失效**（评估中用「小写关系名直接建图」绕开以验证 KAG 有效性），建议统一 `cleanRelationName` 与 Cypher 生成器的大小写约定（如全部转小写）。

**Bug 2：Text2Cypher 生成的关系名与图谱入库的关系名不一致（同义/形态差异）。**

- 本次评测（三元组已用小写建图，规避了 Bug1）中仍出现不匹配：入库关系为 `headquarters_in`，但 LLM 生成的 Cypher 在不同问题下分别输出 `headquarters_in`（命中）与 `headquartered_in`/`located_in`（未命中）。
- 表现：`腾讯的总部在哪里`（生成 `headquartered_in`）、`马化腾/李彦宏的公司位于哪个城市`（生成 `located_in`）三者 KAG 图谱上下文为空，**只能靠 RAG 向量命中兜底**。
- 结论：即使修复大小写，关系名**语义同名不同形态**（`headquarters_in` vs `headquartered_in` vs `located_in`）仍会造成图谱检索空返回。建议在 Text2Cypher 中加入「关系名白名单/归一化映射」，或入库时保存关系名的别名/词向量，提高 Cypher 生成与图谱 schema 的匹配率。

## 五、一句话结论

- **检索准确率**：GraphRAG（RAG+KAG）较传统 RAG **整体约 +20pp（80%→100%，N=20）**，**多跳场景 +30pp（70%→100%，N=10）**，提升主要来自跨关系链推理。（样本量较初版 8 题扩大至 20 题后，小样本高估已修正，结论更稳健。）
- **高并发成本/吞吐**：系统可 **≥10~12 路并发受理**（无内部串行瓶颈），**单任务约 1 次调用 ≈ $0.00034**，较 15 次调用护栏上限约 **15× 成本降低空间**；实际吞吐 **0.29~0.40 tasks/sec**，**瓶颈在上游 LLM 单次生成时延**，加并发 worker/换更快模型可线性提升。
- **额外发现**：生产存在**两处导致 KAG 图谱检索为空**的问题——① `cleanRelationName` 大写化与 Cypher 小写化不匹配（大小写敏感）；② Text2Cypher 关系名同义不同形态（`headquarters_in`/`headquartered_in`/`located_in`）。均为线上实际失效点，需优先修复。

## 六、公开数据集实测（重要补充与修正）：GraphRAG 在真实开放域多跳问答上「提升为 0」

> 上面的「结论一 +20pp」用的是**人工构造、三元组为 ground-truth** 的干净合成数据。为验证该结论能否泛化到真实数据，改用**公开数据集 QAngaroo/WikiHop**（Wikipedia 多跳问答，dev 子集 20 题：单跳 10 + 多跳 10），并对每个样本的 supports 文本走**全链路**（LLM 抽取三元组 ExtractKnowledge → IngestGraph 建图 → RAG-only vs RAG+KAG 检索对比）。

### 6.1 实测结果（N=20：单跳 10，多跳/跨链 10）

| 指标 | 传统 RAG（Milvus 双路召回） | GraphRAG（RAG + KAG 图谱检索） | 相对提升 |
|---|---|---|---|
| 整体准确率（宽松 recall） | **8/20 = 40.0%** | **8/20 = 40.0%** | **+0.0 个百分点** |
| 仅多跳子集（宽松 recall） | 5/10 = 50.0% | 5/10 = 50.0% | **+0.0 个百分点** |
| 严格（答案被召回且未混入其它候选） | 0/20 = 0.0% | 0/20 = 0.0% | +0.0 |

- 建图完成：**2363 条三元组**（20 样本，0 抽取失败）。
- **KAG 在 WikiHop 上没有带来任何提升（+0.0pp）**，与合成数据的 +20pp 形成强烈反差。
- 「严格」模式两个 pipeline 全为 0：WikiHop 的 candidates 语义高度相关，检索内容（无论 RAG 片段还是图谱上下文）几乎总会同时命中 ≥2 个候选 → exclusivity 恒失败，该判定口径在本题型下不适用。

### 6.2 根因定位（基于遗留图谱的逐查询诊断，非猜测）

对评测后遗留的 Neo4j 图谱做定向诊断（`tools/wikihop_diag`），逐条执行 `RetrieveGraphContext`，得到实测证据：

**根因 A：实体名大小写/规范化不一致，Cypher 精确匹配直接落空。**
- 查询实体是 Wiki 规范化小写形式（`solva sawan`、`danish general election`），而图谱节点名是从原文抽取的自然大小写（`Solva Sawan`、`Danish general election`、`Upper Bicutan National High School`）。
- `MATCH (n:Entity {name:'Solva Sawan'})` 因 name 精确匹配失败返回空。仅当 Text2Cypher 恰好把实体「脑补」成正确大小写（如 `Upper Bicutan National High School`）才能命中——这正是少数成功案例的原因，本质是碰运气而非稳定能力。

**根因 B：开放域 LLM 抽取极其稀疏且关系词表爆炸，图谱碎片化。**
- 1863 个节点 / 2338 条关系却产生 **约 350+ 种关系类型**（如 `GAVE_KEYS_OF_HEAVEN_TO`、`WAS_CROWNED_KING_OF`、`IS_MOST_POPULOUS_MUNICIPALITY_OF`），每种关系只出现 1~2 次。
- 每个问题对应的目标三元组在如此碎片化的图谱中大概率**根本不存在**。例：`original_language_of_work solva sawan`（答案 `hindi`）→ Text2Cypher 生成 `[:LANGUAGE]`，但该实体在图中无 `LANGUAGE` 关系 → 空。

**根因 C：Text2Cypher 生成的 Cypher 深度不足、匹配路径单一。**
- 单跳类生成 `MATCH (n {name})-[:REL]->(l)`；多跳类倾向一次 2 跳，但依赖精确 name 匹配。
- 多跳命中案例也暴露问题：`located_in... upper bicutan national high school`（真答案 `capital region`）虽返回了 `Taguig City`，但那是**中间层级实体**，不是最终答案，且常混入干扰候选——KAG 只给增量信息、给不了正确终点。

### 6.3 结论与修正

- **合成数据的 +20pp 不能外推到真实开放域**。合成数据三元组 = 人工标定的 ground-truth、关系名统一、实体名精确，KAG 天然受益；而真实开放域中 **LLM 抽取质量（稀疏 + 碎片化）+ 实体/关系名规范化不一致** 才是瓶颈，KAG 无法在此基础上带来检索收益。
- **KAG 的价值与图谱质量强绑定**：在图谱干净、关系 schema 收敛、实体名可对齐的场景才有增量；在开放域长尾、抽取噪声大的场景，**成本（额外 LLM 抽取 + Cypher 生成）与收益不成正比**。
- **当前 KAG 检索层需先解决三件事才具备生产价值**：① 实体名归一化/别名（查询侧与图谱侧统一大小写与空格，或改 `name` 模糊匹配/嵌入对齐）；② 关系名 schema 收敛（`knownRelationTypes` 已注入 prompt，仍需关系归一化映射 + 降低抽取时的长尾关系）；③ Cypher 生成的多跳路径规划（当前 LLM 倾向单跳浅层模式，需示例化/约束到真实 schema）。
- **结论五判定标准说明**：结论一（+20pp）成立的前提是「人工标定 ground-truth 三元组」，已在正文标注；实际开放域表现请以此第六节为准。
