## 1. 项目一句话定义

`GoTaskAI` 本质上是一个 **基于 Go 的异步 AI 任务平台**：

- 前端负责登录、提交任务、展示任务状态
- API Server 负责接收请求、鉴权、建任务、挂 SSE
- Worker Node 负责异步消费任务、做知识增强、调大模型、更新状态
- Redis 同时承担缓存、Asynq 队列、Pub/Sub 事件总线
- MySQL 存用户和任务
- Neo4j 承担 KAG 图谱数据
- SSE 把任务状态实时推回前端

主链路可以压缩成：

```text
前端 -> API -> MySQL/Redis/Asynq -> Worker -> LLM/RAG/KAG
                                  -> Redis Pub/Sub -> API SSE -> 前端
```

## 2. 先建立的核心认识

在本轮阅读里，最先建立的不是某个函数细节，而是项目的运行态骨架：

1. 这是一个 **双进程后端项目**
   - [main.go](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L27-L135)
   - [main.go](file:///d:/Program%20Files/GoTaskAI/cmd/worker/main.go#L23-L92)
2. `API` 不干重活，主要负责接客
3. `Worker` 才是真正处理 AI 任务的一侧
4. 任务不是同步执行，而是先写库、入队、异步消费
5. 实时更新不是 Worker 直接推浏览器，而是：

```text
Worker -> Redis Pub/Sub -> API -> SSE -> Browser
```

6. Redis 在这个项目里不是单纯缓存，而是三角色叠加：
   - 缓存
   - 队列
   - 事件总线

### 4.1 `cmd/api/main.go` 生剖记录

下面这一段保留了本轮对话里“逐块生剖 `main()`”的讲解风格，不只讲结论，也保留讲解过程，方便后面回看时重新进入状态。

这个 [main()](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L27-L135) 函数代码量其实不大，但它是整个 API 进程的骨架。可以按 4 段来理解：

#### 第一段：配置与底层依赖初始化

对应大致是 [main.go:L28-L51](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L28-L51)。

项目一上来不能直接跑业务，得先把基础设施接好。

1. 加载配置

- 这里会调用 [config.go](file:///d:/Program%20Files/GoTaskAI/internal/config/config.go) 里的配置初始化逻辑
- 把配置读进内存并赋给 `cfg`
- 后面所有组件都要依赖这份配置，例如：
  - MySQL 连哪个库
  - Redis 地址和密码是什么
  - HTTP 监听哪个端口

2. 连接并校验 MySQL

- 这部分就是前面解释过的 [main.go:L39-L48](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L39-L48)
- 建立数据库连接
- 设置连接池
- 最关键的是 `AutoMigrate`

这里真正的业务含义不是“顺手建个表”，而是：

- API 启动时会强行检查任务表和用户表是否存在
- 不存在就建
- 建失败就 `os.Exit(1)`

原因很直接：

- 没有 `Task` 和 `User` 这两张表
- 后面的注册、登录、派单根本没法继续

3. 连接 Redis

- 得到一个可用的 `redisClient`
- 这个对象后面会非常忙，至少会用于：
  - 接口限流
  - 任务队列
  - Pub/Sub 广播
  - 一些认证相关状态

#### 第二段：拼装“控制器”和“关键中枢”

对应大致是 [main.go:L53-L71](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L53-L71)。

底层依赖接好以后，接下来不是立刻开路由，而是先把真正干活的对象组装出来。

1. 为什么 `TaskManager` 是中枢

- 核心入口是 [NewTaskManager()](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L28-L42)
- 这里把：
  - `mysqlDB`
  - `redisClient`
  - `redisOpt`
  都传进去了

这件事非常关键，因为这意味着：

- 后面谁拿到 `manager`
- 谁就拥有同时操作：
  - MySQL
  - Redis
  - Asynq 队列
  - Pub/Sub 广播

所以 API 进程并不是自己到处散着操作任务，而是把任务交给 `manager` 去协调。这就是它像“心脏血管桥接点”的原因。

2. 组装 3 个 API Handler

这里会依次造出几类控制器：

- 任务控制器：需要 `manager` 去建任务、派单、查状态
- 认证控制器：需要 `mysqlDB` 和 `redisClient`
- 知识库控制器：需要 `kagManager`

也就是说，下一段 Gin 路由真正调的“干活对象”其实就是这些 Handler。

#### 第三段：Gin 路由是一层层挂起来的

对应大致是 [main.go:L73-L120](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L73-L120)。

对象都准备好了，接下来才轮到把它们绑定到 HTTP 路径上，让前端可以调。

1. 全局准备

- `gin.Default()` 创建路由引擎
- `Use(...)` 挂全局中间件
- 这里挂的是 CORS，中间件代码在 [cors.go](file:///d:/Program%20Files/GoTaskAI/internal/middleware/cors.go)

它的业务意义很简单：

- 如果没有跨域支持
- 前端页面在浏览器里调 API 时会被浏览器直接拦掉

2. 挂载特殊的非 API 路由

- 根路径 `/` 会直接返回前端首页
- 这里本质上是把静态页面托管给 API 服务

另外还挂了 Asynq 自带监控面板：

- 路径是 `/admin/tasks`
- 用于在浏览器里直接看队列状态和积压情况

3. 核心 API 分组挂载

这部分很值得细看，因为路由分组直接体现出权限边界：

- 登录接口挂在 `/api/auth/login`
- 这组路由不加鉴权，因为还没登录

- 任务接口挂在 `/api/tasks`
- 整组挂了 [AuthMiddleware()](file:///d:/Program%20Files/GoTaskAI/internal/middleware/auth.go#L12-L44)
- 也就是说，不带 Token 调这里的任何接口，都会先被中间件拦掉

- `SubmitTask` 前面还串了限流中间件
- 这是为了接口防刷，例如一分钟只能提交几次

#### 第四段：启动与优雅退出

对应大致是 [main.go:L121-L145](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L121-L145)。

现在路由表已经填满，可以正式开门接客了。

1. 为什么要单独起协程

- `ListenAndServe()` 会一直阻塞
- 如果不把它放进 goroutine
- 那主协程就永远卡在这
- 后面的“等待退出信号”和“优雅关闭”逻辑就根本执行不到

所以这里必须把 HTTP 服务放到后台协程里跑。

2. 怎么实现优雅退出

关键逻辑在 [main.go:L134-L144](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L134-L144)：

```go
quit := make(chan os.Signal, 1)
signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
<-quit
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
srv.Shutdown(ctx)
```

可以把它理解成：

- 主协程先睡在 `<-quit`
- 等待 Ctrl+C 或系统终止信号把它唤醒
- 被唤醒之后，不是立刻暴力断电
- 而是给当前 HTTP 服务一个 5 秒宽限期
- 已经接进来的请求尽量在这 5 秒内处理完
- 时间到了还没处理完，再强制关闭

这就是“优雅退出”的真实含义。

#### 这一整段的口语化总结

如果用一句顺口的话来复述这个 [main()](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L27-L135)：

```text
准备依赖 -> 造好武器（Manager/Handler）-> 摆好摊位（Gin 路由）
-> 后台叫卖（ListenAndServe）-> 等城管来（Ctrl+C）
-> 优雅收摊（Shutdown）
```

这一段讲透以后，再回头看 `cmd/api/main.go`，就不会觉得它只是“110 行启动代码”，而会看到它其实就是整个 API 进程的骨架。

#### 第一步：先看两个启动入口

这一步的原始讲解重点是：

- 先看 [main.go](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L27-L135)
- 再看 [main.go](file:///d:/Program%20Files/GoTaskAI/cmd/worker/main.go#L23-L92)
- 这两个文件是整个系统最顶层的启动入口
- 如果没看懂它们，就不要急着钻 `internal/`

先建立起来的运行态全景包括：

- API Server 是网关层，负责：
  - HTTP 接口
  - JWT 鉴权
  - 限流
  - 静态页面
  - SSE 推送

- Worker Node 是计算层，负责：
  - 消费异步任务
  - 调用大模型
  - 做 RAG/KAG 检索
  - 处理重试和取消

- MCP Server 不是常驻独立服务
- 它是 Worker 运行时按需拉起的子进程，用来提供工具调用能力

- 再加上基础设施，完整运行态通常还包括：
  - MySQL
  - Redis
  - Neo4j
  - Ollama
  - 有时还有 Nginx

#### 必须先记住的职责分工

- API Server 不负责真正执行 AI 任务，它只是“接单员”
- Worker Node 不直接对外接 HTTP，它只是“干活的人”
- Redis 在这里不是单一用途，而是同时承担：
  - 消息队列底座
  - 缓存
  - Pub/Sub 事件总线
- MySQL 是最终持久化
- Neo4j 是知识图谱检索底座
- Ollama 是本地模型服务入口

#### 一条完整链路先背下来

1. 前端把请求发到 API Server
2. API Server 做鉴权、参数校验、构造任务对象
3. 任务先落 MySQL，再写 Redis 缓存，再推入 Asynq 队列
4. Worker Node 从 Redis 队列里抢任务
5. Worker 先查是否取消，再改状态为 `processing`
6. Worker 按需做 RAG 检索、KAG 图谱检索、拼装上下文
7. Worker 调 LLM 生成结果
8. Worker 更新任务状态到 MySQL + Redis
9. Worker 通过 Redis Pub/Sub 发布任务更新
10. API Server 订阅更新后，再通过 SSE 推给前端

#### 为什么要拆成两个进程

这也是当时特别强调的架构点：

- AI 任务慢、重、容易阻塞
- HTTP 接口要求快、稳、能抗并发
- 如果把“接请求”和“跑模型”塞进同一个进程
- 请求一多就会把整个服务拖慢

所以项目核心设计思想是：

- 接入层和计算层解耦

这也是面试里很值得讲的一点。

#### 当时对 TaskManager 的口语化解释

- 你可以把它理解成“任务中枢”

- 它把：
  - MySQL
  - Redis
  - Asynq
  - SSE 订阅关系
  串到了一起

并且特别强调：

  - 普通 HTTP API
  - SSE 长连接
- 前端绝大多数动作，本质都是：
  - 先调 HTTP
  - 再等 SSE 回状态

#### 鉴权边界当时是怎么讲的

- 任务接口组 `tasksGroup` 被挂上了 [AuthMiddleware()](file:///d:/Program%20Files/GoTaskAI/internal/middleware/auth.go#L12-L44)
- 所以 `/api/tasks/*` 下面的提交、列表、删除、重试、取消都需要登录
- 但 [StreamTasks()](file:///d:/Program%20Files/GoTaskAI/internal/api/handler.go#L363-L408) 是单独暴露的
- 它不用 `Authorization` 请求头，而是用 URL 参数 `token`
- 原因不是随便写的，而是浏览器 `EventSource` 不方便自定义请求头

#### 登录注册这一层当时的讲法

- 注册时：
  - 校验参数
  - 检查用户名是否存在
  - `bcrypt` 哈希密码
  - 入库
  - 见 [auth.go](file:///d:/Program%20Files/GoTaskAI/internal/api/auth.go)

- 登录时：
  - 查用户
  - 校验密码
  - 生成 JWT
  - 返回给前端
  - 见 [auth.go](file:///d:/Program%20Files/GoTaskAI/internal/api/auth.go)

- 鉴权中间件做的事情是：
  - 从 `Authorization: Bearer xxx` 拆出 token
  - 校验 token
  - 把 `userID` 放进 Gin Context
  - 见 [AuthMiddleware()](file:///d:/Program%20Files/GoTaskAI/internal/middleware/auth.go#L12-L44)

并且还特别强调了一个细节：

- 中间件不会把整个用户对象往下传
- 而是只做 `c.Set("userID", claims.UserID)`
- 这让后续 Handler 只关心“当前是谁”
- 所以你在很多业务函数里会看到 `c.GetUint("userID")`

#### SubmitTask 当时是怎么定位的

这一段当时是专门强调过的：

- [SubmitTask()](file:///d:/Program%20Files/GoTaskAI/internal/api/handler.go#L134-L178) 是项目最值得优先读懂的 HTTP 入口
- 它做的事情是：
  - 收参数
  - 补默认值
  - 从上下文取 `userID`
  - 构造任务对象
  - 把任务交给 [AddTask()](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L116-L128)

同时也明确说明：

- 它不直接调 LLM
- 它不直接返回业务结果
- 它只负责“受理任务”
- 所以返回的是 `202 Accepted`
- 不是 `200 OK`

这也是项目异步架构意识非常明显的地方。

#### 那一轮的阶段总结

那次讲解最后收束成了 4 个判断：

- API Server 的本质不是“业务执行层”
- 它是“接入层 + 编排层”
- 它负责接请求、鉴权、创建任务、查询任务、推流通知
- 它不负责真正跑模型

也就是说：

- 这个项目不是“HTTP 一进来立刻调模型再返回结果”的同步式聊天服务
- 而是“异步任务平台”

## 7. 一次真实请求的完整链路

在“真实请求专题”里，我们把一次任务提交从前端一路跟到了 Worker 和 SSE。

主链路如下：

1. 前端在 [TaskSubmit.vue](file:///d:/Program%20Files/GoTaskAI/web/src/components/TaskSubmit.vue) 采集表单并发出 `submit`
2. [App.vue](file:///d:/Program%20Files/GoTaskAI/web/src/App.vue) 接住事件，调用前端 API 客户端
3. [client.js](file:///d:/Program%20Files/GoTaskAI/web/src/api/client.js) 发 `POST /api/tasks/submit`
4. API 中间件校验 JWT
5. [SubmitTask()](file:///d:/Program%20Files/GoTaskAI/internal/api/handler.go#L134-L178) 构造 `Task`
6. [AddTask()](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L116-L128) 先写 MySQL、再写 Redis 缓存、再入 Asynq 队列
7. API 立刻返回 `202 Accepted`
8. Worker 在 [handleTaskProcess()](file:///d:/Program%20Files/GoTaskAI/internal/worker/pool.go#L116-L263) 中取到任务
9. Worker 改状态为 `processing`
10. Worker 组装 prompt、RAG、KAG、历史消息、工具定义
11. Worker 调用 LLM
12. Worker 成功则写 `completed + result`，失败则重试或标记 `failed`
13. [UpdateTask()](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L237-L255) 把状态写库、写缓存、发 Pub/Sub
14. API 订阅 Pub/Sub，转发到 SSE
15. 前端收到 `task_update`，更新任务列表

这条链最重要的结论是：

- 这是一个 **异步任务系统**
- 不是传统“HTTP 请求 -> 同步返回最终结果”的同步 Web 系统

## 10. SSE + Redis Pub/Sub 实时推送链路回顾

这条链路是项目里非常关键的一段，主文件是：

- [handler.go](file:///d:/Program%20Files/GoTaskAI/internal/api/handler.go#L363-L408)
- [manager.go](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L44-L255)

核心流程如下：

1. 浏览器通过 `GET /api/tasks/stream?token=...` 建立 SSE
2. API 调 [Subscribe()](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L64-L76) 给当前用户创建 channel
3. Worker 每次 [UpdateTask()](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L237-L255) 时都会：
   - 更新数据库
   - 更新 Redis 缓存
   - 发布 `global_task_updates`
4. API 进程中的 [listenForGlobalUpdates()](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L44-L62) 订阅这个频道
5. 收到消息后，通过 [broadcast()](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L92-L104) 精准发给对应用户
6. [StreamTasks()](file:///d:/Program%20Files/GoTaskAI/internal/api/handler.go#L363-L408) 从 channel 里拿消息并 `SSEvent + Flush`
7. 前端收到 `task_update` 事件后更新列表

这一段的本质是：

- Worker 不直接维持浏览器连接
- Redis Pub/Sub 负责跨进程广播
- API 负责把消息转成浏览器能消费的 SSE

## 13. 项目的高并发体现回顾

曾经专门分析过“这个项目的高并发到底体现在哪里”，结论不是“只有 Asynq 队列”。

更准确的说法是：

**同步入口轻量化 + 异步削峰填谷 + Worker 并发消费 + Redis 状态分发**

可以拆成几层：

1. API 不同步跑 LLM，请求很快返回 `202`
2. Asynq 队列承担削峰填谷和优先级调度
3. Worker Pool 的 `Concurrency` 决定真正并发执行能力
4. Redis 缓存减轻数据库压力
5. Redis Pub/Sub + SSE 避免前端高频轮询
6. 数据库连接池支撑底层吞吐

所以项目的高并发不是单点能力，而是一套组合模型。

## 14. 并发瓶颈分析回顾

随后又分析了“项目高并发下最可能先卡在哪里”。

主要候选瓶颈包括：

1. Worker 并发数不足
2. 外部 LLM 吞吐限制
3. Redis 单实例压力
4. SSE 长连接规模
5. MySQL 高频状态更新

优先级通常是：

1. `LLM 服务吞吐`
2. `Worker 执行能力`
3. `Redis 压力`
4. `MySQL 状态更新`

也就是说：

- API 层反而不是最先爆的
- 真正上限更常由异步执行链路决定

## 15. 为什么考虑 Redis Sentinel

随着对高可用的讨论推进，结论逐渐收敛为：

- Redis 可以做高可用
- 对这个项目来说，第一步更适合 `Sentinel`
- 不建议一开始就直接上 `Cluster`

原因是：

1. 当前项目对 Redis 的依赖非常重
2. Redis 同时承担队列、缓存、广播、限流、验证码等职责
3. 如果目标是先解决单点故障，Sentinel 比 Cluster 侵入更小

关于代码改造的结论是：

- **不需要大改业务代码**
- 主要是改：
  - [config.go](file:///d:/Program%20Files/GoTaskAI/internal/config/config.go)
  - [db.go](file:///d:/Program%20Files/GoTaskAI/internal/db/db.go)
  - `Asynq` 的 Redis 接入配置层

## 17. 本地 Docker Sentinel 环境搭建回顾

为了做真实验证，不只是改代码，还搭了一套本地 Docker 高可用环境。

关键文件：

- [docker-compose.yml](file:///d:/Program%20Files/GoTaskAI/docker-compose.yml)
- [config.docker.yaml](file:///d:/Program%20Files/GoTaskAI/config/config.docker.yaml)
- [sentinel-1.conf](file:///d:/Program%20Files/GoTaskAI/docker/redis/sentinel-1.conf)
- [sentinel-2.conf](file:///d:/Program%20Files/GoTaskAI/docker/redis/sentinel-2.conf)
- [sentinel-3.conf](file:///d:/Program%20Files/GoTaskAI/docker/redis/sentinel-3.conf)

本地拓扑最终演进为：

1. 一个 Redis 主节点
2. 两个 Redis 副本
3. 三个 Sentinel
4. API 和 Worker 也进入 Compose 网络

在这个过程中踩到过几类典型问题：

1. Sentinel 配置文件挂载为只读，导致运行时无法保存新配置
2. Redis `protected-mode` 影响主从复制
3. 宿主机直跑 Go 进程时，Sentinel 返回的地址对宿主机未必可达
4. 使用主机名监控主节点时，主容器停掉后 Docker DNS 解析会受影响

最终解决方式是：

1. Sentinel 启动时先把种子配置复制到容器内可写路径
2. Redis / Sentinel / API / Worker 全部放在同一个 Docker 网络
3. 为 Redis / Sentinel / API / Worker 分配固定内网 IP
4. Sentinel 直接监控固定 IP，而不是短生命周期的主机名

## 19. Sentinel 故障切换演练回顾

之后又做了一次真实故障切换演练。

演练步骤：

1. 确认当前主节点是 `172.28.0.10:6379`
2. 手动停止主 Redis 容器
3. 观察 Sentinel 是否完成下线判断和选主
4. 观察 API / Worker 是否继续存活
5. 观察 Worker 是否感知新的 master

最终结果：

1. Sentinel 成功切主
2. 新主节点变成了 `172.28.0.12:6379`
3. Sentinel 日志出现 `+switch-master`
4. API 保持可用
5. Worker 观察到了新的 master 地址

这说明：

- Redis Sentinel 的核心能力已经在本地环境中验证成功

但同时也发现：

- 切主窗口中 Worker 会出现几秒 Redis 超时
- 这是 Sentinel 架构下常见的短暂抖动，并不是代码逻辑错误

因此更准确的结论是：

- **切主成功**
- **服务不中断**
- **存在短暂重连窗口**
