# 知识库扩展查询功能技术方案

> 交付类型：**技术方案评审稿 + 核心算法原型 + 离线验证报告**
> 目标：在不改变现有「Milvus 双路召回 + RRF + rerank」主链路的前提下，新增一个**查询扩展（Query Expansion）前置环节**，用「同义词 / 实体链接 / 语义改写 / 多模态关联」四类扩展手段补齐查询与文档之间的**词法鸿沟（lexical chasm）**，提升召回率与命中质量。

## 一、背景与问题定位

### 1.1 现状检索链路（代码级）

| 环节 | 位置 | 现状 |
|---|---|---|
| 查询向量化 | [store.go#L171-L181](file:///d:/Program%20Files/GoTaskAI/internal/pkg/ragstore/store.go#L171-L181) | `EmbedQuery`（Qwen3-Embedding）+ `buildQuerySparse`（BM25） |
| 双路召回 | [store.go#L182-L198](file:///d:/Program%20Files/GoTaskAI/internal/pkg/ragstore/store.go#L182-L198) | dense COSINE + sparse IP，RRF 融合 |
| 重排 | [pool.go#L500-L527](file:///d:/Program%20Files/GoTaskAI/internal/worker/pool.go#L500-L527) | 可选 DashScope qwen3-rerank |
| 窗口扩展 | [pool.go#L339-L398](file:///d:/Program%20Files/GoTaskAI/internal/worker/pool.go#L339-L398) | 上下文感知分块 B1/B2 |
| 图谱召回 | [kag.go#L99-L170](file:///d:/Program%20Files/GoTaskAI/internal/pkg/kag/kag.go#L99-L170) | Neo4j Text2Cypher |

### 1.2 核心缺口

1. **单一查询串**：`SimilaritySearch` 只接受一个查询字符串，用户「口语化 / 别名 / 缩写 / 跨语言」表述无法命中库里以规范术语存储的文档。
2. **词法鸿沟**：稀疏召回（BM25）依赖精确词项匹配，`车` 与 `汽车`、`DeepSeek` 与 `深度求索`、`维护` 与 `保养` 等词汇不一致会导致召回为空。
3. **图谱与检索割裂**：KAG 已有 Neo4j 实体/别名/关系，但**只用于 Text2Cypher**，未回灌到向量/词法检索做查询增强。
4. **无多模态入口**：当前知识库为纯文本，图像/图表/表格等资产缺 caption/tag 元数据与跨模态索引，视觉意图查询无从命中。

### 1.3 与既有改造的关系

上一轮「上下文感知分块（B1 窗口扩展）」解决的是**命中块上下文割裂**问题；本轮「查询扩展」解决的是**查询表达与文档表达不一致导致的漏召回**问题。二者互补：前者在命中后补上下文，后者在检索前扩查询。

## 二、目标与不做什么

### 2.1 目标
- 在检索前对查询做四类扩展，产出「多个 dense 召回变体 + 一组加权 sparse 扩展词」，提升 Recall@k / MRR。
- 扩展结果严格受**词数、变体数、字符长度**门禁约束，不失控。
- 扩展器可插拔、可降级：任一扩展器失败或不可用，等价于「未扩展」，不影响主链路。

### 2.2 不做
- ❌ 不改 Milvus schema、不重建 Collection（本轮纯查询侧增强）。
- ❌ 不在原型阶段强行接入真实 LLM / Neo4j / CLIP（以接口抽象 + 内存 fake 验证，生产以适配器替换）。
- ❌ 不引入外部同义词/知识图谱大词典（首版用可配置字典 + 已有 Neo4j 图）。

## 三、四类扩展查询技术调研与适配性分析

| 扩展技术 | 原理 | 主要成本/延迟 | 对现有架构的适配性 | 结论 |
|---|---|---|---|---|
| **语义扩展**（Semantic） | LLM 生成查询的等价改写/子问题，多路 dense 召回后 RRF 融合 | 1 次 LLM 调用，约 200–500ms | 高：复用现有 `llm.Client` + `budget` 计量；变体逐条走现有 `SimilaritySearch` | **P0 采纳（可选开关）** |
| **同义词扩展**（Synonym） | 字典命中查询词项，追加同义词到 BM25 词法召回 | 近零（微秒级） | 极高：直接增强现有 `buildQuerySparse`，零外部依赖 | **P0 采纳（默认开启）** |
| **实体链接扩展**（Entity Linking） | 识别查询实体提及（别名→规范实体），追加别名与一跳关联实体 | 微秒级（内存图）或 1 次 Neo4j 查询 | 极高：直接复用现有 KAG/Neo4j 图（`knownRelationTypes`、实体节点） | **P0 采纳（默认开启）** |
| **多模态关联扩展**（Multimodal） | 视觉意图关键词→caption/tag 描述；未来 CLIP 跨模态向量 | 当前纯文本，需先补资产元数据 | 低（现状无图像索引）：文本侧 caption/tag 关联可先落地，CLIP 需新增并行 Collection | **P1 预留（默认关闭）** |

> 调研依据：Azure RAG 检索指南指出「查询改写应补充同义词、相关术语、替代表述并保持原意」；HaluBench（arXiv:2504.05324）证明「查询扩展 + 混合检索 + 动态 RRF」显著提升检索相关性并降低幻觉率；Multimodal RAG 综述（arXiv:2502.08826）确认多模态检索需 CLIP 共享向量空间 + caption/OCR/CLIP 三路融合。以上与本章选型一致。

### 3.1 各技术适配性结论（结合现有架构）
- **语义扩展** 与现有 `rerank` 天然衔接：扩展变体增多候选后，`retrieveTopDocs` 的「召回 3×topK → rerank 收敛」仍成立，只需把多路变体的召回结果并集后再重排。
- **同义词/实体扩展** 直接作用于 `buildQuerySparse`：给 BM25 查询词元加权，无需新增存储或索引，改造面最小、收益最稳。
- **实体链接** 是唯一能打通「KAG 图 ↔ 向量检索」的桥梁，把图谱实体回灌为检索词，复用已建好的 Neo4j 资产。
- **多模态** 当前知识库无图像资产，定位为**规划项**：先落地 caption/tag 文本侧关联，CLIP 跨模态向量作为二期。

## 四、技术选型与路线

### 4.1 选型汇总

| 维度 | 选择 | 理由 |
|---|---|---|
| 扩展编排 | 自研 `Coordinator`（Go） | 轻量、可插拔、便于单测与门禁 |
| 语义扩展 | LLM 生成改写（复用 `llm.Client`） | 复用现有密钥/模型/预算体系 |
| 同义词扩展 | 可配置字典（内存 `MapSynonymProvider`，生产可换 Redis/MySQL） | 确定性、零延迟 |
| 实体链接 | 复用 Neo4j KAG 图（`GraphResolver` 适配） | 复用现有图谱资产 |
| 多模态 | 二期 CLIP 跨模态向量 + caption 元数据 | 现状纯文本，预留接口 |
| 融合 | 变体 dense 多路召回 + RRF；扩展词 sparse 加权 | 与现有 HybridSearch/RRF 一致 |

### 4.2 路线分级
- **P0（本期落地）**：同义词 + 实体链接（默认开）+ 语义（可选开），统一流水线 `queryexpand` 包。
- **P1（下期）**：多模态 caption/tag 关联 + 同义词字典持久化（MySQL/Redis）。
- **P2（远期）**：CLIP 跨模态向量检索、LLM 查询分解（子问题并行召回）、扩展质量反馈闭环。

## 七、核心算法设计

### 7.1 统一流水线（Coordinator）

```text
Expand(query):
    terms, variants = 并行调用各已启用扩展器
    terms    = dedup(terms)         # 按归一化文本去重，同词多来源权重求和（封顶 2.0）
    terms    = 按权重降序裁剪到 MaxTotalTerms
    variants = 去重、剔除与原始查询重复项、截断到 MaxVariantChars、裁剪到 MaxVariants
    return ExpandedQuery{Original, Variants, Terms}
```

**安全兜底**：每个扩展器调用用 `defer recover()` 包裹，单点异常/panic 不影响整体；`Enabled=false` 或查询为空时直接返回原始查询。

### 7.2 同义词扩展（Synonym）
1. 取字典词项，按 rune 长度降序（最长优先匹配）。
2. 判断词项是否作为「词」出现在查询中：ASCII 词按边界匹配（避免 `car` 误命中 `carbon`），含 CJK 按子串匹配。
3. 命中则追加该词项的同义词（权重 0.9），按 `MaxTerms` 裁剪。

### 7.3 实体链接扩展（Entity Linking）
1. 取图谱**表面形式**（规范名 + 别名），最长优先匹配查询。
2. 命中表面形式 → 归一化到**规范实体**（`Canonical`），按规范实体去重。
3. 追加：规范实体（权重 1.0）+ 别名（0.8）+ 一跳关联实体（0.6）。
4. 按 `MaxEntities` 控制命中实体数。

> 与 KAG 的关系：`GraphResolver` 的生产实现即 Neo4j 适配——`SurfaceForms` 查 `Entity.name` 及其别名属性，`Related` 用 `MATCH (a:Entity{name:$e})-[*1..d]-(b) RETURN b.name`，与现有 [kag.go](file:///d:/Program%20Files/GoTaskAI/internal/pkg/kag/kag.go) 的 `knownRelationTypes` / `IngestGraph` 复用同一图。

### 7.4 语义扩展（Semantic）
1. `VariantGenerator` 生成 N 个改写变体（生产 = 一次 LLM 调用，输出 JSON 数组；原型 = 规则改写）。
2. 去重、剔除与原始查询相同项、截断/裁剪。

### 7.5 多模态关联扩展（Multimodal，预留）
1. `MultimodalProvider` 识别查询中的视觉意图关键词（如「图表」「趋势图」）。
2. 映射到文档资产的 caption/标签描述（如「柱状图」「数据可视化」）作为扩展词。
3. 二期：CLIP 对查询与图像分别编码，跨模态向量检索 + RRF 融合。

| 指标 | 目标值 | 测量方式 |
|---|---|---|

## 九、数据安全与隐私措施

1. **数据不出域**：同义词字典、实体图均在本地（内存 / MySQL / Neo4j），不新增外发路径；语义扩展复用现有 `llm.Client` 的密钥与端点配置，与现有 LLM 调用同等安全边界。
2. **查询脱敏可选**：扩展器只处理查询词项，不持久化原始查询；如未来接外部同义词 API，需在入口做脱敏/审计。
3. **预算与计量**：语义扩展的 LLM 调用纳入现有 `llm.Budget`（[budget.go](file:///d:/Program%20Files/GoTaskAI/internal/pkg/llm/budget.go)），受 `MaxCallsPerTask` 约束，避免被扩展放大成本。
4. **注入安全**：实体名/别名来自受控图，写入 Cypher 时沿用现有 `cleanRelationName` / `validateReadOnlyCypher` 的防护口径；扩展词仅参与 BM25 加权，不拼入任何执行语句。
5. **门禁防注入污染**：`MaxTotalTerms` / `MaxVariants` / `MaxVariantChars` 上限保证扩展结果有界，避免无关扩展词稀释召回与注入质量。

| 扩展引入噪声、精确率下降 | High | 扩展词带权重参与排序 + `MaxTotalTerms` 上限 + 复用 rerank 收敛；可关闭语义扩展 |
| 语义扩展 LLM 延迟/成本 | Medium | 默认关闭；纳入 budget；可加缓存（同查询同结果） |
| 同义词字典覆盖不全 | Medium | 字典可配置持久化；二期接 LLM 动态补同义词 |
| 实体链接跨语言别名不匹配 | Medium | 依赖 Neo4j 图别名完备性；缺失时退化（等价未扩展） |
| 扩展器异常拖垮主链路 | Low | `recover()` 兜底 + 单点失败返回空，不阻断检索 |
| 扩展结果失控（词/变体过多） | Low | 硬门禁 `MaxTotalTerms`/`MaxVariants`/`MaxVariantChars`，单测覆盖 |

## 十二、迭代优化建议

- **短期（P0 落地）**：按 §六 将 `Coordinator` 接入 `retrieveKnowledge`，`buildQuerySparse` 增加加权扩展词；补充真实知识库上的 Recall/Precision 回归。
- **中期（P1）**：同义词字典持久化到 MySQL/Redis 并可运营维护；多模态 caption/tag 元数据打标；对语义扩展做结果缓存与命中率监控。
- **长期（P2）**：CLIP 跨模态向量检索（并行 Collection + RRF）；LLM 查询分解（复杂问题拆子问题并行召回）；用真实用户查询构建扩展质量反馈闭环，动态调整权重。
