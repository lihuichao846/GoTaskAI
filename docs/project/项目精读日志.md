## 第 1 篇：精读 `cmd/api/main.go`

本篇精读的目标不是简单解释语法，而是回答下面几个更关键的问题：

1. `API Server` 启动时到底按什么顺序做事
2. 为什么这个入口文件看起来不长，却是整个 API 进程的骨架
3. `TaskManager`、`Handler`、`Gin` 路由、`MySQL`、`Redis` 之间到底怎么连接起来
4. 为什么这里会涉及 goroutine、优雅退出、静态文件托管、Asynq 监控面板等看似“不属于业务”的东西

精读文件：

- [main.go](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L27-L145)

阅读这个文件时，最重要的原则是：

- 不按 import 数量读
- 不按“每个函数名字像什么”读
- 要按“程序启动时真正发生的执行顺序”读

一句话先定性：

> `cmd/api/main.go` 不是业务实现文件，而是 API 进程的总装入口。  
> 它的职责是把配置、数据库、Redis、任务中枢、知识增强组件、HTTP Handler、Gin 路由和服务生命周期控制全部装配起来。

## 1. 先给 `main.go` 一个总定位

如果用最口语化的话概括这个 `main()`，它干的是下面这些事：

```text
读配置
-> 接 MySQL / Redis
-> 创建 TaskManager
-> 可选接 Neo4j / KAG
-> 创建各类 Handler
-> 创建 Gin 路由
-> 托管首页和监控面板
-> 挂 API 接口
-> 启动 HTTP 服务
-> 等待退出信号
-> 优雅关闭
```

所以这个文件最重要的认识是：

- 它不是“执行业务”
- 它是“装配业务运行环境”

也就是说：

- 真正处理登录的是 `internal/api/auth.go`
- 真正处理任务提交的是 `internal/api/handler.go`
- 真正管理任务流转的是 `internal/queue/manager.go`
- 真正负责 HTTP 世界搭建的是这个入口文件

这个区分非常重要，因为很多人第一次读项目时，容易把入口文件误当成“业务主文件”，然后被各种初始化代码绕晕。

更准确的说法应该是：

- `main.go` 是 API 进程的骨架
- `internal/api/*` 是控制器层
- `internal/queue/*` 是任务中枢层
- `internal/db/*` 是基础设施接入层

## 2. 第一段：配置加载

对应代码：

- [main.go:L27-L30](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L27-L30)

核心代码是：

```go
config.InitConfig("config/config.yaml")
cfg := config.AppConfig
```

### 2.1 这一步到底在做什么

它不是“随便读个 yaml”，而是在做 API 进程启动前最基础的一件事：

- 把整个系统需要的运行参数读进内存

包括但不限于：

- HTTP 监听端口
- MySQL DSN
- Redis 模式和地址
- Neo4j 地址
- 队列工作数
- 大模型接口地址

配置结构定义在：

- [config.go](file:///d:/Program%20Files/GoTaskAI/internal/config/config.go#L13-L75)

配置文件位置在：

- [config.yaml](file:///d:/Program%20Files/GoTaskAI/config/config.yaml)

### 2.2 为什么这里先读配置

因为后面几乎所有初始化都依赖它：

- 连接 MySQL 要用 `cfg.MySQL.DSN`
- 初始化 Redis 要用 `cfg.Redis`
- HTTP 监听端口要用 `cfg.Server.Port`
- 是否开启 Neo4j 要看 `cfg.Neo4j.URI`
- Gin 是否切 `release` 模式要看 `cfg.Server.Mode`

所以：

- 配置是后面所有组件的“共同上游依赖”

### 2.3 `InitConfig()` 比表面上更重要

`InitConfig()` 的实现不只是 `viper.ReadInConfig()` 那么简单，见：

- [config.go](file:///d:/Program%20Files/GoTaskAI/internal/config/config.go#L80-L101)
- [config.go](file:///d:/Program%20Files/GoTaskAI/internal/config/config.go#L117-L176)

它实际做了几件很工程化的事情：

1. 尝试解析并定位配置文件
2. 支持从当前工作目录和可执行文件路径向上寻找项目根目录
3. 支持环境变量覆盖配置项
4. 最终把配置统一反序列化到 `AppConfig`

这意味着：

- 项目不要求你必须卡死在某个目录启动
- 可执行文件和 `go run` 两种方式都更稳

这对一个多入口项目非常重要。

- 机器收集


本质上这是一个“进程生命周期里程碑”：

- 说明 API 进程已经开始启动
- 后面如果中途崩了，日志上至少能知道启动走到了哪一层

## 4. 第三段：初始化数据库和缓存

对应代码：

- [main.go:L36-L50](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L36-L50)

1. 连接 MySQL

### 4.1 连接 MySQL

代码：

```go
mysqlDB := db.InitMySQL(cfg.MySQL.DSN)
```

实现位置：

- [db.go](file:///d:/Program%20Files/GoTaskAI/internal/db/db.go#L15-L22)

业务意义：

- 后面的用户注册、登录、任务创建、任务状态更新都需要落数据库
- 如果 MySQL 连不上，整个系统的核心业务都无法成立

所以这里是硬依赖。

### 4.2 设置连接池

代码：

```go
sqlDB, err := mysqlDB.DB()
if err == nil {
    sqlDB.SetMaxIdleConns(cfg.MySQL.MaxIdleConns)
    sqlDB.SetMaxOpenConns(cfg.MySQL.MaxOpenConns)
}
```

对应：

- [main.go:L38-L42](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L38-L42)

这一步的重点不是 Go 语法，而是数据库连接管理思想：

- `SetMaxIdleConns`：控制空闲连接数量
- `SetMaxOpenConns`：控制最大连接数量

本质上是在做两件事：

- 避免每次数据库访问都重新建连接
- 避免连接数无上限膨胀把数据库压垮

这说明入口文件已经不只是“能连上数据库”，而是考虑了服务长期运行时的资源边界。

### 4.3 自动迁移表结构

代码：

```go
if err := mysqlDB.AutoMigrate(&model.Task{}, &model.User{}); err != nil {
    slog.Error("Failed to auto migrate database", "error", err)
    os.Exit(1)
}
```

对应：

- [main.go:L44-L47](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L44-L47)

这里最容易被误解成“顺手建一下表”。

实际上它的真实业务意义是：

- API 启动时检查任务表和用户表是否存在
- 不存在时自动创建
- 结构不兼容时尽量对齐
- 如果失败，直接终止启动

对应的数据模型：

- [task.go](file:///d:/Program%20Files/GoTaskAI/internal/model/task.go)
- `internal/model/user.go`

为什么必须在启动时做这件事：

- 没有 `Task` 表，任务系统根本无法运行
- 没有 `User` 表，登录注册无法运行

所以这里不是“可优化项”，而是系统起步条件检查。

### 4.4 连接 Redis

代码：

```go
redisClient := db.InitRedis(cfg.Redis)
```

实现：

- [db.go](file:///d:/Program%20Files/GoTaskAI/internal/db/db.go#L24-L53)

这一步的关键认知是：

- Redis 在这个项目里不是只做缓存

它至少承担了三种角色：

1. 任务缓存
2. Asynq 队列底座
3. Pub/Sub 事件总线

也就是说，这一行代码接上的不是一个“单功能组件”，而是一整条异步链路的重要基础。

### 4.5 Redis 这里还有一个容易忽略的工程点

`InitRedis()` 已经支持：

- 单机模式
- Sentinel 模式

这意味着：

- 业务层代码不用知道 Redis 是普通单机还是高可用模式
- 只要入口拿配置初始化好，下面用起来就统一了

这就是基础设施接入层的价值：屏蔽底层差异。

## 5. 第四段：创建核心任务中枢 `TaskManager`

对应代码：

- [main.go:L51-L54](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L51-L54)

核心代码：

```go
redisOpt := db.NewAsynqRedisConnOpt(cfg.Redis)
manager := queue.NewTaskManager(mysqlDB, redisClient, redisOpt)
defer manager.Close()
```

这一段是整个 `main.go` 里最值得精读的地方之一。

### 5.1 `redisOpt` 是什么

`redisOpt` 不是普通 Redis 客户端，它是：

- Asynq 使用的 Redis 连接配置

对应实现：

- [db.go](file:///d:/Program%20Files/GoTaskAI/internal/db/db.go#L55-L77)

也就是说：

- `redisClient` 给业务代码读写 Redis 用
- `redisOpt` 给 Asynq 队列系统连接 Redis 用

二者相关，但职责不同。

### 5.2 `TaskManager` 为什么这么关键

创建位置：

- [main.go:L53](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L53-L53)

定义位置：

- [manager.go](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L15-L25)
- [NewTaskManager](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L27-L41)

它拿到了下面这些能力：

- MySQL 持久化
- Redis 缓存
- Asynq 入队
- Redis Pub/Sub 订阅
- 当前 API 进程内的 SSE 客户端管理

所以它不是普通工具类，而是：

> 任务域统一服务层 / 任务协调器 / 任务中枢

### 5.3 为什么说任务相关事情几乎都绕不开它

因为后面很多关键动作都经过它：

- `AddTask()`：建任务、写库、写缓存、入队
- `GetTask()`：先查缓存，再查数据库
- `UpdateTask()`：更新状态、刷新缓存、发全局广播
- `Subscribe()`：为某个用户注册 SSE 通道
- `Unsubscribe()`：取消订阅
- `GetTaskHistory()`：给多轮对话提供历史任务上下文

对应文件：

- [manager.go](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go)

### 5.4 `NewTaskManager()` 启动时还做了一件隐藏但非常重要的事

它内部会起一个后台 goroutine：

- [manager.go:L37-L38](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L37-L38)

真正跑的是：

- [listenForGlobalUpdates](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L43-L56)

这件事的意义是：

- API 进程启动后，会一直订阅 Redis 的全局任务更新频道
- 后面 Worker 一旦更新任务状态，API 才能收到消息，再推给前端 SSE

换句话说：

- `TaskManager` 不只负责“写任务”
- 还负责“接收跨进程任务更新并转发到本地 SSE 客户端”

这就是它为什么是中枢，而不是简单封装类。

### 5.5 `defer manager.Close()` 的意义

`Close()` 实现见：

- [manager.go:L58-L61](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L58-L61)

主要是关闭内部持有的 Asynq Client。

虽然只是一个 `defer`，但体现的是良好的资源生命周期管理：

- 启动时创建
- 退出时释放

## 6. 第五段：可选初始化 Neo4j 和 KAG 管理器

对应代码：

- [main.go:L56-L63](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L56-L63)

核心代码：

```go
var kagManager *kag.KAGManager
if cfg.Neo4j.URI != "" {
    neo4jDriver := db.InitNeo4j(cfg.Neo4j.URI, cfg.Neo4j.Username, cfg.Neo4j.Password)
    defer neo4jDriver.Close(context.Background())
    kagManager = kag.NewKAGManager(neo4jDriver, llm.NewClient())
    slog.Info("Connected to Neo4j successfully, KAG ingestion enabled")
}
```

### 6.1 为什么这里是可选的

因为 Neo4j 不是整个项目的绝对硬依赖。

没有 Neo4j 时：

- 登录注册照样可以跑
- 任务提交照样可以跑
- Worker 处理普通任务也可以跑

但没有 Neo4j 时：

- KAG 图谱增强能力会被禁用

所以这里体现的是一个很好的架构分层：

- 基础任务平台是一层
- GraphRAG / KAG 增强是一层

### 6.2 `InitNeo4j()` 做了什么

实现位置：

- [neo4j.go](file:///d:/Program%20Files/GoTaskAI/internal/db/neo4j.go#L10-L25)

它会：

1. 创建 Neo4j Driver
2. 调用 `VerifyConnectivity()` 做连通性验证

这意味着：

- 系统不是“先把 driver 存下来，以后再说”
- 而是启动时就确认 Neo4j 真的可用

### 6.3 `KAGManager` 为什么还依赖 LLM Client

创建逻辑在：

- [main.go:L61](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L61-L61)

对应定义：

- [kag.go](file:///d:/Program%20Files/GoTaskAI/internal/pkg/kag/kag.go#L16-L27)

这说明 KAG 能力不是单纯查图库。

它至少有两类工作：

1. 知识抽取：把原始文本变成实体关系三元组
2. 在线检索：把自然语言问题转成 Cypher，再去 Neo4j 查询

这两步都需要 LLM 参与。

所以你可以把 KAG 理解为：

- `LLM + Neo4j` 的组合能力

而不是：

- “单独一个图数据库查询工具”

这里的核心认识是：

- 重试任务
- 取消任务
- SSE 推流

它之所以只需要 `manager`，是因为：

它拿 `redisClient` 是因为向量库底座走 RedisVector；
它拿 `kagManager` 是因为图谱入库走 Neo4j + LLM 抽取链路。

### 7.5 这一段的一个关键阅读技巧

- 先看对象是怎么被创建出来的

## 9. 第八段：创建 Gin 引擎并挂全局中间件

对应代码：

- [main.go:L73-L75](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L73-L75)

代码：

```go
r := gin.Default()
r.Use(middleware.CORSMiddleware())
```

### 9.1 `gin.Default()` 在这里不是重点，重点是“HTTP 世界从这里开始建立”

到这一行开始，程序从“装依赖”进入“搭对外接口框架”。

你可以把 Gin 引擎理解成：

- 整个 HTTP 世界的总入口

后面所有路由、所有中间件、所有页面托管，都会挂在这个 `r` 上。

### 9.2 为什么要挂 CORS

`CORSMiddleware()` 的意义是：

- 支持独立前端跨域访问当前的 Go 后端

这点很关键，因为项目当前同时存在：

- 后端直接托管的兼容页面
- `web/` 下独立前端入口

如果没有 CORS，浏览器层就会先把跨域请求拦掉，后端甚至收不到请求。

所以这不是“锦上添花”，而是：

- 给前后端分离演进留出的通道

## 10. 第九段：静态首页托管

对应代码：

```go
r.StaticFile("/", config.ResolveProjectPath("public", "index.html"))
```

### 10.1 这说明前端还保留着兼容模式

虽然项目已经有 `web/` 目录的独立前端工程，但这里说明：

- API Server 依然能直接托管首页

这意味着项目不是纯粹“前后端完全分离”状态，而是：

- 同时兼容旧模式和新模式

### 10.2 `ResolveProjectPath()` 在这里的价值

见：

- [config.go](file:///d:/Program%20Files/GoTaskAI/internal/config/config.go#L103-L115)

它让程序不依赖当前工作目录，也能稳定找到：

- `public/index.html`

这一点非常重要，因为：

- 双击脚本启动
- 在项目根目录运行
- 从 `bin/` 目录启动二进制

这些场景下的相对路径可能都不同。

所以真正被解决的是：

## 14. 第十三段：启动 HTTP 服务为什么要放进 goroutine

对应代码：

- [main.go:L124-L130](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L124-L130)

代码：

```go
go func() {
    slog.Info("GoTaskAI API Server listening", "port", cfg.Server.Port)
    if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
        slog.Error("Server failed", "error", err)
        os.Exit(1)
    }
}()
```

### 14.1 为什么这里一定要起 goroutine

因为：

- `ListenAndServe()` 是阻塞调用

如果不放进 goroutine：

- 主协程会卡死在这里
- 后面的退出信号监听逻辑就永远执行不到

所以这里的结构分工其实是：

- 后台 goroutine：负责持续接收 HTTP 请求
- 主协程：负责等待系统退出信号并做收尾

### 14.2 这一段是服务生命周期控制的关键点

很多初学者只会写：

```go
r.Run(":8080")
```

但这个项目写法更成熟，因为它考虑了：

- 启动日志
- 服务异常退出
- 正常关闭和异常关闭的区分

其中：

- `http.ErrServerClosed` 是正常关闭时的返回
- 所以不能把它当成真正错误

这属于很典型的服务端工程细节。

对应代码：

## 16. 第十五段：优雅退出

对应代码：

- [main.go:L137-L144](file:///d:/Program%20Files/GoTaskAI/cmd/api/main.go#L137-L144)

代码：

```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

if err := srv.Shutdown(ctx); err != nil {
    slog.Error("Server Shutdown Error", "error", err)
}
```

### 16.1 为什么不能收到退出信号就立刻强杀

因为此时可能存在：

- 正在执行中的 HTTP 请求
- 正在回包中的接口
- 正在推送中的 SSE 连接

如果直接暴力断掉，可能会造成：

- 响应中断
- 前端收到半截内容
- 用户体验很差

### 16.2 `WithTimeout(5*time.Second)` 的意义

它给了服务一个宽限期：

- 停止接新请求
- 尽量处理完当前已经进来的请求
- 最多等 5 秒

这就是“优雅退出”的真实含义。

### 16.3 `Shutdown()` 的实际效果

它不是立即切断电源，而是：

1. 不再接收新连接
2. 尝试平稳结束现有连接
3. 超时后再真正关闭

### 16.4 这一步为什么很工程化

因为它说明作者考虑的不是：

- “程序怎么跑起来”

而是：

- “程序作为服务，怎么平稳退出”

这是从脚本思维走向服务思维的一个明显标志。

## 4. 先看请求体结构：`SubmitRequest` 和 `BatchSubmitRequest`

对应：

- [handler.go:L33-L36](file:///d:/Program%20Files/GoTaskAI/internal/api/handler.go#L33-L36)
- [handler.go:L94-L100](file:///d:/Program%20Files/GoTaskAI/internal/api/handler.go#L94-L100)

### 4.1 为什么先看结构体

因为控制器层的第一件事往往不是“干活”，而是：

- 把 HTTP 请求体反序列化成程序内部可操作的结构

比如这里的 `SubmitRequest`：

```go
type SubmitRequest struct {
    Type         model.TaskType     `json:"type"`
    SessionID    string             `json:"session_id"`
    SystemPrompt string             `json:"system_prompt"`
    Payload      string             `json:"payload" binding:"required"`
    Priority     model.TaskPriority `json:"priority"`
}
```

这说明前端提交任务时，能影响任务行为的主要参数包括：

- 任务类型
- 会话 ID
- System Prompt
- 实际用户输入
- 优先级

### 4.2 这里最重要的字段是哪个

最关键的是：

- `Payload`

因为它是真正的任务输入。

而且通过：

```go
binding:"required"
```

可知：

- `payload` 是提交任务的硬必要字段

### 4.3 `SessionID` 的意义

它不是给数据库做普通分组这么简单。

后面 Worker 在处理任务时会用它去查历史任务：

- 进而构造多轮上下文

## 10. `SubmitTask()` 第四步：构造任务实体

对应：

- [handler.go:L153-L166](file:///d:/Program%20Files/GoTaskAI/internal/api/handler.go#L153-L166)

代码核心：

```go
task := &model.Task{
    ID:           uuid.New().String(),
    UserID:       userID,
    SessionID:    req.SessionID,
    Type:         req.Type,
    SystemPrompt: req.SystemPrompt,
    Priority:     req.Priority,
    Payload:      req.Payload,
    Status:       model.StatusPending,
    MaxRetry:     3,
    CreatedAt:    time.Now(),
    UpdatedAt:    time.Now(),
}
```

### 10.1 这一步是“从 HTTP 世界进入任务世界”

这是一个非常关键的转折点。

前面还是：

- JSON 字段
- 用户请求
- Web 接口参数

到了这里，开始变成：

- 任务实体
- 任务状态机
- 可持久化对象
- 可入队对象

也就是说，`SubmitTask()` 真正干的核心工作不是“直接跑任务”，而是：

- 把外部请求翻译成内部任务对象

### 10.2 为什么要在这里就生成 UUID

因为这个任务从一开始就要拥有全局唯一 ID。

后面很多地方都要靠它：

- 前端拿它查任务状态
- Worker 靠它识别具体任务
- SSE 推送靠它定位哪条任务更新了
- 取消任务、重试任务也都靠它

所以任务 ID 必须在进入系统的第一刻就确定下来。

### 10.3 为什么初始状态一定是 `pending`

因为这时任务还没有被 Worker 真正拿去执行。

系统当前只做了：

- 接收请求
- 生成任务对象

还没做到：

- 开始处理

所以此时最准确的状态就是：

- `pending`

这也是整个状态机的第一站。

### 10.4 为什么这里就设置 `MaxRetry`

因为重试策略本身就是任务元数据的一部分。

也就是说，任务从创建起就带着：

- 最多允许失败后再试多少次

这为后面 Worker 的错误处理链路埋好了规则。

### 11.3 为什么失败时返回 `503 Service Unavailable`

因为如果入队失败，本质上不是“请求格式错了”，而是：

- 服务当前无法完成任务受理

所以这里用 `503` 比 `500` 或 `400` 更贴切。

它表达的是：

- 服务暂时不可用

## 12. `SubmitTask()` 第六步：为什么返回 `202 Accepted`

对应：

代码：

### 12.1 这是整个异步任务系统的标志性设计

这里返回的不是：

因为结果此时根本还没出来。

## 17. `RetryTask()`：它展示了任务状态机如何回到起点

对应：

- [RetryTask](file:///d:/Program%20Files/GoTaskAI/internal/api/handler.go#L269-L310)

这个函数特别适合用来理解任务状态机。

### 17.1 为什么只能重试 `failed`

代码里明确限制：

```go
if task.Status != model.StatusFailed {
    c.JSON(http.StatusBadRequest, gin.H{"error": "只能重试已失败的任务"})
    return
}
```

这说明状态机不是任意跳转的。

比如：

- `completed` 不能随便重试
- `processing` 不能直接手动重试

只有彻底失败的任务，才允许人工干预把它重新送回流程。

### 17.2 重试时具体重置了什么

代码：

```go
task.Status = model.StatusPending
task.Retries = 0
task.Error = ""
```

这一步很像“回炉重造”：

- 状态回到等待中
- 已重试次数清零
- 旧错误清空

也就是说，这不是在原状态上继续勉强跑，而是：

- 重新当作一条待处理任务看待

### 17.3 为什么先 `UpdateTask()` 再 `Enqueue()`

因为系统要先把“这条任务已经回到 pending”这个事实写入数据库和缓存，
再把它重新推进队列。

否则会出现状态和队列事实不一致的问题。

这里体现了一个很重要的工程原则：

- 先修正系统状态，再触发后续流程

## 18. `CancelTask()`：它展示了 API 和 Worker 的跨进程协作

对应：

- [CancelTask](file:///d:/Program%20Files/GoTaskAI/internal/api/handler.go#L312-L360)

这个函数特别值得讲，因为它不只是 CRUD，而是：

- API 调用 Worker 的内部控制能力

### 18.1 为什么取消任务不能只改数据库

因为如果任务已经进入 Worker 执行中，仅仅把数据库状态改掉，并不能马上打断正在执行的那一侧。

所以这里优先尝试：

- 用 gRPC 直接通知 Worker 强制取消

### 18.2 gRPC 调用部分说明了什么

代码核心：

```go
conn, err := grpc.Dial("localhost:50051", grpc.WithTransportCredentials(insecure.NewCredentials()))
...
client := pb.NewWorkerServiceClient(conn)
...
resp, err := client.CancelTask(ctx, &pb.CancelRequest{TaskId: id})
```

这说明：

- API 和 Worker 虽然是两个独立进程
- 但它们之间并不是完全零通信

这里走的是：

- 内部同步控制链路

这和普通业务任务流不同，普通任务流是：

- API -> Asynq -> Worker

而取消任务这里是：

- API -> gRPC -> Worker

### 18.3 为什么还要有 fallback

如果 gRPC 失败，代码会走保底逻辑：

```go
task.Status = model.StatusCancelled
task.Error = "Task was cancelled by user (fallback)"
h.manager.UpdateTask(task)
```

这说明系统并没有把取消能力完全押注在 gRPC 上。

它的策略是：

1. 优先强控制
2. 失败时退化成最终一致性方案

这是一种非常成熟的工程思路。

即使 Worker 当下没法立刻取消，至少：

- 系统对外状态已经变成 `cancelled`
- Worker 后续轮询状态时也会主动跳过

## 23. `StreamTasks()` 第四步：等待客户端断开或任务更新

对应：

- [handler.go:L392-L406](file:///d:/Program%20Files/GoTaskAI/internal/api/handler.go#L392-L406)

代码核心：

```go
clientGone := c.Writer.CloseNotify()

for {
    select {
    case <-clientGone:
        return
    case task := <-ch:
        c.SSEvent("task_update", task)
        c.Writer.Flush()
    }
}
```

### 23.1 这就是 SSE 长连接处理的核心循环

这里的结构非常像一个“监听器”：

- 客户端断开了，就退出
- 收到任务更新，就推给前端

### 23.2 `Flush()` 为什么必须有

因为如果只写进缓冲区不立刻 flush，前端可能收不到实时数据。

所以 `Flush()` 的意义就是：

- 立即把这次事件真正发出去

这一步是保证“实时感”的关键之一。

## 24. 但 `StreamTasks()` 的真正关键问题是：`ch` 里的数据从哪来？

这是理解整个微服务实时推送链的核心问题。

答案不是：

- Handler 自己去查数据库
- Handler 自己定时轮询

真正链路是：

1. Worker 完成任务或更新状态
2. Worker 调 `TaskManager.UpdateTask()`
3. `UpdateTask()` 更新 MySQL、更新 Redis 缓存、再向 Redis Pub/Sub 发布消息
4. API 进程中的 `listenForGlobalUpdates()` 一直在订阅这个频道
5. 收到消息后再 `broadcast()` 给对应用户的本地 channel
6. `StreamTasks()` 从这个 channel 取出任务更新并 SSE 推送

对应底层：

- [UpdateTask](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L236-L254)
- [listenForGlobalUpdates](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L43-L56)
- [broadcast](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L91-L104)

这条链建议你直接背下来：

```text
Worker -> Redis Pub/Sub -> API TaskManager -> SSE channel -> Browser
```

这就是为什么前端能实时更新，而 Worker 又不需要直接连浏览器。

## 1. 为什么 `TaskManager` 是整个项目的核心之一

先看结构体定义：

- Redis
- Asynq

这就是良好分层带来的简洁性。

## 2. `NewTaskManager()`：它不只是 new 一个对象

对应：

代码：

```go
func NewTaskManager(db *gorm.DB, rdb *redis.Client, redisOpt asynq.RedisConnOpt) *TaskManager {
    m := &TaskManager{
        db:          db,
        rdb:         rdb,
        asynqClient: asynq.NewClient(redisOpt),
        ctx:         context.Background(),
        clients:     make(map[uint]map[chan *model.Task]bool),
    }

    go m.listenForGlobalUpdates()

}
```

### 2.1 它做了 4 件事

1. 接住 MySQL
2. 接住 Redis
3. 创建 Asynq Client
4. 初始化本地 SSE 订阅表

如果只做到这里，它已经是任务域的“写入与读取管理器”了。

但它还做了第五件更关键的事：

5. 起一个后台 goroutine 去监听 Redis Pub/Sub

### 2.2 为什么 `go m.listenForGlobalUpdates()` 这么关键

因为这一步让 `TaskManager` 从“本地任务管理器”升级成了“微服务任务中枢”。

如果没有这一句：

- Worker 更新状态时，API 进程感知不到
- SSE 就没法做到跨进程实时推送

所以你可以把这句理解成：

- API 进程一启动，就开始接通来自 Worker 的跨进程状态广播

也就是说，`NewTaskManager()` 不只是初始化状态，还顺手接通了“任务更新消息总线”。

## 3. `listenForGlobalUpdates()`：跨进程广播进入 API 进程的第一站

对应：

- [listenForGlobalUpdates](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L43-L56)

代码：

```go
func (m *TaskManager) listenForGlobalUpdates() {
    pubsub := m.rdb.Subscribe(m.ctx, "global_task_updates")
    defer pubsub.Close()

    ch := pubsub.Channel()
    for msg := range ch {
        var t model.Task
        if err := json.Unmarshal([]byte(msg.Payload), &t); err == nil {
            m.broadcast(&t)
        }
    }
}
```

### 3.1 这段代码的真实含义

它的意思不是“查 Redis 数据”，而是：

- 订阅 Redis 的一个消息频道
- 谁往这个频道发了任务更新，我就收到

这个频道名是：

- `global_task_updates`

### 3.2 为什么这里用的是 Redis Pub/Sub，而不是数据库轮询

如果不用 Pub/Sub，API 要想知道 Worker 有没有更新任务状态，就只能：

- 周期性轮询数据库
- 或周期性轮询 Redis 缓存

这会带来两个问题：

1. 浪费请求和资源
2. 实时性差

而 Pub/Sub 的好处是：

- Worker 一更新，消息立刻广播
- API 进程被动接收

所以它是一种“推模式”，不是“拉模式”。

### 3.3 这一步只做了“接收消息”，还没推给前端

收到 Redis 消息后，它做的是：

```go
m.broadcast(&t)
```

说明这一步只是把：

- 进程间广播消息

转成：

- 当前 API 进程内部的本地分发

换句话说：

- Redis Pub/Sub 解决的是“Worker 怎么告诉 API”
- `broadcast()` 解决的是“API 收到后怎么告诉自己挂着的浏览器连接”

## 4. `clients` 这张表到底是什么

先回到字段：

- [manager.go:L22-L25](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L22-L25)

```go
clients   map[uint]map[chan *model.Task]bool
```

这个结构不太直观，但它非常重要。

### 4.1 它本质上是：

```text
userID -> 这个用户当前所有活跃 SSE channel 的集合
```

为什么是“一个用户 -> 多个 channel”？

因为同一个用户可能：

- 开多个浏览器标签页
- 开多个页面窗口
- 在多个设备上同时登录

所以不能写成：

- `userID -> 单个 channel`

### 4.2 为什么还要有 `clientsMu`

因为这些订阅和取消订阅动作可能同时发生：

- 某个浏览器刚连上
- 某个浏览器刚断开
- 某条任务状态刚更新

这时如果不加锁，直接并发改 map，会有并发安全问题。

所以这里用了：

- `RWMutex`

来保护这个“在线 SSE 订阅表”。

这说明 `TaskManager` 不只是懂数据库和 Redis，它还在管理并发共享内存状态。

## 5. `Subscribe()`：为某个用户创建一个本地消息收件箱

对应：

- [Subscribe](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L63-L75)

代码：

```go
func (m *TaskManager) Subscribe(userID uint) chan *model.Task {
    m.clientsMu.Lock()
    defer m.clientsMu.Unlock()

    if m.clients[userID] == nil {
        m.clients[userID] = make(map[chan *model.Task]bool)
    }

    ch := make(chan *model.Task, 10)
    m.clients[userID][ch] = true
    return ch
}
```

### 5.1 这个函数做的不是“立即推消息”

它做的是准备工作：

- 给这个用户创建一个 channel
- 把这个 channel 登记到 `clients` 表里

所以你可以把它理解成：

- 给当前用户发一个“收件箱”

后面只要有属于这个用户的任务更新，就会被投递到这个收件箱里。

### 5.2 为什么 channel 带缓冲 `10`

```go
ch := make(chan *model.Task, 10)
```

这表示：

- 即使前端消费稍微慢一点，短时间内也还能缓存一些任务更新

如果完全无缓冲：

- 每次发送都要严格等接收方同步接住
- 很容易把广播流程卡住

所以缓冲 channel 是一种典型的“削峰”设计。

## 6. `Unsubscribe()`：长连接结束后的清理动作

对应：

- [Unsubscribe](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L77-L89)

代码：

```go
func (m *TaskManager) Unsubscribe(userID uint, ch chan *model.Task) {
    m.clientsMu.Lock()
    defer m.clientsMu.Unlock()

    if userClients, ok := m.clients[userID]; ok {
        delete(userClients, ch)
        close(ch)
        if len(userClients) == 0 {
            delete(m.clients, userID)
        }
    }
}
```

### 6.1 为什么必须取消订阅

因为 `StreamTasks()` 建立的是长连接。

浏览器关闭标签页或刷新页面后，这个 channel 如果还留着，就会出现：

- 无效订阅残留
- 内存浪费
- 后续广播还往废弃通道发消息

所以取消订阅本质上是：

- 长连接资源回收

### 6.2 为什么最后还要删掉空用户项

如果一个用户最后一个 channel 也没了：

- 就没必要继续保留 `m.clients[userID]`

这是一种很细致的内存清理动作。

## 7. `broadcast()`：从“某条任务更新”找到“该推给哪个用户”

对应：

- [broadcast](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L91-L104)

代码：

```go
func (m *TaskManager) broadcast(t *model.Task) {
    m.clientsMu.RLock()
    defer m.clientsMu.RUnlock()

    if userClients, ok := m.clients[t.UserID]; ok {
        for ch := range userClients {
            select {
            case ch <- t:
            default:
            }
        }
    }
}
```

### 7.1 这是本地分发层的核心

Redis Pub/Sub 把消息带到了 API 进程，但还没告诉具体哪个浏览器。

`broadcast()` 做的就是：

- 从任务对象里拿到 `t.UserID`
- 找到这个用户当前所有在线 channel
- 把任务更新塞进去

所以它是：

- “按用户定向投递”的那一层

### 7.2 为什么这里是遍历“这个用户的所有 channel”

因为同一个用户可能开多个页面。

系统设计目标是：

- 用户所有在线页面都能同时收到更新

所以这里不是“只推给一个连接”，而是：

- 推给这个用户的所有活跃连接

### 7.3 为什么 `select { case ch <- t: default: }` 很关键

这段的真实意义是：

- 尝试发
- 但如果这个 channel 已经满了，就丢弃，不阻塞整个系统

这是一个很典型的“不要让单个慢消费者拖垮整个广播系统”的设计。

也就是说：

- 系统优先保证整体可用性
- 而不是无条件等待最慢的那个连接

这种取舍很有工程味。

## 8. `cacheTask()`：为什么任务状态要放进 Redis

- [cacheTask](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L106-L113)

```go
func (m *TaskManager) cacheTask(t *model.Task) {
    data, err := json.Marshal(t)
```

### 8.1 这不是多余的一层

### 8.2 为什么 key 设计成 `task:<id>`

因为单个任务查询最自然的主键就是任务 ID。

这样查的时候可以直接：

- `GET task:<id>`

简单直接。

说明这里的缓存定位是：

- 任务状态的短中期热点缓存

不是永久数据来源。

最终真实来源仍然是 MySQL。

## 9. `AddTask()`：把任务正式纳入系统

对应：

- [AddTask](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L115-L127)

代码：

```go
func (m *TaskManager) AddTask(t *model.Task) error {
    if err := m.db.Create(t).Error; err != nil {
        return err
    }

    m.cacheTask(t)

    return m.Enqueue(t)
}
```

### 9.1 这是整个异步任务链的真正落点

前面在 `SubmitTask()` 里只是构造了任务对象。

到了 `AddTask()`，任务才真正：

- 被数据库持久化
- 被缓存系统记住
- 被推进异步队列

所以这里是任务从“内存对象”变成“系统中的正式任务”的关键一步。

### 9.2 为什么顺序是：先 MySQL，再 Redis，再 Asynq

这个顺序非常值得讲。

#### 第一层：先写 MySQL

因为 MySQL 是最终持久化存储。

要先保证：

- 任务已经有正式记录

否则如果先入队，再写库失败，就会出现：

- Worker 可能开始处理了
- 但数据库里没有这条任务

这会非常混乱。

#### 第二层：再写 Redis 缓存

因为一旦数据库写成功，这条任务就已经是“真实存在”的任务了。

此时把它缓存起来，可以加速后续读取。

#### 第三层：最后入队

因为只有前两步成功后，才适合让 Worker 真正开始处理。

所以这个顺序体现的是：

- 先建立事实
- 再提供加速
- 最后触发执行

这是非常合理的。

## 10. `Enqueue()`：任务怎么进入不同优先级队列

对应：

- [Enqueue](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L129-L149)

代码核心：

```go
switch t.Priority {
case model.PriorityHigh:
    queueName = "high"
case model.PriorityLow:
    queueName = "low"
default:
    queueName = "default"
}

payload, err := json.Marshal(t)
...
task := asynq.NewTask("task:process", payload)
_, err = m.asynqClient.Enqueue(task, asynq.Queue(queueName), asynq.MaxRetry(3))
```

### 10.1 它做了两件事

1. 根据业务优先级映射到队列名
2. 把任务对象包装成 Asynq 任务推进 Redis 队列

### 10.2 为什么这里还要再序列化一次

因为 Asynq 传递的不是 Go 内存对象本身，而是：

- 可传输的 payload

所以必须先把 `Task` 转成 JSON。

### 10.3 为什么队列名是 `high/default/low`

因为 Worker 池那边会按不同队列配置不同的消费权重。

也就是说，这里不是“只是分个名字”，而是在为后面的调度策略埋钩子。

### 10.4 `asynq.MaxRetry(3)` 和任务里的 `MaxRetry`

这里有个很值得注意的地方：

- 任务实体里有 `MaxRetry`
- Asynq 入队时也配置了 `MaxRetry(3)`

这说明：

- 业务层和队列层都在约束“最多重试几次”

当前项目里两边都统一到了 3。

## 11. `GetTask()`：典型的缓存旁路读取

对应：

- [GetTask](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L151-L171)

代码逻辑：

1. 先查 Redis
2. 查不到再查 MySQL
3. 再把数据库结果回写 Redis

### 11.1 这是标准的 Cache-Aside 模式

也就是：

- 读请求优先查缓存
- 缓存没有再查数据库
- 查到后再补回缓存

这套模式的好处是：

- 平时快
- 缓存丢了也不会丢数据

### 11.2 为什么这里非常适合做缓存

因为单个任务状态是典型的热点读场景：

- 前端可能会查
- SSE 更新后也可能手动刷新
- 取消、重试前也会先查

所以单任务状态天然适合缓存。

## 12. `DeleteSession()`：它不是单纯“批量删”

对应：

- [DeleteSession](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L173-L204)

这个函数很值得讲，因为它同时牵涉：

- 数据删除
- 缓存清理
- 任务取消语义

### 12.1 为什么查询条件是 `(session_id = ? OR id = ?)`

这段逻辑是在兼容两类场景：

1. 正常多轮会话中的任务，靠 `session_id` 关联
2. 没显式 session 的单次任务，把自身 `id` 当根标识

所以这里的设计目标是：

- 不管是多轮还是单轮，都能作为“会话整体”被清理

### 12.2 为什么删除数据库后还要继续遍历任务

因为除了数据库记录，还要处理：

- Redis 缓存
- 正在排队/执行的任务

这里体现的是：

- 任务不是只存在于数据库里

它还可能存在于：

- Redis 缓存
- Asynq 队列
- Worker 的处理中

### 12.3 为什么对 `pending/processing` 任务还要改成 `cancelled`

因为即使数据库记录准备删掉，从“系统运行态”看，这些任务可能还活着。

把它们标成 `cancelled` 的意义是：

- Worker 后续如果碰到，会主动跳过

所以这里是“逻辑取消 + 数据清理”的组合操作。

## 14. `GetTasksByUserID()`：为什么它直接查 MySQL 而不是 Redis

对应：

### 14.1 因为这不是单 key 热点读取

## 15. `UpdateTask()`：整个微服务实时更新链的总开关

对应：

- [UpdateTask](file:///d:/Program%20Files/GoTaskAI/internal/queue/manager.go#L236-L254)

这是整个 `manager.go` 最应该优先精读的函数之一。

代码：

```go
func (m *TaskManager) UpdateTask(t *model.Task) {
    t.UpdatedAt = time.Now()

    m.db.Save(t)
    m.cacheTask(t)

    data, err := json.Marshal(t)
    if err == nil {
        m.rdb.Publish(m.ctx, "global_task_updates", data)
    }
}
```

### 15.1 这个函数做的不是单纯“改数据库”

它一次性串了三层动作：

1. 改 MySQL
2. 刷 Redis 缓存
3. 发 Redis Pub/Sub 广播

这正是它最值钱的地方。

### 15.2 为什么这一步是微服务解耦的关键

如果项目还是单体：

- Worker 和 SSE 都在同一个进程里
- 改完状态后直接 `broadcast()` 就行

但现在不是。

现在是：

- Worker 在一个进程
- API 在另一个进程
- 浏览器连的是 API，不是 Worker

所以 Worker 不能直接把消息推给浏览器。

它只能：

- 先把状态变化发布到 Redis

然后：

- API 进程订阅到这个变化
- 再分发到本地 channel
- 最后 SSE 推给前端

这就是为什么 `UpdateTask()` 是整个实时更新链的总开关。

### 15.3 为什么必须“先写库，再发广播”

因为广播代表的是：

- “这条任务状态已经正式变了”

所以应该先保证：

- 数据库事实已更新
- 缓存事实已更新

再告诉别人：

- 状态变了

否则会出现“前端已经收到 completed，但数据库里还没更新”的不一致问题。

## 4. `NewPool()` 第一部分：创建 Asynq Server

对应：

- [pool.go:L35-L48](file:///d:/Program%20Files/GoTaskAI/internal/worker/pool.go#L35-L48)

代码：

```go
srv := asynq.NewServer(
    redisOpt,
    asynq.Config{
        Concurrency: workers,
        Queues: map[string]int{
            "high":    6,
            "default": 3,
            "low":     1,
        },
    },
)
```

### 4.1 这里的 `workers` 决定了什么

它控制的是：

- Worker 进程内部同时最多并发执行多少个任务

这和 API 并发不是一回事。

API 负责接请求，而这里控制的是：

- 真正消耗 LLM、RAG、KAG 资源的执行并发

### 4.2 `Queues` 这一段特别关键

这里定义了：

- `high: 6`
- `default: 3`
- `low: 1`

这不是“最多多少任务”的意思，而是：

- 消费调度权重

即：

- 高优任务更容易被优先取出来执行

这和前面 `TaskManager.Enqueue()` 里按优先级放入不同队列正好对应起来。

所以整个优先级链是：

```text
任务 Priority
-> Enqueue() 选择 high/default/low 队列
-> Worker 池按权重优先消费不同队列
```

### 4.3 这说明项目的优先级不是摆设

很多项目虽然定义了“高/中/低优先级”，但后面根本没实现真实调度差异。

这里不是。

这里从：

- 任务实体
- 队列名
- Worker 调度权重

是一条贯通的链。

意思是：

- 向量检索所需的 embedding 能力，依赖本地 Ollama 提供的嵌入模型

#### 第二层：创建 Embedder


说明 Worker 之后在做相似度检索时，要把查询文本变成向量。

说明最终的向量库底座还是 RedisVector。

### 6.2 为什么这里允许 RAG 初始化失败

- 初始化失败就打印日志

这说明项目把 RAG 视为：

- 增强能力

而不是：

- 基础任务执行的绝对硬依赖

也就是说，即使没有 RAG，Worker 依然可以：

- 处理普通任务
- 调基础 LLM

这体现了能力降级意识。

### 6.3 `WithIndexName("idx:pangu_v2", false)` 的意义

这里的 `false` 表示：

- 不主动创建索引

说明这个 Worker 不是负责“建向量库结构”的那一侧，而是：

- 只消费既有知识库

和前面的 `RAG Ingest` 接口形成了职责分离：

## 21. 第十一步：错误处理与重试

对应：

- [pool.go:L236-L252](file:///d:/Program%20Files/GoTaskAI/internal/worker/pool.go#L236-L252)

这是整个执行链里非常有工程味的一段。

### 21.1 如果模型调用报错，先看还有没有重试机会

代码：

```go
if t.Retries < t.MaxRetry {
    t.Retries++
    t.Status = model.StatusPending
    t.Error = fmt.Sprintf("AI API error, retrying %d/%d: %v", t.Retries, t.MaxRetry, err)
    p.manager.UpdateTask(&t)
    return err
}
```

### 21.2 为什么失败后状态先改回 `pending`

因为从系统视角看，这条任务还没有彻底死亡，而是：

- 准备等待下一次重试

所以它不应该显示成 `failed`，而应该回到“待处理”。

### 21.3 为什么这里要 `return err`

这一步非常关键。

不是为了让函数报错给人看，而是为了告诉 Asynq：

- 这次执行失败了，请按队列层的重试策略安排下次重试

也就是说，业务代码只负责表达：

- “这次没做成”

而真正的：

- 重试调度
- 退避时间控制

交给 Asynq 完成。

这就是为什么不用自己写复杂重试器。

### 21.4 如果重试次数耗尽怎么办

代码：

```go
t.Status = model.StatusFailed
t.Error = fmt.Sprintf("Failed after %d retries. Last error: %v", t.MaxRetry, err)
p.manager.UpdateTask(&t)
return nil
```

这里改成：

- `failed`

并且返回 `nil`。

为什么返回 `nil`？

因为：

- 到这里业务已经决定“不再重试”
- 所以不能再让 Asynq 继续认为它要自动重试

这一步体现的是：

- 业务层和队列层协同控制重试终点

## 24. 为什么说 `pool.go` 是“执行编排器”而不是“模型调用器”

如果这个文件只是模型调用器，它应该只做：

- `result := llm.Generate(prompt)`

然后结束。

但这里不是。

它要处理：

- 队列消费
- 任务状态机
- 取消逻辑
- RAG
- KAG
- 历史上下文
- MCP 工具规范
- 调用超时
- 错误重试
- 最终广播

这说明它真正的职责是：

- 在多个增强模块、执行规则和外部依赖之间做统一编排

所以叫“执行编排器”更准确。

## 25. 这个文件最值得建立的 8 个认知

1. `Pool` 不是简单线程池，而是 Worker 执行编排器
2. `NewPool()` 会同时组装 Asynq Server、RAG Store、LLM Client、MCP Client、KAG Manager
3. `task:process` 是队列任务类型和 Worker 处理函数之间的绑定点
4. Worker 执行前后都会检查任务是否已取消，说明代码考虑了排队取消和处理中取消两种情况
5. `processing` 不是装饰状态，而是 Worker 真正开始接手任务后的状态
6. RAG、KAG、历史上下文和 MCP 工具调用都不是独立回答，而是被统一拼装进一次完整的模型调用链
7. 返回 `err` 给 Asynq 是触发自动重试的关键手段
8. 成功、失败、取消三条路径都通过 `UpdateTask()` 回写系统并驱动前端实时更新

## 5. `mcpToolToOpenAITool()`：这个函数是 MCP 和 OpenAI Tool 之间的桥

对应：

- [mcpToolToOpenAITool](file:///d:/Program%20Files/GoTaskAI/internal/pkg/llm/client.go#L63-L78)

代码核心：

```go
func mcpToolToOpenAITool(t mcp.Tool) openai.Tool {
    var params jsonschema.Definition
    schemaBytes, _ := json.Marshal(t.InputSchema)
    json.Unmarshal(schemaBytes, &params)

    return openai.Tool{
        Type: openai.ToolTypeFunction,
        Function: &openai.FunctionDefinition{
            Name:        t.Name,
            Description: t.Description,
            Parameters:  params,
        },
    }
}
```

### 5.1 这个函数到底在解决什么问题

MCP Server 返回的工具定义格式是：

- `mcp.Tool`

而 OpenAI 兼容聊天接口要求的工具定义格式是：

- `openai.Tool`

二者不是同一个类型。

所以必须有一个适配层，把：

- MCP 工具描述

翻译成：

- 模型能理解并调用的 Tool 定义

### 5.2 为什么这一步很关键

因为模型要想调用工具，前提是它得先“知道有哪些工具、叫什么、参数怎么传”。

而这一步就是把 MCP 工具世界暴露给模型的入口。

你可以把它理解成：

- 把后端工具注册表翻译成模型可读的菜单

## 7. 第一阶段：先组装消息数组

对应：

- [client.go:L81-L97](file:///d:/Program%20Files/GoTaskAI/internal/pkg/llm/client.go#L81-L97)

代码核心：

```go

messages = append(messages, openai.ChatCompletionMessage{
    Role:    openai.ChatMessageRoleSystem,
    Content: systemPrompt,

messages = append(messages, openai.ChatCompletionMessage{

    Content: userPrompt,
})
```

### 7.1 这里体现的是标准聊天模型上下文结构

消息顺序是：

1. system
2. 历史消息
3. 当前 user 消息

这说明 `Generate()` 不是只接一句 prompt，而是明确遵循：

- 聊天模型消息数组格式

### 7.2 为什么先放 system prompt

因为 system prompt 决定的是：

- 模型的角色
- 回答规则
- 工具使用约束
- 知识增强上下文

也就是说，它是整个推理环境的“地基”。

### 7.3 为什么 `history` 可以直接传进来

因为 Worker 或 API 在调用 `Generate()` 之前，已经可能先把历史上下文准备好了。

`Generate()` 的职责不是去查历史，而是：

- 把调用方给的历史，按聊天格式拼进去

这说明它的边界比较清晰：

- 它负责编排模型输入
- 不负责决定历史从哪来

## 9. 第三阶段：进入真正的聊天生成循环

对应：

- [client.go:L115-L123](file:///d:/Program%20Files/GoTaskAI/internal/pkg/llm/client.go#L115-L123)

代码：

```go
for {
    req := openai.ChatCompletionRequest{
        Model:    c.model,
        Messages: messages,
    }

    if len(tools) > 0 {
        req.Tools = tools
    }
```

### 9.1 为什么这里是 `for {}`，而不是只调一次

因为一旦支持工具调用，模型交互不再一定是一轮结束。

可能发生这样的链路：

1. 模型先说“我要调用工具”
2. 系统去执行工具
3. 工具结果再回灌给模型
4. 模型再基于工具结果生成最终答案

这就要求：

- 至少两轮模型交互

所以必须用循环，而不是一次请求写死。

### 9.2 这也是为什么我说它是“工具调用协调器”

因为它不只是调用模型，还要协调：

- 模型
- 工具
- 工具结果
- 再次模型调用

## 11. 第五阶段：兼容某些开源模型的不规范 tool call 输出

对应：

- [client.go:L136-L169](file:///d:/Program%20Files/GoTaskAI/internal/pkg/llm/client.go#L136-L169)

这段代码是整个文件里最有“工程补坑感”的地方之一。

### 11.1 它在解决什么真实问题

理想情况下，模型如果要调用工具，应该在：

- `msg.ToolCalls`

字段里规范返回。

但某些开源模型，特别是某些本地模型，会出现两类不规范行为：

1. 不把工具调用写进 `tool_calls`
2. 而是直接把 JSON 写进 `content`

于是系统如果只信 `msg.ToolCalls`，就会误判成：

- 模型没调工具

### 11.2 代码怎么补这个坑

它会：

1. 检查 `ToolCalls` 是否为空
2. 如果为空但 `Content` 非空，就用正则去抓可能的 JSON
3. 如果抓到了，再手动解析成 `ToolCall`

关键逻辑在：

- [client.go:L139-L167](file:///d:/Program%20Files/GoTaskAI/internal/pkg/llm/client.go#L139-L167)

### 11.3 为什么这段很值得讲

因为这不是“理论上应该怎么工作”，而是：

- 真实项目里为了兼容模型生态的不稳定行为，额外写的修正逻辑

这类代码很能体现工程经验。

## 17. 把 `Generate()` 压缩成一条主线

你可以直接把 `Generate()` 背成下面这条线：

```text
组装 system + history + user 消息
-> 如果有 MCP，就获取工具列表并转换为 OpenAI Tool
-> 发起模型调用
-> 拿到模型回复
-> 如果模型工具调用格式不规范，尝试从 content 中修复提取
-> 把当前模型回复追加进 messages

-> 把工具结果整理成 tool 消息追加回 messages
-> 继续下一轮模型调用
-> 直到模型给出最终答案
```

如果你能把这条主线吃透，`GoTaskAI` 的工具调用链基本就讲明白了。

## 19. 这个文件最值得建立的 8 个认知

1. `llm.Client` 不只是聊天客户端，也负责 embedding 调用
2. `NewClient()` 的关键意义是把模型配置和 OpenAI 兼容接口统一收口
3. `Generate()` 接收的不是一句 prompt，而是一整套 system/history/user 组合上下文
4. MCP 工具只有先被转换成 OpenAI Tool，模型才知道自己能调用什么
5. `Generate()` 之所以是循环，不是因为代码写复杂了，而是因为工具调用天然需要多轮交互
6. 某些开源模型不会规范返回 `tool_calls`，所以必须做额外兼容修复
7. 工具执行结果不是直接返回用户，而是先作为 `tool` 消息回灌给模型
8. 最终答案是在“模型 -> 工具 -> 模型”这一循环收敛后得到的
