## 一、项目概述（面试开场白）

### 1. 一句话介绍

> 这是一个基于 **Go + Gin + Vue3** 的企业级**异步 AI 任务调度与 GraphRAG 对话平台**，后端拆分为「API Server（接入层）+ Worker Node（计算层）」两个微服务，用 Redis 同时承担缓存、消息队列、事件总线三种角色，实现高并发削峰填谷、故障重试和跨进程实时推送。

### 2. 30 秒自我介绍话术（可直接背）

> 我做了一个叫 GoTaskAI 的项目，它解决的是「大模型调用耗时长、并发低、知识推理有盲区」这三个痛点。后端我拆成了两个进程：API Server 负责接请求、鉴权、限流和建任务；Worker Node 负责异步消费任务、做 RAG 向量检索和 KAG 图谱检索，最后调用大模型。关键设计是：API 收到请求后不等待大模型，而是把任务丢进 Redis 的 Asynq 队列立刻返回 202，由 Worker 慢慢消费，这就实现了流量削峰。Worker 完成后通过 Redis Pub/Sub 广播，API 再用 SSE 推给前端，实现了跨进程的实时状态同步。整个项目用了 Gin、GORM、Asynq、Neo4j、MCP 这套技术栈。

## 三、系统架构

### 1. 运行态进程（面试核心，务必先讲清）

```
┌─────────────── API Server（接入层，IO 密集型）───────────────┐
│  接 HTTP、JWT 鉴权、Redis 限流、托管前端、建任务、SSE 推送    │
└──────────────────────────┬───────────────────────────────────┘
                           │ ① 任务入队（Asynq）
                           ▼
                   ┌────── Redis ──────┐
                   │ 缓存 + 队列 + 总线  │
                   └──────┬──────┬─────┘
                          │      │ ③ Pub/Sub 广播
             ② 消费任务    │      └──────────────┐
                          ▼                      ▼
┌─────────────── Worker Node（计算层，CPU/网络密集）───────────┐
│  消费队列、RAG/KAG 检索、调 LLM、更新状态、gRPC 取消任务      │
└─────────────────────────────────────────────────────────────┘
                           ▲
                           │ SSE 推流（Worker→Redis→API→前端）
                     [前端浏览器]
```

### 2. 一条完整请求的生命周期（必背）

1. 前端登录拿到 JWT，存 localStorage
2. 前端 `POST /api/tasks/submit`（带 Bearer Token）
3. 中间件鉴权 + Redis 限流
4. `SubmitTask` 构造 Task（UUID、默认优先级、状态 pending）
5. `AddTask`：写 MySQL → 写 Redis 缓存 → 入 Asynq 队列
6. 立即返回 `202 Accepted`（关键：不等待结果）
7. Worker 从队列取任务 → 置 `processing`
8. 拼装上下文：RAG 检索 + KAG 检索 + 历史对话
9. 调 LLM（失败则指数退避重试，超 3 次置 `failed`）
10. 成功置 `completed` + 结果
11. `UpdateTask`：写 MySQL + 写 Redis + **发 Pub/Sub**
12. API 订阅 Pub/Sub → 转 SSE 推给前端
13. 前端收到 `task_update` 事件，更新列表

## 四、核心模块与技术点（按「是什么→为什么→怎么做→面试怎么答」）

### 1. 微服务拆分（API + Worker）

- **是什么**：把「接客」和「干活」拆成两个独立进程。
- **为什么**：AI 任务慢、重、易阻塞；HTTP 接口要求快、稳、抗并发。放一个进程会互相拖累。
- **怎么做**：`cmd/api/main.go` 和 `cmd/worker/main.go` 两个入口；Worker 还支持 `processes` 配置拉起多个子进程。
- **面试答**：核心是「接入层与计算层解耦」，接入层只做轻量操作快速返回，计算层独立扩容。

### 2. Asynq 消息队列（削峰 + 优先级 + 重试）

- **是什么**：基于 Redis 的异步任务队列。
- **为什么**：大模型调用慢，用队列把「瞬时洪峰」蓄起来，Worker 匀速消费。
- **怎么做**：
  - 三优先级队列 `high:6 / default:3 / low:1`
  - `AddTask` 三步：落 MySQL → 写缓存 → 入队
  - 失败返回 error 给 Asynq，自动指数退避重试，`MaxRetry: 3`
- **面试答**：一句话「API 快速收单 + 队列削峰填谷 + Worker 并发消费」。

### 3. Cache-Aside 缓存（MySQL + Redis 双写）

- **怎么做**：读先查 Redis，未命中查 MySQL 再回写；写先更新 MySQL 再更新 Redis 缓存（带 24h TTL）。
- **面试答**：这是旁路缓存模式，用 TTL 兜底保证最终一致性；追问可延伸到「删除 vs 更新缓存」「延时双删」「Canal 订阅 Binlog」。

### 4. SSE + Redis Pub/Sub（跨进程实时推送）

- **为什么**：任务进度是单向数据流（后端→前端），SSE 比 WebSocket 轻、比轮询省。
- **怎么做**：Worker 更新状态时 `Publish("global_task_updates")`，API 进程 `Subscribe` 后 `broadcast` 给对应用户的 channel，`StreamTasks` 用 `c.SSEvent` + `Flush` 推送。
- **关键细节**：SSE 用 URL 参数传 token（EventSource 无法自定义 Header）。
- **面试答**：这是微服务解耦的关键——「Worker 不直接连前端，而是 Worker → Redis Pub/Sub → API → SSE → 浏览器」。

### 5. 认证体系（JWT + bcrypt）

- 注册：bcrypt 单向哈希存密码。
- 登录：查库比对密码 → 签发 JWT（HS256，24h）。
- 鉴权：`AuthMiddleware` 解析 Bearer Token → 把 `userID` 注入 Gin Context。
- 忘记密码：验证码存 Redis（5 分钟）模拟短信。
- **面试答**：无状态 JWT 适合分布式，中间件统一注入身份，Handler 只关心「当前是谁」。

### 6. Redis 限流（防刷）

- 用 Redis `INCR` + `EXPIRE` 实现固定窗口限流，Key 优先用 userID，降级用 IP。
- 超限返回 429。
- **面试答**：INCR 原子操作保证并发安全，Redis 故障时降级放行保证可用。

### 7. RAG（向量检索）

- 入库：文档分块（500 字 / 50 重叠）→ bge-m3 embedding → 存 RedisVector。
- 检索：问题向量化 → 相似度检索 top3 → 注入 systemPrompt。
- **面试答**：解决「大模型知识盲区」，用检索到的外部知识增强回答、降低幻觉。

### 8. KAG（知识图谱）

- 入库：LLM 抽取三元组（source-relation-target）→ Neo4j `MERGE` 入库。
- 检索：LLM 做 Text2Cypher 生成查询语句 → 执行 → 结果注入 prompt。
- **面试答**：RAG 是「搜文本」，KAG 是「查关系」，两者结合实现「双路召回」。

### 9. MCP 工具调用（联网搜索）

- Worker 通过 Stdio 拉起 `search_mcp.exe` 子进程，注册 `internet_search` 工具。
- LLM 判断需要搜索时，调用工具 → 拿结果回填 → 再生成答案（工具调用循环）。
- **亮点细节**：针对 Qwen2.5 不标准输出 `tool_calls` 的问题，用正则从 Content 提取 JSON 工具调用。
- **面试答**：MCP 赋予模型「外挂工具」的 Agent 能力。

### 10. 多轮对话记忆

- 前端给每个会话生成 SessionID，任务按 session 分组。
- Worker 取「最近 6 条已完成任务」反转排序，拼成 user/assistant 历史消息。
- **面试答**：滑动窗口机制，既保留短期记忆又控制 Token 消耗。

### 11. Redis Sentinel 高可用

- 代码支持 `standalone` / `sentinel` 双模式。
- 本地搭了 1 主 + 2 副本 + 3 Sentinel，完成故障切换演练。
- **面试答**：Redis 在项目里三重角色太关键，所以第一步上 Sentinel（主从 + 自动 failover），后续可演进 Cluster。

### 12. gRPC（同步控制通道）

- Worker 内置 gRPC Server（50051），提供 `CancelTask` RPC。
- 用于「强制取消任务」这种需要同步打断的场景，异步队列无法立刻打断。
- 协议定义在 `api/proto/worker/worker.proto`。

## 五、项目亮点（面试最值得讲的 3-5 个点）

1. **异步解耦 + 削峰填谷**：API 秒回 202，队列蓄洪，Worker 匀速消费，天然抗高并发。
2. **GraphRAG 双路召回**：RAG（向量）+ KAG（图谱）混合检索，既解决知识盲区又支持复杂关系推理。
3. **跨进程实时推送**：Redis Pub/Sub + SSE 打通 Worker→API→前端，实现真正的微服务解耦。
4. **Redis 三重角色**：一个 Redis 同时当缓存、消息队列、事件总线，体现对中间件的深度理解。
5. **MCP 工具调用**：赋予模型联网搜索的 Agent 能力，紧跟前沿协议。

---

## 六、难点与挑战（体现思考深度）

1. **大模型输出不规范**：Qwen2.5 不按标准 `tool_calls` 输出，需要正则从 Content 里提取工具调用 JSON 做兼容。
2. **取消任务的并发安全**：多 Worker 共享 MySQL/Redis 状态源，取消通过「关键阶段检查状态」实现，避免把取消任务回写成 completed。
3. **SSE 鉴权**：EventSource 无法自定义 Header，改用 URL 参数传 token。
4. **Redis Sentinel 改造**：切主有短暂重连抖动窗口，Sentinel 返回内网地址对宿主机不可达，需要固定 IP 监控。
5. **缓存一致性**：任务状态高频变化，用 Cache-Aside + TTL 兜底。

## 八、简历项目描述模板（可直接改）

> **GoTaskAI 异步 AI 任务调度与 GraphRAG 对话平台**（Go + Gin + Vue3）
> - 后端拆分 API Server 与 Worker Node 两个微服务，通过 Redis 承担缓存、Asynq 队列、Pub/Sub 事件总线三重角色，实现高并发流量削峰与故障重试。
> - 设计 Cache-Aside 缓存策略 + JWT 鉴权 + Redis 限流中间件，保障接口安全与数据最终一致性。
> - 实现 GraphRAG 双路召回：基于 RedisVector 的 RAG 向量检索 + 基于 Neo4j 的 KAG 图谱检索（LLM 抽取三元组 + Text2Cypher 查询），降低大模型幻觉。
> - 集成 MCP 协议实现联网搜索工具调用，并通过 Redis Pub/Sub + SSE 实现跨进程实时状态推送。
> - 完成 Redis Sentinel 高可用改造，本地搭建 1 主 2 副本 3 哨兵并完成故障切换演练。
