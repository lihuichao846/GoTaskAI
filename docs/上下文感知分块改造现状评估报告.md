> 日期：2026-09-09

## 1. 评估结论速览

| 维度 | 现状 | 结论 |
| --- | --- | --- |
| 切分策略 | `textsplitter.RecursiveCharacter`，`ChunkSize=500` / `ChunkOverlap=50`，按 UTF-8 rune 计 | 无上下文感知，命中块彼此孤立 |
| 存储 schema | `kb_chunks`：`chunk_id`/`kb_id`/`doc_id`/`text`/`dense`/`sparse` | **缺 `chunk_index` 列**，无法按序还原文档 |
| 检索输出 | `SimilaritySearch` 仅输出 `text`/`kb_id`/`doc_id` | 命中块无位置信息，无法做窗口扩展 |
| 注入侧 | 摘要层 + 命中片段按 Score 分层截断 | 命中块不携带前后邻居上下文 |
| 文档关系 | Milvus + MySQL（queue）+ Redis（asynq）+ Neo4j（KAG）+ LLM | 依赖清晰，无循环依赖 |

**核心缺口**：当前 RAG 命中块是**扁平、离散**的。多个命中块同属一文档时，用户只能看到零散句子，缺乏局部连续上下文。改造目标即让命中块能通过 `doc_id + chunk_index` 还原其在原文中的位置，从而注入相邻窗口块。

## 3. 模块现状与数据流

### 3.1 建库侧（切分与入库）

**Worker 路径** [pool.go](file:///d:/Program%20Files/GoTaskAI/internal/worker/pool.go#L858-L883)：

```go
splitter := textsplitter.NewRecursiveCharacter()
splitter.ChunkSize = 500
splitter.ChunkOverlap = 50
chunks, err := textsplitter.SplitDocuments(splitter, []schema.Document{{
    PageContent: doc.Content,
    Metadata: map[string]any{"kb_id": payload.KBID, "doc_id": doc.ID},
}})
p.ragStore.AddDocuments(ctx, chunks)
```

- 每个 `schema.Document` 的 `Metadata` 只有 `kb_id`、`doc_id`，**无位置序号**。
- 构建期还会生成 per-doc 摘要（[L837-L856](file:///d:/Program%20Files/GoTaskAI/internal/worker/pool.go#L836-L856)），供摘要层注入。

**API 路径** [rag.go](file:///d:/Program%20Files/GoTaskAI/internal/api/rag.go#L128-L140)：

```go
splitter := textsplitter.NewRecursiveCharacter()
splitter.ChunkSize = 500
splitter.ChunkOverlap = 50
chunks, err := textsplitter.SplitDocuments(splitter, []schema.Document{doc})
h.ragStore.AddDocuments(ctx, chunks)
```

- `Metadata` 仅 `{"source": "web_upload"}`，无 `kb_id`/`doc_id`（入库时落到 `defaultKBID`）。
- 与 Worker 侧切分参数一致，但两处分别硬编码，**需保持切分逻辑统一**。

**差距**：两处均需在 `SplitDocuments` 后，按返回切片顺序为每个 chunk 的 `Metadata` 写入 `chunk_index`（0 起始）。

### 3.2 存储侧（Schema 定义）

[schema.go](file:///d:/Program%20Files/GoTaskAI/internal/pkg/ragstore/schema.go#L30-L58)：

- `chunk_id`：Int64，主键，AutoID（构造时）——唯一标识每一条 chunk。
- `kb_id`、`doc_id`：VarChar(128)。
- `text`：VarChar(16384)。
- `dense`：FloatVector(dim)。
- `sparse`：SparseVector。

索引：`dense` = HNSW + COSINE；`sparse` = SPARSE_INVERTED_INDEX + IP。

**差距**：schema 无 `chunk_index`。若直接给存量 Collection 加列，Milvus 2.4.2 原生不支持对已存在 Collection 增列，因此必须走**兼容分支**（见 §5）。

### 3.3 存储侧（写入）

[store.go](file:///d:/Program%20Files/GoTaskAI/internal/pkg/ragstore/store.go#L75-L127) `AddDocuments`：

```go
cols := []entity.Column{
    entity.NewColumnVarChar("kb_id", kbIDs),
    entity.NewColumnVarChar("doc_id", docIDs),
    entity.NewColumnVarChar("text", texts),
    entity.NewColumnFloatVector("dense", s.dim, dense),
    entity.NewColumnSparseVectors("sparse", sparse),
}
s.client.Insert(ctx, s.coll, "", cols...)
s.client.Flush(ctx, s.coll, false)
```

- 从 `chunk.Metadata` 读 `kb_id`/`doc_id`（[store.go L86-L90](file:///d:/Program%20Files/GoTaskAI/internal/pkg/ragstore/store.go#L86-L90)）。
- 插入后强制 `Flush`，保证检索立即可见。

**差距**：需从 metadata 读 `chunk_index`（Int64），并新增 `entity.NewColumnInt64("chunk_index", idxs)`。

### 3.4 存储侧（检索）

[store.go](file:///d:/Program%20Files/GoTaskAI/internal/pkg/ragstore/store.go#L131-L204) `SimilaritySearch`：

- 双路召回：`dense`(COSINE) + `sparse`(IP)，`routeN = topK*2`，RRF 融合。
- 输出字段：`outputFields = ["text", "kb_id", "doc_id"]`（[L158](file:///d:/Program%20Files/GoTaskAI/internal/pkg/ragstore/store.go#L158)）。
- 解析结果时按列名取 `text`/`kb_id`/`doc_id` 填 `Metadata`。

**差距**：需在 `outputFields` 中追加 `chunk_index`，并在解析时读入 `meta["chunk_index"]`。

**缺失能力**：现无 `GetChunksByDocID`，无法按 `doc_id` 取回该文档的完整有序 chunk 序列（窗口扩展依赖）。

### 3.5 注入侧

[pool.go](file:///d:/Program%20Files/GoTaskAI/internal/worker/pool.go#L233-L308) `retrieveKnowledge`：

- `TopK`：无 reranker 取 3，有 reranker 取 `Rerank.TopN`。
- `appendKBDocs`：先注入摘要层（`collectDocSummaries` 取 `doc_id` 去重 → `GetDocumentSummaries`），再按 Score 分层注入命中片段。
- 总量门禁：`write` 在超过 `MaxContextChars` 时停止追加。
- 分层截断：`chunkByScore`（高分全文→低分短截断），`truncateChunk`（按 rune 截断）。

**差距**：
1. 命中片段是孤立的，未按 `doc_id+chunk_index` 还原文档上下文。
2. 需在注入命中层前，为每个命中块做窗口扩展（取前后 `chunk_context_window` 块），并去重。

## 4. 系统架构与依赖关系

```
┌─────────────────────────────────────────────────────────────────────┐
│  Worker (pool.go)                                                    │
│   handleKBBuild → SplitDocuments → ragStore.AddDocuments             │
│   retrieveKnowledge → retrieveTopDocs → ragStore.SimilaritySearch    │
│         │                    │                                        │
│         │ (切分+注入)          │ (双路召回 RRF)                       │
│         ▼                    ▼                                        │
│  ragStore (Milvus)  ◄──────────────  gse 中文分词 (bm25.go)           │
│   ┌──────────────────────────────┐                                    │
│   │ Collection: kb_chunks         │                                    │
│   │ chunk_id / kb_id / doc_id    │◄── 缺 chunk_index（改造点）        │
│   │ text / dense / sparse        │                                    │
│   └──────────────────────────────┘                                    │
└─────────────────────────────────────────────────────────────────────┘
          ▲                               ▲
          │ manager.GetDocument           │ manager.GetDocumentSummaries
          │ manager.GetDocumentSummaries  │ manager.UpdateDocument
          │ manager.Increment...          │
   ┌──────────────┐               ┌──────────────┐
   │ MySQL (queue)│               │ Redis (asynq)│
   └──────────────┘               └──────────────┘
```

- **Milvus**（`kb_chunks`，dim=1024）：向量检索主存，改造核心。
- **MySQL**（`TaskManager`）：保存 `Document`（含 `Content`/`Summary`/`ChunkCount`/`Status`）与 KB 元数据。`GetDocumentSummaries` 摘要层数据源；B2 降级时也提供 `Content` 全文兜底。
- **Redis**（asynq）：`kb:build` 任务队列。
- **Neo4j**（KAG）：图谱检索，与本次窗口扩展**正交**，不受影响（[config] `GraphTopN` 已隔离）。
- **LLM**：构建期生成 per-doc 摘要；运行期不调 LLM（窗口扩展为纯存储读取，零 LLM 成本）。

**依赖关系无循环**：Worker 依赖 `ragStore`（Milvus）与 `manager`（MySQL），`ragStore` 不依赖 Worker，符合单向分层。

## 5. 与改造方案的差距分析

### 5.1 核心能力缺口

| 能力 | 现状 | 方案要求（B1） | 差距 |
| --- | --- | --- | --- |
| 有序定位 | 无 `chunk_index` | 每 chunk 有 `doc_id + chunk_index` | **缺失** |
| 局部上下文 | 命中块孤立注入 | 命中块 ±N 窗口块连续注入 | **缺失** |
| 文档还原 | 无按文档取块 API | `GetChunksByDocID(docID)` 有序返回 | **缺失** |
| 去重 | 仅摘要层按 `doc_id` 去重 | 命中层需按 `doc_id+窗口区间` 去重 | **缺失** |

### 5.2 兼容性风险（存量 Collection）

- Milvus 2.4.2 **不支持**对已存在 Collection 动态加列。
- 现有 `kb_chunks` 已按旧 schema 建好并入库。若直接复用：
  - `AddDocuments` 写 `chunk_index` 列会因字段缺失报错；
  - `SimilaritySearch`/`GetChunksByDocID` 读不存在字段也会报错。

**应对（方案 B2 降级）**：
- 通过 `DescribeCollection` 读取 `Schema.Fields`（SDK `Schema.Fields []*EntityField`，含 `Name`/`DataType`/`PrimaryKey`），检测是否存在 `chunk_index`。
- **存在**：走 B1（窗口扩展主路径）。
- **缺失**：走 B2——`GetChunksByDocID` 降级为读取 `manager.GetDocument(docID).Content` 全文，或按 `doc_id` 从 Milvus `Query` 取 `text`（无 `chunk_index` 时按实体返回顺序降级，不做窗口扩展），并在日志提示建议迁移到新 Collection。

**迁移建议**：建议单次重建（DropCollection + 全量入库）以启用完整 B1，避免长期停留在 B2。该决策在方案文档中已评估，属于一次性成本。

## 6. 实施路线与风险控制

| 阶段 | 内容 | 回归验证 |
| --- | --- | --- |
| B | 建库侧打 `chunk_index`（`pool.go`+`rag.go`） | 断言 chunk 元数据含有序 `chunk_index` |
| C | 存储侧加列 + 写入（`schema.go`+`store.go`） | `AddDocuments` 成功写入，`DescribeCollection` 见新列 |
| D | 检索侧输出 `chunk_index` + `GetChunksByDocID` | 按 `doc_id` 取回有序 chunk |
| E | 注入侧窗口扩展 + 去重 + 配置项 | 命中块 ±N 邻居连续注入，无重复块 |
| F | 全量测试（单元/集成/性能/兼容） | 见方案 §"回归验证方法" |
| G | 交付（版本记录、测试报告、文档更新） | 验收标准逐项对齐 |

**风险清单**：
1. **加列兼容**（最高）：必须 `DescribeCollection` 探测，存量走 B2，禁直接改 schema 期望。
2. **切分一致性**：`pool.go` 与 `rag.go` 两处切分参数须保持一致，否则 `chunk_index` 语义偏移。
3. **去重正确性**：同一 doc 多命中块同属一个窗口区间，需按 `doc_id+窗口区间` 去重，避免重复注入。
4. **截断与扩窗优先级**：扩窗后 `chunkByScore` 应先裁整窗再按 Score 分层，需在单元测试固定行为。
5. **性能**：`GetChunksByDocID` 每次注入可能多次 `Query`，需评估频次；建议对同文档的 `chunk_index` 列表做内存聚合后再注入。

## 7. 结论

现状逻辑清晰、依赖单向、无循环，具备良好改造基础。核心改造为**引入 `chunk_index`（B1）**，并**以存量探测 + B2 降级（b) 保证兼容**。注入侧将升级为「命中块 + 局部窗口连续上下文」，在总字符上限约束下提升检索语义连贯性，且零额外 LLM 成本。
